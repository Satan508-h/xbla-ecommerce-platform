# 技术决策记录（ADR）

> 记录每个**重要且不容易改**的技术决策：当时有哪些备选、为什么选了它、
> 以及这个选择带来了什么代价。
>
> 这份文档是面试时最有力的材料 —— 它能证明的不是「我会用某个技术」，
> 而是「我评估过多个方案，知道各自的代价」。

**格式**：Context（背景）→ Options（备选）→ Decision（决策）→ Consequences（代价与影响）

## ADR-001 · HTTP 客户端选 JDK 内置的

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

`client/` 层要手写 HTTP 调用（项目约定不用 Spring AI / LangChain4j，链路必须可逐行解释）。
需要一个能发 POST JSON、并且能**流式读取 SSE** 的客户端。

### Options

| 方案 | 优点 | 代价 |
|---|---|---|
| **JDK 内置 `java.net.http.HttpClient`** | 零新增依赖；`BodyHandlers.ofLines()` 原生支持流式；没有隐藏的连接管理魔法 | API 偏底层，超时语义需要自己搞清楚 |
| Apache HttpClient 5 | 工业级成熟，连接池/重试机制完善 | 多一个依赖；部分行为是库内部实现，不如手写清楚 |
| OkHttp | API 简洁，社区广 | 多一个依赖；方 block 式 API 与 Spring 生态融合度一般 |
| Spring WebClient | 响应式，背压支持好 | 要引入 WebFlux 整条响应式栈，与 Spring MVC 是两套心智模型 |

### Decision

**JDK 21 内置 `java.net.http.HttpClient`。**

理由：这是**唯一零依赖**的方案，而它恰好原生支持本项目的核心需求（SSE 流式读取）。
项目定位是「链路可逐行解释」，没有第三方库封装反而更符合。

### Consequences

- ✅ `pom.xml` 里没有一个 HTTP 客户端依赖
- ⚠️ **超时语义要自己搞清楚**（见 ADR-004）：`HttpRequest.timeout()` 对
  `ofLines` 只覆盖到响应头，对 `ofString` 覆盖整个响应体 —— 两者必须配不同的值
- ⚠️ 没有 per-read 超时，流式场景的空闲检测要靠上层（`SseEmitter` 的超时回调
  里关闭上游流）来兜底

## ADR-002 · 流式接口设计成「阻塞 + 回调」

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

流式调用既要**逐段把正文推出去**，又要在结束时**拿到 token 用量**。
需要一个方法签名同时表达这两件事。

### Options

| 方案 | 问题 |
|---|---|
| `Flux<Chunk>` | 要引入 WebFlux 响应式栈 |
| `Stream<Chunk>` | **惰性**执行，try-with-resources 一关就废；流中间抛的异常会被包装成 `UncheckedIOException`，**堆栈里完全看不出是哪家供应商出的问题** |
| **`chatStream(req, Consumer<String> onDelta)` 返回 `StreamResult`** | 回调式偏「老派」 |

### Decision

**阻塞 + 回调，usage 走返回值。**

`Consumer<String>` 天然表达「每来一个增量就做一次副作用」——
正好对应 SSE 的 `emitter.send()`。而 `Stream<Chunk>` 的异常包装问题
在降级链里是致命的：我们恰恰需要从异常里读出「是哪家失败、什么原因」。

### Consequences

- ✅ 能在任意时刻抛出**真正的业务异常**（`ModelCallException` 带 provider/model/状态码）
- ✅ service 层完全不用知道响应式编程
- ⚠️ 调用方必须注意：**回调里不能做耗时操作**，它会直接阻塞上游读取循环
- ⚠️ 回调抛出的异常会被归类为 `CLIENT_ABORTED`（用户断开），见 ADR-006

## ADR-003 · 自己 `@Bean` 熔断器注册表，不用自动配置

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

`resilience4j-spring-boot3` 的自动配置类
`AbstractCircuitBreakerConfigurationOnMissingBean` 上挂着：

```java
@Condition(AspectJOnClasspathCondition.class)
```

即「类路径上得有 AspectJ 才装配」。问题是这个注解挂在**父类**上，
而 `@Conditional` 不是 `@Inherited` 的 —— 它到底生不生效，
取决于 Spring 处理元数据注解继承的具体策略。

### Options

| 方案 | 问题 |
|---|---|
| 依赖自动配置 | Bean 可能**静默不创建**，日志里只有一行 WARN。配置全对、依赖也加了、Bean 就是没有 —— 这类问题排查成本极高 |
| 用 `@CircuitBreaker` 注解 | fallback 链表达不了「流式已吐字就不能降级」；状态机被藏在切面里，不符合「可逐行解释」 |
| **自己 `@Bean CircuitBreakerRegistry`** | 配置源要自己对接 |

### Decision

**在 `ChatChainConfig` 里自己建 registry**，配置统一来自 `xbla.llm`。

同时 `pom.xml` 里**仍然引 `spring-boot-starter-aop`** 作为保险，
也为了让熔断器的健康指标能挂进 `/actuator/health`。

`CircuitBreakerConfigurationOnMissingBean` 上有 `@ConditionalOnMissingBean`，
看到我们提供了就会自动退让，不冲突。
`/actuator/circuitbreakers` 端点也不关心 registry 是谁建的。

### Consequences

- ✅ 完全不依赖 AspectJ 是否在类路径 → 那个不确定性被彻底绕开
- ✅ 熔断器参数和模型配置在同一个前缀下，改一处就够
- ⚠️ 需要自己写「配置项 → Resilience4j 对象」的转换（`CircuitBreakerProps.toResilienceConfig()`）
- 📌 顺带解决：**预热**。自动配置是「第一次用到才创建」，
  启动后立刻看 `/actuator/circuitbreakers` 会是一片空白。我们预热了所有条目

## ADR-004 · 熔断器的耗时口径用 TTFB，不用整个流时长

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

Resilience4j 的熔断器有「慢调用率」阈值（`slow-call-rate-threshold`）。
需要决定：流式调用结束时，喂给 `onSuccess(duration, unit)` 的应该是什么？

### Options

| 方案 | 后果 |
|---|---|
| 整个流的持续时间 | ★ **一次 60 秒的正常长回答会被判定为慢调用** |
| **TTFB（建连 + 首字节）** | 需要额外测量和传递 |

### Decision

**用 TTFB。** `StreamResult.breakerObservedMs()` 明确返回 `ttfbMs`。

如果按整个流时长计，失败率一超阈值，熔断器就会在
**系统最健康、正在正常干重活**的时候跳闸 —— 这是最坏的反向优化：
越努力服务，越容易被判成故障。

TTFB 才是真正反映「这家供应商有没有问题」的指标：
正常 1-3 秒，超过配置的 15 秒（`slow-call-duration-threshold`）确实说明不对劲。

### Consequences

- ✅ 长回答不会被误判
- ⚠️ `StreamResult` 要多带一个 `ttfbMs` 字段
- 📌 失败路径仍用实际耗时 —— 一次跑 60 秒然后失败的调用，
  被判成「慢调用」是合理的

## ADR-005 · 流式降级有硬边界：吐过字就不能降级

**日期**：2026-09-18　**状态**：已采纳（架构约束，非偏好）　**阶段**：2

### Context

降级链在任何失败时都应该尝试下一家吗？

### Decision

**不是。** 只有「一个字节都没发给用户」时才能降级：

```
statusCode != 200 ─────────────────────→ 可以降级
statusCode == 200
  ├─ 首个 content 增量之前失败 ────────→ 可以降级
  └─ 已吐字后失败 ─────────────────────→ 不能降级
```

### Consequences

**这是 SSE 架构的固有约束，不是可以优化掉的东西。**

用户已经看到前面吐出来的字了。换一家从头重来，他会看到
**两段拼接起来的、前后矛盾的话** —— 比如前半句在讲退货流程，
后半句突然变成了发货时效。这比直接报错糟糕得多，因为用户可能真的信了。

- ✅ 语义诚实：能降级时降级，不能时如实报错
- ✅ 这种情况仍**计入熔断失败** —— 下一轮请求会提前降级到 P1
- ⚠️ 实现上：`contentChars` 的统计和分类发生在 `OpenAiCompatibleLlmClient` 内部
  （信息最全的地方），router 只读 `kind.isFallbackWorthy()`

## ADR-006 · 「用户断开」单独分一类错误

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

用户关闭页面时，`emitter.send()` 会抛 `IOException`（Broken pipe）。
这和「模型供应商出问题」抛出的异常**在类型上完全一样**。

### Decision

**新增 `ModelErrorKind.CLIENT_ABORTED`：既不计熔断失败，也不降级。**

不区分的后果有两个，都很恶劣：

1. **污染熔断统计**：用户每关一次页面就记一次供应商失败。
   几个人关几次标签页，一个完全健康的供应商就被熔断打开了 ——
   **系统自己把好服务判成坏的**。
2. **误报降级**：明明是我们自己断开的上游流，却去降级重试，白白多花一次钱。

### Consequences

- ✅ 熔断统计只反映供应商的真实健康度
- ✅ 顺带一个收益：**用户断开时我们主动关闭上游流** ——
  上游一关，模型不再产生 token，**计费停止**。
  否则用户点了关闭，我们还在为一个 4000 token 的回答付钱
- ⚠️ `chatStream` 的回调里要 catch 住下游异常并包装，不能让原始 `IOException`
  直接冒泡（那会被当成网络故障）

## ADR-007 · 402 归为「余额不足」而不是「请求错误」

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2　**来源**：**测试中发现**

### Context

初版实现里 `fromHttpStatus` 把「其余 4xx」一律归到 `BAD_REQUEST`。
而 `BAD_REQUEST` 的策略是**既不降级也不计熔断**。

实测时硅基流动账户余额不足，返回：

```json
HTTP 402 {"code":30001,"message":"Sorry, your account balance is insufficient"}
```

日志里显示为：

```
模型调用失败 [bad_request] ... HTTP 402
```

**整条降级链在这一档直接终止了。**

### Decision

**新增 `ModelErrorKind.QUOTA_EXHAUSTED`（402），可降级 + 计熔断**，
并在 `fromHttpStatus` 里显式判断 402，不让它落到「其余 4xx」分支。

402 的真实含义是「这家服务不了我们」，和请求体对不对毫无关系。
而且**同一家供应商上不同模型的免费/收费状态可能不同** ——
实测时 `deepseek-ai/DeepSeek-V4-Flash` 能用而 `Qwen/Qwen3-8B` 报 402，
所以降级到同家的另一个模型是有意义的。

计入熔断也是对的：402 在充值之前不会自愈，让熔断器跳闸可以避免
每个请求都白白等一次往返。

### Consequences

- ✅ 余额不足时能自动降级到其他模型
- 📌 **这个 bug 是跑出来的，不是设计时想到的** ——
  错误分类表一开始根本没有 402 这一行。
  这正是「一步一验证」策略的价值：如果等到阶段 7 评测时才发现，
  排查方向会完全跑偏（会以为是「所有模型都挂了」）

## ADR-008 · 配置分三层：providers / models / chat-chain

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

降级链上 P0 是 DeepSeek 官方，P1 和 P2 是硅基流动上的**不同模型**。
配置怎么组织？

### Options

| 方案 | 问题 |
|---|---|
| 扁平：每个模型一个条目，连接信息重复写 | 硅基流动的 Key 要写两遍，改一处忘一处 |
| 按供应商分组 | 无法表达「P1/P2 同供应商不同模型」 |
| **三层：连接 / 模型 / 策略** | 配置项变多，要跨层引用 |

### Decision

```yaml
xbla.llm
├── providers    ① 连接：域名 + 密钥（可被多个模型复用）
├── models       ② 模型：provider 引用 + 真实模型 ID + 单价
└── chat-chain   ③ 策略：降级顺序（引用 models 的 key）
```

**供应商是「连接」，模型是「计价与协议」，链路是「策略」。**
三者职责不同，变化频率也不同 —— 分层之后，
「换个模型」只改 models，「调整降级顺序」只改 chat-chain，
「换供应商」只改 provider 引用。

### Consequences

- ✅ 密钥只写一份
- ✅ 启动期能做完整的引用校验（chain → models → providers），
  写错模型名直接启动失败，而不是运行时静默降级
- ⚠️ 配置项变多，需要 `spring-boot-configuration-processor` 提供 IDE 补全
- ⚠️ **Map 的 key 有命名限制**：Spring Boot 只允许小写字母、数字、短横线。
  所以 `deepseek-v3.2` 必须写成 `deepseek-v3-2`，
  否则要用 `[key]` 括号语法

## ADR-009 · 丢弃 `reasoning_content`，只取最终回答

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

`deepseek-flash` 是**推理模型**，响应里多一个非标准的 `reasoning_content` 字段。
实测推理 token 占总输出的 **87%**（124 个输出里 108 个是推理）。

### Options

| 方案 | 后果 |
|---|---|
| 存库 + 前端折叠展示 | 加一个 Flyway 迁移；`chat_message` 表要改 |
| **DTO 里不声明这个字段** | 将来想加回来要改表 + 历史数据已丢 |
| 只写日志 | 日志会非常长（推理内容是回答的 5-10 倍） |

### Decision

**DTO 里不声明，靠 Jackson 静默忽略。**

现有配置 `spring.jackson.deserialization.fail-on-unknown-properties: false`
已经开着了，所以这是**零代码实现** ——
`WireChatMessage.Message` 和 `WireDelta` 里只声明 `content`，
服务端多返回的字段自动被跳过。

### Consequences

- ✅ 零过滤代码。不需要在每个 chunk 里判断「这个增量是推理还是正式回答」——
  那种判断一旦漏了，会把模型的内心独白当成答案推给用户，
  而且这种 bug 在日志里完全看不出来
- ✅ `usage.completion_tokens_details.reasoning_tokens` 仍然保留在 DTO 里，
  用于**诊断**（推理占比异常高 → 该调大 max-tokens 或换模型）
- ⚠️ 代价：如果将来产品上想展示「思考过程」，要改表 + 重新灌数据
- 📌 **换成 `Qwen/Qwen3-8B` 等非推理模型时这个设计依然成立** ——
  没有 `reasoning_content` 字段，Jackson 就当它不存在

## ADR-010 · 成本拿不到用量时记 NULL，绝不估算

**日期**：2026-09-18　**状态**：已采纳　**阶段**：2

### Context

`qa_log` 有 `cost NUMERIC(10,6)` 列。但用量在某些情况下拿不到：
供应商不支持 `stream_options.include_usage`、连接在 usage 汇总 chunk
到达之前就断了、用户中途关闭页面。

### Options

| 方案 | 后果 |
|---|---|
| 按字符数估算 | 数字看起来「完整」，但**是编的** |
| **记 NULL** | 查询时要做 null 处理 |

### Decision

**记 NULL。** `ModelCostCalculator.calculate()` 在用量不可用时返回 `null`。

`qa_log` 是**只增不改不删**的表，评测数据全部来源于它。
编一个数字进去，会永久污染阶段 7 的所有成本指标，
而且事后**无法分辨「哪些是真实值、哪些是估算的」**。

NULL 至少是诚实的：看到 NULL 就知道「这次没拿到用量」，
可以单独统计「用量缺失率」这个指标。

### Consequences

- ✅ 数据可信
- ⚠️ 查询时要处理 NULL（`SUM(cost)` 会自动跳过 NULL，行为正确）
- 📌 顺带一个相关约定：降级事件为空时也写 `null` 而不是 `[]`，
  这样运维查询可以写 `WHERE degradation_events IS NOT NULL` 一眼筛出降级请求

## ADR-011 · 流式演示用 GET + EventSource

**日期**：2026-09-18　**状态**：已采纳（阶段 2 临时方案）　**阶段**：2

### Context

需要一个浏览器端演示验证「打字机效果」。

### Options

| 方案 | 代价 |
|---|---|
| **`GET /api/chat/stream` + `EventSource`** | URL 长度受限（中文百分号编码成 3 倍字节）；问题文本出现在 URL 里 |
| `POST /api/chat/stream` + `fetch` + `ReadableStream` | 要手写 SSE 解析（约 40 行），且浏览器兼容性要自己处理 |

### Decision

阶段 2 **用 GET + EventSource**。

理由：`EventSource` 是浏览器原生 API，演示页只要十几行代码，
能把注意力放在真正要验证的东西（流式是否生效）上。

### Consequences

- ✅ 演示页极简，一眼能看懂
- ⚠️ 阶段 8 做正式前端时**要换成 POST + fetch** ——
  用户的问题可能很长，URL 放不下
- 📌 **必须记住的两点**（都已经踩过）：
  1. **每个终止分支都要 `es.close()`** —— `EventSource` 在连接关闭后会
     **自动重连**，不 close 会导致同一个问题被反复提问、反复计费
  2. **事件名不能用 `error`** —— `EventSource` 有内置的 error 事件（连接层错误），
     同名会让业务错误和网络错误混在一起。所以用 `failed`

## ADR-012 · Tika 用 3.3.2，不用最新的 4.0.0

**日期**：2026-09-18　**状态**：已采纳　**阶段**：3

### Context

阶段 3 要用 Apache Tika 做多格式文档解析。查 Maven Central，
最新版是 **4.0.0**（2026-08 发布），3.x 线最新是 **3.3.2**。
Spring Boot 3.5.16 的 BOM **不托管** Tika（grep 本地 BOM 确认命中数为 0），
版本必须自己写。

### Options

| 方案 | 优点 | 代价 |
|---|---|---|
| **3.3.2** | API 与网上绝大多数教程一致；中文资料多、踩坑少 | 不是最新大版本 |
| 4.0.0 | 最新 | 破坏性变更极多（见下） |
| 只引 `tika-core` + PDFBox/POI | 依赖树最干净 | 要自己装配 Parser 集合，且**没有 Markdown/HTML 支持** |

### Decision

**3.3.2。**

4.0.0 的破坏性变更清单（查官方迁移指南得到，不是推测）：

- **SPI 签名变更**：`Parser.parse` 的参数从 `InputStream` 改成 `TikaInputStream`，
  不再有 `InputStream` 重载；`Detector.detect` 的签名也跟着变了
- **配置格式从 XML 改成 JSON**，旧的 `TikaConfig` XML API 整个删除
- **Metadata 键全部加 `tk:` 前缀**，且 `set` 保留键会抛异常
- **默认开启 fork 解析**（子进程隔离），打包方式也从 fat jar 改成 zip 分发
- 直接调用具体解析器时，**嵌入文档会被静默跳过**（不报错、不抛异常、就是没内容）

本项目要的是「链路可逐行解释」和「踩坑少」，不是版本号最新。
而且 3.x 线仍在维护，不是 EOL。

### Consequences

- ✅ 文档、StackOverflow 答案、示例代码基本都能直接用
- ⚠️ 将来升 4.x 时上面每一条都要处理一遍
- 📌 **踩到的第一个坑**：`tika-parsers-standard-package` 的 POM 里
  `tika-core` 声明成 `<scope>provided</scope>`，而 **provided 不具有传递性** ——
  整包装了几十个解析器模块，唯独缺了核心引擎，编译直接报
  「程序包 org.apache.tika.parser 不存在」。
  **必须显式再引一次 `tika-core`**，且两者版本号必须严格一致（用 `${tika.version}` 属性统一）
- 📌 依赖体积：Tika 拉进来 22 个 `tika-parser-*-module` 加上
  PDFBox 3.0.8 / POI 5.5.1。实测**与 Spring Boot 的 BOM 无版本冲突**
  （`mvn dependency:tree` 里 `omitted for conflict` 命中数为 0）

## ADR-013 · 标题提取用三条策略，其中 PDF 那条最绕

**日期**：2026-09-18　**状态**：已采纳　**阶段**：3

### Context

路线图 3.3 要求「标题层级 + 定长 + 重叠窗口」切分。
没有标题层级就只能退化成定长切分，不同章节的内容会被切进同一个切片。
但 Tika 对四种格式的标题输出形态**完全不同**。

### 实测结果（照着 dump 出来的，不是推测）

| 格式 | Tika 输出的样子 | 提取方式 |
|---|---|---|
| `.docx` | 正文里直接内联 `<h1>` `<h2>` `<h3>` | **策略①** 读标签名 |
| `.pdf` | **正文里一个 h 标签都没有**。标题被抽成 `<body>` 末尾一个嵌套 `<ul>`（文档大纲），和正文完全分离 | **策略②** 从大纲建「标题文本→层级」映射表，再回正文按行精确匹配 |
| `.md` | 被识别为 `text/markdown`，但**Tika 3.3.2 根本没有 Markdown 解析器**（翻遍所有 tika jar 确认），实际由 `TextAndCSVParser` 兜底 —— 整个文件塞进**一个 `<p>`**，`#` 号原样留在文本里 | **策略③** 按行首模式判断 |
| `.xlsx` | sheet 名变成 `<h1>`，数据在 `<table><tr><td>` | sheet 名当一级标题，每行拼成一行文本 |

### Decision

三条策略并存，优先级从上到下。PDF 那条的做法：

**PDF 格式本身不存储「这是标题」这个信息** —— 它只记录「在 (x,y) 画一个
12 号字体的字符串」。标题和正文的区别只体现在字号上，而 Tika 的 XHTML
输出不带字号。所以能从 PDF 拿到结构信息的唯一来源就是**文档大纲**
（阅读器左侧那个目录树）。

但大纲只告诉你「有哪些标题、各是几级」，**不告诉你它们在正文的哪个位置**。
所以用「标题文本精确匹配」把两者关联起来：扫描正文每一行，
如果它恰好等于大纲里的某个标题，就认为它是标题。

### Consequences

- ✅ 四种格式都能提取出标题层级（实测：14 个标题 / 15 个 / 6 个 / 1 个）
- ⚠️ **已知失效场景**（诚实标注）：PDF 没有大纲时提不出任何标题，
  退化为纯定长切分。这是信息论上的限制，不是实现缺陷
- ⚠️ 正文里有一句话**恰好**等于某个标题文本时会被误判成标题 ——
  影响可控（只多切一刀，不丢内容）
- ★ **踩到的坑（极具迷惑性）**：Tika 生成的 PDF 大纲 HTML **不是良构的**，
  同样的层级关系会输出成两种嵌套形态：

  ```html
  形状 A：嵌套 <ul> 在 <li>【里面】
    <ul><li>七天无理由退货规则
      <ul><li>一、适用范围</li></ul>
    </ul>

  形状 B：嵌套 <ul> 是同级 <li> 的【兄弟】
    <ul><li>星辰 X1 智能手机用户手册</li>
      <ul><li>产品简介</li></ul>
    </ul>
  ```

  第一版只处理了形状 A。结果**两份 PDF 里一份完全正常、另一份的标题层级整个丢失**
  —— 而且不报错，只是悄悄退化成「一个标题 + 定长切分」，
  表现为检索质量变差，从日志里完全看不出原因。
  现在两种形状都处理，并且有专门的回归测试（`PdfOutlineTest`）
  用手工构造的 XHTML 把两种形状都钉死

## ADR-014 · 入库流水线不放在数据库事务里，用补偿删除

**日期**：2026-09-18　**状态**：已采纳（架构约束）　**阶段**：3

### Context

一份文档入库要经过「解析 → 切分 → 向量化 → 写库」四步。
最自然的写法是给整个流程加 `@Transactional`，失败自动回滚。

### Decision

**不加事务。失败时用「按 document_id 删掉这次写的切片」来补偿。**

理由是**向量化要调外部 API，一份几百片的文档要跑几十秒到几分钟**。
事务开着跨越这几分钟，意味着**一条 HikariCP 连接被独占了这几分钟**。
而连接池的 `maximum-pool-size` 只有 10 —— 4 个并发的入库任务
就能把池子占掉四成，再叠加正常的问答请求，**整个应用的数据库访问会集体排队**。

这是分布式系统里「不要用事务包裹远程调用」这条原则在单体应用里的翻版。

### Consequences

- ✅ 数据库连接不会被长时间占用
- ⚠️ 「④写库」这一步失去了原子性。用补偿删除弥补：
  任何一步失败就把这次写的切片按 `document_id` 全部删掉。
  **不删的话后果很具体**：检索只认 `kb_chunk.deleted = 0`、**不看文档状态**，
  于是「一份标着处理失败的文档，它的半截内容照样被检索命中」
- ⚠️ 补偿删除本身也可能失败（数据库挂了），这种情况只能靠日志告警 + 人工清理
- 📌 顺带确定了「重新入库」的语义：入库前先按 `document_id` 清场，
  所以重复入库是**替换**而不是累加

## ADR-015 · 表格行用 standalone 标记，不和相邻块合并

**日期**：2026-09-18　**状态**：已采纳　**阶段**：3　**来源**：**实测中发现**

### Context

切分器最初的设计是「同一个章节内的正文块合并成一个切片」。
这个假设对**散文段落**成立 —— 合并起来上下文更完整。

但入库一份 20 行的售后 FAQ 表（xlsx）之后，实测结果是这样：

```
chunk 0（467 字）：售后FAQ / 问题 | 答案 | 分类 / 退货需要多长时间 | ... / 退款多久到账 | ...
                   / 拆封了还能退货吗 | ... / 运费谁承担 | ... （共 13 条问答）
chunk 1（469 字）：... （另外 7 条）
```

### Decision

**给 `TextBlock` 加一个 `standalone` 标记，表格行标为 `true`，切分时按它分组。**

```
输入: [段落A][段落B][表格行1][表格行2][段落C]
分组: [A,B] [行1] [行2] [C]
```

规则只有一句：**standalone 的块自成一派，两边的普通块也不能和它合并。**

### Consequences

- ✅ 实测效果：FAQ 从 **2 个切片变成 21 个**，每条问答都成了独立的检索单元
- ✅ 散文段落的行为完全不变（默认 `standalone=false`）
- 📌 **为什么用布尔标记，而不是「把表格行伪装成标题」之类的技巧**：
  后者会让 `heading_path` 里出现「售后FAQ > 第 3 行」这种毫无意义的内容，
  还会被展示到引用来源里给用户看。
  **标记要表达真实语义，不能为了绕过一个实现细节而编造结构**
- 📌 这个问题的可怕之处在于**它不报错**：切片照样入库、照样有向量、
  检索照样能返回结果，唯一的症状是「答案质量莫名其妙地差」

## ADR-016 · 向量列从 String 改成 float[] + 自定义 TypeHandler

**日期**：2026-09-18　**状态**：已采纳　**阶段**：3

### Context

阶段 1 建表时 `KbChunk.embedding` 声明成了 `String` 占位，因为当时只建表、不读写向量。

### Options

| 方案 | 问题 |
|---|---|
| 保持 `String` | ★ **编译器拦不住任何错误**。传进去一个 512 维的文本、一段 JSON、甚至一句「待填」，都要等到运行时被 PostgreSQL 拒绝才知道 |
| `double[]` | 白白多占一倍空间和带宽 |
| **`float[]` + TypeHandler** | 要写一个类型处理器，还要记得加 `autoResultMap = true` |

### Decision

**`float[]` + `VectorTypeHandler`。**

写入路径三步：`float[]` → 拼成 `[0.1,0.2,...]` 文本 → 以「未指定类型」发给
PostgreSQL（靠 JDBC URL 的 `stringtype=unspecified`）→ PG 用 vector 类型
自己的输入函数解析。读取是反向的。

### Consequences

- ✅ 类型安全：维度不匹配在代码层面就能约束住
- ✅ 实测确认数据库真的在校验维度：写 512 维会被拒绝，
  报错信息是 `expected 1024 dimensions`。
  也就是说「维度是 1024」不是文档里写的，是**数据库在强制执行**
- ⚠️ **`autoResultMap = true` 不能漏**。漏了的症状极具迷惑性：
  **写入正常、查询也正常，就是查出来永远是 null**。
  为此专门写了一条集成测试，注释里写明了「这条测试存在的全部理由」
- 📌 `toLiteral` / `parse` 声明成 `public` 而不是 `private`：
  手写 SQL 做向量检索时也要把 `float[]` 转成 pgvector 字面量
  （`WHERE embedding <=> CAST(? AS vector)`），
  这个知识属于这个类，散出去就会变成两份可能不一致的实现

## ADR-017 · 数据库同步先渲染成 Markdown 落盘，走同一条流水线

**日期**：2026-09-18　**状态**：已采纳　**阶段**：3

### Context

知识库有两个来源（`kb_document.source_type`）：
文件上传（1）和数据库同步（2）。数据库同步要把
`after_sale_policy` 和 `product` 表的内容变成知识库文档。

### Options

| 方案 | 后果 |
|---|---|
| 数据库来源直接从内存字符串进流水线 | 入库要分叉成两条路径：一条从文件读、一条从内存读。**两套测试、两处可能不一致的状态处理** |
| **先渲染成 Markdown 落盘，再走标准流水线** | 多占一点磁盘（几百 KB 的文本文件） |

### Decision

**先渲染成 Markdown，用 `DocumentStore.saveText()` 落盘，然后走和文件上传
完全相同的路径。**

渲染成 Markdown 而不是纯文本，是因为这样 `#` 会被解析层的策略③ 识别成标题，
于是切分、向量化、写库的代码**一行都不用为数据源分叉**。

### Consequences

- ✅ 入库只有一条代码路径
- ✅ 附带收益：**可重放**。阶段 7 重新入库不用重新查源表，
  而且 `file_hash` 去重能直接生效（源表没改动的行不会被重复向量化）
- 📌 **商品描述刻意拆成四个二级标题**（基本信息 / 卖点 / 适用人群与场景 / 规格参数），
  这不是为了好看，是为了让**每个小节成为独立的检索单元**：

  | 用户问题 | 应该命中的小节 |
  |---|---|
  | 「这个手机多少钱」 | 基本信息 |
  | 「这个适合送长辈吗」 | **适用人群与场景** |

  如果整段挤在一起，向量会把「价格 3999」和「适合送长辈」平均成一个模糊的点，
  两个问题匹配到的都是同一坨内容，谁也答不准。
  **这正是 `product.suitable_for` 字段存在的意义** ——
  用数据建模解决检索问题，比事后调 prompt 更根本
- ⚠️ 实测发现渲染出来的小节普遍偏短（30~90 字），
  低于 `minChars=80` 的合并阈值。**判断是「不是问题」**：
  「规格参数 > 电池 / - 电池容量：5000mAh」这种 40 字的切片，
  是一个语义完整、指向明确的检索单元。
  真正该关心的不是「切片够不够长」，而是「一个切片里的内容是不是同一个主题」

## ADR-018 · 「检索结果稳定一致」成立在 ID 序列层面，不在分值层面

**日期**：2026-09-18　**状态**：已采纳　**阶段**：3　**来源**：**实测推翻了原有假设**

### Context

阶段 3 的验收标准 3：「同一个问题检索两次，结果稳定一致」。
看起来是句废话，但拆开看有**两个独立的环节**。

### 实测结果

**环节一：向量化是确定的吗？—— 不是，但只在某些时候不是。**

代码注释里原本写的是「同样的文本调两次 embedding 接口，返回的向量逐位相同，
这一点由模型服务保证」。**这个假设被实测推翻了**：

```
【第一次实测】问题「退货要几天」，连续调用 6 次 /v1/embeddings，比较前 5 个分量：
  第 1 次  : [-0.034807, 0.014949, -0.012569, 0.00099,  -0.029749]
  第 2~6 次: [-0.034728, 0.014979, -0.012669, 0.000731, -0.02966 ]
  → 6 次调用出现了 2 种不同结果

【第二次实测】换一个问题「这个适合送长辈吗」，同样 6 次：
  → 漂移 0.000e+00，六次完全一致
```

**所以准确的说法是：漂移是间歇性的，不是每次都会发生。**
差异量级约 **3e-4**，这**不是 bug，是 GPU 推理的固有性质** ——
分布式/并行计算里浮点加法不满足结合律，归约顺序不同结果就不同。
什么时候会走不同的归约路径（冷启动？批处理分组？GPU 负载？）目前没有定论，
但**「间歇性」这一点比「不确定」更危险**：

> 一个假设「向量化逐位确定」的系统，会 **99% 的时候正常工作、
> 1% 的时候莫名其妙地不对** —— 而且那 1% 无法复现。
> 这是最难排查的一类问题，因为它看起来像是「偶尔抽风」，
> 而不是像「一直坏」那样有明确的排查方向。

**环节二：排序是确定的吗？—— 靠代码保证，可以做到。**

HNSW 是**近似**索引，距离相同时返回顺序不保证（底层是图遍历，
顺序取决于遍历路径）。靠 SQL 里 `ORDER BY embedding <=> ?, id`
的兜底键解决。

### Decision

**判定「稳定」只看 ID 序列是否逐位一致，不看分值是否相等。**

- ✅ 命中的切片 ID 序列完全一致（实测 5 次逐位相同）
- ✅ 分值稳定到小数点后 3 位（同 5 次，最大漂移 3.767e-04）
- ❌ 分值**不会**逐位相同，别用 `equals` 比较两次检索的分数

### Consequences

- ✅ 端到端验收通过，而且**知道它为什么通过**
- 📌 **这个判据最初是写错的**：第一版自检代码用 `scoreRuns.equals()` 直接比
  double，于是永远报「不稳定」—— 而实际上链路是好的。
  **判据写错比没有判据更糟**，它会让人跑去查一个根本不存在的问题
- 📌 **兜底键没有牺牲索引效率**（用 `EXPLAIN` 验证过）：
  - 不带兜底键：`Index Scan using idx_kb_chunk_embedding`
  - 带兜底键：`Incremental Sort` → `Index Scan using idx_kb_chunk_embedding`
    （`Presorted Key` 利用索引已排好的前缀）

  也就是说**确定性和索引效率可以兼得**
- ⚠️ **什么时候这个漂移会真的咬人**：当两个切片的相似度差距小于 3e-4 时，
  它们的相对顺序可能在不同请求间翻转。本项目实际数据里相邻名次的差距
  在 0.002 量级（漂移的 6 倍以上），所以顺序稳定。
  但切片数量级上来、语义高度集中之后这个前提就不成立了，
  那时要靠结果缓存来保证可复现性
- ★ **这条发现的实用价值**：**别把「检索结果不稳定」当成 bug 去查**。
  先看 ID 序列是否一致 —— 一致就说明链路是好的，分数抖动属于正常范围

## ADR-019 · 定义任何 `ObjectMapper` Bean 都会静默关掉 Boot 的 Jackson 自动配置

**日期**：2026-09-18　**状态**：已采纳　**阶段**：3　**来源**：**运行时 500 报错**

### Context

新增的知识库状态查询接口一调用就 500：

```
Java 8 date/time type `java.time.OffsetDateTime` not supported by default:
add Module "com.fasterxml.jackson.datatype:jackson-datatype-jsr310"
```

按提示去查依赖，发现 `jackson-datatype-jsr310:2.21.4` **明明就在 classpath 上**
（由 `spring-boot-starter-web` 传递引入）。所以不是「缺依赖」，是「模块没被注册」。

### Decision

**在 `JacksonConfig` 里显式声明一个 `@Primary` 的 `ObjectMapper`，
用 Spring Boot 的 `Jackson2ObjectMapperBuilder` 构建。**

### Consequences

**根因链条**（这是这个坑最值得记住的部分）：

```
① HttpClientConfig 定义了 @Bean("modelObjectMapper") ObjectMapper
                      ↓
② Spring Boot 的 JacksonAutoConfiguration.jacksonObjectMapper()
   标着 @ConditionalOnMissingBean —— 看到容器里已经有 ObjectMapper 了，
   于是【整个自动配置退让】，那个配好 JavaTimeModule 等一堆模块的
   primary mapper 从未被创建
                      ↓
③ Spring MVC 的 MappingJackson2HttpMessageConverter 是按类型注入 ObjectMapper 的，
   容器里只剩那个「模型协议专用」的 mapper，它没有 JavaTimeModule
                      ↓
④ OffsetDateTime 序列化失败
```

**可怕之处在于两件毫不相干的事被隐式绑在了一起**：
`modelObjectMapper` 是为「调外部模型 API」配的（丢弃 unknown 字段、序列化跳过 null），
而它顺手把「本应用对外返回的 JSON 长什么样」也接管了。
错误信息只会让人去查依赖，不会让人想到「是模型层的那个 Bean 干的」。

- ✅ 现在两套 mapper 职责显式分开：

  |  | `webObjectMapper` | `modelObjectMapper` |
  |---|---|---|
  | 服务对象 | 本应用对外的 HTTP 接口 | 调用外部模型的 HTTP 请求 |
  | 未知字段 | 报错（早暴露契约变更） | 忽略（模型会加非标准字段）|
  | null 字段 | 照常输出（契约要稳定）| 跳过（不传 ≠ 传 null）|
  | 时间类型 | JavaTimeModule | 用不到 |

- 📌 **同类陷阱的通用形式**：Spring Boot 里凡是标了
  `@ConditionalOnMissingBean` 的自动配置，只要你手动定义了同类型的 Bean，
  它就会**静默退让**（顶多一行 DEBUG 日志）。
  定义「某个专属用途」的 Bean 之前，先想想这个类型有没有被自动配置托管
- ⚠️ 顺带发现的第二个坑：`KbDocumentResponse` 里的 `finished()` 方法
  **不会被 Jackson 序列化**。Jackson 处理 record 时**只输出 record 组件**，
  写在 record 体里的普通方法不算属性。改成 record 组件才生效 ——
  而这一点最初是靠「响应 JSON 里没有这个字段」发现的，
  文档里写的「Jackson 会把它识别成 finished 属性」是错的

## ADR-020 · 中文关键词检索用「双字切分 + ts_rank」，不用 pg_trgm

**Context**

CLAUDE.md 说阶段 4 的关键词召回用「PostgreSQL 全文检索」。但 PostgreSQL 内置的
分词器是为英文设计的，中文切不开 —— 实测
`to_tsvector('simple','电池容量是5000mAh支持快充')` 把整句粘成**一个**词元。
后果是「退货」在全库 43 条相关切片里只能命中 **3** 条（漏检 93%）。

`docs/04` §11.1 当时倾向 `pg_trgm`，理由是它是 PostgreSQL 自带扩展、零成本，
不需要自建 Docker 镜像编译 `pg_jieba` / `zhparser`。

**Options**

| 方案 | 召回 | 排序区分度 | 成本 |
|---|---|---|---|
| A. `pg_jieba` 自建镜像 | 应该最好 | — | 要写 Dockerfile 编译 C++ 扩展，编译失败会阻塞整个阶段 |
| B. `zhparser` 自建镜像 | 成熟 | — | 同上且配置更复杂 |
| C. **`pg_trgm`** | ✅ | ❌ **完全并列** | 零成本（镜像自带） |
| D. **bigram（双字切分）+ `ts_rank`** | ✅ | ✅ | 要自己写分词器和 GIN 索引 |

**Decision**

选 **D**。实测数据（查询「退货要几天」）：

```
pg_trgm word_similarity : 4 条正确切片全部并列 0.3333   ← 没有排序能力
单字 + plainto_tsquery  : 0 行                          ← AND 语义，中文必然空
双字 + OR + ts_rank     : 0.022244 / 0.021636 / 0.020686 ← 有区分度
```

**`pg_trgm` 为什么不行**：它只生成 **3 字窗口**，而中文词大多是 2 字。
查询「退货要几天」的 6 个三元组里，首尾补空格得到的 `"  退"` 和 `"几天 "`
在长文本中间**永远不可能出现**，所以最多 3 个可能命中。它只能当二元过滤器。

**这一条对 RRF 是致命的**：融合只取**排名**不取**分数**，并列时的顺序等于
「按 id 排」—— 语义上毫无意义，等于把关键词这一路废掉。

**Consequences**

- ✅ 关键词路真的能提供互补价值（实测「星辰X1 电池」把「充电与电池」排到第一，
  且**对空格不敏感**：查询写 `星辰X1`、文档写 `星辰 X1` 照样命中）
- ⚠️ 要自己维护分词器 + `search_text` / `search_vector` 两列 + GIN 索引
- ⚠️ **换分词器需要全量重建索引** → 提供了 `POST /api/debug/kb/reindex?force=true`，
  这也是阶段 7 做「bigram vs jieba」A/B 对比的入口
- ⚠️ bigram 的候选集比词级分词大（实测占全库 1.3%~3.8%，型号类查询另见 ADR-021）

## ADR-021 · 分词规则：只在「连续同类字符段」内部生成词元

**Context**

最初的规则是「丢弃含空格的 bigram」。实测证明那只是**症状不是根因**，
而且规则本身有漏洞 —— 它拦不住 `5000mAh`：逐字符切 2-gram 会得到
`50 00 0m ma ah`，**每一个都不含空格**，那条规则完全看不见它们。

真正的机制是：**bigram 跨过了字符段边界**。跨段切出的词元（如 `"1 "`）
写进 `search_text` 后，`to_tsvector` 会把它们退化成**裸的单字词元**：

```sql
SELECT to_tsvector('simple','星辰 辰X X1 1 电 电池');
→  '1':4 'x1':3 '星辰':1 '电':5 '电池':6 '辰x':2      ← 裸单字 1 和 电 出现了
```

而裸单字在中文里是**最高频词元**。实测查询「星辰X1 电池」的候选集
从 3.8% 涨到 **36.6%**。

**Decision**

```
段类型              处理                          例子
─────────────────────────────────────────────────────────────────
CJK（长度 ≥ 2）     切 2-gram                     退货要几天 → 退货 货要 要几 几天
CJK（长度 = 1）     ★ 丢弃                         日 → （无）
ASCII / 数字        整体保留为一个词元（转小写）      X1 → x1、5000mAh → 5000mah
ASCII（长度 = 1）   ★ 丢弃                         7 → （无）
跨段                不生成任何词元
```

「单字丢弃」是**被实测数据推着改的**（最初的设计是保留，理由是「丢字会丢信息」）：

| 裸单字 | 出现条数（/1652） | 来源 |
|---|---|---|
| `元` | 192（12%） | 「5999 元」行尾 |
| `年` | 159（10%） | 「2026 年」行尾 |
| `2` | 166（10%） | 小节号「2.1 有效期」 |

一个字符没有任何区分能力，只有污染候选集的作用。

**Consequences**

- ✅ 裸单字词元数量从 946 条降到 **0**
- ✅ ASCII 段整体保留还带来一个额外好处：型号中间有没有空格都能匹配
- ⚠️ **代价**：查询里若含被空格孤立的单字，那个字不参与关键词召回
  （向量路仍然覆盖）。查询**只**由单字构成时会得到零个词元，由调用方短路处理
- ⚠️ 非 CJK 表意文字（西里尔、希腊、带重音的拉丁字母）会被当作分隔符丢弃。
  对中文电商语料无影响；要支持其他语言应给它们各自的「段类型」（按词切分）

## ADR-022 · `search_text` 保持普通列，用生成列派生 `search_vector`

**Context**

Java 侧分词器只能产出「空格分隔的词元串」，产不出 `tsvector`。
需要一层转换，两个做法：

**A. 表达式索引** `CREATE INDEX ... USING GIN (to_tsvector('simple', search_text))`
**B. 生成列** `search_vector tsvector GENERATED ALWAYS AS (to_tsvector('simple', search_text)) STORED`

**Decision**

选 **B**。

1. **表达式索引要求 WHERE / ORDER BY 里的表达式与索引定义字面完全一致。**
   差一个引号（`'simple'` vs `"simple"`）、差一个空格，索引就**静默不生效**，
   退化成全表扫描 —— 不报错、不警告，只是慢。这是最难排查的一类问题。
2. **`ts_rank` 也需要 tsvector。** 表达式索引下要写
   `ts_rank(to_tsvector('simple', search_text), q)`，候选集内每行重算一遍；
   生成列直接读存储的列值。
3. **换分词器后的重建语义更干净。** 生成列：`UPDATE search_text` 自动重算 tsvector
   并维护 GIN 索引。表达式索引：必须 `REINDEX`。
4. 教学价值：`SELECT search_text, search_vector FROM kb_chunk LIMIT 5`
   能肉眼看到切成了什么，调分词器时比打日志快。

**Consequences**

- ⚠️ 多存一份 tsvector（1652 行约 1–2 MB，可忽略）
- ⚠️ `ALTER TABLE ADD COLUMN ... GENERATED` 会**重写全表**（1652 行，毫秒级）
- ⚠️ ★ **生成列不能引用另一个生成列**（PostgreSQL 限制）。所以 `search_text`
  必须保持普通列 —— 这正好是「分词留在 Java 侧」的额外理由：
  哪天想把分词下沉到 SQL，两列就得合并成一个，又回到表达式索引那条路上
- ⚠️ **`to_tsvector` 的 `'simple'` 参数必须显式写**。单参数版本
  `to_tsvector(text)` 是 **STABLE**（依赖 `default_text_search_config`），
  而生成列要求 IMMUTABLE，写漏了迁移会直接失败。
  **这是好事** —— 失败得响亮，而不是静默出错
- ⚠️ `to_tsvector('simple','')` 得到的**不是 NULL 而是空 tsvector**，
  所以「忘了写 search_text」和「写了空串」要靠查 `search_text` 才能区分。
  覆盖率探针必须写 `search_text IS NULL OR search_text = ''` 两个条件

## ADR-023 · ★ 保留词元重复（不做去重）—— 一个被实测纠正的错误

**Context**

最初对分词结果做了去重，理由是「倒排索引只关心有没有这个词，词频是噪声，
而且去重能让 tsvector 显著变小」。

全量回填后实测发现**这个理由是错的**：

```
查询「退货要几天」命中 43 条切片，统计不同分值的个数：
  去重版   →  1 种分值      ← 排序退化成「按 id 排」，语义上毫无意义
  不去重版 →  8 种分值      ← 正解「自签收之日起 7 天内」排第 3
```

**根因**：PostgreSQL 的 `ts_rank` 对 **OR 查询**取的是
「单个词元得分的**最大值**」，而单词语元的得分**只取决于词频**。
去重让每个词元的频率恒为 1，于是所有命中同一个词的切片拿到**完全相同**的分数。
（`ts_rank_cd` 也一样，实测同样全部并列 0.1。）

**Decision**

**不去重**，原样保留词频。

**Consequences**

- ⚠️ `search_text` 和 tsvector 的体积略大（中文 bigram 大多本来就互不相同，
  实际增幅有限）
- ⚠️ **这个错误如果没被实测抓到，系统会「能跑、不报错、结果看起来也合理」**，
  但关键词这一路在 RRF 里等于完全失效 —— 因为融合只取排名，
  而排名退化成了「按 id 排」。
  **这正是阶段 4 基线指标存在的意义**：它把「静默退化」变成了「一个可以看出异常的数字」
- ★ **可复用的教训**：在替换掉一个排序信号之前，
  先确认它是不是那个排序算法**唯一的输入**。
  「词频是噪声」这个直觉和 `ts_rank` 的实际算法正好相反

## ADR-024 · 检索用独立的有界线程池，且检索失败不影响回答

**Context**

一次检索要并行跑两路召回，两路都是**阻塞**操作（向量化 HTTP + 数据库查询）。

同时有三个失败语义需要确定：单路失败怎么办、两路都失败怎么办、重排失败怎么办。

**Decision**

**① 独立线程池 `retrieveExecutor`**：core=4 / max=16 / queue=64 / AbortPolicy /
关闭等待 **5 秒**。

**不用虚拟线程** —— 理由和 `sseExecutor` 一致：虚拟线程是**无界**的，
没有队列、没有上限，也就没有任何背压。在阶段 6 的 Redis 分布式限流到位之前，
有界平台线程池更稳妥。

**② 关闭等待 5 秒，和 `ingestExecutor` 的 60 秒刻意相反**：
检索是**只读、幂等、可重跑**的，用户本来就在等，早点拿到错误比多等 55 秒好；
而入库是**非幂等**的（写一半会留僵尸文档），宁可慢不可丢。

**③ 失败语义**：

| 情况 | 行为 |
|---|---|
| 单路失败 | 继续，用另一路的结果 |
| 两路都失败 | 继续，返回空上下文（问答退化成裸聊） |
| 重排失败 | **回落 RRF 顺序** |
| 线程池满 | 该路记失败，另一路照常 |
| **任何情况** | **不向上抛异常** |

**Consequences**

- ⚠️ ★ **`retrieveExecutor` 的 max 上限不是线程数，是 Hikari 连接池。**
  实测 `maximum-pool-size: 10`、`connection-timeout: 30000` ——
  16 个并发检索任务会抢 10 个连接，抢不到的卡在 **30 秒**超时上，
  比我们自己毫秒级拒绝糟得多。**这条约束写进了 bean 的 javadoc**，
  否则将来有人把 max 调到 64 会觉得「反正只是线程」
- ⚠️ `AbortPolicy` 下 `CompletableFuture.supplyAsync` 会在**提交时同步抛**
  `RejectedExecutionException`（任务压根没被接受，异常不在 lambda 里）。
  所以提交动作本身必须包在 try/catch 里 ——
  **否则如果第一个 future 提交成功、第二个被拒，第一个就成了没人等的孤儿任务**
- ⚠️ **检索的异常绝不能冒到 `ChatServiceImpl` 的 catch**，因为那个 catch 的语义是
  「**模型链路**失败 → `qa_log.status = 2`」。检索的问题混进去，阶段 7 会把
  「检索挂了」统计成「模型挂了」—— **归因彻底错乱，且从数据上看不出来**。
  所以有独立的 `retrieveSafely()`
- ⚠️ **重排必须能回落**：`RerankClient` 只有硅基流动提供、**没有降级链**
  （接口 javadoc 明写），一次 429 就能让整次检索失败。而重排是锦上添花的一环

## ADR-025 · 检索上下文拼进 system prompt，且固定指令在前

**Context**

`ChatRequest` 有 `systemPrompt` 和预留的 `history` 两个字段，检索上下文放哪？

**Options**

- A. 给 `ChatRequest` 加一个 `context` / `documents` 字段
- B. **拼进 `systemPrompt`**（新增 `RagPromptBuilder` 负责组装）
- C. 塞进 `history`

**Decision**

选 **B**。

**否决 A**：`client/package-info.java` 把 client 层钉死成
「全项目唯一允许出现模型 HTTP 请求的地方」，它的职责是**协议**，不是 prompt 策略。
加一个 `context` 字段意味着以后每次调整引用格式、分块模板都要动 client 包 ——
错误的耦合方向。而且 `ChatRequest.of(systemPrompt, ...)` 的 `systemPrompt`
**本来就是注入点**，所以这个方案**一行 client 层的代码都不用改**。

**否决 C**：`history` 是给阶段 5 的会话记忆预留的，挪用它会让语义混乱。

**★ 顺序约束：固定指令在前，可变上下文在后。**

这不是排版偏好，是省钱。DeepSeek 的上下文缓存是**前缀匹配**的：
只有请求的开头部分与上一次完全相同，那一段才能命中缓存。
而缓存命中价 **0.02 元/百万 token**、未命中 **1.0 元** —— **差 50 倍**。

```
[固定的角色设定与回答要求]   ← 每次都一样，可命中缓存
[本次检索到的资料]           ← 每次都不同，从第一个字起未命中
```

反过来拼的话，整个 system prompt 从第 1 个 token 起就没有任何一次能命中缓存。
**这条可以在 `qa_log.cost` 上直接验证。**

**★ 空上下文时整块省略，不留空标题。** 写「以下是相关资料：（空）」比不写更糟 ——
它把模型的注意力引向「资料在这里」这个结构，而那里什么都没有。
正确做法是换成一句「本次未检索到知识库内容，请如实说明」的说明。

**Consequences**

- ⚠️ system prompt 变长（5 条切片约 1–2K 字符），输入 token 增加
- ✅ 但缓存命中那部分按 0.02 计价，实际成本增幅远小于 token 比例

## ADR-026 · 评测集存「锚点」而不是 chunk_id，且必须 fail loudly

**Context**

阶段 4 要建 20 题基线评测集，每题需要标注「应该召回哪些切片」。
最直接的做法是把 `kb_chunk.id` 存进 YAML 提交到 git。

**Decision**

**不存 id，存「该切片里独有的一段原文」**，加载时用
`WHERE content LIKE '%' || anchor || '%'` 反查。

原因：`kb_chunk.id` 是 **BIGSERIAL**，每台机器、每次重灌语料都不一样。
硬编码 id 提交进 git 后，换台机器跑基线**不会报错**，
只会让 `Recall@K` 静默变成 0 或随机数 ——
**这是「阶段 7 的 A/B 对比做不了」最隐蔽的一种成因，因为它没有任何症状。**

反查结果只有三种，每一种都必须有**明确行为**：

| 命中条数 | 含义 | 行为 |
|---|---|---|
| 1 | 正常 | 采用 |
| 0 | 语料变了 / 切分改了 / 锚点写错 | **抛异常** |
| >1 | 锚点太泛，**或**内容真的重复 | 默认**抛异常**；写 `allow_multiple: true` 才接受 |

`allow_multiple` 是**显式 opt-in** 而不是放宽默认值，因为「命中多条」有两种成因：
锚点太泛（必须报错）vs 内容真的重复或都能回答问题（必须接受）。
写评测题的人要主动确认「这几条真的都算对」。

**Consequences**

- ⚠️ 改语料或切分粒度后可能有一批题目加载失败 —— **这正是想要的效果**，
  比静默漂移好得多
- ✅ `allow_multiple` 在阶段 4 就派上了用场：B-004「退货运费谁承担」的
  两个锚点命中 3 条切片（`售后FAQ` + `售后政策汇编` 的两份副本）
- ★ **可复用的原则：评测系统最不能犯的错就是「悄悄」**。
  基线漂移必须吵闹

> ⚠️ **但 ADR-026 只解决了一半的问题**（2026-09-19 修订时补的）。
>
> 它保证「一个锚点命中多条**时不会静默取第一条**」，
> 但**它管不了「锚点本身只覆盖了答案的一部分」**——
> 而后者才是真正的坑：B-011「价格保护怎么申请」的锚点老老实实命中了
> 唯一一条切片，fail-loud 机制**完全正常工作**，
> 可那条切片（价格保护政策 > **附加条件**）根本不是「怎么申请」的答案。
>
> 结果是：重排把真正回答问题的切片（促销活动规则 4.3 **申请方式**、
> 售后FAQ「价保怎么申请」）提到前面时，MRR 把它记成**变差**。
>
> **教训：fail-loud 只能守住「机制正确」，守不住「语义正确」。**
> 锚点唯一 ≠ 锚点是对的。完整的修法见 **ADR-029**。

## ADR-027 · 文档类型由「语料清单」逐文件声明，不用文件名启发式

**日期**：2026-09-19（阶段 4 收尾）
**状态**：已采纳

**背景**

扫描接口原来是 `POST /api/kb/documents/scan?docType=2` —— **整个目录共用一个类型**。
于是 `data/corpus/` 里的文件全被标成「售后政策」，
18 份里错了 4 份（促销活动规则应为 3、售后FAQ 应为 4、
商品说明书-星辰X1 应为 5、商品导购指南 应为 1）。

这个错误**极其安静**：入库全部成功、状态全部正常、检索也照跑，
只有 `doc_type` 一列是错的。而它是**阶段 5 意图定向检索的过滤条件**
（「用户问售后 → 只在 doc_type=2 的切片里搜」）——
标错的后果是「某一类查询永远返回空」，症状和「知识库里确实没有」一模一样。

**决策**

新增 `data/corpus/manifest.yml`，逐文件声明 `doc_type`。
扫描时清单优先，**清单没声明的文件回落用 URL 参数并打 WARN**。

**为什么不用文件名启发式**（看到「说明书」就判 5）

启发式对**不认识的文件名会静默给默认值**。加一份「2026春季新品.md」，
启发式认不出来 → 落进默认类型 → 又一次安静地标错。
显式清单的代价是每加一个文件要写一行，换来的是
**「这个文件没被声明」这件事本身是可见的**。

**两种失败，处理方式刻意不同**

| 情况 | 行为 | 理由 |
|---|---|---|
| 清单文件**不存在** | WARN + 回落 URL 参数 | 向后兼容：删掉它仍按老方式工作 |
| 清单存在但**格式错误** | **抛异常** | 写错了就该停下来。静默忽略某个字段 = 让作者以为它生效了 |

**★ 一个必须一起解决的陷阱**

`findReusableByHash` 命中去重时**直接 return**，不会碰 `doc_type`。
于是「改了清单里的归类」如果不做额外处理，表现为**改了 YAML 却毫无效果**——
因为文件内容一个字都没变，去重照样命中。

所以命中去重时增加**校正**：`kb_document` 和冗余的
`kb_chunk.doc_type` **一起改**，且**不重新向量化**
（`doc_type` 既不参与 embedding 也不参与分词，只改列就够）。

> ★ 冗余列必须一起改：意图定向检索过滤的是 `kb_chunk.doc_type`，
> 只改主表会得到「界面上看着对、检索时按旧值过滤」。

**Consequences**

- ✅ 实测：重新扫描后 4 份文档的 `doc_type` 被校正，**`submitted=0`**（无重复向量化）
- ✅ 新增文件忘了登记、清单里的文件被改名，都会有 WARN
- ⚠️ `商品导购指南.md` 归到 `1`（商品详情）是个**判断**而非精确匹配 ——
  词表里没有「导购指南」这一档。理由与代价都写在清单的注释里，
  阶段 5 定义意图树时如果发现不合适，**改一行 YAML 重扫即可**

## ADR-028 · 语料生成器必须产出「字节确定」的文件

**日期**：2026-09-19（阶段 4 收尾）
**状态**：已采纳

**背景**

入库去重（`findReusableByHash`）比的是**文件字节的 SHA-256**。
而实测发现：**重新生成一次语料，docx / xlsx / PDF 三个文件的哈希全变了。**

| 文件 | 重新生成后 | 库里 | |
|---|---|---|---|
| 促销活动规则.md | `e0751dbd…` | `e0751dbd…` | ✅ 一致（md 是确定性的） |
| 售后FAQ.xlsx | `81031c57…` | `f577a500…` | ❌ |
| 售后政策汇编.docx | `ebcdca80…` | `31311442…` | ❌ |
| 商品说明书-星辰X1.pdf | `22b0aa97…` | `fd6086b8…` | ❌ |

原因是这三种格式都会把**创建时间**写进文件。

**后果很严重**：`generate_corpus.py` + `POST /scan` 这个组合
会在知识库里**再灌一遍**，而且**真的会调用向量化接口**。
重复内容长期挤占 Top-5 名额，挤掉别的答案 —— 这正是
「售后政策汇编被灌了两份」的同类问题，只是触发条件更隐蔽。

**决策**

把三种格式的时间戳都钉死。**但实现方式不是逐个库设属性** ——
实测两个库都不可靠：

- **zip 条目自带的时间戳**：docx 有 17 个、xlsx 有 9 个条目，两个库都写「此刻」，
  **没有开关可关**
- **`core.xml` 的 `<dcterms:modified>`**：openpyxl 在 `save()` 里覆盖掉它，
  显式给 `wb.properties.modified` 赋值**实测无效**

所以改成**生成之后统一重写 OOXML 包**（`_normalize_ooxml`）：
重写 zip 条目时间戳 + 正则替换 `core.xml` 里的两个日期字段。
**不依赖库的内部行为，换版本也不会悄悄失效。**
PDF 侧用 reportlab 自带的 `rl_config.invariant = 1`（它就是为可复现构建设计的）。

**Consequences**

- ✅ 实测连跑 3 次，6 个文件哈希全部一致
- ✅ 「重新生成 + 重新扫描」变成幂等操作：内容没变就跳过，变了才重灌
- ⚠️ **踩过一次假阴性**：第一次测「通过」，是因为两次生成间隔不到一秒、
  时间戳碰巧相同。**验证确定性必须有足够的时间间隔**，否则测的是缓存
- ★ **可复用的原则：任何「内容没变就不重复处理」的机制，
  都要求产物的字节是确定的。**否则去重会静默失效 ——
  它不报错，只是每次都判定「内容变了」

## ADR-029 · ★ 评测集的 gold 必须是「多答案」，且补全时不能参考系统输出

**日期**：2026-09-19（阶段 4 收尾）
**状态**：已采纳

**背景**

阶段 4 的第一版基线给出两个「发现」：RRF 融合有增益、重排拖后腿。
**两个都是假的。**

逐题打开那 4 道「被重排弄坏」的题之后发现，**其中 3 道的正解标错了**：

| 题 | 标注的 gold | 重排提到前面的 | 谁真的答对了 |
|---|---|---|---|
| B-011 价格保护怎么申请 | `109` = 价格保护政策 **> 附加条件** | `13` = 促销活动规则 4.3 **申请方式**<br>`28` = 售后FAQ「价保怎么申请」 | **重排** |
| B-010 优惠券过期了怎么办 | `5` = 优惠券**有效期** | `25` = 售后FAQ「不能，过期自动失效不予补发」 | **重排** |
| B-009 优惠券怎么用 | `6` = 使用**限制** | `7` = 适用**范围** | 两者都是答案 |

**根因**：同一批业务规则被**多个文档**覆盖 ——
优惠券有 4 份文档 12 个切片在讲、价保有 3 份文档 7 个切片、发票有 3 份文档 5 个切片。
而题是**反向构造**的（看了一个切片就写问题，把那一个当唯一正解）。

**单答案 MRR 在这种语料上度量的是「有没有命中标注者随手挑的那一片」，
不是「有没有答对」。**

**决策**

把每道题的**所有合法答案**补进 anchors。已有 14 道题补全。

**★ 补全时的纪律（这条比结论本身重要）**

判断依据**只能是**「只读这一段文字 + 问题，它是否回答了问题」。
**不允许因为「某个配置把它排上来了」就补进去** ——
那是拿系统输出拟合标准答案，评测从此失去意义。

这条纪律必须能指出反例，否则等于没有：
**B-013「发票能开纸质的吗」刻意保持单答案**。
重排把 `30`（售后FAQ「可以开**电子**发票吗」）提到 `110` 前面，
但问题问的是**纸质**发票，`30` 没有回答它 ——
**重排在这道题上是真的错了，gold 不应该为它辩护。**

另两条：
- **相关 ≠ 回答**。B-010 未采用 `160`（「已过期的优惠券不予返还」）——
  它讲的是**退货时**过期券退不退，不是「过期了该怎么办」
- **每加一条都要写明理由，包括未采用的候选**。否则下一个人无法区分
  「被考虑过并否决」和「被漏掉了」

**受控对比（同一批检索结果，两套 gold 定义）**

| 对比 | 旧 gold | 新 gold |
|---|---|---|
| 重排 vs 融合 | −0.0167 | **+0.0250** |
| 融合 vs 纯向量 | +0.0250 | **−0.0250** |

**两个符号同时翻转。**

**Consequences**

- ⚠️ **新数字同样不能当结论**：量级 0.025 = `0.5/20`，
  就是一道题从第 1 名掉到第 2 名。**n=20 上任何「X 比 Y 好」都不可信**
- ⚠️ 补全 gold 会**机械地抬高**所有指标（命中机会变多），
  修订前后的数字**不能直接比**
- ✅ 唯一稳的是**按查询形态切片的互补结构**：词典型题上纯向量封顶，
  口语句上只有带重排的完整链路满分（见 `docs/06` §3.3）
- ★★ **最重要的教训：评测集的问题不会表现为「跑不起来」，
  只会表现为「结论是错的」。**
  第一版基线能跑、有数字、有洞察、还配了机制解释 —— 但它是假的。
  唯一能发现它的方式是**逐题打开看**，问「这道题被判为变差，到底发生了什么」。
  **只要聚合指标、不看逐题明细，这类错误 100% 会漏掉**

## ADR-030 · 意图树的顶层按【业务语义】切，检索策略挂在叶子层

**日期**：2026-09-19（阶段 5.1）
**状态**：已采纳

**背景**

5.1 要定义「5 类意图」。切法有两种，而且它们导出的系统结构完全不同：

| | 按业务语义切 | 按答案来源切 |
|---|---|---|
| 顶层长什么样 | 商品咨询 / 购买决策 / 促销活动 / 售后服务 / 订单物流 | 知识库-商品 / 知识库-售后 / 知识库-促销 / 实时工具 / 无需检索 |
| 意图与检索策略的关系 | **多对多**，要单独维护映射 | **一对一**，5.4 是平凡映射 |
| 顶层是什么 | 「用户想干什么」 | 「程序该去哪找」 |

**决策**

按**业务语义**切。检索策略（`doc_types`、走不走工具）挂在**叶子层**。

**理由**

按答案来源切更省事，但那意味着**意图 == 检索策略** ——
它就不再是「意图」了，而是「路由目标」。
面试官问「你的意图树怎么设计的」，答「按答案来源分的」，
听起来像是把实现细节冒充成了业务抽象。

而且它有一个具体的表达力缺陷：**「订单到哪了」和「怎么退货」会被分到两个顶层分支**，
因为它们答案来源不同 —— 可用户并不这么想问题。真正的分类维度是
「买之前 / 买之后 / 我的这笔单子」，而不是「静态文档 / 实时数据库」。

**代价**

意图 → `doc_type` 变成**多对多**：同一个 `doc_type` 被多个叶子引用
（`doc_type=4` 同时被 `COUPON` / `PRICE_PROTECTION` / `RETURN_EXCHANGE` /
`RULES_AND_PROCESS` 引用）。

这个代价后来证明是**收益**：正因为要显式维护这张多对多映射，
才必须去查「每条规则的答案到底分布在几份文档里」——
而这一查就查出了「**10/20 道题的 gold 横跨多个 doc_type**」这个事实。
如果映射是一对一的，这个问题会在 5.4 掉分时才暴露，而且没人能解释为什么。

## ADR-031 · ★ `doc_types` 声明的是「答案全集」，不是「过滤条件」

**日期**：2026-09-19（阶段 5.1）
**状态**：已采纳

**背景**

树里每个叶子要声明它和 `doc_type` 的关系。两种写法：

```yaml
# 写法 A：答案全集
doc_types: [2, 3, 4]     # 价格保护的答案在这三种文档里都可能有

# 写法 B：过滤主类型
doc_type: 3              # 5.4 就 WHERE doc_type = 3
```

**决策**

写法 A。它声明的是一个关于**语料的【事实断言】**，不是 5.4 的行为。

**理由**

**它换来了一个可自动验证的验收标准**：

```
对每一道评测题：该题 gold 切片的 doc_type 集合 ⊆ 该题意图声明的 doc_types 集合
```

不满足 = **树画错了**。这个信号是自动的，不靠人看。

写法 B 则**没有任何可自动验的东西** —— 5.1 的验收只能写成
「人工检查每个叶子的主类型看着合理」，而这个标准没法跑。

**更关键的是归因**。看 `B-011`（价格保护怎么申请），它的 gold 跨 `{2,3,4}`：

| | 判成「售后服务」 | 判成「促销活动」 |
|---|---|---|
| 过滤后剩下 | `{2,4}` | `{3,4}` |
| 切掉的 | `doc 3` 那个 anchor | `doc 2` 那个 anchor |

**无论怎么路由，硬过滤都会切掉一部分正确答案。**
用写法 B，这道题掉分时**没人能说清是「树错了」还是「过滤太激进」** ——
而这两种原因的修法**完全相反**：一个是改 YAML，一个是改 5.4 的策略。

写法 A 把它拆成两个独立的问题：
- 「树错了」→ 由 `IntentTreeConsistencyTest` 自动抓（20/20 通过）
- 「过滤太激进」→ 由 7.2 的**过度检索率**度量（5.4 的事）

**★ 这条验收标准做过证伪**

把 `PRICE_PROTECTION` 的 `doc_types` 从 `[2,3,4]` 临时改成 `[3]` 再跑，测试立刻变红：

```
B-011 [PRICE_PROTECTION]：gold 落在 [2, 3, 4]，但这些类型没有被声明，多出来的是 [2, 4]
```

**一个「树坏了也照样绿」的测试等于没有**，所以「它会不会红」是实测过的，不是假设的。

**代价**

`doc_types` 允许重叠、允许多个，读起来比「一个叶子一个类型」复杂一点。
另外它是**断言**，就有断言错的风险 —— 这由上面那条测试兜住。

## ADR-032 · 兜底意图不占「5 类」的名额

**日期**：2026-09-19（阶段 5.1）
**状态**：已采纳

**背景**

路线图 7.1 写的是「150 题，覆盖 **5 类**意图」。而系统一定需要一个兜底分支
（闲聊、问候、答不了的问题）。它算不算 5 类之一？

**决策**

不算。5 类是 5 个**业务**意图，兜底是第 6 个分支，标 `out_of_scope: true`。

**理由**

**指标形状**。其他类的 ground truth 是 `expected_chunk_ids = [123, 456]`，
兜底类的只能是**空集**。同一个列承载两种形状的语义，7.2 算指标时
处处都要先判断「这题是不是兜底」。

拆开之后两个指标各管一种错，而且它们**性质相反**：

```
Top-1 意图准确率  ← 分母 = 5 类业务意图的题
越界率            ← 本该兜底却被判成业务意图的比例
```

混在一起算，一个指标里两种错会**互相抵消** —— 把「该兜底没兜底」和
「该分类没分类」平均成一个数字，那个数字不描述任何真实的东西。

**代价**

代码里多一个「业务意图计数排除 `out_of_scope`」的逻辑
（`Tree.businessIntents()`）。为了让这个计数不会悄悄变，
`IntentTree` 里钉了一个 `EXPECTED_BUSINESS_INTENTS = 5` 常量 ——
**真要改成 6 类，改这个常量的同时必须一起改 `docs/10` 和 `docs/06` 的指标定义**。
这是刻意的摩擦。

## ADR-033 · `eval_question.intent` 存【叶子】码，且在评测集里必填

**日期**：2026-09-19（阶段 5.1）
**状态**：已采纳

**背景**

`eval_question.intent` 是 `VARCHAR(32) NOT NULL`，阶段 4 时写的是哨兵值
`UNCLASSIFIED`（理由是「意图树属于阶段 5，还没定义」）。
现在树定义好了，那一列该存什么？

**决策**

存**叶子码**（`SPEC_QUERY` / `PRICE_PROTECTION` / `RULES_AND_PROCESS`），
不存顶层码（`PRODUCT_INQUIRY` / `PROMOTION`）。而且在评测集 YAML 里**必填**。

**理由**

**顶层码可以由树 roll-up 出来，反过来推不出来。**
只存顶层，「价格保护这类题答得怎么样」就**永远算不出来** ——
除非回头重标一遍。

而顶层和叶子错，是**两种不同的错**：

```
顶层错  = 路由去了错误的知识库区域   （严重）
叶子错  = 区域对了但细分偏了         （往往无影响，因为相邻叶子的 doc_types 常常重合）
```

只存顶层码，7.2 的指标分不出这两者。

**为什么必填**：`UNCLASSIFIED` 存在的理由是「意图树还没定义」——
现在定义了，理由就不成立了。留一条「缺了就写哨兵」的退路，
等于保留一个**已经没有任何意义的逃生口**，
而它绕过的是 7.2 最能说明问题的那一列。

**代价**

7.1 标注时要面对 13 个选项而不是 5 个。但判据很清晰
（「这句话在问什么」，而不是「答案在哪几个文档」——后者由 ADR-031 的测试自动管），
所以标注成本的增加主要在**判据的确立**上，不在每一题的用时上。

**附带修掉的一个缺陷**

动工时发现 `doc 208`（`新品上架通知.docx`）躺在库里：
文件名是「新品上架通知」，内容却是「七天无理由退货规则」，还被标成了
`doc_type=3` 促销规则。它是阶段 3 手工测试时走**单文件上传接口**灌进去的，
**绕过了扫描和语料清单** —— 所以清单的 WARN 拦不住它。

后果正好落在 5.4 上：`doc_type=3` 只有 16 条切片，它占了 **19% 的噪声**。
已软删除（`deleted = 1`，可恢复）。

> ⚠️ 那个口子现在还开着：单文件上传不经过语料清单。

## ADR-034 · 意图树缺文件 → 启动即崩；语料清单缺文件 → WARN 回落

**日期**：2026-09-19（阶段 5.1）
**状态**：已采纳

**背景**

`CorpusManifest`（阶段 4 收尾）的失败语义是：清单**不存在**时打 WARN
并回落到 API 的 `?docType=` 参数；清单**存在但格式错**时才抛异常。

意图树要不要沿用这套？

**决策**

**不沿用，而且刻意相反**：

| | 语料清单 | 意图树 |
|---|---|---|
| 文件不存在 | WARN + 回落参数 | **抛异常，应用起不来** |
| 内容畸形（启动时） | 抛异常 | **抛异常，应用起不来** |
| 内容畸形（运行中） | —（不缓存，每次都读） | **打 ERROR，沿用上一次的好树** |

**理由**

**① 缺文件时的差别，取决于「有没有一个不比失败更差的选项」。**

清单有：老路径 `?docType=` 还在，删掉清单应用仍按老方式工作，这是**真兜底**。
意图树没有：唯一能做的「回落」是**把所有问题判成同一类** ——
那不是兜底，那是**静默地把系统变成坏的系统**。

> 这条原则比结论本身有用：**要不要兜底，取决于兜底的结果是不是真的更好，
> 不取决于「风格要统一」。** 同一个项目里两处失败语义相反，是对的。

**② 运行中不崩，是因为可用性。**

意图树**每次意图识别都要读**，所以它是**缓存 + 按文件修改时间热加载**的
（这一点又和语料清单相反 —— 清单只在人工触发扫目录时读一次，不缓存）。
于是「运行中文件被改坏」是一个真实存在的路径。如果配置里打错一个字母
就让整个问答接口 500，那是实打实的可用性故障。和 `RetrievalPipeline` 的
「检索失败不影响问答」同一个原则：**能降级就不要把错误冒到用户面前，但必须留痕。**

留痕的方式是把错误存进 `lastRefreshError` 字段，由调试探针报出来 ——
因为 ERROR 日志滚过去之后就没人记得了。

## ADR-035 · 分类目标 = 「行为不同的最小集合」，而不是树的全部叶子

**日期**：2026-09-19（阶段 5.2）
**状态**：已采纳

**背景**

意图树有 16 个叶子（13 个业务 + 3 个工具）。分类时让模型从里面选一个，
还是选一个别的什么集合？

**决策**

引入 <b>分类目标</b> 这一层概念，规则只有一条：**行为相同的不区分。**

| 顶层意图的 `retrieval` | 分类目标 |
|---|---|
| `KB` | 展开到**叶子**（叶子之间 `doc_types` 不同，5.4 行为不同） |
| `TOOL` / `NONE` | **只算一个目标**，用顶层 code（叶子 `doc_types` 都是空集，5.4 行为一样） |

于是 16 个叶子 → **15 个分类目标**（13 个业务叶子 + `ORDER_LOGISTICS` + `OUT_OF_SCOPE`）。

**理由**

三个工具叶子（订单状态 / 库存 / 我的优惠券）的 `doc_types` **都是空集**，
5.4 对它们的行为完全一样（都不检索）。区分它们只对 5.9 有意义 ——
而 5.9 有更好的机制：**MCP 工具 schema 本来就是给模型选工具用的**，
让意图识别先选一遍是重复劳动。

更实际的是：那三个叶子在语义上高度重叠（都是「查我的东西」），
一个 9B 模型很容易在它们之间摇摆 —— 而摇摆的结果**对检索没有任何影响**，
纯粹是给 7.2 的准确率添噪声。

**副作用（好的那个）**

**将来加一个 TOOL 类意图，不需要改 prompt 的结构**，它自动变成一个目标。

**代价**

「分类结果的 code」和「树的叶子」不再是同一个集合 ——
`classificationTargets()` 里可能出现顶层 code。

这需要一处额外的校验（`IntentFewShot` 会拒绝把 `TOOL_LEAF` 当成目标），
以及一处说明：`eval_question.intent` 存的是**分类目标的 code**，
它**总是**树里存在的东西，但不总是叶子。

## ADR-036 · ★ few-shot 样本与评测集必须**【结构上】不相交**

**日期**：2026-09-19（阶段 5.2）
**状态**：已采纳

**背景**

5.2 动工前对了一遍：`intent-tree.yml` 里那 55 条 `examples`，
和 20 道评测题**有 18 条逐字相同**。

```
B-001 退货要几天         ← RETURN_EXCHANGE 的示例就是这一句
B-009 优惠券怎么用       ← COUPON 的示例
B-011 价格保护怎么申请   ← PRICE_PROTECTION 的示例
B-017 这个适合送长辈吗   ← SCENARIO_PICK 的示例
……（干净的只剩 B-014 / B-015）
```

成因是写树的时候为了「真实、有代表性」，直接从语料和已有的题里挑句子。

**如果拿这 55 条当 few-shot，5.2 的验收会完全失去意义** ——
测的是「模型能不能把 prompt 里刚看过的句子照抄回来」。

**决策**

**拆成两份文件**：

| 文件 | 职责 | 能不能含评测题 |
|---|---|---|
| `intent-tree.yml` 的 `examples` | 给人看的**文档** | 可以，无所谓 |
| `intent-fewshot.yml` | 给模型看的 **prompt 素材** | **一句都不行** |

并且**把纪律做成断言，而不是靠人记**：

1. `IntentTree.ClassificationTarget` **刻意不携带 `examples` 字段** ——
   prompt 构建器想用树里的示例，在类型层面就写不出来
2. `IntentFewShotTest` 同时读两份真文件，断言这里的每一句都不等于
   任何一道评测题
3. 有一条**反证测试**：断言树里的 `examples` 与评测集的重合数 **> 0**。
   它证明「拆成两份文件」不是多此一举；哪天示例被清理得不重合了，
   那条会红，届时可以重新讨论要不要合并

**理由（为什么不是「改掉那 18 条示例」）**

那是**一次性**的修法，而且是**恶性**的：7.1 扩到 150 题时新题会再次撞上示例，
到时又要改一轮 —— 而那时树已经定稿、5.2 已经调好，改它意味着推翻重测。

拆成两份之后，`examples` 可以随便用最典型的问法（它的职责就是文档），
few-shot 永远不会撞车。

**代价**

多一个文件要维护；每个分类目标至少要写 2 句样本。
但这两句是**从语料重新造**的，不是从考题里挑的 —— 两者天然独立。

**顺带定下的严格性**：某个分类目标**没有样本**时**直接崩**，不是 WARN。
理由是这个项目的通用判据 —— **失败的结果是不是比停下来更差。**
没有样本的目标不会被跳过，它会以「只有一句干巴巴的 description」的形式
留在候选列表里，于是准确率掉一点，而**没有任何信号告诉你为什么**。
修它的成本只有几行 YAML。

## ADR-037 · 分类 prompt 不放 `doc_types`，也不诱导「拿不准用兜底」

**日期**：2026-09-19（阶段 5.2）
**状态**：已采纳

**背景**

叶子已经声明了 `doc_types`（答案落在哪些文档类型），而它恰好是
5.4 真正要用的东西。把它一并写进分类 prompt，模型不是能"分得更准"吗？

**决策**

**不放。** 而且另外加一条：不写「拿不准时输出 OUT_OF_SCOPE」。

**理由**

**① `doc_types` 是检索策略，不是用户意图。**

这正是 ADR-030 / ADR-031 花了两节讲清楚的事。
把它放进 prompt 会诱导模型按「答案在哪几个文档里」去分类，
而不是按「用户在问什么」—— 于是**分类体系从用户视角悄悄漂移成实现视角**。

最麻烦的是：**这件事从准确率上看不出来**。大部分时候两条路给出同一个答案，
只有在两者分歧的少数样本上才会暴露 —— 而那时你会以为是模型不行。

**② 兜底的含义不能被扩大。**

「拿不准时输出 OUT_OF_SCOPE」是一句很自然但错误的话。
兜底的含义是**「这句话与平台业务无关」**，不是「我分不清售后下面哪一类」。

混起来的后果很隐蔽：**「模型没把握」和「问题确实无关」在数据上分不开了** ——
而 5.3 的澄清反问（验收标准 4：「那个怎么样」→ 触发澄清反问）
恰恰要靠「没把握」这个信号。

正确的写法是把它限定回本义：
「只有这句话与商品、促销、售后、订单**都无关**时才输出 OUT_OF_SCOPE；
在两个业务类别之间拿不准时，选更接近的那一个。」

**验证**

`IntentPromptBuilderTest` 有三条对应的测试，每条都配了反证：
断言 prompt 里**没有** `doc_type` / 树示例 / 「拿不准时输出 OUT_OF_SCOPE」，
并且断言那些东西**确实存在**于别处（否则断言恒真）。

## ADR-038 · 分类失败**不重试不换模型**，回落到「不做定向检索」

**日期**：2026-09-19（阶段 5.2）
**状态**：已采纳

**背景**

分类可能失败（全链路调用失败、模型返回非法 code、返回空正文）。
失败之后怎么办？

**决策**

| 失败形态 | 行为 |
|---|---|
| 调用没成功（超时 / 全链路失败） | **不重试、不换模型**。`outcome = CALL_FAILED`，`code = null` |
| 模型回了，但不是合法 code | `outcome = UNKNOWN_CODE`，**保留模型原话** |
| 模型返回空正文 | `outcome = CALL_FAILED`（★ 这是推理模型吃光 max_tokens 的探测器） |

三种情况统一由调用方（5.4）处理成：**不做定向过滤，照常检索**。

**理由**

**① 分类是高频附加调用。** 每次提问都要跑一次，而它的价值是「让检索更准」，
不是「让问答能跑」。失败的合理兜底是**退化成阶段 4 的完整行为** ——
用户无感，只是可能多召回一些无关切片。

换个模型重试只会把延迟叠上去，而**正确率并没有保证** ——
同一家的另一个模型未必更擅长这个分类，而跨供应商重试意味着又一次网络往返。

**② 三种失败必须分开。** 如果只用一个 `null` 表示失败，
「模型在乱答」和「供应商挂了」就混成了一种，而**这两件事的排查方向完全相反**
（前者改 prompt，后者改基础设施）。这和 `ModelErrorKind` 刻意区分多种失败是同一个思路。

**③ 失败时 `code` 存 `null`，不猜一个值。** 同 ADR-010 的原则：
拿不到就记 NULL，不估算。猜一个意图会让 `qa_log.intent` 这个列变成不可信的。

**附带定下的两件事**

**① `max_tokens` 默认不覆盖**（用全局的 2048）。

分类的输出只有几个 token，直觉上给 16 就够 —— 但降级链的 P0
`deepseek-flash` 是**推理模型**（实测推理 token 占总输出 87%）。
给小的后果是推理把额度吃光、`content` 返回**空字符串**，
表现为「分类永远失败」而日志里没有任何异常。

这个坑 CLAUDE.md 里记着（阶段 2 踩过，现象是「AI 不说话」），
所以这里显式调用 `ChatResponse.isEmptyContent()` —— 那个方法就是为探测它写的。

**② `temperature = 0.0`，但它【不等于】确定性。**

实测（2026-09-19）：同一个问题、同一个模型跑 8 次，出现过 7:1 的结果分裂
（`RETURN_EXCHANGE ×7` / `REFUND ×1`，`modelKey` 全程一致，不是降级导致的）。

成因是推理模型的固有性质（GPU 浮点并行归约 + batching），
和阶段 4 记下的「向量化接口有约 3e-4 漂移」是同一类现象。
而分类的输出只有几个 token —— **几个 token 的差异就直接是另一个答案**。

**后果**：单次测量的准确率有约 **±5%** 的逐题波动（n=20 时一道题就是 5%）。
报准确率必须重复多次，见 `docs/06`。

**为什么不现在做「多次采样取多数」**：那能压住方差，而且顺手能拿到
「N 次采样的一致度」当置信度 —— **但那正好是 5.3 的设计决定**。
现在做等于替它拍板，而那时的设计会知道更多
（比如供应商到底给不给 token logprob）。

## ADR-039 · 澄清反问的触发信号是「信息充分性」，**不是**分类置信度

**日期**：2026-09-19（阶段 5.3）
**状态**：已采纳

**背景**

路线图 5.3 写的是「**置信度计算** + 澄清反问」，隐含的假设是
**「分类置信度低 → 澄清」**。这个假设看着很自然 ——
系统分不清用户想问什么，那就问一句好了。

**动工前把三种候选信号全测了一遍，全都不成立：**

| 信号 | 实测（2026-09-19） |
|---|---|
| **token logprobs** | DeepSeek 支持（硅基流动直接 `HTTP 400 top_logprobs is not allowed`）。所有问题首 token 的 logprob 都是 **-0.000**，领先次候选 5~13 个 log 单位。**连那个已知会翻转的问题都报 -0.000** —— 零区分度 |
| **采样一致度** | 跑 8 次取众数：「那个怎么样」**8/8 = 1.00**（最该澄清的，零信号）；「退货要几天」**7/8 = 0.88**（完全正常的问题反而更低）。**两个方向都反了** |
| **模型自报** | 不采信，同 ADR-037 |

**决策**

澄清的触发信号改为**「这句话是否包含足够的信息来回答」** ——
由分类 prompt 直接判出来（`role: CLARIFY` 那个目标），
**不经过任何置信度中间量**。
`qa_log.intent_confidence` 与 `chat_message.intent_confidence` 两列
**继续留 NULL，不写**。

**理由**

**① 这两个问题正交。**

```
信息完整但分类边界模糊（「退货要几天」）→ 分类器不确定，但【不该】澄清
信息不足但分类器自信（「那个怎么样」）→ 分类器确定，但【该】澄清
```

三种信号度量的都是前者，而这里要的是后者。**怎么调阈值都不对。**

**② 不写未校准的置信度。** 同 ADR-010 的 NULL 原则 ——
一个没校准的数字存进库里，早晚会被当成阈值用。
而实测已经证明它**反相关**：存一个反相关的值比不存更坏。

**③ logprobs 那条揭示了一件更根本的事。**

那个 8 次里翻了 1 次的问题，logprobs 领先次候选 **10.1**（比值约 24000:1）——
按那个分布，8 次里一次都不该翻。

> **「模型在分布上很确定」和「同一份分布下浮点噪声会不会让它翻转」是两件事。**
> 报出来的 logprob 不是校准过的概率，它看不见推理内核里的浮点归约。

**代价**

`intent_confidence` 两列建好了却一直空着。这是刻意的 ——
**留空可以接受，填一个反相关的值不行。**

## ADR-040 · 「信息不足」是第三种 role，不是兜底的另一种说法

**日期**：2026-09-19（阶段 5.3）
**状态**：已采纳

**背景**

实测发现：在**没有**「信息不足」这个选项时，分类器对「那个怎么样」
给出的正是一个**自信的 `OUT_OF_SCOPE`**。

于是用户收到「我只处理商品导购与售后问题」—— **而那句话明明就是在问商品。**
用户不会知道是系统没听懂，只会觉得「这客服答非所问」。

**决策**

在意图树里引入 `role` 枚举，**取代原来的 `out_of_scope: true` 布尔量**：

```
BUSINESS        用户在问本平台的业务     → 正常检索并回答
OUT_OF_SCOPE    不是我的业务             → 「我只处理导购和售后问题」
CLARIFY         是我的业务，但你得再说点 → 「你指的是哪款商品？」
```

**理由**

**① 语义差别很大，混起来用户会拿到错误的回答。**
这是 ADR-037 那条纪律的**第二次现身**：把「答不了」冒充成「不该答」。

**② 用枚举而不是两个布尔量。** 两个互斥的布尔量可以同时为真，
而那个状态是无意义的、只能靠校验拦住。**枚举让「只能三选一」在类型层面成立。**

**附带发现：样本集必须是「双腿」的**

第一版澄清样本全是「指代 → 澄清」，**样本集是单边的**，于是模型学成了
「见『这个』就澄清」——「这个有保修吗」「这个能用优惠券吗」「这个多久发货」
全被判成信息不足。补上「有指代但能回答」的样本之后，四分之三被修好。

> ★ **判据写在 description 里，而样本决定了模型实际学到什么。**
> 判据说「单独能不能回答」，但样本全在演示「有指代就澄清」——
> **模型学的是样本，不是判据。**

**代价**

树的顶层角色从 2 种变成 3 种，树、加载器、prompt、决策器都要认这个新角色；
`ClassificationTarget` 的候选数从 15 变成 16。

**已知的、刻意不修的**

「这个适合送长辈吗」被误判成信息不足（1/20）。它**不是**样本覆盖缺口 ——
补完之后四个格子都有人了。原因是「适合送长辈」在模型眼里不像
「保修」「发货」那样是个可查询的主题。

**而模型的答案未必算错**：这句话单独拿出来，「这个」确实没解析。
这与阶段 4 的 B-011（当时也是 gold 标错了）同型。
n=20 时分不清「补样本覆盖」和「照考题调 prompt」，所以不修 —— 记在案。
5.5（会话记忆）上线后「这个」有上文时会被消解，这个分歧会自然消失。

## ADR-041 · 澄清短路整条链路；「没发生」的列一律写 NULL；`qa_log` 加 status=3

**日期**：2026-09-19（阶段 5.3）
**状态**：已采纳

**背景**

澄清反问要走完整链路（检索 → 生成）再返回一句「你指的是哪款商品」，
还是直接短路？

以及：澄清的结果怎么落 `qa_log`？

**决策（三件事，同一条原则）**

**① 短路。** 分类插在**检索之前**（非流式）／**`sink.onStart` 之后**（流式）。

**② 「没发生」的列写 NULL。** 澄清路径给 `baseLog` 传
`retrievalTrace = null` 和 `trace = null`，于是 `provider` / `model` /
`usage` / `cost` / `degradation_events` / `references` / `retrieval_detail` /
`retrieval_latency_ms` 全部为 NULL。

**③ `qa_log.status` 增加第三个取值 3（澄清反问）。**

**理由**

**① 短路的理由是最直白的**：澄清路径的全部价值就是
让用户立刻得到反馈（实测 559ms vs 正常问答 3~8 秒）。
走完检索再澄清，那几百毫秒和向量化的钱**纯属白花**。

而且「短路」**只能用调用次数证明** —— 一个「检索了、生成了一堆、
最后丢弃」的实现，返回的文本和真正短路的**一模一样**。
所以 `ChatClarificationIntegrationTest` 里那条对照测试的两次调用
只差一次 mock 返回值，结果却是「调了两次 + 检索了一次」。

**② NULL 的理由是本项目反复踩的坑。**

第一版实现传了一个**空的** `RetrievalTrace`，序列化出来是：

```json
{"vector_hits":[],"keyword_hits":[],"fused":[],"reranked":[],"final_top_k":[]}
```

**这和「检索跑了、两路都没召回任何东西」逐字相同** ——
而两者的排查方向完全相反：一个是链路没走到检索，一个是召回有问题。

同 `references` 那条既有约定：**没有就是 NULL，不是空数组。**

**③ status=3 的理由：澄清既不是成功也不是失败。**

它没生成答案，但也没失败 —— 那恰恰是系统正确工作的表现。

| 塞进 | 后果 |
|---|---|
| 1 成功 | `final_answer` 里躺着一句反问，但看起来像正常回答 → 答案质量指标会给它打分；检索指标会把它算成「没召回到」 |
| 2 失败 | 阶段 7 会把「系统正确识别出该反问」统计成「模型挂了」 |

> ★ **这是同一个坑的第三次现身**：
> 阶段 4 的检索异常差点被记成「模型挂了」（R3）→
> 5.2 的分类失败要分三种原因（ADR-038）→ 这次是澄清。
> **规律一样：能让两种不同性质的东西共用一个值时，
> 统计迟早会悄悄错，而且从数据上看不出来。**

**为什么不用 `intent = 'NEEDS_CLARIFICATION'` 来筛**

那需要阶段 7 每处统计都写
`WHERE status = 1 AND intent <> 'NEEDS_CLARIFICATION'`。
**「每处都要记得加一个条件」是最容易漏的形态** ——
漏了不报错，只是数字偏低。变成 `status` 的取值之后，
`WHERE status = 1` 天然就是对的。

**代价**

- 多一次迁移（V7），CHECK 约束从 `(1,2)` 变成 `(1,2,3)`
- `baseLog` 多了两个 null 守卫
- `ChatAskResponse` 加了一个 `intent` 字段（12 → 13），两个构造点要改

**另外加了一个小东西**：`QaLog.STATUS_SUCCESS` / `STATUS_FAILED` / `STATUS_CLARIFY`
三个常量（同 `KbDocument.STATUS_*` 的做法）。裸数字写错不会报错，
只会让统计悄悄偏。

## ADR-042 · 意图定向过滤做成 SQL 硬条件，不做软加权

**背景**：意图树的每个叶子声明了 `doc_types`（答案可能落在的文档类型全集），
5.4 要决定它怎么作用于检索。

| 方案 | 做法 | 否决/采纳理由 |
|---|---|---|
| **硬过滤** ✅ | SQL 里 `AND doc_type = ANY('{2,4}')` | 候选池真的变小，干扰项不再参与竞争 |
| 软加权 | 候选池不变，`doc_types` 命中给 RRF 额外权重 | **否决**：召回永远不受损是它唯一的优点，但收益也小得多 —— 池子不收窄，低分的越界内容照样能挤进 top-k。而且 `[1]` 这种 1.1× 的类型加权等于没加 |
| 不做 | 维持阶段 4 | **否决**：`kb_chunk.doc_type` 这个冗余列从 3.5 就为它埋着，不做等于承认当初的设计多余 |

**选硬过滤的依据是一条可证明的安全性质**：

`IntentTreeConsistencyTest` 已经证了 `gold doc_types ⊆ declared` 是 **20/20**。
也就是说每一道题的正解切片**必然通过过滤**，而池子里干扰项变少 ——
**过滤只可能让召回更好或持平，不可能更差**。

> ★ 这条推理是本项目里「5.1 那条看起来只是自检的验收标准」真正兑现的地方。
> 它写出来的时候（2026-09-19，5.1）只是一句「树画得对不对」，
> 到 5.4 才变成**硬过滤的安全证明**。
> —— 如果一个设计决策能让你在几天后白拿一条证明，那是好决策。

**风险在哪**：100% 集中在「gold ⊄ declared」的题上，也就是**分类错误**。
而这条风险**这 20 道题测不到**（它们全是分类正确的样本）。
见 ADR-039 的同一条纪律：**报告要写清证据覆盖不到哪里**。

**代价**：`Retriever` 接口签名从 `retrieve(String, int)` 变成
`retrieve(String, RetrievalOptions)`。

## ADR-043 · 过滤的决策权在 RetrievalPipeline；判据用「池子绝对大小」而不是「收窄倍数」

**背景**：调用方知道意图，检索层知道配置和库里的实际数据量 ——
「要不要真的过滤」这个判断该放哪？

**选了：放在 `RetrievalPipeline.resolveScope`**，调用方只传**声明**。

```
调用方说：「这个意图的答案可能在 {2,4} 里」
pipeline 决定：「池子只有 5 条，这个过滤不划算，我不下推」
```

| 备选 | 否决理由 |
|---|---|
| 调用方自己判断 | **调试探针和线上会走两套规则** —— `/api/debug/kb/retrieve` 看到的就不是线上跑的东西了。同 `RetrievalDetailBuilder` 的既有理由 |
| 逻辑写两遍（各判断一次） | 两份实现迟早不一致，且「不一致」的表现是「探针结果正常、线上悄悄不同」 |

**判据：`poolSize >= vector-top-k` 才过滤。**

否决「收窄倍数 ≥ 阈值」的理由是**实测**：

```
[5]  池子   5   328×
[4]  池子  21    78×
[2,4] 池子 67    24×
[1]  池子 1555  1.1×
```

倍数从 1.1× 到 328× 都有，而**倍数越大反而越危险** ——
`[5]` 的 328× 意味着池子只有 5 条，比 `topK=20` 还小，
于是取出来的**恒等于全池**：「按相关度截断」这个动作消失了，
问「开机键在哪」也会把 5 条说明书全塞进 prompt。

**判据的方向和风险的方向正好相反** —— 这是「收窄倍数」这个指标本身的缺陷。

**代价**：每个带范围的请求多一次 `count(*)`（走 `idx_kb_chunk_doc_type`，亚毫秒级）。
真要省可以缓存「每个 doc_types 集合的池子大小」，但缓存失效要挂在入库流程上 ——
那属于阶段 7 的优化，不是现在的问题。

## ADR-044 · `doc_types: []` 解读成「不限制」，不是「什么都不匹配」

**背景**：意图树里有三类叶子声明的是空集 ——
`ORDER_STATUS` / `INVENTORY` / `MY_COUPON`，它们该走 MCP 工具（5.7 才落地），
答案不在知识库里。而分类失败时也拿不到任何类型。

| 解读 | 后果 |
|---|---|
| **不限制** ✅ | 空集 = 退回阶段 4 的行为，不引入回归 |
| 什么都不匹配 | `doc_type = ANY('{}')` 恒为 false，**永远检索不到东西** |

**选前者的两条理由都是具体的**：

1. **三个工具意图在 5.7 之前本来就落回知识库检索。** 解读成「什么都不匹配」
   会让它们**退化成裸聊** —— 而用户问「我的订单到哪了」时，
   裸聊会**编一个订单状态出来**。这比「拿通用规则回答」糟得多。
2. **分类失败时的合理兜底就是阶段 4 的行为**（同 ADR-038 的原则）。

**★ 由此推出一条更要紧的约束**：**「清洗之后变成空集」和「本来就是空集」
必须走同一条路。**

`RetrievalOptions` 在构造期就把越界的 `doc_type` 剔掉
（比如把「售后」的 2 误写成 22）。剔完如果是空集，那就是「不限制」——
如果这里改成返回 `"{}"`，症状是**「这个问题永远检索不到东西」**，
静默、没有报错、Java 侧完全看不出来。

## ADR-045 · `retrieval_detail` 扩第 6 段 `filter`：它属于「恒定存在」，不是「非空才出现」

**背景**：`retrieval_detail` 的 5 个 key 在 V5 迁移的注释里被冻结，
`RetrievalDetailBuilderTest` 用 `hasSameElementsAs` 钉死了 key 集合。
而 5.4 需要记录「这次用了哪些 doc_types、有没有回落」。

| 方案 | 否决/采纳理由 |
|---|---|
| **加第 6 段** ✅ | 机器可读，报告能按它切片统计「回落触发了几次」 |
| 塞进现有的 `events` 字符串流 | **否决**：`events` 是给人排查看的自由文本，按它切片统计要解析字符串 |
| 不记，靠 `qa_log.intent` 反查 | **否决**：`intent → doc_types` 是纯函数没错，但记不下**实际生效**的那个值 —— 回落了没有、池子多大，都得拿同一份配置重算 |

**为什么这是「加法式扩展」而不是「改结构」**：
前 5 个 key 一个都没动、含义一个都没变，阶段 4 的基线脚本按固定路径取
`reranked` 等段，**完全不受影响** —— 所以**不需要重跑历史基线**。
后者才是「改结构」，代价高一个量级。

**★ `filter` 属于「恒定存在的 key」，不是附加字段。**

本项目对附加字段的既有约定是「非空才出现」（`events` / `sub_questions` /
`rewritten_question`），但 `filter` 不能这么办：

「**这次到底过滤了没有**」是一次检索的**固有属性**。
即使答案是「没有」，那也是一个必须能被机器读到的事实。
做成「key 不在 == 没过滤」，脚本就依赖了一个**隐式约定** ——
**而隐式约定在改代码时会静默失效**（加个字段、改个条件，key 就出现了，
脚本读到的意思全变了，不报错）。

**代价**：
- `RetrievalDetailBuilderTest` 里 3 处 key 集合断言从 5 改成 6
- `hasSameElementsAs` 会红 —— 这正是它该有的行为（它是刻意的契约检查）
- ⚠️ **JSONB 会重排键**（按 key 长度 + 字节序），所以
  `"filter"` 从库里读出来不一定在最后。**不要写「从库里读出来断言 key 顺序」的测试**

## ADR-046 · 会话历史只喂给生成，不喂给意图分类

**背景**：滑动窗口记忆读出来了，给谁用？

| 方案 | 否决/采纳理由 |
|---|---|
| **只给生成** ✅ | 改动面最小，且**不碰分类链路** |
| 生成 + 分类 | **否决**：会动到「分类器的输入只有这一句话」这个前提 |

**选它的核心是一条依赖关系**：

```
5.2 的 95% Top-1 / 100% 检索范围（Top-1 于 2026-09-20 复测为 90%，见 docs/05 §5.2 ④-b）
5.4 的 gold ⊆ declared（20/20）      三条全都建立在
5.5 的历史约束                       「分类器只看这一句话」之上
```

让历史进分类 prompt，会让**上面两条验收同时失效**，
而 20 道题的评测集**测不出**这个变化是好是坏 ——
因为那套题是单轮的，压根没有「有上下文时该怎么分」的样本。

**做这个决定时明确记下的代价**（当时就知道会踩）：

> 有上下文时「那个怎么样」仍然会触发澄清反问。

**★ 实测把这个代价量化了**：`scripts/probe_memory.py` 里那句最自然的追问
「按照我一开始说的预算和用途，你推荐哪款？」三次运行里
**2/3 被澄清闸门挡掉**（三次：澄清 / 放行 / 澄清）。

**★ 同时实测确认了收益**：另外一个形状（「推荐一款适合老人的手机」，
自成一体但没重复任何细节）在记忆**开**时用上了第 1 轮的预算、
记忆**关**时没有 —— 同一句话、同一份语料、只改一个开关。

**★ 顺带证伪了一个 5.3 的预留设计**：

`ClarificationDecider` 上那个 `history` 参数，注释写着
「5.5 上来之后，这里先尝试用 history 消解指代」。
**但它是纯判断器，消解不了指代** —— 「那个」指什么只有分类器能回答。
可行的链路是「历史 → 分类器 → 直接判成 SCENARIO_PICK → 走不到决策器」。

那个参数**保留但恒空**（删一个 public 方法属于另一个决定），
注释按实情改写。这是「预留点被证伪」的记录 —— **留着比删掉它有用**。

## ADR-047 · 读历史在「落用户消息」之前；孤儿用户消息必须丢弃

**背景**：`ChatRequest.history` 的契约是「不含本轮提问」，而
`ChatServiceImpl` 在检索之前就要把用户消息落库（阶段 4 的理由：
检索失败时问题仍在库里，评测数据完整）。

**选了：把「读历史」插在 `saveUserMessage` 之前。**

```
resolveSession → 【读历史】→ saveUserMessage → 分类 → 检索 → 生成
```

**另一种做法**是「读的时候排除本轮那条」，但那需要把「本轮用户消息的 id」
从 `saveUserMessage` 一路传回来。**多一条贯穿三层的返回值换 1ms 的查询，不值** ——
而且顺序本身就是最好的约束，它不需要任何人记得维护。

**★ 这个 bug 为什么危险**：顺序写反了，历史里就有一份本轮的提问，
而它马上又作为 `userQuestion` 再发一次 ——
**模型收到两条一模一样的用户消息**。
而日志和落库数据**两边各自都是对的**，错的是它们的相对顺序。
所以护栏只能建在「形状」上：断言 history 不含本轮提问、且以助手回复结尾。

**孤儿用户消息（同一次会话里第二个坑）**

上一轮在 `saveUserMessage` 之后、`saveAssistantMessage` 之前挂了，
库里就留下一条落单的用户消息。**它必须被丢掉**：

| 不丢的后果 | 说明 |
|---|---|
| 连续两条 user 消息 | 在 OpenAI 兼容协议里是**畸形输入** |
| 轻则 400 | 而 400 在降级链里属于「**不降级**」那一类 → 整次问答直接失败 |
| 重则被拼起来理解 | 模型把「我上一轮问的」和「我这一轮问的」当成一句话 |

判据：**最新一条是用户消息 = 它的回答从来没落过库**
（因为读历史发生在落本轮用户消息之前，当轮那条不可能出现）。

**★ 还有个容易漏的半轮**：取数要**多取一条**。
只取 `2×maxTurns` 条再丢孤儿，窗口会变成 9.5 轮 ——
**少的那半轮是最早的那条**，表现为「模型偶尔想不起上上轮说过什么」。

> ⚠️ **2026-09-19（5.6）更正上面这条的可见后果。**
> 「只丢最新那一条」是不够的，而且后果比「想不起上上轮」严重得多：
> **连续两次失败之后这个会话会永久答不出话**。见 ADR-049。

## ADR-048 · ★ 摘要游标锚在「窗口起点 - 1」，宁可重叠绝不空洞

**背景**：`chat_summary.end_message_id` 是摘要和窗口的**接缝**。

**选了：每次压缩的终点取「当前窗口起点 - 1」。**

```
窗口起点 W  >  end_message_id + 1   →  中间那段没人管，该压了
窗口起点 W  == end_message_id + 1   →  严丝合缝
```

**否决了「溢出几条就压几条」。** 那个算法里，压缩终点和窗口起点**各走各的** ——
只要步调差一点，接缝处就出现**空洞**：那几条消息既掉出了窗口、
又不在任何一次压缩的区间里，于是**永远消失**，而且没有任何报错。
锚死在窗口上则由构造保证。

| 情形 | 结果 |
|---|---|
| 窗口末尾**没有**孤儿 | 摘要求和窗口**严丝合缝** |
| 窗口末尾**有**孤儿 | 窗口起点比 W 更早 → 两者**重叠**若干条 |
| （反方向）W 跟着孤儿漂 | 窗口起点漂到 W 之后 → **空洞**，永久丢失 |

重叠是模型把同一条消息看两遍，无害；空洞是不可恢复的。
所以规则是**宁可重叠，绝不空洞**。

★ **W 的定义只有一处**（`ConversationMemory.windowStartId`）。摘要层、窗口层、
调试探针三处调的是同一个方法 —— 各写一份「碰巧一样」的表达式，
正是会有消息永久消失的那种耦合。

**代价**：每次要压的区间长度不固定（取决于距上次压缩过了几轮），
所以有一次读不完就分多次的上限（`MAX_MESSAGES_PER_RUN = 100`）。

**副产品**：`pending`（已掉出窗口、还没进摘要的条数）在正常运行中**必然非零** ——
压缩是异步的，还要走一次 1–2 秒的模型调用，这期间对话早往前走了。
它不是 bug，`/api/debug/agent/memory` 把它单独列出来就是为了说清这件事。

## ADR-049 · ★★ 丢孤儿要丢【末尾全部】，不是只丢最新那一条

**背景**：ADR-047 定了「孤儿用户消息必须丢弃」。5.5 的实现是
**只看最新那一条**。5.6 动工前复读那段代码，发现这个判据不够。

**选了：从末尾往前，丢掉所有连续的 user 消息。**

历史必须以 assistant 结尾，或者为空 —— 这是它能被拼进 `messages` 数组的
**充分必要条件**。

```
第 N   轮失败 → 孤儿 O_N
第 N+1 轮失败 → 读的时候丢掉 O_{N+1}（它是新的）
                但 O_N 还在，而它现在是历史的【末尾】
                → history 以 user 结尾，再拼上本轮问题
                → 连续两条 user → 400 → 不降级 → 这一轮也失败
                → 留下 O_{N+2} …… 每一轮都重演
```

**★ 两次连续失败之后，这个会话就再也答不出话了**，
而单次失败（最常见的形态）完全看不出来。

为什么必须修在读的一侧：`ChatServiceImpl` 类注释第 ① 条明确写着
「失败时**不写**助手消息」—— 硬塞一句「服务异常」能绕过 `NOT NULL`，
但会污染阶段 7 的评测语料。那个决定是对的，所以清理只能在读这一侧做。

**回归护栏**：`ConversationMemoryIntegrationTest` 的「五、连续失败」那一节。
★ 断言的是**下游真正会发出去的东西**（`toWireMessages()` 的 role 序列），
因为只看 `turns` 的列表内容，看不出「三条连续 user」这种形状问题。

## ADR-050 · 摘要压缩走【异步单线程池】，不走同步

**背景**：一次摘要压缩要花一次 LLM 调用。**实测最慢 41.5 秒**
（`deepseek-flash` 那次失败了，降级到 P1 的硅基流动）。

**选了：生成完成、响应返回之后，把任务丢给 `memoryExecutor`。**

**为什么异步是安全的**：压缩的输入是**已落库的、不可变的过去**。
待压缩的消息早已落库、内容不会变；窗口那边读的是另一段区间。
唯一的竞态是「同一会话的两次压缩同时跑」，而那被**单线程**挡住了。

**为什么单线程是正确性要求，不是保守**：一次执行是
「读游标 → 调模型 → CAS 推进游标」。两个执行重叠的话，
两个都会基于**同一个旧游标**去调模型，然后一个 CAS 胜出、一个失败 ——
失败的那个**白花一次 LLM 调用**（钱真的花了）。

⚠️ 光把 `corePoolSize` 设成 1 是**不够的**：线程池的增长逻辑是
「核心线程满了先入队，队列满了才扩容」。`maxPoolSize` 也必须锁死成 1。

**为什么任务可以随便丢**（队列满时 AbortPolicy，由 `SessionSummarizer` 吞掉）：
**压缩是自愈的**。游标不动，下次触发会把这一段连同新掉出来的一起压进去。
这正好是和 `ingestExecutor` 的 CallerRuns 相反的地方 —— 入库非幂等，
写一半会留僵尸文档；压缩幂等且可重做。

**41.5 秒这个数字本身就验证了这个决定**：同步的话，
一次普通问答会从 2 秒变成 43 秒。

## ADR-051 · 摘要只做单行滚动；`summary_level = 2` 是已知不用的死列

**背景**：V5 建的 `chat_summary` 表预留了 `summary_level IN (1,2)`
（1 段落级 / 2 会话级），那是教科书式的**分层摘要**设计。

**选了：每个会话永远只有一行摘要，level 恒为 1，原地 UPDATE。**
游标 `end_message_id` 往前推，`start_message_id` 不动（摘要是累积的）。
`level = 2` 刻意不用。

**否决了真的做两层。** level 2 要解决的是「极长会话里 level-1 累积太多行」，
而**本项目真实会话最长 10 轮**（库里实测）。为一个没有发生过的规模做两层，
换来的是「level 2 什么时候触发」「读的时候要拼几行」「拼出来多长不可控」
三个新问题。

**否决了删掉那一列**：改表要动 V5 迁移，而 V1–V5 一个字都不能改
（`validate-on-migrate: true`）。所以在 `docs/04` 和 entity 注释里写明它是死列 ——
同 ADR-046 处理 `ClarificationDecider.history` 那个参数的方式：
**保留但说清实情，不留一个「看起来以后会用」的坑**。

## ADR-052 · ★ 摘要的固定上限挡不住增长，得靠 prompt 里的「丢弃顺序」

**背景**：提示词里同时写着「保留事实」和「不超过 N 字」，
**这两条会打架**。实测模型选择了保留事实：

```
209 → 435 → 740 → 1129 字（目标 800，硬上限 1600）—— 单调上涨
```

**选了：把裁决写死，并给出【可执行的丢弃顺序】。**

```
① 助手回答里的解释、依据、引用编号、办理流程的步骤细节
   —— 这些【下次检索还能再查到】
② 与用户目的无关的问答
③ 用户已经明确排除掉的选项
★ 无论如何都要保留：用户的预算、用途、商品型号、偏好和限制
   —— 这些是【再检索一次也查不到】的东西
```

**那条洞察是整段的支点**：摘要**不是**对话记录，
而是「这个用户是谁、他要什么」的存档。助手的回答是**可再生**的
（再检索一次就有），用户说过的自己**不可再生**。
所以摘要的主角是**用户**，不是助手。

**效果**：同样规模 1129 字 → **885 字**，而且第一句就是
「用户要给爸妈买手机，预算两千左右」。

**★ 又加了一层，但只部分有效**：当上一次的摘要已经超预算时，
换用带「你上次超了」这句**具体状态**的强制压缩指令
（`SummaryPromptBuilder.OVER_BUDGET_WARNING`）。
实测 1066 → 936 字，**下去了但没到 800**。

**稳定态是 900–1100 字的振荡**，远在硬上限 1600 之下。
⚠️ 这是一个**已知的、没有完全解决的问题**，见 `docs/05` §9.6 ⑤。

**★ 硬上限截断是从【尾部】切的，这是有意的。** 摘要按时间顺序写，
尾部是「最近发生的事」—— 而越靠后越可能是**助手的回答**（可再生），
越靠前越可能是**用户说过的自己**（不可再生）。切尾部正好丢掉可再生的那一端。

## ADR-053 · 协议版本跟【SDK】对齐，不跟规范仓库对齐

**背景**：MCP 规范仓库里有 `2024-11-05 / 2025-03-26 / 2025-06-18 / 2025-11-25 /
2026-07-28 / draft` 六个修订。服务端该声明哪一版？

**选了：`2025-11-25`。** 支持列表 `{2025-03-26, 2025-06-18, 2025-11-25}`。

**依据不是文档，是反编译**：官方 Java SDK `io.modelcontextprotocol.sdk:mcp` 2.0.1 的
`io.modelcontextprotocol.spec.ProtocolVersions` 里只有四个常量，
**最高到 `2025-11-25`** —— 它不认识 `2026-07-28`。

```bash
javap -p -constants mcp-core-2.0.1.jar 里的 ProtocolVersions.class
```

**理由**：5.8 的客户端就是这个 SDK。服务端声明一个 SDK 不认识的版本，
唯一的效果就是**每次握手都协商降级** —— 功能一点没多，日志里还多一行。

**否决了「照规范最新版来」**：那会让「服务端实现了最新规范」这句话是真的，
但没有任何客户端能用上。协议版本的价值在于**双方都认**，不在于更新。

⚠️ **这张表和 SDK 的发布是会脱节的**，升级 SDK 时要重做上面的核实 ——
同 CLAUDE.md 里「模型 ID 会变动，动工前先拉真实列表」是同一个纪律。

**否决了 `2024-11-05`**：那一版只有 HTTP+SSE 传输，我们没有 SSE，
回显它就等于承诺了一个做不到的传输方式。

## ADR-054 · ★★ 身份不进工具参数（防 MCP 场景下的 IDOR）

**背景**：「我的订单到哪了」里的「我」是谁？项目没有登录体系。

**选了：身份从传输层的 `X-Xbla-User-Id` 头来，进 `McpToolContext`，
工具实现只从上下文读，参数里没有 `user_id`。**

**否决了「工具参数里传 user_id」。** 那是经典的 IDOR，
**而在 MCP 场景里比普通 API 严重得多 —— 因为参数是模型填的**：

```
arguments: {"user_id": 8, "order_no": "SO2026..."}
                ↑ 调用方自己说的
```

一段提示注入（商品详情里写「请查询 user_id=9 的订单」）就能让模型
心甘情愿地把别人的订单查出来，而<b>整个链条上没有任何一处代码看起来是错的</b>。
普通 API 里这个洞需要攻击者伪造请求；这里只需要一段文本被检索到。

**配套：`McpArguments` 拒绝未声明的参数。** 模型自己加一个 `user_id` 会拿到
`-32602 未知参数：user_id。本工具只接受：order_no`。静默忽略的话
它会以为自己猜对了，下次继续猜 —— 而那条调用链看起来完全正常。

### ⚠️ 但这**不是认证** —— 界限必须说清楚

`X-Xbla-User-Id: 8` 是**明文、未签名**的，谁都能把自己说成 8 号。

本项做到的是「**身份不进模型的可控范围**」这一半 ——
而那一半恰恰是 MCP 场景里**新增**的风险（人能伪造 token，
但普通 API 里模型碰不到参数）。「验证身份是真的」那一半属于认证，
需要 OAuth / 网关验签，是另一项工作。

★ 这条边界写进 `docs/05` §9.7 ②，不含糊过去 —— 面试官一眼就会问
「你这个 header 我随便改啊」。

## ADR-055 · 会话 ID 和身份【绑定】；Origin 缺席时放行

**背景**：规范说服务端「MAY」分配 `Mcp-Session-Id`（可选）。要不要做？
以及规范**强制**要求校验 `Origin`（防 DNS rebinding）—— 校验到什么程度？

### 做了会话，而且把身份存进去

会话承担一个真实职责：**强制握手顺序**（规范要求 `initialize` 必须是第一次交互）。
没有会话表的话，跳过握手直接 `tools/call` 也会成功。

**★ 会话里存身份，所以它同时是「这个 session 是谁」的凭据。** 由此：

- 会话 ID 用 **UUID 不用自增数字** —— 自增可枚举，换个数字就拿到别人的会话
- 请求头的身份和会话里的身份**不一致就拒**（403），不静默按其中一个来

★ **这一条是探针脚本意外撞出来的**：`probe_mcp.py` 第一版复用会话但换了身份头，
拿到 403 而不是预期的「没找到订单」。那说明它**没测到越权** ——
被更前面的一层挡住了。两层职责不同（这层管「会话不能被顶替」，
工具 SQL 那层管「查到的数据是不是你的」），**都要有**。
见 `McpControllerGuardTest.Session`。

### ★ Origin 校验：头**缺席时放行**

DNS rebinding 是**浏览器**发起的：恶意页面让用户的浏览器去 POST
`localhost:8080/mcp`，而浏览器的同源策略拦不住跨源 POST。

**而浏览器在所有跨源请求上都会带 `Origin`。** 头不存在只可能是非浏览器客户端
（官方 SDK、curl、服务端之间的调用）—— 那种客户端本来就不受同源策略约束，
也就没有 rebinding 可言。

「缺席就拒」只会挡住合法客户端（包括 5.8 要用的 SDK），攻击者一点不受影响。
**判据要和威胁模型对齐**，不能只看「严格一点更安全」。

## ADR-056 · ★ `isError` 的判据是「有没有给出答案」，不是「答案是不是空的」

**背景**：规范把「Invalid input data / Business logic errors」划进 `isError: true`，
读起来像是「查不到也算错」。

**选了：`isError` 只表示「工具没能给出答案」。**

| 情况 | isError | 去向 |
|---|---|---|
| 「你有 0 张券」 | `false` | 完整的答案 |
| 「订单 SO123 不存在」 | `false` | 这也是个答案：「没有这一单」 |
| 「数据库连不上」 | `true` | 工具**没能**给出答案 |
| 「订单号格式不对」 | `true` | 参数问题 → 其实是 JSON-RPC 协议错误 |

**理由**：把「查无此单」标成错的后果是 —— 模型看到错误标记，
会说「系统出了点问题，请稍后再试」，而它应该说的是
「没找到这个订单，请核对订单号」。
**一句系统故障的道歉，用户会去重试；而重试一万次也变不出那个订单。**

★ 这条和 ADR-041（澄清路径的列写 NULL 而不是空对象）是同一种态度：
**「没有发生」和「发生了但结果为空」必须能被区分开**。

## ADR-057 · 工具体验：参数名只写一次，类型不做宽松转换

**背景**：工具定义要描述同一个东西两次 ——
① 给模型看的 `inputSchema`；② 实现里真正去读的那个 key。

**选了：`ToolField` 常量同时承担两件事。** schema 生成和取值都走它，
名字只写一次，所以**物理上不可能漂移**。

```java
private static final ToolField ORDER_NO =
        ToolField.requiredString("order_no", "订单号，形如 SO20260101123456。…");
public List<ToolField> inputFields() { return List.of(ORDER_NO); }   // ①
String orderNo = ORDER_NO.requireString(args);                       // ②
```

**否决了「YAML 声明 schema + Java 执行器按名字查」**（本项目的
`intent-tree.yml` / `manifest.yml` 都是这个风格）：schema 在 YAML、
读参数在 Java，**又是一处「两份碰巧一样」的耦合**。写错 schema 里的 key
是静默失效 —— 而这正是 5.6 刚踩过的坑（接缝锚点写在两处）。

**否决了「注解 + 反射」**：那正是 5.8 要用的官方 SDK 的做法，
手写 Server 再用注解等于在重写那个 SDK；而且反射让「参数从哪来」
不能逐行读，和 CLAUDE.md 第 1 条相悖。

### ★ 类型不做宽松转换

字符串字段收到数字 `12345` → **报错**，不转成 `"12345"`。
整数参数收到字符串 `"5"` → **也报错**，两个方向都不转。

宽松转换的后果：模型发 `12345` 当订单号，我们转成字符串去查库，查不到，
于是它得到一个「订单不存在」的答案 —— 而真正的问题是它发错了类型。
**模型会把这次失败归因到业务上，永远学不会改类型。**

⚠️ 只做一半的宽松（只转数字→字符串）比全都转更糟：两边行为不一致，
而 schema 在两处看起来都是对的。

## ADR-058 · `Map.copyOf` 不能用来包工具的结构化输出

**背景**：`McpToolResult` 的 `data` 需要一个防御性拷贝，第一版写的是
`Map.copyOf(data)` —— 那是很自然的直觉（同 `List.copyOf`）。

**它抛 NPE。** `Map.copyOf` 和 `Map.of` 一样**拒绝 null 值**，
而「key 在、值是 null」恰恰是 JSON Schema 里**可选字段**的合法形态：

```
一笔还没发货的订单：logistics_no = null
但那个 key 必须出现 —— 缺 key 和值为 null 在 JSON Schema 里是两件事
```

**改成：`Collections.unmodifiableMap(new LinkedHashMap<>(data))`。**

★ **这个坑值得单独记一笔，因为它的表现会带偏排查方向**：
NPE 抛在**构造函数**里，栈顶指向 `McpToolResult` 而不是那个 null 字段。
现象是「工具明明查到数据了，包装结果时却崩了」。

回归护栏在 `McpToolResultTest`（含一条「`Map.of` 确实会炸」的正-反对照），
以及 `QueryOrderStatusToolIntegrationTest.optionalFieldsArePresentButNull`。

## ADR-059 · MCP Client 每次工具调用都重新握手，不维持长连接

**背景**：5.8 要接官方 Java SDK 做 MCP Client。SDK 的 `McpSyncClient` 支持
「initialize 一次、之后一直用同一个会话」。

**决策**：**每次 `listTools` / `callTool` 都新建客户端，握手、用完关闭。**

**为什么**（用户拍板；代价是每次多两个 RTT，本机回环下是毫秒级）：

| 长连接要处理的事 | 每次重连 |
|---|---|
| Server 重启 → 会话失效，要重连 + 重试 | 下次调用自然是新会话 |
| 会话 2 小时 TTL 到期（**一定发生**） | 不存在 |
| 连接健康检查、心跳、探活 | 不存在 |
| `McpSyncClient` 能不能多线程共用？要查文档 | 每次一个客户端，天然隔离 |

**★ 但这不是「延迟不重要」，是「现在还不重要」**：等 5.9 的四个工具串起来调，
或者 Client 指向一台**远程** Server（一个 RTT 是几十毫秒而不是微秒），
就该把连接池化 —— 那时候要处理的就是上面那张表里的四件事。

**另一个收益是测试性的**：`SdkMcpToolGatewayIntegrationTest` 里那条
「连续换三个身份，第三个必须和第一个一样」才成立 ——
如果实现把身份放进了某个共享字段，那个 bug 在长连接下会表现为
「A 的会话带着 B 的身份」，而日志里一切正常。

## ADR-060 · ★★ 工具决策轮的「空正文」是**成功**，不是「AI 不说话」

**背景**：阶段 2 有一条空正文探测器 —— HTTP 200、`content` 为空 →
当失败处理，让降级链接手。它的目的是抓「推理模型把 max-tokens 吃光」。

**实测（2026-09-19，`deepseek-flash`）**：连续 5 次让模型
「需要订单信息就直接调用工具，不要说话」，**5 次的 `content` 全是空串**。

**决策**：判据从 `isEmptyContent()` 改成 `hasAnyContent()` ——
**正文或者工具调用，有其一即算成功**。

**如果只判正文**：每一次工具调用都会掉进失败分支 →
`EMPTY_CONTENT` 是**可降级**的 → 降级链走一圈 → 三家全失败 →
`qa_log.status=2`，错误消息写着「输出 0 token，推理占 0%」。
**一个指向完全错误方向的诊断** —— 真正发生的事是
「模型很有礼貌，一个字都没说，只给了工具调用」。

**★ 同一个决策的第二半：`reasoning_content` 必须回传。**

`deepseek-flash` 在 thinking 模式下要求把 `reasoning_content`
连同 `tool_calls` 一起发回去，否则 400。而 **400 不降级**。

这与阶段 2 的「不存也不返回 `reasoning_content`」**不冲突，但要写清楚**：

- 那条决策管的是**响应方向**：不落库、不返给前端 ✓ 继续有效
- 5.8 补的是**请求方向**：它要在**一次工具往返的两条 HTTP 请求之间**活着
- 它只活在内存里，不碰 `qa_log`、不碰 `chat_message`

**一句话：「不存」不等于「不传」。**

★ 更细的实测：单独丢掉 `reasoning_content` **不一定**报错
（服务端可能按 tool_call id 去缓存里找回推理），
但**丢掉它同时改动了 id** 一定报错。所以两条一起守。

## ADR-061 · ★★ 线格式的 `tool_calls` 是**嵌套**的 —— 两个方向都要映射

**背景**：`ToolCall(id, name, arguments)` 是**平的**领域对象。
而协议里的 JSON 是**嵌套**的：

```json
{"index":0, "id":"call_00_…", "type":"function",
 "function":{"name":"query_order_status","arguments":"{…}"}}
```

**决策**：新增 `WireToolCall`（嵌套，含 `index` / `type`），
两个方向各做一次显式映射：`toDomain()` 和 `fromDomain()`。

### ★★★ 为什么这条 ADR 值得单独写：它让实现连续挂了两次

**第一次（响应方向）**：`WireChatResponse.Message.toolCalls` 直接收 `ToolCall`。
Jackson 在顶层找不到 `name`，**静默给 null**。后果链条：

```
name=null → 官方 SDK 的 CallToolRequest.Builder.name(null) 抛
IllegalArgumentException("name must not be empty")
→ 整次问答 status=2，qa_log 里的错误消息和订单毫无关系
```

⚠️ **而当时 486 个测试全是绿的。** 因为所有测试都是
`new ToolCall("id", "query_order_status", "...")` 直接构造的 ——
**恰好把那一段坏掉的代码跳过去了**。

**第二次（请求方向）**：修完响应方向之后，回声（第二跳）时发出去的仍是扁平形状。
服务端的反应精确得多：

```
HTTP 422  messages[1]: missing field `type`
```

⚠️ **测试依然全绿** —— 因为断言都下在**领域对象**（`ChatRequest.Turn`）上，
而领域对象是平的。**形状的错只存在于序列化之后，没序列化就永远看不见。**

### ★ 一句话总结（这条比 ADR 本身重要）

**DTO 的形状，只有真的序列化/反序列化过一次才算验证过。**

- 桩造出来的对象，验证不了「桩自己是不是照协议造的」
- 因此本阶段补了两个测试：`WireToolCallTest`（喂**真实抄下来的**报文）
  和 `ToolCallingShapeTest.Serialization`（**真的序列化一次**再断言 JSON 结构）
- ⚠️ 手写 JSON 也不行 —— 写 JSON 的人和写 record 的人是同一个，
  他脑子里的形状是同一个。所以 `WireToolCallTest` 里那份报文是
  **从真实 API 响应里逐字抄的**。

**另一个教训**：`WireToolCallTest` 第一版用了裸的 `new ObjectMapper()`，
于是真实报文里的 `"object":"chat.completion"` 被判成错误
（`FAIL_ON_UNKNOWN_PROPERTIES` 默认 **true**），六个用例挂了四个 ——
**用一个和线上不一样的 mapper 去测线格式 DTO，测的是另一个程序。**

## ADR-062 · ★★ 工具的任何失败都不能让问答失败

**决策**：`ToolLoop` 把**三类失败**都翻译成工具结果喂回模型，
而不是抛异常：

| 发生了什么 | 处理 | 为什么 |
|---|---|---|
| 模型编了不存在的工具名 | 服务端原话（「未知的工具：X」）喂回去 | 模型手上有完整工具清单，**它能自己改** |
| 模型给的参数不是合法 JSON | 一句说明喂回去 | 同上，这是模型的输出错误 |
| 工具连不上 / 超时 | 「实时查询暂时不可用」喂回去 | 模型改不了，但**用户需要一句人话** |

**为什么工具宕机不能让整次问答失败**：用户问的可能只是「我的券还有几天过期」，
而一个可选功能的故障不该让整个问答变成「服务内部错误」。

**★ 另一半：gateway 的异常契约必须是**完整的**。**

`McpToolGateway` 承诺「所有失败都抛 `McpGatewayException`」，
但第一版把请求**构造**放在了 `withClient` **外面** ——
于是 `CallToolRequest.builder()` 抛的 `IllegalArgumentException`
直接穿了出去，没被包成 `McpGatewayException`，`ToolLoop` 的兜底也接不住。

**「把所有失败都收口成一种异常」这句话，只有构造也在里面才成立。**

★ 因此 `ToolLoop` 里还留了一个 `catch (RuntimeException)` 兜底，
日志级别是 **ERROR 而不是 WARN** —— 走到那里说明 gateway 违反了自己的契约，
**那是个 bug，不是一次失败**。

**★ 附：这条决策让 5.7 的 `isError` 语义真的被用上了。**

5.7 定的是「`isError` = 工具有没有给出答案」——
「查无此单」是 `isError:false`。5.8 在它上面又加了一层同样的判断：
**「这次失败该由谁修」** —— 模型能改的（工具名、参数）原话告诉它，
模型改不了的（连不上）替它说一句人话。

## ADR-063 · `qa_log` 加 `tool_calls`；多轮成本**累加**、路由**覆盖**

**决策**：V8 迁移给 `qa_log` 加一列 `tool_calls JSONB`。

**为什么必须有它**：没有这一列，
**「工具意图答错了」和「工具根本没被调用」在数据上完全一样** ——
都是 `status=1`、有 `provider`、有 `final_answer`。
而这两种情况的排查方向**正相反**（一个是分类/接线问题，一个是工具实现问题）。

**格式**：`[{"round":1,"tool":"query_order_status","isError":false,"detail":"chars=89"}]`
- **NULL = 一次都没调**（不是空数组）—— 同 `references` / `degradation_events` 的既有约定
- **不存工具返回的内容** —— 那是订单数据，要复现就按同一个参数重调（工具是只读的）
- **不加索引** —— `qa_log` 是写入最频繁的表，而这一列只在分析路径上。
  同 `retrieval_detail`：分析用的列，让分析的时候慢一点

**★ 多轮合并的五条规则**（`ModelCallTrace.mergeRound`，写在那个类的 javadoc 里）：

| 字段 | 规则 | 为什么 |
|---|---|---|
| 降级事件 | 追加 | 每一轮的降级都发生过 |
| 路由 | **覆盖**（用最后一轮） | 产出最终回答的就是它 |
| token 用量 | **累加** | 覆盖会让第 1 轮的花费凭空消失 |
| 耗时 | 累加 | 同上 |
| 成本 | **累加** | ★ **不能拿「总 token × 最后一轮单价」重算** —— 降级时两轮单价不同 |

★ 累加是**三态逻辑**，不是「null 当 0」：
`current==null` 取新值（第一轮）、`incoming==null` 则合计为 null（不知道）、
否则相加。写成「任一方为 null 就返回 null」的话，
第一次合并的结果就是 null，之后永远是 null ——
**`qa_log.cost` 恒为 NULL，而没有任何报错**。

## ADR-064 · `Map.copyOf` 还会**打乱顺序** —— 本项目第二次踩它

**背景**：5.7 的 `McpToolRegistry` 把工具按名字排序，注释写着
「保证 `tools/list` 的顺序稳定」。但最后一步写的是
`Map.copyOf(sorted)` —— 而它返回的 `ImmutableCollections.MapN`
**迭代顺序由 hash 决定，且 JDK 9+ 用一个每次 JVM 启动随机生成的 `SALT` 扰动 hash**。

实测（三个独立 JVM，同一份已排序的 `LinkedHashMap`）：

```
run 1: [query_my_coupons, query_order_status, query_inventory, search_after_sale_policy]
run 2: [search_after_sale_policy, query_my_coupons, query_order_status, query_inventory]
run 3: [query_order_status, query_inventory, search_after_sale_policy, query_my_coupons]
```

**决策**：改用 `Collections.unmodifiableMap(sorted)`。

**★ 为什么 5.7 没发现**：当时**只有一个工具**，怎么测都测不出来。
5.9 加到四个才会显形。

**★ 代价不是「不好看」**：`tools` 数组是 Prompt 前缀的一部分，
顺序一变 → 每次重启后第一个请求整段未命中 →
`cache-hit-input: 0.02` 和 `input: 1.0` 差 **50 倍**。

**★ 同类问题还有 `Map.of`**：`ToolSpec.toWireTool()` 里用它拼 JSON，
键序同样每次启动都变。已改成 `LinkedHashMap`。

**规律（写进 CLAUDE.md）**：
**凡是会进 Prompt 前缀的 JSON，一律用 `LinkedHashMap`。**

⚠️ 这是本项目**第二次**踩 `Map.copyOf`（第一次是 ADR-058「拒绝 null 值」）。
两次的共同点：**「防御性拷贝」是个看起来无害、
实际上会悄悄改掉一个你依赖的性质的写法。**
用它之前先问一句：「我还依赖这个 Map 的什么？」

## ADR-065 · 身份只在**需要它的那条路**上必需，入口不设 401

**背景**：`/api/chat` 原本完全没有用户概念。5.8 的工具要查「我的订单」，
必须知道「我」是谁。

**决策**：身份走 **`X-Xbla-User-Id` 请求头**（和 `/mcp` **同一个头名**），
**但头缺席时不是 401** —— 只有工具那一条路会回一句
「我需要先知道你是哪位」。

**为什么不做成全局必需**：
- 知识库问答、意图分类、会话记忆**都不需要**知道你是谁
- 全局 401 会把整个服务变成需要登录的，而**演示页和现有的每一个 curl 命令都没有带头**
- **必需的校验放在真正需要它的地方**，而不是入口处一刀切

**为什么走头不走 body**：走 body 的话同一个身份就有两个来源，
两边不一致时以谁为准会变成一个新问题 —— 而正确答案永远是「头」，
因为头是**传输层**的，body 是**调用方可以随便填**的。

**★ 两跳用同一个头名**，意味着 `ChatServiceImpl` 和 `SdkMcpToolGateway`
之间**不需要任何身份转换** —— 少一次转换就少一个出错的地方。

⚠️ **它的边界**：和 `McpToolContext` 里写的一样，
**这个头是明文未签名的，不是认证**。做到的是「身份不进模型的可控范围」，
另一半（验证它是真的）属于 OAuth。

## ADR-066 · 5.8 只把工具接进**非流式**路径

**决策**：`ChatService.ask(request, userId)` 接了工具；
`askStream(request, sink)` **没接**，签名里连 `userId` 都没有。

**为什么可以在 5.9 之前不管它**：工具往返的**决策轮本来就必须是非流式的** ——
要拿到完整的 `tool_calls` 参数才能执行，流式只会多一层增量累积逻辑，
而那一轮**本来就不该有用户可见的输出**。

所以两条路径的差别**只在最后一轮**（把工具结果变成人话那一轮）：
非流式收完整响应，流式边推边攒。`ToolLoop` 只写一份，
5.9 接流式时改的只是「最后一轮怎么生成」。

⚠️ **但这个不对称必须写进签名旁边的注释**，不能只在 ADR 里。
「两条平行路径少改了一条」是本项目已经踩过的坑（ADR-047），
而那种漏改**编译能过、测试能绿、只有演示的时候才看得出来**。
所以 `ChatService.askStream` 的 javadoc 第一句就是
「它还没有 `userId` 参数 —— 而且这不是遗漏」。

## ADR-067 · 「售后政策」**不做成 MCP 工具**，走结构化注入

**决策**：路线图 5.9 写的第四个工具 `search_after_sale_policy` **不实现为 MCP 工具**。
改为：意图树里 `AFTER_SALE.RETURN_EXCHANGE` 声明 `structured_facts: POLICY`，
知识库路径组装 prompt 时按类目查 `after_sale_policy`，把**退货/换货天数**拼进 system prompt。

### 顺带发现：意图树里那三个 TOOL 叶子，目前是「文档」不是「代码」

`classificationTargets()` 的规则是「行为相同的不区分」——
`retrieval != KB` 的顶层**只算一个目标**。所以模型只会输出 `ORDER_LOGISTICS`，
**从不输出** `ORDER_STATUS` / `INVENTORY` / `MY_COUPON`。具体调哪个工具，
是 `ToolLoop` 把**全部工具**给模型、让模型自己选。

> ★ 这其实是好事：**加第四个工具本来就不需要动意图树**。
> 真正卡住的只有一件事 —— `AFTER_SALE` 是 KB，模型在那个意图下拿不到工具。

### 三条路

| 方案 | 做法 | 为什么否决 |
|---|---|---|
| **A. 结构化注入** ✅ | KB 路径加一次查表，硬数据拼进 prompt | — |
| B. 新增叶子 `AFTER_SALE.POLICY_LOOKUP` | 让叶子能覆盖父顶层的 `retrieval` | 要改 `IntentTree` 的核心设计原则（「`retrieval` 是整类的性质」）；⚠️ 更要紧的是它会**多出一个分类目标**，5.2 的准确率基线和 5.4 的 20 题基线都要重跑 |
| C. KB 路径也带上工具 | 检索照跑，工具也照给，模型自己选 | 架构上最统一（也是 `classificationTargets` 注释里预言的方向），但改动最大：每次 KB 问答多一份 `tools`、模型可能在不需要工具时也调、`qa_log` 的归因变复杂。**值得做，但不该和 5.9 一起做** |

### ★ 关键论据：「退货要几天」是个**确定性问题**

让模型决定「要不要查表」，是把一个确定性的事变成了概率。
而它答错的方式极其隐蔽 —— 从散文「自签收之日起 7 天内支持无理由退货，15 天内支持换货」里
把 **换货**的 15 天读成 **退货**的 15 天，**句子读起来完全通顺**，用户不会怀疑。

### 代价（不粉饰）

路线图那行从「四个业务工具」改成「**三个 MCP 工具 + 一个结构化上下文来源**」。
`AfterSalePolicy` 的实体注释里那句「供 MCP 工具精确查询」也要一起改 —— 它写的是意图，不是事实。

## ADR-068 · `structured_facts` 是**叶子**粒度，且**不参与分类**

**决策**：`structured_facts` 声明在**叶子**上，和 `retrieval` 的顶层粒度刻意不同。

**为什么不是顶层**：`retrieval` 是整类的性质（「订单物流这一类都去查实时数据」），
但这件事**不是**：`PROMOTION` 这一整类里，`PRICE_PROTECTION` 不需要硬数据、
`FULL_REDUCTION` 更不需要。按顶层声明只能要么全给、要么全不给。

**★★ 为什么这条特别要紧**：`classificationTargets()` **只看 `retrieval`**，
所以 `structured_facts` **不会让分类 prompt 多出一个选项** ——
加它对 5.2 的意图准确率和 5.4 的评测基线**零影响**。
这正是它比方案 B（新增叶子）便宜的地方。

**⚠️ 配套的加载期校验**：非 `KB` 的叶子声明它会**启动即崩**。
走工具那条路根本不进 `RagPromptBuilder`，声明了也永远不会生效 —— 而那是**静默**的。
（由 `IntentTreeStructuredFactsTest` 钉住。）

## ADR-069 · 硬数据只带**天数**，不带 `conditions`

**实测**：`conditions` **已经在知识库里** —— 12 条切片，形如：

```
电脑类商品售后规则 > 附加条件
私自拆机、刷机、进水、摔损等人为损坏不在保修范围内。
```

**所以注不注入它，是「要不要让 prompt 里有两份一样的文字」**。
答案是不。一份数据带两处不会更准，只会让模型在两份一样的文字之间做无谓的对照。

★ 而天数**不在**结构化可读的位置 —— 它在 `content` 里是**散文**
（「自签收之日起 7 天内支持无理由退货，15 天内支持换货」）。
**只有这一项**是「表里有、文档里没有准确值」的东西，所以只带它。

★ 另一条推论：`after_sale_policy` 里有一半记录是<b>没有天数</b>的通用规则
（价格保护、发票、优惠券返还、以旧换新、物流损坏）—— 过滤条件是
`return_days IS NOT NULL`，把它们也带进 prompt 只会让模型分心。

## ADR-070 · `structured_facts` 放在**摘要之后**，不是之前

**直觉**：越稳定的越靠前。硬数据几乎不变，摘要每 N 轮才变一次 → 硬数据该在前面。

**实际判据不是「谁更稳定」，是「谁更常在」**：

| | 出现频率 |
|---|---|
| 摘要 | **每轮都有**（只要有历史） |
| 结构化事实 | 只有售后退换货那一类才有 |

放在摘要**之后**，两种情况下前缀都能一路吃到摘要结束；
放在**之前**，有事实的那次会把摘要往后推 —— 而摘要是每轮都有的，
那一段缓存**每次都丢**。把不常在的放在后面，让常在的那部分前缀尽可能长久地命中。

**同一条规则的另一个应用**：硬数据拼进 `fixed`（固定段）而不是 `chunks` 分支 ——
于是「检索一条都没召回」时它**还在**。那正是最需要它的时刻：
知识库什么都没给，而用户问的是「退货要几天」。
（由 `StructuredFactsPromptTest` 钉住。）

## ADR-071 · `query_inventory` 只匹配**商品名**，不匹配类目和品牌

**决策**：`WHERE name LIKE '%…%'`。**不加** `OR brand LIKE … OR category LIKE …`。

**看起来更贴心的那个写法很危险**：

```
用户问「手机还有货吗」
  只匹配 name    → 0 命中 → 「没有找到名称为『手机』的商品」  ✅ 正确
  加上类目       → 命中 40 个 → 返回前 3 个                  ❌ 灾难
```

那 3 个是**按 id 排序的前 3 个**，和用户想问的东西毫无关系 ——
但它**看起来像一份答案**，而模型会把它当成答案。

★ 这和 [ADR-044] 那条「工具意图没有检索时模型会编一个订单状态出来」是**同一类风险**：
我们提供了一个看起来像答案的东西。**宁可回「没找到」，也不要回一份随机的候选。**

**同理**：查不到时**不给**「你是不是想找…」的候选清单。一份猜出来的候选，
模型会从里面挑一个报给用户 —— 而用户问的是另一个东西。

**职责放回模型**：工具描述里写明「用户只说了品类时，先问用户具体是哪一款」。
（3 个新增测试钉住，见 `QueryInventoryToolIntegrationTest#MatchScope`。）

## ADR-072 · ★★ 商品名**会重复** —— 正文里总是带商品编号

**实测（2026-09-20，真实数据）**：200 个商品里 **17 组、共 35 个重名**。

```
华为 Magic mini  → P000001 / P000013
小米 BCD Pro     → P000177 / P000179 / P000188
```

`product.name` 上没有唯一约束（唯一的是 `product_no`），
而名称是「品牌 + 型号」拼出来的，型号词表不够大。

**★ 这不是种子数据的 bug，是真实电商的常态** ——
同名不同款（不同年份、不同批次、渠道专供）到处都有。工具必须能表达它。

**决策**：正文标题里**总是**带 `product_no`。
⚠️ 「总是」这两个字是关键：写成「只在检测到重名时才带」会让**正文的形状随数据变化**，
而正文长度直接关系到 `ToolLoop.MAX_TOOL_RESULT_CHARS` 的截断位置和 prompt 前缀的稳定性 ——
那些代价远大于多打 8 个字符。

**★★ 这个事实是被【探针第一次手动调这个工具】发现的，而它当时看起来像我的实现有 bug**
（「怎么返回了两个同名商品？」）。真相在数据里，不在代码里。
不实际调一次，这个信息不会出现在任何地方 —— 单元测试用的是自己造的夹具，
而夹具里不会有两个同名商品，除非你知道要造。

## ADR-073 · 券的「可用」判据是 **status + 时间**两个条件的合取

**决策**：`status == 1 && (expired_at == null || expired_at > now)`。

**为什么不能只判 `status`**：`status = 1` 而 `expired_at` 已经过去，在真实系统里是**存在**的
—— 把过期券刷成 `3` 需要一个定时任务，而那个任务可能有延迟，或者压根没跑（本地库就没有）。

后果很具体：工具报「这张券可用」，**用户拿去下单被拒** —— 那时他不会再信这个助手。

★ 而且发现不一致时**如实说出来**（「其中 1 张券的状态仍显示为未使用，但有效期已过」），
不静默归到「已过期」里 —— 那是一条**关于数据的事实**，不是我们该替它圆的。

**反方向的判据不同**：`expired_at` 为 **null 视为不过期**。
理由是两种错的代价不对称：
- `null = 不过期` 最坏是把一张实际上不存在的券当成可用 → 用户下单时会被拦
- `null = 已过期` 是把一张**真券藏起来** → 用户根本无从发现

## ADR-074 · `SeedRunner` 的幂等粒度改成**按表**；随机流必须**按方法隔离**

### 一、幂等：从「一个总开关」到「每张表各自判断」

原来开头是 `if (productService.count() > 0) return;` —— 于是**什么都补不了**。
而 5.9 恰好需要「补一张表、别动其它表」：`user_coupon` 有 0 行，
但重灌商品会连带把 208 份文档、1652 条切片和它们的向量全部作废
（`kb_chunk.related_product_id` 指向 `product.id`）。

**顺带发现**：`user_coupon` 一直是空的，**不是数据没灌，是这一步从来没写过** ——
尽管 `SeedRunner` 的插入顺序注释里一直写着它。

**配套的纪律**：

> **每一步需要什么，就从库里读什么；不要靠「前面的步骤在同一进程里刚创建的那些对象」。**

否则「跳过第 2 步」会顺手把第 3 步也弄坏。按这条写之后，
**「整个库是空的」只是「每张表都空」的一个特例**，两条路径走同一份代码。

**验证**：补券那一跑的日志是
`①已有30条，跳过 / ②已有200条，跳过 / ⑥已有8条，跳过 / ⑦已有120条，跳过 / ⑨已有12条，跳过 / ⑩ 71 条（灌）`
—— 已存在的表**一条都没动**。

### 二、★ 随机流是**位置依赖**的，而位置依赖 = 顺序依赖 = 不可复现

一个 `Random` 是**一条流**：第 N 次取值取决于「在它之前被取过多少次」。
于是每个方法的输出都隐式地依赖**它前面跑过哪些方法**。

这在「每次从空库全量灌」的世界里没问题。但按表幂等之后出现了第二条路径：

```
全新建库        ：createUsers → createProducts → … → createOrders → createUserCoupons
只补 user_coupon：                              createUserCoupons
```

两条路径下 `createUserCoupons` 从同一条流里读到的位置**完全不同** →
**同一份代码、同一个种子，产出两套不同的券**。
而症状是「我这儿查出来 3 张券，你那儿是 2 张」—— 一个会被归因成「数据没同步」的问题，
实际上是我们自己的不确定性。

**修法**：新方法用**新流**（`new Random(RANDOM_SEED + 1)`）。

⚠️ **为什么不统一改老方法**（那才是根治）：那会改掉**所有现有数据** ——
200 个商品的名称、578 个 SKU、库存、订单，以及已经向量化入库的 208 份文档与 1652 条切片。
改完必须重建整个库并**重新花钱做一遍向量化**。

**所以：新方法用新流，老方法一个字节都不动。** 这条教训记在这里，
将来再有人加种子表时，请照 `createUserCoupons` 的做法给新流。
（由 `UserCouponSeedTest#independentOfOtherCalls` 钉住。）

## ADR-075 · 名额 = ZSet 成员（score = 过期毫秒）；**释放只广播，分配只在 acquire**

### 一、不用 Redisson `RSemaphore`，因为**它表达不了我们要的语义**

`docs/02` §11⑥ 原来写着「`RSemaphore` 控制并发」，§23⑤ 同时写着
「必须给名额加过期时间兜底」。**这两条不可能同时成立**：

```
RSemaphore 的许可是【一个计数 value】
    → 「计数 8」这个整数里，没有「第 3 个名额是谁、它什么时候过期」这个概念
    → 没法给其中某一个名额单独设 TTL
```

而放弃过期兜底意味着「进程被强杀 → 永久少一个名额」，验收标准 3 直接不成立。

**所以：名额做成 ZSet 成员，`score = 过期毫秒`。**

| 需求 | 计数型信号量 | 成员型（本项目） |
|---|---|---|
| 限制并发数 | ✓ | ✓ `ZCARD` |
| 单个名额独立过期 | ✗ | ✓ 每个成员自带 score |
| 「名额现在被谁占着」可见 | ✗ | ✓ 探针直接 `ZRANGE` 列出来 |
| 释放时校验「是不是我的」 | ✗ | ✓ `ZREM` 的返回值 |
| 回收不依赖清理代码被执行 | ✗ | ✓ score 过期即失效 |

★ 最后两行是**排查能力**上的差别，不是性能差别。实测那次
「8 个上限、ZSet 里 14 个成员」的排查，靠的就是能把成员一个个列出来看 ——
如果它是一个整数计数，那条线索根本不存在。

### 二、★★★ 释放**不分配** —— 「提拔队首」会在队首已死时漏名额

原设计（`docs/02` §22⑥ / §23⑥ / §22 面试追问点，三处都写着）是
「释放名额的同时立刻把名额分给排队中的下一个人」。它有一个**填不上的洞**：

```
队首已断线（关页面 / 超时 / 进程被杀）→ 它仍在队列里，但已经不在等了
释放者把它「提拔」进名额表
   → 它永远不会来用这个名额
   → 名额被幽灵占着，直到 TTL 过期 —— 期间后面所有人卡住
```

**这直接威胁验收标准 1（无死锁）。**

改成「释放只移除自己 + 广播」之后：

```
分配只在一个地方发生：acquire.lua 的「ZCARD < maxPermits → 占住」
死人不参与竞争 —— 因为「抢」这个动作需要一个活着的线程去做
⇒ 「分给幽灵」从设计上不可能发生
```

★ 代价要说清楚：**这牺牲了严格 FIFO**。等待者是「谁先重试到谁赢」，
不保证队首先拿。这是一个**刻意的取舍**：严格 FIFO 要求「只给队首发名额」，
而队首死了就会阻塞整条队列到 TTL。**「可能不公平」比「可能死锁」好。**

⚠️ 位置**仍然**单调不增（`ZRANK` = 排在我前面的人数，而前面的人只会离开），
所以推给前端的「你前面还有 N 位」仍然是对的 —— 只是这 N 个人不保证按顺序被服务。

### 三、被否决的另外两条

| 方案 | 否决理由 |
|---|---|
| `INCR` / `DECR` | 「读-判断-写」不是原子的，并发下直接超卖。而且没有位置、没有成员、没有过期 —— 排查时什么都看不到 |
| 释放时用 Lua 原子地「释放 + 提拔队首」 | 见第二节。原子性解决不了「队首已死」这个语义问题，**它只是让错误发生得更确定** |

## ADR-076 · ★★★ 续期走 Lua：**keepalive 不能创建租约**

**这是本项目在真机上抓到的、后果最隐蔽的一个 bug。**

### 一、现象

12 轮 × 100 并发压测，**1 次**出现 `ZCARD(slots) = 14` 而上限是 8。
那一次的 `/slots` 探针输出：

```
permitsInUse: 14   expiredNotYetSwept: 0   heldHere: 7
孤儿 7 个: 9925 9925 9925 9925 9925 9925 9925    ← score 完全相同
本机 7 个: 9927 9927 9927 9927 9927 9927 9927
```

- `expiredNotYetSwept: 0` → **不是僵尸**，那些名额都是「活」的
- 7 个 score **完全相同** → 是**一次心跳批量写入**的指纹（`renewHeld` 用同一个 `now`）
- 它们的 `renewedByThisProcess = false` → **本机已经不认领它们了**

**后果不是超卖，是容量静默变少**：真跑的请求没超过 8 个，但可用名额从 8 掉到 ~5。
那一轮 100 并发跑了 **23.6 秒而不是 15.9 秒**，正好是 `100 / 5 × 1.2`。
**没有异常、没有日志、没有任何指标。**

### 二、根因：`ZADD` 会**创建**成员

第一版的续期就是两条普通命令：

```java
redis.opsForZSet().add(keys.slots(), traceId, expiresAt);   // ← ZADD 在成员不存在时会【创建】它
redis.opsForZSet().add(keys.alive(), traceId, now);
```

于是：

```
t0  心跳：heldSnapshot() → 快照里有 X      ← 快照是【旧的】
t1  release(X)：registry.forget(X)          ← 本机忘了
t2  release(X)：ZREM slots X                ← Redis 也删了
t3  心跳：ZADD slots X (now + ttl)          ← 用旧快照把 X 【复活】
```

### 三、★★ 为什么原来的防护没挡住 —— 这条比 bug 本身更重要

`release()` 里的顺序是「**先删本地、再删 Redis**」，`LocalPermitRegistry` 的
类注释第二节专门论证过它防的就是「心跳复活」。**那个论证是对的，但不够。**

> **它防的是「两步执行顺序反了」，防不住「两步之间插进来一次心跳」。**

心跳不是一次原子操作，而是「取快照 + 逐个写」两步 ——
**而这两步之间可以完整地跑完一次 `release()`。**

★ **教训：靠顺序保护不了跨两步的窗口，只能让那一步本身不可能做错。**

### 四、修法：`renew.lua` —— 判定成员还在，才延长

```lua
if redis.call('ZSCORE', KEYS[1], ARGV[1]) then
    redis.call('ZADD', KEYS[1], tonumber(ARGV[2]) + tonumber(ARGV[3]), ARGV[1])
    redis.call('ZADD', KEYS[2], ARGV[2], ARGV[1])
    return 1
end
return 0
```

一句话：**keepalive 不能创建租约。**（etcd 的 `Lease.KeepAlive`、Chubby 的 `KeepAlive` 都是这个形状。）

### 五、★ 它对「续期失败怎么办」这条既有策略的修正

原策略是「**续期失败只记日志、不放弃**」——理由是「抖动是暂时的，主动放弃反而把名额真空出来」。
**那条策略对「连不上」仍然成立，但对新出现的第二种情况是错的**：

| 情况 | 我们知道什么 | 该怎么办 |
|---|---|---|
| `execute` 抛异常（连不上 Redis） | **不知道**它还在不在 | **不放弃**，下一轮重试 |
| `renew` 返回 0（Redis 明确说「它不在了」） | **确切知道**自己已经失去了它 | 记 WARN，**绝不去抢回来** |

★ 把它们合并成一个分支，就会在第二种情况下做出「重新 ZADD 抢回来」的动作 ——
**而那才是真正的超卖**（那个名额已经被回收，甚至已经被别人合法抢走）。

⚠️ 续期返回 0 时**不**把本地登记删掉：本地表比 Redis 多几条是安全的，少几条才危险。
留着它的代价是零（续期变成 no-op），删掉它会让自愈的可能性永久消失。

### 六、验证方式（★ 值得单独说）

**「跑了 20 轮没重现」不算验证。** 修完后的验证是：

```
20 轮 × 100 并发：峰值每轮都是 8，孤儿 0
★ 而日志里出现了 7 条「续期时发现名额已不在 Redis 里」
```

**那 7 条 WARN 是关键** —— 它证明那个毫秒级窗口**在这 20 轮里又撞上了 7 次**，
只是每次都被挡住了。没有它，20 轮全绿也可能只是运气。

钉住它的是一条**确定性**的测试（`renewalNeverCreatesAPermitFromNothing`）：
`markHeld` 一个 Redis 里不存在的 id → `renewHeld()` 之后它**必须仍然不在** Redis 里。
它不撞窗口，直接把窗口的**结果**摆出来。注入验证：去掉 Lua 里的判定 → 精确失败
（`expected: <0> but was: <1>`）。

## ADR-077 · 两个「改一行就静默坏掉」的结构约束

### 一、`queueCapacity = 0` —— 它不是调优参数，是承重参数

```java
executor.setQueueCapacity(0);   // 走 SynchronousQueue
```

```
queueCapacity > 0  →  等待中的任务会静静躺在【执行器自己的队列】里
                      【没有任何线程在跑它们】→ 没人能推 SSE 位置
                      → 用户看到的是一个空白页面
queueCapacity = 0  →  任务立刻拿到线程，最多 max 个
```

★ 「空白页面」正是 `AsyncConfig` 里注释**明确否决过**的东西。
阶段 6 之所以能反过来做（「等一会儿」而不是「立刻拒绝」），
**就是因为我们能推位置了** —— 而 `queueCapacity` 一改，这个能力就没了，且不会有任何报错。

**所以它刻意不出现在 `application.yml` 里。一个「改了会静默破坏功能」的参数，不该给出配置项。**

### 二、排队必须在 `ChatService` **之外**

这一条比「职责划分」硬得多。`ChatServiceImpl` 的顺序是
`读记忆 → 写用户消息 → 意图识别 → ……`。排队若插在**写用户消息之后**：

```
排队超时 → 用户消息已经落库 → 一对没有回答的孤儿 user 消息
   → 下一轮它进历史 → 模型收到两条连续 user 消息 → 400 → 不降级
   → ★ 连续两次失败之后，这个会话【永久答不出话】（ADR-049）
```

★ 所以排队只能在 `saveUserMessage` **之前** —— 而它在 `ChatServiceImpl` 内部，
唯一的「之前」就是**外面**。**是 ADR-049 决定了这个包边界，不是分层洁癖。**

## ADR-078 · Pub/Sub 是**优化**，轮询是**正确性来源**（附 A/B 实测）

### 一、设计

```
await(maxMs = poll-interval)：
    有信号  → 提前醒来，立刻再抢一次（延迟 ~1ms）
    没信号  → 睡满 poll-interval（200ms）再抢一次
    信号丢了 / 订阅断了 / 应用刚起还没订阅上 → 【同样只是睡满】
```

★★ **关键语义：这是一个「有上限的等待」，不是「条件等待」。**
所以 Pub/Sub 只能让等待变短、**不可能让它变长**。

**这就是「Pub/Sub 消息丢了怎么办」的答案：不怎么办。**

### 二、订阅一个**公共频道**，不是每请求一个

后者需要动态增删 listener，而 `RedisMessageListenerContainer` 的 add/remove **是带锁的** ——
高并发下它自己会变成瓶颈，而且漏删一个就是内存泄漏。
代价是「本机惊群」：一次广播唤醒本实例的**所有**等待者，各自跑一次 acquire 去抢，只有一个能赢。

### 三、★★ 一个真机 bug：容器订阅失败后 `start()` 变成**静默 no-op**

实测：Redis 不通 → 应用启动 → Redis 恢复 → 20 秒后 `PUBSUB NUMSUB` 仍然是 0。

根因在库的实现里：`RedisMessageListenerContainer.start()` 在 subscribe 之前就置
`started = true`，**抛出异常后不重置**。于是之后**每一次 `start()` 都是静默成功的空操作**。

```
✗ 一次 start() + 依赖库的「无限重试」 →  冷启动失败 = 订阅永久死亡
✓ 监督循环 + 每次都用【全新的容器】重建 →  自愈
```

★ 这个 bug 的形态值得记：**日志里写着「订阅已建立」，而实际上一直在纯轮询。**
功能是对的（轮询兜底），只是慢了 —— 所以它**不会让任何测试变红**。

### 四、★ A/B 实测：Pub/Sub 的收益比想象中小得多

`xbla.ratelimit.wakeup.enabled` 这个开关存在的**唯一目的**就是让上面那句话可验证。
100 并发、`permits=8`、`holdMs=1200ms`，同一台机器：

| | Redis acquire 次数 | 墙上时间 | 25 项断言 |
|---|---|---|---|
| Pub/Sub **开** | 3881 | **15.9s** | 25/25 |
| Pub/Sub **关** | **3456** | 16.3s | 25/25（⑩ 断言翻转） |

★★ **结论和直觉相反**：在本项目的规模下，Pub/Sub **多花了 12% 的 Redis 往返，
只省下 2.5% 的时间**。

原因是：8 个名额、100 个等待者 → **平均每 173ms 就有一次名额交接**，
而 `poll-interval` 是 200ms。**交接间隔短于轮询周期时，轮询本来就够快。**

⚠️ 而 S6 的单测量到的是「有 Pub/Sub 3ms vs 无 Pub/Sub 1897ms」——
**那量的是 best case（1 个名额、1 个等待者）。**
★ 两个数字都对，它们回答的是不同的问题：
**「Pub/Sub 能省多少延迟」**（best case，200 倍）vs **「在我这个并发下能省多少」**（2.5%）。

⚠️ 更要紧的是**代价随队列深度线性放大**：一次释放唤醒**全部**等待者。
探针的 `amplification`（一次广播平均叫醒几个人）实测在 `permits=1` 时是 **48.5** ——
500 个等待者时，一次释放就是 500 次 Lua 调用。**Redis 单线程，那里才是它开始变贵的地方。**

## ADR-079 · 非流式接**同一批**名额：预算、503、以及必须剥掉的 `ExecutionException`

### 一、共用名额的理由是「否则限流没有意义」

加这个之前，非流式是**唯一一条绕过限流的路**：直接调 `chatService.ask(...)`，
不排队、不抢名额 —— 而它压的是**同一批下游**（同一个模型供应商、同一个 Hikari 连接池）。

> **一条能绕过的限流，只是「对配合的调用方生效的限流」。**

### 二、★ 排队预算 30 秒，不是 120 秒 —— 而且理由比体验硬

```
流式：每 200ms 推「你前面还有 N 位」→ 等 120 秒是【有信息的等待】
非流式：HTTP 请求-响应，没有通道 → 等 120 秒是【一个转圈的页面】
```

★ 但真正的原因是：**我们的超时必须比客户端自己的超时【先】发生。**
curl / 演示页 / 脚本普遍 30~60 秒就放弃；我们持 120 秒才回 503 的话，
用户看到的是「连接错误」，**而我们那句精心写的「前前排队人数过多」永远送不到。**

（`queueTimeout(120s) < sseTimeout(180s)` 是同一条逻辑，那边留 60 秒余量。）

### 三、被拒绝 → HTTP **503** + `Retry-After`，不是 500

```
500 → 「系统坏了」  → 用户截图报障、怀疑数据出问题
503 → 「暂时忙」    → 用户知道重试就行
```

★ **队列满根本不是故障 —— 它恰恰是限流【正常工作】的证据。**
把正常工作报成故障，是最容易让一个可用的系统被当成不可用的那类错误。

`Retry-After` 用当前的 `poll-interval` 换算（那是「名额周转」的时间尺度），
并且**至少 1 秒** —— 告诉客户端「马上重试」比不说更糟：它会让一群客户端在同一瞬间涌回来。

### 四、★★★ `ExecutionException` 必须剥掉 —— 否则上面那些规则**白写**

```java
work 里抛出 ModelCallException（比如「余额不足」）
    → future 里存的是 ExecutionException(cause = ModelCallException)
    → 直接往外抛 → Spring 找不到匹配的 handler
    → 落到兜底分支 → 500「服务内部错误」
```

**`@ExceptionHandler` 是按异常类型匹配的。** 裹一层就全废了。

★ 这个 bug 的形态很隐蔽：**它不会让任何单元测试失败**（那些测试直接调 service，
不经过 HTTP 层），也不会有异常漏出来（500 看起来就是个「合理的失败」）。
只有真的发一个会触发领域异常的请求才会看到。

### 五、⚠️ 一个诚实的缺口：非流式的客户端断线检测不到

流式靠 `SseEmitter` 的 `onCompletion/onTimeout/onError` 知道「人走了」。
**同步的 HTTP 请求没有等价的回调** —— `HttpServletRequest` 不告诉你对面还在不在。

所以断线的非流式请求会把它在队列里的位置占到 `nonStreamQueueTimeout` 为止。
★ **影响有界，而且比流式那边小**：断线的流式请求会占住一个**名额**（整个问答时长），
断线的非流式请求只占一个**队列位置**（不占名额），而且会自己超时。
彻底解决需要异步 Servlet（`DeferredResult`），见 `docs/10`。

## ADR-080 · 两个被误报成「未预期的异常」的正常事件

> 这是同一类错误的**第三次**出现（前两次：ADR-061 的 `ExecutionException`、本次的客户端断开）。
> 后果都不是功能坏了，而是**信号被淹没**。

### 一、客户端断开：一次关标签页 = 一条 ERROR + 一屏堆栈 + 一条 WARN

用户在回答生成到一半关掉页面时，Spring 的异步派发会把这件事
**当成「handler 方法抛了一个异常」**递上来：

```
AsyncRequestNotUsableException: Servlet container error notification for disconnected client
  ← Caused by: java.io.IOException: Connection reset by peer
```

没有专门的 handler 时，它落到兜底分支，于是（实测，一次 RST 就够复现）：

```
ERROR  未预期的异常                    + 一整屏 60 行堆栈
WARN   Failure in @ExceptionHandler …#handleOther(Exception)
```

★ **第二条尤其糟**：兜底分支要写一个 500 的响应体，而连接已经死了 ——
**于是一个「处理异常的方法」自己又抛了一次异常。**

**修法**：`@ExceptionHandler(AsyncRequestNotUsableException.class)`，
记 **DEBUG**、返回 **`void`**（什么都不写）。

★ 返回 `void` 是刻意的：连接都没了，写任何东西都只会再炸一次 —— 而那正是上面那条 WARN 的来源。

⚠️ **监控按 ERROR 计数的话，「用户关页面」和「数据库连不上」长得一模一样**，
而前者每天几千次、后者一年一次。**这才是真正要修的东西。**

### 二、★★ `queue_ms` **不能**用来判断「是哪一种拒绝」—— 同一列三个「总是」全错

`qa_log.queue_ms` 的注释在本项目里改过**三次**，每次错的都是同一件事：
**拿一个只带「量级」的数去回答一个关于「原因」的问题。**

```
① 阶段 6.5「立刻拒绝时它是 0」      → 对「队列满」错（它是差值，实测 2ms）
② 阶段 6.7「它不可能是 0」          → 对「池满」错（那两处传的字面量就是 0）
③ 阶段 6.8「0 = 池满，>0 = 队列满」 → 全错，见下表
```

压测实录（`qa_log`，`status=4`）：

| `error_msg` 的原因 | `queue_ms` | 次数 |
|---|---|---|
| 排队线程池已满 | **0** | 34 |
| 队列已满 | 2 | 2 |
| 队列已满 | 1 | 1 |
| **队列已满** | **0** | 1 ← **判决性的一行** |
| 排队超时 | 3138 | 1 |

**`queue_ms = 0` 在两种原因下都出现过。** 它判不了。

★ 四种拒绝各自对症一个**不同的旋钮**，而它们的 `queue_ms` 可以完全相同：

```
「队列已满」        →  maxQueue
「排队线程池已满」  →  queuePool.maxPoolSize
「sse 线程池已满」  →  answerExecutor 的容量
「排队超时」        →  permits / 容量本身
```

★ **精确判据只能是 `error_msg` 的原因串。**（`queue_ms` 仍然能回答**量级**：
0~个位数 = 几乎是立刻就拒了；接近排队上限 = 等满了预算 —— 但只能用来交叉验证，不能定性。）

★★ **这条教训比那个字段重要**：**同一列在多个路径上有多种形状时，
任何一句「它总是 X」都注定是错的。** 前两次修正都只是把「总是 X」换成「总是 Y」，
所以第三次还是错的。**该写下来的是那张表，不是那句话。**

⚠️ 更值得说的是：**它是被一个我自己写的 flaky 断言抓出来的。**
`ChatAdmissionBlockingTest` 里 `assertTrue(queueMs >= 1)` 一直绿着，
只是因为量到的通常是 2 毫秒 —— 换一台更快的机器、或者只是跑第二遍，它就红了。
**偶发红的测试比没有测试更糟，但这一次它比没有测试好得多。**

## ADR-081 · 评测流量用 `qa_log` 上的**两个显式标记**，不靠 question 文本 JOIN

**决策**：`qa_log` 加 `eval_run_id` / `eval_question_no` 两列（都可空）+ 一个
`WHERE eval_run_id IS NOT NULL` 的部分索引。评测行和真实用户**走同一条写入路径**，
只是多盖两个章。

**为什么不靠文本 JOIN**：两个方向都会静默出错，而且**症状都反过来**：

```
真实用户恰好问了同一个问题   → 被算进评测。没有症状，
                              只会让评测数字慢慢变成真实数据的数字
评测题被改写了一个字         → 那一行静默【退出】评测。
                              结果是对账通过、分母变小、指标看起来更好了
```

★ 两个方向的共同点是：**没有任何报错**，而纠正它们需要你当初就想到这件事。

**否决：单独开一张 `eval_qa_log` 表。** 那会切断「评测行和真实行经过同一条链路」
这个性质 —— 而评测要测的**正是那条链路**（排队、限流、落库、状态码）。
一张旁路表会让评测变成「测一个很像线上但不一样的系统」。

**★★ 落点上有两个必须记住的位置**：

```
ChatController 读两个头 → Admission.EvalMark（可空）→ CallContext → baseLog
                                                        ↑ 它正是为「加字段不改签名」而设的
★ rateLimitedLog（被排队拒掉那条路，【绕过 baseLog】）也必须写
  —— 否则「被队列拒掉的评测行」在书里查不到，而对账会报「少了 N 行」
```

★ 更根本的一层：`CallContext` 在本项目里有 **≥4 个构造点**，漏一个就编译通过、
无日志，评测流量伪装成真实用户。所以跑题器**必须对账**：
每个提交的 `traceId` 都要能在 `qa_log` 里查到且 `eval_run_id` 相符，否则**整轮作废**。

## ADR-082 · `retrieval_detail` 的扩展一律是**加法式**的

**决策**：加 `sizes` 段（`vector` / `keyword` / `fused` / `reranked` 各自的总条数），
**已有字段一个不改**。

**为什么必须要它**：`MAX_ENTRIES_PER_SECTION = 20` 会截断，而
`not_recalled` / `fusion_dropped` 是从**被截断的**两路和 `fused` 算出来的。
迭代里把 top-k 调大之后，**第 21 名的正解会变成「没召回到」** ——
而旧 JSON 里**看不出**那是截断还是真的没召回到。

★★ 这是一个**事后不可辨**的坑：那轮迭代一旦跑完，那个数就**永远解释不清了** ——
重算报告没用，缺的那个段当时就没写进库。

**实测**：`fused` 每行恰好 20 条，而 RRF 返回的是完整并集（20~40 条）；
影子区（第 21 名及以后藏着正解的行）实测 **0/389** —— 也就是说**这一次**没有踩到，
但那是运气，不是保证。

**否决：把 `fused` 的长度上限调大。** 那会让所有历史 JSON 的语义变掉
（同一个字段在不同轮次里含义不同）—— 正是本项目最反对的那种「一个字段两条路」。

★ **同 5.4 加 `filter` 那一次**：`RetrievalDetailBuilderTest` 会因此变红，
**那是该红** —— 它刻意守在那里，让「扩结构」成为一次**被看见的决定**。

## ADR-083 · 延迟报**五段**，且明写「**不相加等于 total**」

**决策**：`queue` / `retrieval` / `rerank` / `llm` / **未归类**。
命名用「未归类」，并在报告里注明**含意图分类与会话记忆**。

**为什么不是四段**：两个结构性问题

```
① rerank ⊂ retrieval —— 它是【包含关系】，不是并列项
   （实测：retrieval_latency_ms ⊇ rerank_latency_ms，retrieve() 用 try/finally 包着 doRetrieve()）
② ★★ 意图分类是一次 0.5~2.5 秒的模型往返，它进了 total 却不在任何一列里
   实测 未归类 p50 = 823ms、p95 = 1872ms —— 这一块【从来没被量过】
```

**否决：把「未归类」硬并进 `retrieval`。** 那会让「检索慢」和「分类慢」混成一个数，
而**两者的修法完全相反**（一个调检索参数，一个调 prompt / 换模型）。
★ 同理不能并进 `llm`：分类是「一问一答」，生成是「长输出」，量级和优化手段都不同。

★★ **报告里必须写「四段不许说成相加等于 total」** —— 这是本项目
「一个字段两条路时断言必须说清是哪条路」（ADR-080）在延迟上的同一条纪律。

## ADR-084 · 多轮题**单独 run_id、单独一节、单独分母**

**决策**：多轮集（`stage7-multi`）跑在独立的 run 里，不混进单轮指标。

**为什么不能混算**：

```
① 分类器的输入【按决策不含历史】（ADR-046）——
   所以「追问轮该判成什么意图」不是一个可测量的量，它取决于上一轮说了什么
② repeat 之间会串味：同一题的第 2、3 次如果复用会话，
   它们就不是「同一个输入的重复测量」了
③ ★ 摘要压缩走异步单线程池（最慢实测 41.5 秒），会与下一轮抢跑
④ 两套题的构造方式不同，混在一起会让「口语题占多数」这条纪律失效
```

**否决：给多轮题加个 `is_multi` 标记，在同一个 run 里过滤掉。**
那会让报告里出现**两套分母**挂在同一个 runId 下 —— 而这个阶段的核心纪律是
**「每个数字都要能写出分母」**。分母说不清的 run 就不该是一个 run。

★ **实现上连带的三件事**：每题标一个「把它单独说该怎么说」的 gold；
repeat 用**全新会话**；摘要开关记进**配置快照**（否则「开了」和「没开」的轮次看起来一样）。

## ADR-085 · 新开关的 `FilterScope.Reason` 用**新取值**，不复用 `no_declaration`

**决策**：`xbla.rag.retrieve.by-intent.enabled = false` 时，
`reason` 取 `DISABLED_BY_CONFIG` —— **不复用** `no_declaration`。

**为什么**：复用会让 `probe_kb.py --docTypes` 那套**已经写进文档的 A/B 手法
静默变成空操作** —— 关掉开关之后，「按 docType 过滤」看起来仍然是生效的。

**实测（同一个请求，开关开 vs 关）**：

```
开关【开】  范围: ✅ 已下推  doc_types=[2, 4] 池子=67    原因=ok
开关【关】  范围: ⏭️  未下推  doc_types=[2, 4] 池子=None  原因=disabled_by_config
```

★ 注意 `doc_types` 仍然**如实记录调用方声明**（它确实声明了），只是没被用上。
合起来就是**一句可读的话**：**「声明非空 + `applied=false` → 去看 `reason`」**。

**否决：把 `doc_types` 清空来表示「没生效」** —— 那就丢失了「调用方本来要什么」，
而排查「为什么范围没下推」时，你要的恰恰是那个声明。

★★ 这是本项目第三次在「**同一个字段要表达两件事**」上做取舍
（前两次：ADR-041 澄清路径的 NULL、ADR-080 的 `queue_ms`）——
处置一致：**不是让字段变聪明，而是让「读的人有一句话可以念」。**

## ADR-086 · 评测流量要在**读**侧也排掉 —— 光写标记是不够的

**日期**：2026-09-24　**状态**：已采纳　**阶段**：8

**决策**：会话列表接口（`GET /api/chat/sessions`）**必须**排除评测会话，判据是
`NOT EXISTS (SELECT 1 FROM qa_log q WHERE q.session_id = s.id AND q.eval_run_id IS NOT NULL)`。
前端**不做**任何过滤，也不做「猜哪个是评测」的启发式。

**Context**：阶段 8 要做一个「历史会话列表 + 切换」的前端。

**实测（动工前查的，不是上线后发现的）**：

```
chat_session 总数                     4111
其中 qa_log 带 eval_run_id 的会话      4022   ← 97.8%
真实的                                  89
```

一句朴素的 `ORDER BY last_active_at DESC LIMIT 20` 会得到**一屏**
「商品支持七天无理由退货吗」—— 阶段 7 的 159 题 × 3 次重复，每题都建了一个会话。

★★ **这是 ADR-081 那条纪律换了个地方重新出现**：

```
ADR-081（阶段 7）  eval_run_id 会在某些【写】入路径上被静默丢掉
                  → 评测流量伪装成真实用户
                  → 修的是【写】

本 ADR（阶段 8）    标记好好地在库里，但没有任何人想到要按它过滤
                  → 同一个伪装，从【读】那一侧进来
                  → 修的是【读】
```

⇒ **一个标记只有在「写的时候写全」+「读的时候记得用」两个条件同时成立时才有意义。**
只做前半句，它就是一个躺在库里没人看的列。

**判据的方向也是刻意的**：用「没有【评测】行」而不是「有【真实】行」。
因为还有一类会话是**一行 `qa_log` 都没有**的（会话建好了、用户消息也落库了，
但紧接着推送失败 —— 见 `docs/10` 阶段 7 的逐出口审计）。
那种会话**应该**出现在列表里，用户确实打了字。反过来写会把它一起挡掉。

★ 实测这条判据够用：89 个非评测会话里 **0 个是空会话**，不需要再叠条件。

**⚠️ 但同一个过滤【不】加在单会话的消息接口上** —— 那是**故意**的不一致：

```
列表        是【浏览】   → 不筛的话 97.8% 的位置被评测占掉
单会话消息  是【精确键查找】→ 一个确实存在的行被回 404，会让人以为数据丢了
```

★ 换句话说：**「排除评测流量」是列表这个读模型的属性，不是会话本身的属性。**
这和 `qa_log.status ≠ 1` 那套的区别是：那个过滤的是**统计口径**，
这个是**展示口径**。两者看着像同一件事，管的东西不同。

**验证**：`ChatHistoryQueryIntegrationTest` —— 含一条**正-反对照**
（断言「那行数据确实存在，是过滤器把它拿掉的」，否则「不在列表里」可能是恒真的）。

**否决：前端过滤** —— 判据只能有一处，而且它在数据那一侧
（`qa_log.eval_run_id`），不在展示那一侧。前端再判一次就是第二个事实来源，
且它会与后端漂移。

## ADR-087 · 技术细节面板用**新的只读白名单端点**，不复用 debug 端点

**日期**：2026-09-24　**状态**：已采纳　**阶段**：8

**决策**：新增 `GET /api/chat/trace/{traceId}` 和 `GET /api/status/ratelimit`，
**不复用** `/api/debug/mcp/qa-log` 和 `/api/debug/ratelimit/state`。

**为什么**：那 7 个 debug 控制器是 `@Profile("local")` 的 ——
**生产 profile 下根本不会被注册**。它们能：

```
POST /api/debug/ratelimit/leak     改状态（造僵尸名额）
POST /api/debug/ratelimit/reset    改状态（清空所有 key）
GET  /api/debug/llm/chat           无条件消耗 API 额度
```

★ 把它们跟着公网隧道一起暴露，等于把 API 额度和限流状态交给任何拿到地址的人。
所以「生产也要有的那个出口」必须是**新写的、只读的、白名单的**。

**两个端点各自的取舍**：

| | 不复用它的原因 |
|---|---|
| `/api/chat/trace` | 不返回 `error_msg`（那条列可能带上游错误详情和内部模型 ID —— 同 `GlobalExceptionHandler` 对 `ModelCallException` 的处置：**完整信息打日志，对外只给一句可读的**） |
| `/api/status/ratelimit` | 从 debug 那个 map 里**挑子集**，尤其**不给 `queueHead`** —— 那是队列里**别人的 traceId** |

★★ **判据是白名单而不是黑名单**：写出来的字段才给出去。
将来 debug 的 map 里加字段，**不会自动出现在对外端点里** ——
同 `eval_report.py` 的 `OMITTED_PATHS`、`QaLogMapperProjectionTest.NOT_SELECTED`：
**「给出去的」和「不给的」都要是被看见的决定。**

**★ 路径也刻意不放在 `/api/debug/` 下**：那个前缀在本项目里已经等于
「local 专用、可以花钱、可以改状态」。把一个生产端点放进去会让那个含义失效，
也会让「公网上 `/api/debug/**` 必须 404」这条验收判据变成一条**有例外的规则**
—— 而**一条有例外的规则，下次就没人照着查了**。

**实现上的一个细节**：`RateLimitStatus` 的每个字段都来自**类型化的取值口**
（`permitsInUse()` / `queueSize()` / `config()`），**没有一个字符串键名**。
从 map 里按键名取值不会有编译错误，只会让状态页上出现一个看起来很正常的 `0`
—— 同 `QaLogMapper` 那条「显式列清单会漂移」。

**验证**：`StatusControllerTest` —— 含一条**正-反对照**：
断言 debug 端点里那些被排除的键**确实存在**，否则「status 里没有 `queueHead`」
可能只是因为那个字段压根不存在于任何地方，那这个测试就在验一个空集。

★★ 而这条对照**当场就抓到了一个盲区**：`$.data.redis.seq` 在 debug 端点上
**键存在、值是 null**（队列没跑过，Redis 里没有 `seq` 这个键），
而 `jsonPath(...).exists()` 对「键不存在」和「键存在但是 null」**给出相同答案**。
既然这个类全部的价值就是分辨「有没有」，判据换成了 `JsonNode.has()`。

## ADR-088 · 「一键启动全栈」用 **Compose profile**，不改默认行为

**日期**：2026-09-24　**状态**：已采纳　**阶段**：8

**决策**：

```bash
docker compose up -d                      # 中间件（行为【一字不变】）
docker compose --profile full up -d       # 中间件 + 应用 + Nginx（全栈）
```

**Context**：路线图的验收标准 2 写的是「在干净环境能 `docker compose up -d`
一键拉起」。而这个 compose 文件里的中间件**同时是另外三件事的前提**：

```
./mvnw clean test         858 个用例需要 postgres + redis
scripts/probe_*.py        全部假设 localhost:8080
scripts/eval_run.py       阶段 7 的可复现链
```

**为什么不让 `up -d` 默认起全栈**：那样每一次跑测试、跑探针、日常开发，
都会顺手把应用容器和 Nginx 一起启起来 —— 构建慢，而且很容易忘了它们在跑
（然后被「8080 到底是谁占着」绕进去）。

⚠️ **这是对验收标准 2 的一处【有意的偏离】**：那条命令要多带一个
`--profile full`。写在这里，是为了让「偏离」是一次被看见的决定。

**★★★ 动工时的实测反例（差点把它做坏）**：

第一版把模型密钥写成 compose 的 `${DEEPSEEK_API_KEY:?}`（「必需变量」），
理由是「缺密钥就启动失败更好排查」。结果：

```
$ docker compose config --services
error while interpolating services.app.environment.DEEPSEEK_API_KEY:
required variable DEEPSEEK_API_KEY is missing a value
```

★★ **Compose 会插值文件里的【所有】服务，不管 profile。**
所以那一行等于要求「想用中间件跑测试的人也必须先配好模型密钥」——
**恰好破坏了这个方案要保住的东西。**

⇒ 修法：强制校验**下移到消费它的那一层** ——
`application-prod.yml` 里本来就写着 `api-key: ${DEEPSEEK_API_KEY:? ...}`。
应用容器照样**启动即失败**、错误信息照样点出缺的是哪一个。
**失败的特性一样，只是位置对了。**

**否决：拆成两个 compose 文件** —— 全栈要 `-f` 两个文件，
命令最长，也最容易把两个文件配得不一致（而那种不一致是静默的）。

## ADR-089 · 应用容器**不映射端口** —— 让两条运行方式并存

**日期**：2026-09-24　**状态**：已采纳　**阶段**：8

**决策**：`app` 服务**不写 `ports`**，只在 docker 网络里被 `nginx` 以
`app:8080` 访问。宿主机 8080 留给 `./mvnw spring-boot:run`。

**为什么**：这个项目同时有两套运行方式，而它们**都必须活着**：

| | 本地开发 | 容器全栈 |
|---|---|---|
| 应用端口 | 宿主机 **8080** | 容器内 8080，**不映射** |
| 用它的东西 | `mvnw test`(858)、`probe_*.py`、`eval_run.py` | 部署演示 |

★ 如果应用容器也映射 8080，两条路就**不能同时存在**（端口冲突）。
而阶段 7 那套「可复现」的链全部假设 `localhost:8080` ——
把它弄断，等于把这个项目最值钱的部分弄断。

**顺带的好处**：应用容器连宿主机都不暴露，公网就更够不到。
隧道只指向 Nginx，而 Nginx 是唯一有访问控制的那一层。

**⚠️ 一处【不】需要改的地方**（记下来，免得以后有人「顺手改」）：

```yaml
xbla.mcp.client.base-url: http://localhost:8080
```

这是 MCP client 指向**自己**（Server 和 Client 在同一个 JVM 里）。
容器内 `localhost:8080` 仍然解析到应用自身，所以**不用改** ——
前提是容器里的 `server.port` 保持 8080。改端口会让所有工具静默查不到东西。

**否决：让应用容器映射到 8081 之类的别的端口** ——
那就多了一个「哪个端口是哪条路」的映射要记，而 `localhost:8080`
是 CLAUDE.md 里几十条命令的共同前提。

## ADR-090 · 评测报告用**文件系统白名单**，不用配置里的路径白名单

**日期**：2026-09-24　**状态**：已采纳　**阶段**：8

**决策**：报告的放行靠**镜像里逐个 `COPY` 两个文件名**（`deploy/Dockerfile.web`），
Nginx 那侧只写 `location /docs/ { alias /srv/public-docs/; }`，
**不**在配置里再列一遍文件名。

**Context**：有两份文档要给人看（`11-评测报告.md` / `11-附录-逐题.md`），
而 `docs/00-项目总览.md` 是**简历故事线 + 面试讲稿，不进公开仓库**
（靠 `.git/info/exclude`）。

★★ **关键：git 的排除和 Nginx 的挂载是两套机制。**
`.git/info/exclude` 只是让文件不被提交 —— 它**照样躺在磁盘上**。
挂 `docs/` 整个目录就等于公开它。

**为什么选文件系统白名单而不是配置白名单**：

```
配置白名单   两条 location = 匹配中文文件名 + 一条兜底 404
             → 依赖「nginx 拿解码前还是解码后的 URI 去匹配 location」
               这个细节，而它在不同版本、不同编码形式下有过变化
             → 写错了的症状是「报告页 404」，看起来像文件没打进去

文件系统     /srv/public-docs/ 里【只有】两个文件
             → 目录里没有的文件，任何 URL 写法都拿不到
             → 而那个目录里有什么，是 Dockerfile 里逐行写着的
                —— 那才是该被 review 的地方
```

★ 白名单因此在**三处**出现，而它们必须一致：

```
deploy/Dockerfile.web                COPY 哪两个文件（生产）
deploy/nginx.conf                    注释里点名（生产）
frontend/vite.config.js              PUBLIC_DOCS（开发期的中间件）
```

★★ **为什么开发期也要有一份**：开发服务器如果比生产宽松，会出现
「本地能打开、部署上去 404」；反过来更糟 ——
**本地测不出来、上线才发现泄露**。两处同源，配错一边时症状是
「两边行为不一致」，那是**最容易发现**的形态。

**验证（2026-09-24 实测，开发期中间件）**：

```
/docs/11-评测报告.md         → 200  71636 bytes
/docs/00-项目总览.md         → 404   ★ 简历讲稿没出去
/docs/../docs/00-项目总览.md → 400   ← Vite 自己挡的，没到中间件
/docs/.hidden.md             → 404
```

★ 注意第三行返回的是 **400 而不是 404** —— 它在更前面就被拒了。
结论（拒绝）一样，但**成因不同**。写清楚才不会被下一个来查的人
误读成「这个白名单挡不住穿越」。

**否决：把报告复制进 `frontend/public/`** —— 那会让它变成**一份快照**，
`python scripts/eval_report.py` 重跑之后页面还是旧数字。
而「快照和源文件不一致」这件事**没有任何迹象**。
★ 运行时读文件则让「重跑报告」和「页面上的数字」之间没有需要记得做的同步步骤。

## 附录：被否决的方案汇总

| 决策点 | 选了 | 否决了 | 核心理由 |
|---|---|---|---|
| HTTP 客户端 | JDK 内置 | OkHttp / Apache HttpClient | 零依赖 + 原生 SSE |
| 流式接口形态 | 阻塞 + 回调 | `Flux` / `Stream<Chunk>` | `Stream` 的异常包装会丢失供应商信息 |
| 熔断器装配 | 自己 `@Bean` | 依赖自动配置 | 条件装配可能静默失效 |
| 熔断耗时口径 | TTFB | 整个流时长 | 长回答会被误判为慢调用 |
| 降级边界 | 只降「未吐字」 | 任何失败都降级 | 会拼出前后矛盾的回答 |
| 400 的处理 | 不降级不计熔断 | 当普通失败 | 会用一个自己的 bug 掩盖所有供应商 |
| 降级事件传递 | 显式参数传 `ModelCallTrace` | ThreadLocal | 推送线程不继承请求线程的 ThreadLocal |
| SSE payload | Map + JSON | 纯 String | 纯 String 中文会乱码 + 换行破坏分帧 |
| 成本缺失时 | 记 NULL | 按字符估算 | `qa_log` 只增不改不删，估算值会永久污染 |
| `list_active_at` | 手工 set | 依赖自动填充 | 自动填充只管 `updated_at` |
| 文档解析器 | Tika 3.3.2 | Tika 4.0.0 | 4.x 破坏性变更太多（SPI 签名、配置格式、Metadata 键全部改了）|
| PDF 标题来源 | 文档大纲 + 文本匹配 | 字号启发式 | Tika 的 XHTML 输出不带字号，拿不到 |
| 入库事务 | 补偿删除 | `@Transactional` | 向量化要几分钟，不能让数据库连接被占那么久 |
| 表格行切分 | `standalone` 标记 | 伪装成标题 | 会让 `heading_path` 出现「第 3 行」这种假结构 |
| 向量列类型 | `float[]` + TypeHandler | `String` | String 时编译器拦不住维度错误 |
| 数据库同步 | 渲染成 Markdown 落盘 | 内存字符串直送 | 入库路径会分叉成两条 |
| 「结果稳定」的判据 | 只看 ID 序列 | 连分值也比 | 向量化本身有 3e-4 漂移，比 double 会永远报不稳定 |
| 中文关键词检索 | bigram + `ts_rank` | `pg_trgm` | 实测 4 条正确切片全部并列 0.3333，没有排序能力，对 RRF 等于废掉这一路 |
| 中文关键词检索 | bigram + `ts_rank` | `pg_jieba` / `zhparser` | 要自建 Docker 镜像编译，失败会阻塞整个阶段；换分词器的入口已留好 |
| MCP Client 连接 | 每次重新握手 | 长连接复用 | 2 小时 TTL 是**一定发生**的，长连接要处理重连/探活/并发；本机回环下多两个 RTT 是毫秒级 |
| MCP 依赖 | `mcp-core` + `mcp-json-jackson2` | 聚合包 `mcp` | 聚合包会拖进 **Jackson 3**，而本项目是 Jackson 2；共存不报错，但两个 ObjectMapper 几年后没人说得清哪个在生效 |
| 售后政策工具的形态 | **结构化注入 KB 路径** | 做成第四个 MCP 工具 | 「退货要几天」是**确定性问题**，让模型决定要不要查表等于把确定性变成概率 |
| 售后政策工具的备选路 | 结构化注入 | 新增叶子 `AFTER_SALE.POLICY_LOOKUP` | 会让分类 prompt 多一个选项 → 5.2 和 5.4 的基线都要重跑 |
| `structured_facts` 的粒度 | **叶子** | 顶层（对齐 `retrieval`） | `PROMOTION` 里只有价格保护需要它 —— 顶层粒度只能要么全给要么全不给 |
| 硬数据带哪些字段 | **只带天数** | 连 `conditions` 一起带 | `conditions` 已经在知识库里（实测 12 条切片），带进来就是让 prompt 有两份一样的文字 |
| 硬数据在 prompt 里的位置 | **摘要之后** | 摘要之前（它更稳定） | 判据不是「谁更稳定」是「谁更常在」；摘要是每轮都有，硬数据只有一类问题才有 |
| 硬数据与「检索为空」的关系 | **拼进固定段，检索为空时仍在** | 拼进资料段 | 知识库一条都没召回时，那几行天数恰恰是最需要的 |
| `query_inventory` 的匹配面 | **只匹配商品名** | 加 `OR 品牌 OR 类目` | 品类词会命中几十个商品再返回前 3 个 —— 那是按 id 排的随机结果，却看起来像答案 |
| 查不到商品时的输出 | **一句「没找到」** | 「你是不是想找…」+ 候选清单 | 模型会从候选里挑一个报给用户，而用户问的是另一个东西 |
| 同名商品的区分 | **正文总是带 `product_no`** | 只在检测到重名时才带 | 正文形状不能随数据变 —— 它关系到截断位置和前缀缓存 |
| 券「可用」的判据 | **status 与时间两个条件的合取** | 只看 `status == 1` | 刷状态的定时任务可能有延迟；报一张用不了的券，用户不会再信这个助手 |
| 券 `expired_at` 为 null | **视为不过期** | 视为已过期 | 两种错的代价不对称：前者被下单拦住，后者把真券**藏起来**，用户无从发现 |
| `SeedRunner` 的幂等粒度 | **按表** | 开头一个总开关 | 总开关在「只有一张表缺数据」时什么都不补，而那正是补种子的常见场景 |
| 用户券的随机流 | **独立的第二个 `Random`** | 共用一条流 | 按表幂等之后有两条路径，共用流会让同一份代码产出两套数据 |
| 工具调用探针 | **走完整 MCP 客户端链路** | 直接调工具 Bean | 后者跳过 schema 校验、身份注入、会话握手 —— 拿到的不是模型拿到的东西 |
| 探针的断言基准 | **「回答里的东西工具确实说过」** | 「回答里有某个词」 | 后者被模型的措辞绑架（5.8 的「没找到 → 没查到」） |
| 工具清单缓存 | 不缓存，每次拉 | 缓存 N 分钟 | 与 ADR-059 保持一致；缓存会引入「新加的工具没生效」这个新状态 |
| 工具结果失败 | 喂回模型 | 抛异常 / 静默降级 | 一个可选功能的故障不该让整个问答变成「服务内部错误」 |
| 工具名对不上 | 把服务端原话喂回去 | 自己写一句「工具调用失败」 | 5.7 那句话本来就是**写给模型看的**，转一手就磨掉了有用信息 |
| 多轮的 route | 覆盖（用最后一轮） | 保留第一轮 / 记全部 | 产出最终回答的是最后一轮；前面降过级的事在 `degradation_events` 里看得见 |
| 多轮的 cost | 逐轮算好再相加 | 总 token × 最后一轮单价 | 降级时两轮单价不同，重算会给出一个看起来合理但错的数 |
| `qa_log` 工具列 | 加 `tool_calls` | 只打日志 | 不加的话「工具答错了」和「工具没被调用」在数据上完全一样 |
| `qa_log.tool_calls` 索引 | 不加 | GIN 索引 | `qa_log` 是写入最频繁的表，而这一列只在分析路径上；同 `retrieval_detail` |
| 身份来源 | 请求头（与 `/mcp` 同名） | 请求体字段 | body 是调用方随便填的；两个来源不一致时以谁为准是个新问题 |
| 无身份时 | 一句实话，不调模型 | 401 / 让模型自由发挥 | 只有工具那条路需要身份；让模型发挥的唯一素材就是通用规则，也就是编 |
| 工具轮次上限 | 限制「能带工具的轮数」 | 限制模型调用总次数 | 后者会让「最后一次调用没有工具可用」，模型只能对着已有信息硬答 |
| 最后一轮 | 撤掉工具，强制作答 | 继续带工具 | 否则模型可以再要一次工具，而我们没有轮次可跟 —— 返回一个**没有正文的 tool_calls** |
| 5.8 的范围 | 只接非流式 | 两条路径一起接 | 决策轮本来就必须非流式（要拿全参数才能执行），差别只在最后一轮；先在最干净的路径上验完 |
| 中文关键词检索 | bigram + `ts_rank` | 单字 + `plainto_tsquery` | AND 语义下中文查询实测命中 0 行 |
| 词元重复 | 保留（记词频） | 去重 | 去重让 `ts_rank` 分数全部并列，排序退化成「按 id 排」 |
| 单字词元 | 丢弃 | 保留 | 实测「元」出现在 12% 的切片里，零区分度、纯噪音 |
| tsvector 的来源 | 生成列 | 表达式索引 | 表达式差一个引号就静默退化成全表扫描 |
| 分词逻辑的位置 | Java 侧 | SQL 函数 | 要能单测；且生成列不能引用生成列，SQL 方案在结构上走不通 |
| 检索并行 | 有界平台线程池 | 虚拟线程 | 无界 = 没有背压，阶段 6 限流到位前不安全（同 `sseExecutor`） |
| 检索失败 | 降级为裸聊 | 抛异常 | 用户至少能拿到基于模型自身知识的回答，比 500 好 |
| 重排失败 | 回落 RRF 顺序 | 抛异常 | `RerankClient` 无降级链，一次 429 就能让整次请求失败 |
| 检索上下文注入 | 拼进 systemPrompt | 给 `ChatRequest` 加字段 | 会让 client 层知道「检索上下文」这个概念，耦合方向错误 |
| 评测集标注 | 原文锚点 | 硬编码 chunk_id | BIGSERIAL 换台机器就失效，且**不报错**，基线静默漂移 |
| 文档类型的来源 | 语料清单逐文件声明 | 扫描时统一传 `?docType=` | 整个目录一个类型，18 份里错了 4 份，而错标只表现为「某类查询永远返回空」 |
| 文档类型的来源 | 语料清单逐文件声明 | 文件名启发式 | 启发式对不认识的名字**静默给默认值**，加个文件就又一次安静地标错 |
| 清单缺文件时 | WARN + 回落参数 | 抛异常 | 向后兼容：删掉清单应仍按老方式工作 |
| 清单格式错误时 | 抛异常 | 静默忽略该字段 | 静默忽略 = 让作者以为它生效了 |
| 语料生成物的字节 | 钉死时间戳（确定） | 每次写入当前时间 | 哈希每次都变 → 去重静默失效 → 重扫再灌一遍并**真的花向量化钱** |
| 时间戳的钉法 | 生成后重写 OOXML 包 | 逐库设属性 | 实测两个库都不可靠：zip 条目时间戳没开关，`core.xml` 的 `modified` 被 openpyxl 覆盖 |
| PDF 确定性 | `rl_config.invariant` | 手工改 `/CreationDate` | reportlab 自带该模式，就是为可复现构建设计的 |
| 评测集 gold | **多答案** | 每题一个正解 | 语料里同一规则被多份文档覆盖，单答案 MRR 会把正确答案记成「变差」 |
| 补全 gold 的依据 | 只读切片文字判断 | 参考系统排序结果 | 拿系统输出拟合标准答案 = 评测失去意义（反例：B-013 刻意保持单答案） |
| 意图树顶层切法 | 业务语义（用户想干什么） | 答案来源（知识库/工具） | 按答案来源切，意图就退化成路由目标；且会把「订单到哪了」和「怎么退货」分到两个顶层 |
| 检索策略的位置 | 挂在叶子层 | 挂在顶层 | 顶层回答「用户想干什么」，叶子才回答「去哪几张表里捞」 |
| 叶子声明的 `doc_types` | **答案全集**（可重叠、可多个） | 过滤主类型（单值） | 全集能换出一个可自动验证的验收标准；主类型在 B-011 掉分时说不清是树错还是过滤太激进 |
| 主类型错误提示 | 报出「多出来的是哪些」 | 只说「不匹配」 | 要让人拿着报错就能去改 YAML，而不是回头翻语料 |
| 兜底意图的归属 | 不占 5 类名额 | 算第 5 类 | 兜底类的 ground truth 只能是空集，混在一起两个性质相反的错会互相抵消 |
| `eval_question.intent` | 存**叶子**码 | 存顶层码 | 顶层可由树 roll-up 得出，反过来推不出来；顶层错和叶子错是两种不同的错 |
| 评测集 `intent` 字段 | 必填 | 缺则写 `UNCLASSIFIED` 哨兵 | 哨兵值的理由是「意图树还没定义」，定义之后理由消失，留退路 = 留一个没意义的逃生口 |
| 意图树缺文件 | **抛异常，起不来** | WARN + 回落 | 没有「不比失败更差」的选项 —— 回落只能等于把所有问题判成同一类 |
| 意图树畸形（运行中） | 打 ERROR + 沿用旧树 | 抛异常 | 配置打错一个字母就让问答接口 500 是可用性故障；但必须留痕（`lastRefreshError`） |
| 意图树的读取 | 缓存 + 修改时间热加载 | 每次读文件 / 只在启动读 | 每次识别都要用，读文件太贵；只在启动读则改一句示例要重启，阶段 7 的 A/B 会很难受 |
| 业务意图数量 | 代码里钉 `= 5` | 从 YAML 读多少算多少 | 它是 7.2 指标分母的契约，「悄悄变成 6 类」必须可见 —— 和 `doc_type` 抄一遍 CHECK 约束是同一手法 |
| 单文件上传的文件 | 暂不校验 | 加 `data/corpus/` 检查 | 阶段 3 的 doc 208 就是这么混进来的（文件名骗人 + doc_type 错 + 19% 噪声），但当前阶段优先级不高，先记录在案 |
| 分类粒度 | **行为不同的最小集合** | 树的全部 16 个叶子 | 工具叶子的 doc_types 都是空集，5.4 对它们行为一样；区分它们只给准确率添噪声 |
| 分类用的 few-shot | 独立文件，**结构上**不含评测题 | 用树里的 `examples` | 那 55 条与评测题重合 18/20，用了就是在测「照抄能力」 |
| 防泄漏的做法 | 字段层面不给 + 测试断言 + 反证测试 | 写在注释里提醒 | 提醒靠人记；不给字段则「写错」在类型层面不可表达 |
| 分类目标缺样本 | **抛异常** | 打 WARN 继续 | 缺样本的目标不会被跳过，它会让准确率掉一点而**没有任何信号** —— 修它只要几行 YAML |
| 分类 prompt 的内容 | 只有判据 + 样本 | 连 `doc_types` 一起给 | 会诱导模型按「答案在哪几个文档里」分类，分类体系从用户视角漂移成实现视角，而**准确率上看不出来** |
| 兜底的提示语 | 「都无关时才用」 | 「拿不准时用」 | 后者让「模型没把握」和「问题确实无关」在数据上分不开，而 5.3 的澄清反问要靠前者 |
| 模型返回的解析 | 无害清洗后**精确匹配** | 在回复里搜「像 code 的单词」 | 后者会把「模型在胡说、话里碰巧出现一个 code」当成成功，而两者修法相反 |
| 分类失败后 | **不重试，回落「不过滤」** | 换个模型重试 | 分类是高频附加调用，退化成阶段 4 行为用户无感；重试只叠延迟，正确率没保证 |
| 失败时的 `intent` 取值 | 存 **null** | 猜一个最可能的 | 同 ADR-010：拿不到就记 NULL，猜的值会让这一列不可信 |
| 分类的输出长度上限 | 用全局默认 2048 | 给 16（反正只输出一个 code） | P0 是推理模型，额度给小吃光后 `content` 返空串 —— 表现为「分类永远失败」而无异常 |
| 分类的 temperature | 0.0 | 不设 | 不主动往方差里再加东西。但**它不等于确定性**，实测 8 次出现过 7:1 分裂 |
| 非确定性的处理 | 文档化 + 重复测量 | 立刻上「多次采样取多数」 | 那是 5.3 的设计决定（采样一致度正好是置信度来源），现在做等于替它拍板 |
| 意图准确率的指标 | Top-1 **和**检索范围两个都报 | 只报 Top-1 | 实测两者是 95% vs 100%（Top-1 于 2026-09-20 复测为 90%，差值仍在）：相邻叶子分歧对检索零代价，只报 Top-1 会把它和致命路由错误平均成一个数 |
| 澄清的触发信号 | **信息充分性**（分类直接判） | 分类置信度阈值 | 三种信号（logprobs / 采样一致度 / 自报）实测**与「该不该澄清」全都无关**，采样一致度甚至反相关 |
| 置信度的落库 | 两列**继续留 NULL** | 存采样一致度 | 未校准的数字早晚被当阈值用；而实测证明它反相关 —— 存反相关的值比不存更坏 |
| logprobs 的使用 | **不用** | 当分类置信度 | 全库都是 -0.000，零区分度；且它看不见推理内核的浮点噪声 —— 那个翻了 1/8 的问题它报 24000:1 |
| 非业务分支的建模 | `role` 枚举（BUSINESS / OUT_OF_SCOPE / CLARIFY） | 两个布尔量 | 两者互斥，布尔量可以同时为真而那个状态无意义；枚举让「三选一」在类型层面成立 |
| 「信息不足」的去处 | 独立 role + 独立分类目标 | 塞进 OUT_OF_SCOPE | 用户问「那个怎么样」会收到「我只处理导购和售后问题」—— 把「答不了」冒充成「不该答」 |
| few-shot 样本的覆盖面 | **双腿**（有指代/无指代 × 能/不能回答） | 只放「指代 → 澄清」 | 单边样本让模型学成「见『这个』就澄清」，把「这个有保修吗」也拿去反问 |
| 澄清路径 | **短路**（不检索、不生成） | 走完整链路再反问答 | 走完再澄清，那几百毫秒和向量化的钱纯属白花；实测短路 559ms vs 正常 3~8s |
| 「短路」的验证方式 | **调用次数** | 看返回的文本 | 「检索了、生成了一堆、最后丢弃」的实现返回的文本和真短路**一模一样** |
| 澄清行的检索列 | 写 **NULL** | 传空 trace（得到空数组的 JSON） | 空 trace 序列化后与「检索跑了但两路都没召回」**逐字相同**，而两者排查方向相反 |
| 澄清的 `qa_log.status` | **新增 3** | 归入 1（成功）或 2（失败） | 归 1 会让答案质量指标给一句反问打分、检索指标把它算成没召回到；归 2 会把「正确识别出该反问」记成「模型挂了」 |
| status 的取值 | Java 常量 `QaLog.STATUS_*` | 代码里写裸数字 | 写错不报错，只会让阶段 7 的筛选悄悄偏 |
| 分类失败时 | **不澄清**，照常检索 | 也去反问用户 | 把「我分不清」伪装成「你没说清」，等于把自己的故障算到用户头上 |
| 意图定向过滤的形态 | `doc_type` **硬过滤（SQL）** | 软加权 / 不做 | gold ⊆ declared 是 20/20，所以硬过滤**可证明**不会丢召回；软加权把这条可验证性质丢掉了 |
| 过滤条件的下推位置 | **SQL 的 WHERE** | 查出来再在 Java 里筛 | `{2,4}` 只占全库 4.1%，「先取 20 条再筛」平均只剩不到 1 条 |
| 过滤条件的参数形态 | **数组字面量 **`"{2,4}"` + `CAST` | `<foreach>` 拼 `IN (?,?)` | 前者只占一个参数位、SQL 文本恒定，计划可复用；后者每种集合大小都是一条新 SQL |
| 过滤的决策权 | **在 `RetrievalPipeline`** | 在调用方 | 调试探针和线上必须走同一套规则，否则探针看到的不是线上跑的东西 |
| 「值不值得过滤」判据 | **池子绝对大小 < vector-top-k** | 收窄倍数 ≥ 阈值 | 实测倍数 1.1×~328×，而**倍数越大越危险** —— 判据方向和风险方向相反 |
| 池子计数查询 | `countByDocTypes` 只按 `deleted` + `doc_type` | 再带上各路的守卫条件 | 它只做一次量级判断；带上守卫会把「池子小」和「索引没建好」两种原因混成一个数 |
| 范围参数的归属 | `RetrievalOptions` record（构造期归一） | 多加一个 `List<Integer>` 形参 | 裸 List 表达不了「没声明」和「声明了空集」的区别，而这两者语义不同 |
| 过滤后一无所获 | **全池重查一次** | 直接返回空上下文 | 用户不该因为「过滤后没东西」拿到裸聊回答。★ 正常不触发，是备用闸 |
| 回落时 trace 的写法 | **覆盖**两路结果 | 追加/保留第一次的空结果 | 保留空结果会让 JSON 自相矛盾（`vector_hits` 空但 `final_top_k` 非空），且看起来像 bug |
| `applied` 的语义 | **最终**用了过滤吗 | 打算用吗 / 曾经用过吗 | 必须和 `vector_hits` 那几格描述同一件事，逐格自洽的 JSON 才能单独拿出来解释 |
| `doc_types: []` 的解读 | **不限制** | 什么都不匹配 | 解读成不匹配会让三个工具意图在 5.7 前退化成裸聊，而裸聊会**编一个订单状态出来** |
| 越界 `doc_type` 的处理 | 构造期剔除 | 拼 SQL 时转义 / 直接放行 | 剔除后成空集 = 不限制；放行则 `ANY('{22}')` 恒 false，症状是「永远检索不到」 |
| `filter` 段的出现方式 | **恒定存在**（第 6 个 key） | 非空才出现的附加字段 | 「这次过滤了没有」是检索的固有属性；「key 不在 == 没过滤」是会让脚本静默失效的隐式约定 |
| `retrieval_detail` 的扩展 | **加法式**（前 5 段一个不动） | 重排/重命名现有 key | 加法式不需要重跑历史基线 —— 这是它和「改结构」的本质区别 |
| 会话历史给谁用 | **只给生成** | 也进分类 prompt | 会动到「分类器只看这一句话」这个前提，5.2 的意图准确率和 5.4 的 20/20 都建立在它之上 |
| `ClarificationDecider` 的 history 参数 | **保留但恒空**（注释改成实情） | 真的用它消解指代 / 删掉 | 它是纯判断器，**消解不了指代** —— 那个预留的位置本来就是错的 |
| 5.3 那条 `isTrue()` 断言 | **保持 `isTrue()`**（改注释） | 改成 `isFalse()` | 它原来的预言被 ADR-046 的取舍推翻了。现在钉的是「已知的、有意的局限」 |
| 窗口大小 | **按轮数（10）** | 按 token 数 | 实测 10 轮才 1200 字，上限根本碰不到；而不准的 token 估算器一旦被当阈值用，咬人的方式是「历史偶尔少一轮」 |
| 读历史的位置 | **在落用户消息之前** | 读时排除本轮那条 | 后者要把消息 id 贯穿三层换 1ms，不值；顺序本身就是最好的约束 |
| 历史读失败时 | 退化成**无上下文的一轮** | 让问答失败 / 抛异常 | 同 ADR-022：历史读不出来不该让这次问答 500 |
| 孤儿用户消息 | **丢弃** | 保留 | 连续两条 user 消息在 OpenAI 兼容协议里是畸形输入，而 400 属于「不降级」那一类，整次问答直接失败 |
| 孤儿处理时的取数 | **多取一条** | 只取 `2×maxTurns` | 不多取的话窗口变成 9.5 轮，少的那半轮是最早的那条 —— 表现为「想不起上上轮说过什么」 |
| 单条历史消息的超长处理 | **静默截断 + WARN** | 不截断 / 抛异常 | 防的是 max-tokens 被调大后 prompt 被悄悄撑到几十 K（同 `MAX_CHARS_PER_CHUNK`） |
| 陈旧事实的处理 | **加一句「以本次资料为准」** | 不加 | 历史里的答案可能已经错了，而模型天生把上文当事实复述 —— 且这种错读起来很连贯 |
| 历史约束的出现时机 | **只在真的有历史时** | 恒定出现 | 给一轮问答配一句「历史仅供参考」是纯噪音，还会稀释其他指令的权重 |
| 历史约束的位置 | **固定指令段（可变资料之前）** | 和「回答要求」并在一起 | 它是关于整场对话的常设规则，不是「上面那段资料」的使用说明；且留在固定段里才可缓存 |
| 摘要压缩的执行时机 | **异步**（生成完、响应返回之后） | 同步阻塞 / 懒压缩 | 实测最慢一次 **41.5 秒**（P0 失败降级到 P1）。同步的话一次普通问答会从 2 秒变 43 秒 |
| 摘要线程池的并发度 | **单线程（core 和 max 都锁 1）** | 多线程 | 同一会话两次压缩会基于同一个旧游标，一个 CAS 胜出、一个白花一次 LLM 调用 |
| 队列满时的摘要任务 | **丢弃 + INFO 日志** | CallerRuns / 阻塞重试 | 压缩**自愈**：游标不动，下次连这段一起压。和 ingest 的 CallerRuns 相反，因为入库非幂等 |
| 摘要和窗口的接缝 | **游标锚在「窗口起点 - 1」** | 溢出几条压几条 | 后者让终点和窗口各走各的，接缝会出现**永久空洞**且无任何报错 |
| 接缝对不齐时的方向 | **宁可重叠** | 宁可空洞 | 重叠是模型看两遍（无害）；空洞是消息永远消失 |
| 接缝锚点 W 的定义 | **单一出处**（`ConversationMemory.windowStartId`） | 摘要层各写一份 | 两份「碰巧一样」的表达式正是会有消息永久消失的那种耦合 |
| 孤儿用户消息丢几条 | **末尾全部连续的** | 只丢最新那一条 | 只丢一条时，**连续两次失败之后会话永久答不出话**（400 属「不降级」） |
| `summary_level` | **恒为 1，单行滚动** | 真的做 1+2 两级 | 两级解的是「极长会话」，而真实会话最长 10 轮；为一个没发生过的规模做两层是过度设计 |
| `summary_level = 2` 那一档 | **保留但写明是死列** | 删掉 | 删列要动 V5 迁移，而 V1–V5 一个字都不能改（`validate-on-migrate: true`） |
| `chat_summary.token_count` | **恒写 NULL** | 写 `usage.completionTokens` | 后者**含推理 token**（实测占输出 87%），存进去会让这列系统性偏大 —— 一个「有值但用途错」的列比 NULL 更危险 |
| 摘要生成的成本 | **只在日志里**（不进 `qa_log`） | 塞进下一轮的 `qa_log` | `qa_log` 的语义是「一次问答」，摘要是记忆维护。这是继 4.8 之后的第二个显式例外 |
| 摘要长度的控制 | **prompt 里的丢弃优先级 + 超预算时换强制压缩** | 只靠硬上限截断 | 截断是从尾部随机切的；给出「哪些可再生、哪些不可再生」才能让模型自己选 |
| 强制压缩指令的写法 | **带具体状态**（「你上次超了」） | 静态的「请务必不超过 N 字」 | 实测静态要求被当耳旁风；带上状态只是**部分**有效（1066→936），但方向对 |
| 硬上限截断的方向 | **切尾部** | 切头部 | 摘要按时间顺序写；尾部更可能是**可再生的**助手回答，头部是**不可再生的**用户事实 |
| 摘要进 prompt 的位置 | **固定指令之后、可变资料之前** | 资料之后 | 它是**半固定**的（每 N 轮才变一次），排在资料前能让这段缓存前缀大多数轮次命中 |
| MCP 协议版本 | **2025-11-25**（跟 SDK 对齐） | 规范仓库里更新的 2026-07-28 | SDK 2.0.1 不认识它，声明了只会每次握手都协商降级 |
| MCP 传输方式 | **Streamable HTTP 单端点** | stdio | Server 要连库、跑迁移、读 Spring 配置，做成子进程这些都得再来一遍 |
| MCP 响应格式 | **`application/json`** | SSE 流 | 我们没有任何服务端主动推的消息；SSE 只会增加解析层和误解 |
| MCP 身份来源 | **传输层 `McpToolContext`** | 工具参数 `user_id` | 参数是**模型填的** —— 一段提示注入就能查别人的订单，且代码看起来全对 |
| 未声明的工具参数 | **拒绝（-32602）** | 静默忽略 | 忽略会让模型以为自己猜对了，下次继续猜；拒绝还能顺带把 schema 不一致变成响亮报错 |
| 参数类型不匹配 | **报错**，不转换 | 顺手转成字符串 | 宽松转换会让「模型发错类型」伪装成「订单不存在」，它永远学不会改 |
| 会话 | **做，且存身份** | 不做（规范说 MAY） | 它强制了握手顺序，也是「这个 session 是谁」的凭据 —— 自增 ID 可枚举，必须 UUID |
| 会话与请求头身份不一致 | **403 拒绝** | 按其中一个来 | 静默按一个来等于让会话成为身份跳板 |
| `Origin` 头缺席 | **放行** | 拒绝 | rebinding 必须由浏览器发起，而浏览器总会带 Origin；拒绝只会挡住合法 SDK |
| `isError` 的判据 | **工具有没有给出答案** | 规范字面（含 business error） | 「查无此单」标成错会让模型去为系统故障道歉，而重试变不出那个订单 |
| 工具 schema 的写法 | **Java `ToolField` 常量（单一来源）** | YAML 声明 + Java 执行器 | 两处各写一份的漂移是静默的 —— 5.6 的接缝锚点刚踩过一次 |
| 工具定义的实现方式 | **手写 Java 类** | 注解 + 反射 | 那是在重写 5.8 要用的官方 SDK，且反射让「参数从哪来」不能逐行读 |
| 结构化输出的防御性拷贝 | **`Collections.unmodifiableMap`** | `Map.copyOf` | 后者拒绝 null，而可选字段的值合法地就是 null；NPE 还抛在构造函数里，带偏排查方向 |
| `tools/list` 分页 | **不分页** | 实现 cursor 分页 | 规范说 MAY；工具个位数时一次返回对模型友好得多 |
| 工具重名 | **启动即崩** | 后者覆盖前者 | 覆盖会让同一工具名两次启动行为不同，且没有任何日志 |
| 分布式信号量实现 | **手写 Lua + 成员型名额表** | Redisson `RSemaphore` | 计数型表达不了「给单个名额设过期」；且「名额被谁占着」不可见，出问题时没有线索 |
| 名额的数据形状 | **ZSet 成员，score = 过期毫秒** | 一个计数 value | 自描述：能自己清自己，不需要外部信息判断死活 |
| 释放的语义 | **只移除自己 + 广播** | 释放 + 提拔队首 | 释放者判断不了队首死活；提拔幽灵 = 名额被占着直到 TTL，直接威胁「无死锁」 |
| 排队公平性 | **近似（谁先重试到谁赢）** | 严格 FIFO（只给队首发名额） | 死队首会阻塞整条队列到 TTL —— 「可能不公平」比「可能死锁」好 |
| 队列的 score | **`INCR` 单调序号** | 毫秒时间戳 | 同毫秒入队时 `ZRANK` 由 UUID 字典序决定 = 随机；且重抢换 score 会让位置乱跳 |
| 续期的写法 | **`renew.lua`：判定成员还在才延长** | 两条普通 `ZADD` | `ZADD` 会创建成员 —— 用过期快照把已释放的名额复活，真机实测抓到过 |
| 「谁该被续期」的数据源 | **进程内的 `LocalPermitRegistry`** | Redis 里存一份实例表 | 「哪个进程还活着」是进程局部知识；做成分布式反而要引入「谁来清理死实例」 |
| 续期失败的两种处理 | **分开（连不上→不放弃；已失去→记 WARN 不抢回）** | 合并成一条 | 合并会在「已失去」上做出「抢回来」的动作 —— 那才是真的超卖 |
| 排队线程池的 `queueCapacity` | **0（`SynchronousQueue`）** | 可配 | 非 0 会让等待任务静止在执行器队列里，没人能推位置 → 用户看到空白页，且不报错 |
| 排队的位置 | **`ChatService` 之外** | `ChatServiceImpl` 里（写用户消息之前） | 排队超时会在库里留下孤儿用户消息 → 连续两次后会话永久答不出话（ADR-049） |
| 唤醒机制 | **Pub/Sub + 轮询兜底** | 只用 Pub/Sub | 消息丢了会永久卡住；轮询是正确性来源，Pub/Sub 只降延迟（实测只省 2.5% 时间、多花 12% 往返） |
| 订阅频道的粒度 | **一个公共频道 + 本机惊群** | 每请求一个频道 | 动态增删 listener 带锁，高并发下是瓶颈且漏删即泄漏 |
| 订阅容器的重建 | **每次全新容器 + 监督循环** | 复用容器靠库的「无限重试」 | 实测：`start()` 在 subscribe 前就置 `started=true` 且失败不重置 → 冷启动失败后订阅永久死亡 |
| 非流式的排队预算 | **30 秒** | 和流式一样 120 秒 | 必须比客户端自己的超时先发生，否则那句「前面人太多」永远送不到 |
| 排队被拒的 HTTP 码 | **503 + `Retry-After`** | 500 / 200 + body.code | 队列满不是故障，是限流正常工作的证据；报成 500 会让人去查一个不存在的 bug |
| 跨线程传递异常 | **剥掉 `ExecutionException`** | 直接往外抛 | `@ExceptionHandler` 按类型匹配，裹一层就全落到兜底 500 —— 而那些规则白写了 |
| 客户端断开的处理 | **专用 handler，DEBUG + 空响应体** | 落到兜底分支 | 一次关页面 = ERROR + 60 行堆栈 + 「异常处理器自己又抛了」；它每天几千次，会淹没真故障 |
| 拒绝原因的判据 | **`error_msg` 的原因串** | `queue_ms` 的数值 | 实测 `queue_ms=0` 在「队列满」和「池满」下都出现过 —— 它判不了（同一列三个「总是」全错） |
| 探针造僵尸的方式 | **直接写 Redis，不登记本地表** | 调 `tryAcquire` 造 | 登记了就会被同进程心跳续期 → 测试自己让自己通过 |
| 探针的队列位置断言 | **先 leak 满名额把队列冻住** | 边排队边读位置 | 不冻住的话「对不上」既可能是 bug 也可能是竞态，而两者修法相反 |
| 评测流量怎么标 | **`qa_log` 上两个显式标记** | question 文本 JOIN | 文本 JOIN 两个方向都**静默**错：真实用户撞题被算进评测 / 题目改写一字就静默退出评测 |
| `retrieval_detail` 怎么扩 | **加法式加 `sizes` 段** | 调大 `fused` 的长度上限 | 改上限会让所有历史 JSON 的语义变掉；而缺 `sizes` 是**事后不可辨**的 |
| 延迟报几段 | **五段**（含「未归类」） | 四段 | `rerank ⊂ retrieval` 是包含关系不是并列；意图分类 p50 823ms 进了 total 却不在任何一列 |
| 多轮题放哪 | **单独 run_id / 单独分母** | 加 `is_multi` 在同一 run 里过滤 | 会在一个 runId 下挂两套分母，而本阶段的纪律是「每个数字都要能写出分母」 |
| 新开关的 `Reason` | **新取值 `DISABLED_BY_CONFIG`** | 复用 `no_declaration` | 复用会让已写进文档的 `probe_kb --docTypes` A/B 手法**静默变成空操作** |
| 报告里的解读句 | **判据的函数** | 硬编码数字 | 硬编码的数字会随数据过期，且**没有任何症状**（本项目已靠这条防住一次算错） |
| `--coverage` / `--refresh` | **只读，不写交付物** | 走和正常生成同一条 `main()` | 一个只读命令写文件是静默的，而且它的破坏恰好发生在你最没防备的时候 |
| 诊断命令的标志 | **互不叠加、各自独立** | 允许拼接 | 拼接会静默短路 —— 实测 `--refresh --selftest` 只跑了自检，一个字节都没刷 |
| 报告缺一节时 | **退化成带真实原因的三态** | 渲染成「这一期没有」 | 「读不到」是关于**我们输入**的事实，「没有做过」是关于**世界**的事实 |
| 错误分支的措辞 | **只陈述核实过的** | 写「多半是 X」 | 两者在报告里长得一样，而前者猜错时**会把读者指向反方向**（实测两次都猜错） |
| 测试里的「不排序的样子」 | **`LinkedHashSet`（顺序可控）** | `Set.copyOf(...).toString()` | 后者是 JDK 桶序 + 每 JVM 随机 SALT → 那个断言自己约 50% 概率红 |
| 评测流量在哪一层排掉 | **读侧也排（列表接口）** | 只在写侧打标记 | 标记只有「写全 + 读时记得用」两个条件都成立才有意义；只做前半句它就是个没人看的列（ADR-086） |
| 单会话消息要不要也排评测 | **不排**（故意不一致） | 和列表保持一致 | 列表是**浏览**，精确键查找不是 —— 后者回 404 会让人以为数据丢了（ADR-086） |
| 技术面板的数据源 | **新写的只读白名单端点** | 复用 `/api/debug/*` | 那些是 `@Profile("local")`，生产不存在；且能烧额度、能改状态（ADR-087） |
| 对外状态端点的字段 | **白名单**（写出来的才给） | 黑名单（除了 X 都给） | debug 的 map 加字段时会**自动**漏出去，且没有任何测试会红（ADR-087） |
| 判「字段在不在」的判据 | **`JsonNode.has()`** | `jsonPath(...).exists()` | 后者对「键不存在」和「键存在但是 null」给出**相同**答案 —— 实测当场红了一次（ADR-087） |
| 「一键启动全栈」怎么组织 | **Compose profile** | 合并进默认 `up -d` | 合并会让每次跑测试都顺手起应用容器；且 `up -d` 是 858 个用例和全部探针的前提（ADR-088） |
| 必需环境变量的校验放哪 | **消费它的那一层**（`application-prod.yml`） | compose 的 `${VAR:?}` | ★ Compose 会插值**所有**服务不管 profile —— 那会让「只起中间件」也失败，恰好破坏 profile 方案要保住的东西（ADR-088） |
| 应用容器要不要映射端口 | **不映射** | 映射 8080 | 映射了本地开发与容器部署就不能并存，而阶段 7 全部脚本假设 `localhost:8080`（ADR-089） |
| 文档放行的实现层 | **文件系统**（镜像里逐个 COPY） | Nginx 配置里的路径白名单 | 后者依赖「用解码前还是解码后的 URI 匹配 location」这个会变的细节；前者对任何 URL 写法都成立（ADR-090） |
| 开发期的文档白名单 | **和生产同源** | 开发期宽松一点无所谓 | 宽松 → 本地能开、上线 404；更严 → 本地测不出来、上线才泄露（ADR-090） |
| 报告页读文件还是读快照 | **运行时读** | 复制进 `frontend/public/` | 快照会让「重跑报告」和「页面上的数字」之间多一个需要记得做的同步步骤，而忘了做**没有任何迹象**（ADR-090） |
