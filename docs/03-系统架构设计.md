# 系统架构设计

> 本文档描述系统的分层结构、模块职责与端到端数据流。
> 阶段 2（模型接入层）已实现，其余部分随对应阶段补全。

---

## 一、分层结构

```
┌─────────────────────────────────────────────────────────┐
│  controller/          对外 HTTP 接口                      │
│  · 只做参数校验 + 响应封装，不写业务逻辑                   │
│  · 唯一额外职责：SSE 的线程调度（属于 Web 层）             │
└────────────────────────┬────────────────────────────────┘
                         │ 依赖
┌────────────────────────▼────────────────────────────────┐
│  service/             业务编排                            │
│  · 串起「建会话 → 存消息 → 调模型 → 写 qa_log」           │
│  · 不感知 HTTP / SSE / 具体供应商                         │
└────────────────────────┬────────────────────────────────┘
                         │ 依赖
┌────────────────────────▼────────────────────────────────┐
│  client/          ★ 模型接入层（全项目唯一发模型 HTTP 的地方）│
│  · LlmClient / EmbeddingClient / RerankClient            │
│  · ChatModelRouter：降级链 + 熔断                         │
│  · 手写 HTTP，不用 SDK                                    │
└────────────────────────┬────────────────────────────────┘
                         │ HTTPS
┌────────────────────────▼────────────────────────────────┐
│  DeepSeek 官方 / 硅基流动                                 │
└─────────────────────────────────────────────────────────┘
```

**依赖方向是单向的**：`controller → service → client → 外部`。
`client` 不知道 `service` 的存在，`service` 不知道 `SseEmitter` 的存在。
这条约束让每一层都能单独测试。

## 二、client 层详解（阶段 2 核心）

### 2.1 为什么只用一个实现类

DeepSeek 官方和硅基流动**都提供 OpenAI 兼容协议**：同样的
`POST /v1/chat/completions`、同样的请求体结构、同样的响应字段。

差别只有三样 —— **域名、密钥、模型 ID** —— 而这三样都是构造时注入的。
所以 `OpenAiCompatibleLlmClient` 一份实现就能服务两家。

这是本项目「双供应商」架构能用很低成本实现的原因。代价是
**两家协议的差异点必须逐个实测确认**，不能假设「兼容」就等于「完全一样」。
实测发现的差异见 §2.5。

### 2.2 三层配置结构

```
xbla.llm
├── providers    ① 连接：域名 + 密钥
├── models       ② 模型：真实模型 ID + 单价
└── chat-chain   ③ 策略：降级顺序
```

**为什么分三层**：供应商是「连接」、模型是「计价与协议」、链路是「策略」。
P1 和 P2 共用同一个硅基流动连接和同一个 Key，但模型不同。
混在一起写的话密钥要重复两份；将来给 P2 换供应商也只改一行 `provider`。

### 2.3 降级链与熔断

```
请求进来
   │
   ├─→ P0  deepseek-flash ──[熔断器 CLOSED?]──→ 调用
   │        ↑ 失败                                    │ 成功 → 返回
   │        └──────── 记录失败 ────────────────────────┘
   │
   ├─→ P1  deepseek-ai/DeepSeek-V3.2 ──[熔断器 CLOSED?]──→ 调用
   │
   └─→ P2  Qwen/Qwen3.5-9B ──[熔断器 CLOSED?]──→ 调用
                                                        │
                                              全失败 → 抛异常
```

**熔断器粒度 = 每个 (供应商, 模型) 一个**，名字就是 `chat-chain` 里的条目 key。
不按供应商做的原因：硅基流动上 P1 被限流时 P2 可能还是健康的，
按供应商做会把健康的 P2 一起拖下水。

**降级事件**通过 `ModelCallTrace` 收集器显式传递（不用 ThreadLocal —— 
流式场景下推送线程不继承请求线程的 ThreadLocal），最终写进
`qa_log.degradation_events`。

### 2.4 错误分类表 ★

这是整个降级策略的灵魂。做成枚举而不是散落的 `if-else`，
因为「哪类失败该降级」和「哪类失败该计入熔断统计」是两个正交的决策。

| 类型 | 触发 | 记熔断失败 | 降级 | 理由 |
|---|---|---|---|---|
| `AUTH` | 401/403 | 是 | 是 | Key 错了，换一家 |
| `QUOTA_EXHAUSTED` | 402 | 是 | 是 | 余额不足，**同家不同模型可能状态不同** |
| `RATE_LIMIT` | 429 | 是 | 是 | 限流，换一家立刻能成 |
| `SERVER_ERROR` | 5xx | 是 | 是 | 对方挂了 |
| `TIMEOUT` | 超时 | 是 | 是 | — |
| `CONNECT` | IO 异常 | 是 | 是 | — |
| `EMPTY_CONTENT` | 200 但正文空 | 是 | 是 | 推理模型吃光 max-tokens |
| `BAD_REQUEST` | 400/422 | **否** | **否** | 我们自己的请求有问题 |
| `CLIENT_ABORTED` | 用户关页面 | **否** | **否** | 不是供应商的错 |
| `PARTIAL_STREAM` | 吐字后中断 | 是 | **否** | 流式架构的硬边界 |

**两条最值得讲的**：

- **`BAD_REQUEST` 为什么不降级也不计熔断**：400 说明我们自己的请求体有问题，
  换一家会以同样方式失败。更关键的是，如果记成失败，连试三家就是三次失败，
  会迅速把所有熔断器推到 OPEN —— 结果是「一个我们自己写错的参数，
  让整个模型层看起来全挂了」，真正的 bug 被掩盖。
- **`CLIENT_ABORTED` 为什么单独分一类**：「往浏览器推送时抛 IOException」
  和「模型供应商出问题」在异常类型上长得一模一样。不区分的话，
  用户每关一次页面就记一次供应商失败 —— 几个人关几次标签页，
  一个完全健康的供应商就被熔断打开了。

> ⚠️ `QUOTA_EXHAUSTED` 是**测试跑出来的**，不是设计时想到的。
> 最初实现把「其余 4xx」一律归到 `BAD_REQUEST`，于是 402 被判成
> 「请求有问题」，整条降级链在那一档直接终止。详见 ADR-007。

### 2.5 实测出的两家差异

不能假设「OpenAI 兼容」等于「完全一样」。实测确认的差异：

| 项 | DeepSeek 官方 | 硅基流动 |
|---|---|---|
| `stream_options.include_usage` | ✅ 支持 | ✅ 支持 |
| usage 汇总 chunk 的 `choices` | `[{...}]`（带内容） | **`[]`（空数组）** |
| usage 字段形状 | 平铺 `prompt_cache_hit_tokens` | **同样平铺**（不只 OpenAI 的嵌套形状） |
| 402 余额不足 | — | **用 402 而不是 400** |

**`choices` 是空数组这一条最危险**：如果用数组 + `choices[0]` 去接，
会在**每个流式请求的最后一刻**抛 `ArrayIndexOutOfBoundsException`。
所以 DTO 里必须用 `List` 并做判空。

### 2.6 SSE 线程模型

```
[Tomcat 请求线程 T1]
   GET /api/chat/stream
   → 返回 SseEmitter(180_000L)
   → Servlet 异步启动，T1 立刻释放回池子     ← 不占用请求线程
        │
        ↓
[sseExecutor 线程 T2]  ← 专用线程池，见 AsyncConfig
   router.chatStream(...)  阻塞在 httpClient.send()
   每收到一个 delta → emitter.send()
        │
        ▼
[客户端] EventSource 逐字渲染

[Tomcat 线程 T3] 仅在 onTimeout / onError 回调时被唤醒
   · 只读标志位 + close 上游流
   · ★ 绝不调 emitter.send（它不是线程安全的，只有 T2 能写）
```

**三条硬性要求**：

1. **必须用专用线程池。** `CompletableFuture.runAsync` 不传 executor 会用
   `ForkJoinPool.commonPool()`，并行度只有「核数-1」。几个并发的阻塞式
   模型调用就能占满它，导致整个 JVM 所有依赖 commonPool 的功能一起僵死。
   现象是「模型好像变慢了」，真正的原因在完全无关的地方。
2. **`traceId` 用方法参数传，不用 ThreadLocal** —— T2 不继承 T1 的。
3. **Tomcat 异步超时默认 30 秒**，不显式设置会无声掐断所有长回答。
   `SseEmitter(180_000L)` + `spring.mvc.async.request-timeout` 双保险。

### 2.7 流式降级边界 ★

```
statusCode != 200 ─────────────────────→ 可以降级
statusCode == 200
  ├─ 首个 content 增量之前失败 ────────→ 可以降级
  └─ 已吐字后失败 ─────────────────────→ 不能降级
                                          记熔断失败 + 发 failed 事件关闭
```

**这是 SSE 架构的固有约束，不是可以优化掉的东西。**
用户已经看到前面吐出来的字了，换一家从头重来会让他看到
两段拼接起来的、前后矛盾的话。

实现上：`OpenAiCompatibleLlmClient.chatStream` 内部维护 `contentChars`，
失败时据此分类 —— 没吐过字按异常本身的性质分类，吐过了就是 `PARTIAL_STREAM`。
**分类发生在信息最全的地方**，router 只管读 `kind.isFallbackWorthy()`。

### 2.8 熔断器的耗时口径 = TTFB

一次 60 秒的**正常**长回答，如果把整个流的耗时喂给熔断器，
会触发「慢调用率」阈值 —— **熔断器在系统最健康、正在正常干重活的时候跳闸**。
这是最坏的反向优化：越努力服务，越容易被判成故障。

所以喂给熔断器的观测值是 **TTFB（首字节延迟）**。
正常情况 1-3 秒，超过 15 秒确实说明这家有问题。

### 2.9 成本计算

三档单价（元/百万 token）：`input`（缓存未命中）/ `cache-hit-input` / `output`。

- `reasoning_tokens` **不参与计价** —— 它是 `completion_tokens` 的子集
- **拿不到 usage 时 `cost` 落 NULL，绝不估算** —— `qa_log` 只增不改不删，
  编出来的数字会永久污染阶段 7 的评测
- 换算用 `movePointLeft(6)`，`setScale(6, HALF_UP)` 对齐 `NUMERIC(10,6)`

## 三、端到端数据流（阶段 2 版）

```
用户提问
   │
   ▼
ChatController                    校验参数，包装 ApiResponse
   │
   ▼
ChatServiceImpl
   ├─ 生成 traceId
   ├─ 会话 upsert（chat_session）
   ├─ 写用户消息（chat_message, role=1）
   │
   ├─→ ChatModelRouter.chat(...)
   │      ├─ P0 熔断器准入 → 调用 → 成功/失败
   │      ├─ P1 ...
   │      └─ P2 ...
   │      └─ 降级事件写入 ModelCallTrace
   │
   ├─ 写助手消息（chat_message, role=2）
   ├─ 写 qa_log（含用量、成本、降级事件）★ 评测数据来源
   └─ 更新会话活跃时间（last_active_at 手工赋值）
   │
   ▼
返回 ChatAskResponse
```

**一个关键约束**：流式路径**不能加 `@Transactional`**。
事务绑定线程，而流式的写库发生在推送线程上、流结束之后 ——
那时请求线程的事务早就提交了。

## 四、包结构

```
com.xbla.rag
├── controller/     ChatController, ModelProbeController(@Profile local)
├── service/        ChatService, ModelProbeService
│   └── impl/       ChatServiceImpl（编排 + 落库）
├── client/         ★ 模型接入层
│   ├── LlmClient / EmbeddingClient / RerankClient        接口
│   ├── OpenAiCompatibleLlmClient                          对话（服务两家）
│   ├── OpenAiCompatibleEmbeddingClient                    向量（硅基流动）
│   ├── SiliconFlowRerankClient                            重排（硅基流动）
│   ├── OpenAiHttpTransport                                共用 HTTP 底座
│   ├── SseLineParser                                      纯函数，可单测
│   ├── ChatModelRouter                                    ★ 降级链 + 熔断
│   ├── ModelCallTrace / ModelCostCalculator
│   ├── ModelErrorKind / ModelCallException
│   └── dto/        线格式对象（OpenAI 协议）+ 领域对象
├── config/         LlmProperties, HttpClientConfig, ChatChainConfig, AsyncConfig
├── dto/            对外 API 的进出参
├── entity/ mapper/ 数据库层
└── common/         ApiResponse, GlobalExceptionHandler, LongArrayTypeHandler
```

**`client/dto/` 和顶层 `dto/` 的区别**：
前者是「协议长什么样」（随供应商变），后者是「接口长什么样」（随业务变）。
分开之后，接口参数怎么演进都不会波及模型调用层。
