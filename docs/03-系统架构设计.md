# 系统架构设计

> 本文档描述系统的分层结构、模块职责与端到端数据流。
> 阶段 2（模型接入层）已实现，其余部分随对应阶段补全。

---

## 一、分层结构

```
┌─────────────────────────────────────────────────────────┐
│  controller/          对外 HTTP 接口                      │
│  · 只做参数校验 + 响应封装，不写业务逻辑                   │
│  · 唯一额外职责：SSE 的线程调度（属于 Web 层）             │
└────────────────────────┬────────────────────────────────┘
                         │ 依赖
┌────────────────────────▼────────────────────────────────┐
│  service/             业务编排                            │
│  · 串起「建会话 → 存消息 → 调模型 → 写 qa_log」           │
│  · 不感知 HTTP / SSE / 具体供应商                         │
└────────────────────────┬────────────────────────────────┘
                         │ 依赖
┌────────────────────────▼────────────────────────────────┐
│  client/          ★ 模型接入层（全项目唯一发模型 HTTP 的地方）│
│  · LlmClient / EmbeddingClient / RerankClient            │
│  · ChatModelRouter：降级链 + 熔断                         │
│  · 手写 HTTP，不用 SDK                                    │
└────────────────────────┬────────────────────────────────┘
                         │ HTTPS
┌────────────────────────▼────────────────────────────────┐
│  DeepSeek 官方 / 硅基流动                                 │
└─────────────────────────────────────────────────────────┘
```

**依赖方向是单向的**：`controller → service → client → 外部`。
`client` 不知道 `service` 的存在，`service` 不知道 `SseEmitter` 的存在。
这条约束让每一层都能单独测试。

## 二、client 层详解（阶段 2 核心）

### 2.1 为什么只用一个实现类

DeepSeek 官方和硅基流动**都提供 OpenAI 兼容协议**：同样的
`POST /v1/chat/completions`、同样的请求体结构、同样的响应字段。

差别只有三样 —— **域名、密钥、模型 ID** —— 而这三样都是构造时注入的。
所以 `OpenAiCompatibleLlmClient` 一份实现就能服务两家。

这是本项目「双供应商」架构能用很低成本实现的原因。代价是
**两家协议的差异点必须逐个实测确认**，不能假设「兼容」就等于「完全一样」。
实测发现的差异见 §2.5。

### 2.2 三层配置结构

```
xbla.llm
├── providers    ① 连接：域名 + 密钥
├── models       ② 模型：真实模型 ID + 单价
└── chat-chain   ③ 策略：降级顺序
```

**为什么分三层**：供应商是「连接」、模型是「计价与协议」、链路是「策略」。
P1 和 P2 共用同一个硅基流动连接和同一个 Key，但模型不同。
混在一起写的话密钥要重复两份；将来给 P2 换供应商也只改一行 `provider`。

### 2.3 降级链与熔断

```
请求进来
   │
   ├─→ P0  deepseek-flash ──[熔断器 CLOSED?]──→ 调用
   │        ↑ 失败                                    │ 成功 → 返回
   │        └──────── 记录失败 ────────────────────────┘
   │
   ├─→ P1  deepseek-ai/DeepSeek-V3.2 ──[熔断器 CLOSED?]──→ 调用
   │
   └─→ P2  Qwen/Qwen3.5-9B ──[熔断器 CLOSED?]──→ 调用
                                                        │
                                              全失败 → 抛异常
```

**熔断器粒度 = 每个 (供应商, 模型) 一个**，名字就是 `chat-chain` 里的条目 key。
不按供应商做的原因：硅基流动上 P1 被限流时 P2 可能还是健康的，
按供应商做会把健康的 P2 一起拖下水。

**降级事件**通过 `ModelCallTrace` 收集器显式传递（不用 ThreadLocal —— 
流式场景下推送线程不继承请求线程的 ThreadLocal），最终写进
`qa_log.degradation_events`。

### 2.4 错误分类表 ★

这是整个降级策略的灵魂。做成枚举而不是散落的 `if-else`，
因为「哪类失败该降级」和「哪类失败该计入熔断统计」是两个正交的决策。

| 类型 | 触发 | 记熔断失败 | 降级 | 理由 |
|---|---|---|---|---|
| `AUTH` | 401/403 | 是 | 是 | Key 错了，换一家 |
| `QUOTA_EXHAUSTED` | 402 | 是 | 是 | 余额不足，**同家不同模型可能状态不同** |
| `RATE_LIMIT` | 429 | 是 | 是 | 限流，换一家立刻能成 |
| `SERVER_ERROR` | 5xx | 是 | 是 | 对方挂了 |
| `TIMEOUT` | 超时 | 是 | 是 | — |
| `CONNECT` | IO 异常 | 是 | 是 | — |
| `EMPTY_CONTENT` | 200 但正文空 | 是 | 是 | 推理模型吃光 max-tokens |
| `BAD_REQUEST` | 400/422 | **否** | **否** | 我们自己的请求有问题 |
| `CLIENT_ABORTED` | 用户关页面 | **否** | **否** | 不是供应商的错 |
| `PARTIAL_STREAM` | 吐字后中断 | 是 | **否** | 流式架构的硬边界 |

**两条最值得讲的**：

- **`BAD_REQUEST` 为什么不降级也不计熔断**：400 说明我们自己的请求体有问题，
  换一家会以同样方式失败。更关键的是，如果记成失败，连试三家就是三次失败，
  会迅速把所有熔断器推到 OPEN —— 结果是「一个我们自己写错的参数，
  让整个模型层看起来全挂了」，真正的 bug 被掩盖。
- **`CLIENT_ABORTED` 为什么单独分一类**：「往浏览器推送时抛 IOException」
  和「模型供应商出问题」在异常类型上长得一模一样。不区分的话，
  用户每关一次页面就记一次供应商失败 —— 几个人关几次标签页，
  一个完全健康的供应商就被熔断打开了。

> ⚠️ `QUOTA_EXHAUSTED` 是**测试跑出来的**，不是设计时想到的。
> 最初实现把「其余 4xx」一律归到 `BAD_REQUEST`，于是 402 被判成
> 「请求有问题」，整条降级链在那一档直接终止。详见 ADR-007。

### 2.5 实测出的两家差异

不能假设「OpenAI 兼容」等于「完全一样」。实测确认的差异：

| 项 | DeepSeek 官方 | 硅基流动 |
|---|---|---|
| `stream_options.include_usage` | ✅ 支持 | ✅ 支持 |
| usage 汇总 chunk 的 `choices` | `[{...}]`（带内容） | **`[]`（空数组）** |
| usage 字段形状 | 平铺 `prompt_cache_hit_tokens` | **同样平铺**（不只 OpenAI 的嵌套形状） |
| 402 余额不足 | — | **用 402 而不是 400** |

**`choices` 是空数组这一条最危险**：如果用数组 + `choices[0]` 去接，
会在**每个流式请求的最后一刻**抛 `ArrayIndexOutOfBoundsException`。
所以 DTO 里必须用 `List` 并做判空。

### 2.6 SSE 线程模型

```
[Tomcat 请求线程 T1]
   GET /api/chat/stream
   → 返回 SseEmitter(180_000L)
   → Servlet 异步启动，T1 立刻释放回池子     ← 不占用请求线程
        │
        ↓
[sseExecutor 线程 T2]  ← 专用线程池，见 AsyncConfig
   router.chatStream(...)  阻塞在 httpClient.send()
   每收到一个 delta → emitter.send()
        │
        ▼
[客户端] EventSource 逐字渲染

[Tomcat 线程 T3] 仅在 onTimeout / onError 回调时被唤醒
   · 只读标志位 + close 上游流
   · ★ 绝不调 emitter.send（它不是线程安全的，只有 T2 能写）
```

**三条硬性要求**：

1. **必须用专用线程池。** `CompletableFuture.runAsync` 不传 executor 会用
   `ForkJoinPool.commonPool()`，并行度只有「核数-1」。几个并发的阻塞式
   模型调用就能占满它，导致整个 JVM 所有依赖 commonPool 的功能一起僵死。
   现象是「模型好像变慢了」，真正的原因在完全无关的地方。
2. **`traceId` 用方法参数传，不用 ThreadLocal** —— T2 不继承 T1 的。
3. **Tomcat 异步超时默认 30 秒**，不显式设置会无声掐断所有长回答。
   `SseEmitter(180_000L)` + `spring.mvc.async.request-timeout` 双保险。

### 2.7 流式降级边界 ★

```
statusCode != 200 ─────────────────────→ 可以降级
statusCode == 200
  ├─ 首个 content 增量之前失败 ────────→ 可以降级
  └─ 已吐字后失败 ─────────────────────→ 不能降级
                                          记熔断失败 + 发 failed 事件关闭
```

**这是 SSE 架构的固有约束，不是可以优化掉的东西。**
用户已经看到前面吐出来的字了，换一家从头重来会让他看到
两段拼接起来的、前后矛盾的话。

实现上：`OpenAiCompatibleLlmClient.chatStream` 内部维护 `contentChars`，
失败时据此分类 —— 没吐过字按异常本身的性质分类，吐过了就是 `PARTIAL_STREAM`。
**分类发生在信息最全的地方**，router 只管读 `kind.isFallbackWorthy()`。

### 2.8 熔断器的耗时口径 = TTFB

一次 60 秒的**正常**长回答，如果把整个流的耗时喂给熔断器，
会触发「慢调用率」阈值 —— **熔断器在系统最健康、正在正常干重活的时候跳闸**。
这是最坏的反向优化：越努力服务，越容易被判成故障。

所以喂给熔断器的观测值是 **TTFB（首字节延迟）**。
正常情况 1-3 秒，超过 15 秒确实说明这家有问题。

### 2.9 成本计算

三档单价（元/百万 token）：`input`（缓存未命中）/ `cache-hit-input` / `output`。

- `reasoning_tokens` **不参与计价** —— 它是 `completion_tokens` 的子集
- **拿不到 usage 时 `cost` 落 NULL，绝不估算** —— `qa_log` 只增不改不删，
  编出来的数字会永久污染阶段 7 的评测
- 换算用 `movePointLeft(6)`，`setScale(6, HALF_UP)` 对齐 `NUMERIC(10,6)`

## 三、端到端数据流（阶段 2 版）

```
用户提问
   │
   ▼
ChatController                    校验参数，包装 ApiResponse
   │
   ▼
ChatServiceImpl
   ├─ 生成 traceId
   ├─ 会话 upsert（chat_session）
   ├─ 写用户消息（chat_message, role=1）
   │
   ├─→ ChatModelRouter.chat(...)
   │      ├─ P0 熔断器准入 → 调用 → 成功/失败
   │      ├─ P1 ...
   │      └─ P2 ...
   │      └─ 降级事件写入 ModelCallTrace
   │
   ├─ 写助手消息（chat_message, role=2）
   ├─ 写 qa_log（含用量、成本、降级事件）★ 评测数据来源
   └─ 更新会话活跃时间（last_active_at 手工赋值）
   │
   ▼
返回 ChatAskResponse
```

```
   │        ⚠️ 混合轮【两样都有】：retrieval_detail 有值 ∧ tool_calls 有值
   │           —— 这正是「混合轮」在数据上的定义
   ├─ 更新会话活跃时间
   │
   └─★ 丢一个摘要压缩任务给 memoryExecutor         【5.6】
          异步、单线程、队列满就丢（压缩是自愈的）
          ⚠️ 必须在「写助手消息」之后 —— 它按 id 区间取数
   │
   ▼
返回 ChatAskResponse
```

★ **两条路径的差异只有一个**：流式路径在检索**之前**多一次
`sink.onStart(traceId, sessionNo)`，让前端别对着空白页等首字节。
所以插在它前面的任何东西（分类、检索）都会**正好抵消**它的价值 ——
这是 5.4 / 5.5 反复强调过的位置约束。

★★ **9.3 起「平行路径」这件事有两个具体的雷**（都真的踩过）：

```
① 分支逻辑：ask() 接了工具分支而 askStream() 没接
   → 工具题在 SSE 上静默降级成 KB 问答（9.1 修的，ADR-091）
② 响应构建：buildToolResponse / buildStreamToolResponse 是两个【独立】的方法
   → 混合轮补 references 时只改了一个，另一条路上的引用栏是空的（9.3 实测抓到）
⇒ 改任何一处都要问「另一条路呢」，判据是两条路各有一个测试，不是「主路径绿了」
```

**一个关键约束**：流式路径**不能加 `@Transactional`**。
事务绑定线程，而流式的写库发生在推送线程上、流结束之后 ——
那时请求线程的事务早就提交了。

#### ★★★ 为什么整层必须在 `ChatService` **之外**

这一条比「职责划分」硬得多。`ChatServiceImpl` 的顺序是
`读记忆 → 写用户消息 → 意图识别 → ……`，而**排队若插在写用户消息之后**：

```
排队超时 → 用户消息已经落库了 → 留下一对没有回答的孤儿 user 消息
   → 下一轮它进历史 → 模型收到两条连续 user 消息 → 400 → 不降级
   → ★ 连续两次失败之后，这个会话【永久答不出话】（ADR-049）
```

所以排队只能在 `saveUserMessage` **之前** —— 而它在 `ChatServiceImpl` 内部，
唯一的「之前」就是**外面**。

★ 同理，`qa_log` 里那两列（`queue_ms` / `queue_position`）由排队层构造好、
**跟着 `CallContext` 一路传进去**，而不是让 `ChatService` 去问排队层要 ——
后者会把一个已经解耦的边界重新缝上。

#### 两条路的差别只有三点，而且都是刻意的

| | 流式 | 非流式 |
|---|---|---|
| 等待方式 | 每 200ms 推 `queued` 位置 | **阻塞**在 `CompletableFuture` 上，无通道可推 |
| 排队预算 | 120 秒 | **30 秒** |
| 被拒绝 | 推一个 `failed` 事件 | 抛 `QueueRejectedException` → **HTTP 503 + `Retry-After`** |

★ 但**「什么算被拒绝」的判据是同一个**（都来自 `giveUp()`），
所以两条路在 `qa_log` 里留下的痕迹完全一致。这是刻意的：
非流式如果自己写一遍排队循环，「名额在哪释放」「拒绝写不写库」这些判断就会变成两份，而两份会漂移。

⚠️ 30 秒那个数不是体验偏好，是一条更硬的约束：**我们的超时必须比客户端自己的超时先发生。**
curl / 演示页 / 脚本普遍 30~60 秒就放弃；我们持 120 秒才回 503 的话，
用户看到的是「连接错误」，**而我们那句精心写的「前面人太多」永远送不到。**

#### SSE 事件契约（在 `meta`/`delta`/`done`/`failed` 之外**追加**两个）

```
event: queued   {"traceId":"…","position":5,"waitedMs":0}
event: admitted {"traceId":"…","queueMs":1200,"queuedAhead":3}
event: meta     …（不变）
```

★ `position` 的语义是**「前面还有几个人」**（`ZRANK` 原生语义，0-based），
**不是「我是第几个」**。这个 off-by-one 由测试钉住 ——
因为「第 1 位」和「前面 0 人」在界面上看起来只像「有点慢」，不像 bug。

★ `queuedAhead` 为 **null** 表示**从没进过队列**；**0** 表示进过、而且是队首。
两者是两回事（同 `queue_ms` 的 NULL 语义）。

## 四、RAG 文档入库链路（阶段 3）

### 4.1 四级流水线

```
kb_document.file_path（落盘的原始文件）
     │
     ├─① 解析   DocumentParser（Tika）     → List<TextBlock>
     ├─② 切分   HeadingAwareChunker       → List<TextChunk>
     ├─③ 向量化 EmbeddingClient（bge-m3）  → List<float[]>
     └─④ 写库   KbChunkMapper             → kb_chunk
     │
kb_document.status: 1待处理 → 2处理中 → 3已入库 / 4处理失败
```

**三个入口，一条流水线**：

| 入口 | source_type | 说明 |
|---|---|---|
| `POST /api/kb/documents` | 1 文件上传 | 单文件，multipart |
| `POST /api/kb/documents/scan` | 1 文件上传 | 扫描 `data/corpus/` 批量灌 |
| `POST /api/kb/documents/sync` | 2 数据库同步 | `after_sale_policy` + `product` 表 |

**数据库同步刻意走同一条路径**：先把表里的行渲染成 Markdown、落盘，
再交给同一个解析器。这样入库代码不为数据源分叉（见 ADR-017）。

### 4.2 ★ 同步返回 vs 异步处理

**四个入库接口都是「受理」语义，不是「完成」语义。**

一份文档入库要跑向量化，可能几十秒到几分钟，放在 HTTP 请求里同步跑浏览器早就超时了。
所以上传接口立刻返回 `docId` + `status=1`，真正的活在 `ingestExecutor` 线程池里跑，
前端轮询 `GET /api/kb/documents/{id}` 看进度。

```
[Tomcat 请求线程 T1]
   POST /api/kb/documents
   → 原件落盘（毫秒级）
   → 写 kb_document(status=1)
   → 提交到 ingestExecutor，立刻返回
        │
        ↓
[ingest-* 线程 T2]
   DocumentIngestWorker.process()
   status 1 → 2 → 3/4
```

**接口语义必须和实际行为一致**。如果上传接口谎称「成功」，
用户在十分钟后查库发现切片数是 0 时，会完全不知道该信哪个。
所以响应里带一个 `finished` 字段，明确告诉前端「现在还不能停轮询」。

### 4.3 线程池参数为什么和 `sseExecutor` 相反

| | `sseExecutor` | `ingestExecutor` |
|---|---|---|
| core / max | 8 / 32 | **2 / 4** |
| queue | **16（故意小）** | **200（故意大）** |
| 拒绝策略 | AbortPolicy | CallerRunsPolicy |

**入库的瓶颈不在我们的 CPU，而在对方的限流阈值。**
向量化接口有 QPS 限制，开 32 个线程不会让总吞吐变高，
只会更快撞上限流（429），然后整批任务一起失败重试。
并发度应该匹配下游能承受的量，而不是我们想要的量。

队列反过来：SSE 让用户干等是坏事，但入库是后台任务，
任务在队列里排队对用户不可见 —— 一个批量灌语料的任务可能有几十上百份文档排队。

### 4.4 ★ 为什么整条流水线不放在事务里

向量化要调外部 API，一份几百片的文档要跑几十秒到几分钟。
事务开着跨越这几分钟 = **一条 HikariCP 连接被独占那几分钟**，
而连接池只有 10 条。4 个并发入库就能占掉四成，整个应用的数据库访问会集体排队。

**用补偿删除代替事务**：任何一步失败，就把这次写的切片按 `document_id` 全部删掉。
不删的后果很具体 —— 检索只认 `kb_chunk.deleted = 0`、**不看文档状态**，
于是「一份标着处理失败的文档，它的半截内容照样被检索命中」。

### 4.5 解析层：三种标题提取策略

Tika 对四种格式的输出形态**完全不同**（实测结论，不是推测）：

| 格式 | Tika 输出 | 策略 |
|---|---|---|
| `.docx` | 正文内联 `<h1>` `<h2>` `<h3>` | ① 读标签名 |
| `.pdf` | **正文里一个 h 标签都没有**，标题是 `<body>` 末尾一个嵌套 `<ul>` | ② 大纲建映射表 → 回正文按行精确匹配 |
| `.md` | **Tika 没有 Markdown 解析器**，整文件塞进一个 `<p>`，`#` 原样保留 | ③ 行首模式（`#` / `第X章` / `一、` / `1.1`）|
| `.xlsx` | sheet 名 → `<h1>`，数据在 `<table>` | sheet 名当标题，行拼成文本 |

**PDF 那条最绕**：PDF 格式本身不存储「这是标题」，
能从它拿到结构信息的唯一来源就是文档大纲。
但大纲只告诉你「有哪些标题、各是几级」，不告诉你它们在正文的哪个位置 ——
所以用**标题文本精确匹配**把两者接起来。

⚠️ 大纲的 HTML **不是良构的**，同样的层级会输出成两种嵌套形态
（嵌套 `<ul>` 在 `<li>` 里面 vs 是 `<li>` 的兄弟）。
只处理一种会导致另一份文档的标题层级**整个丢失且不报错**。详见 ADR-013。

### 4.6 切分层：三件事为什么必须组合

```
① 按标题切段  → 不同章节的内容不混进同一个切片
② 段内定长切  → 一个章节可能几千字，超过单次检索该给 LLM 的上下文量
③ 重叠窗口    → 答案横跨切分点时靠它救回来
```

**没有重叠窗口的后果**：

```
切片1: ...签收后 7 天内可申请无理由 | 切片2: 退货，需要保持商品完好...
       ↑ 结尾是半句                  ↑ 开头是半句
用户问「退货要几天」→ 两个切片都只有半句话，谁都答不出来
```

**两条类不变量**：

1. **段落边界永远不被跨越**（滑动窗口只在单个章节内部进行）
2. **`standalone` 块不和邻居合并**（表格行是自包含记录，见 ADR-015）

**另外两个设计点**：

- **标题路径会拼进切片正文**（`include-heading-in-content: true`）。
  用户问「退货政策是什么」时，「退货」二字可能**只出现在标题里**，
  正文写的是「签收后 7 天内可申请」。标题不参与向量化就丢了关键语义线索。
- **整段短于 `merge-threshold-chars` 时不切**。避免切出「500 字 + 100 字」
  这种尾巴 —— 那 100 字单独占一个向量，性价比很低。

### 4.7 向量列：`float[]` ↔ `vector(1024)`

```
Java float[]  ──①拼成 "[0.1,0.2,...]"──>  String
                              │
              ②以「未指定类型」发给 PG（靠 JDBC URL 的 stringtype=unspecified）
                              │
              ③PG 用 vector 类型自己的输入函数解析
                              ▼
                        vector(1024)
```

`VectorTypeHandler` 负责这个转换。两个易错点：

- **类上必须加 `autoResultMap = true`**。漏了的话写入正常、查询也正常，
  就是**查出来永远是 null** —— 「一半能跑」的 bug 最难排查
- **`stringtype=unspecified` 不能省**。pgjdbc 默认把 String 当 varchar 发送，
  而 PostgreSQL 不会把 varchar 隐式转成 vector

### 4.8 向量检索与结果稳定性

```sql
SELECT ..., 1 - (embedding <=> CAST(? AS vector)) AS score
FROM kb_chunk
WHERE deleted = 0 AND embedding IS NOT NULL
ORDER BY embedding <=> CAST(? AS vector), id   -- ★ 那个 id 不能省
LIMIT ?
```

- `<=>` 是余弦**距离**（0=相同、1=正交、2=相反），实测确认。
  返回值里用 `1 - 距离` 换成相似度
- **`ORDER BY` 里的 `id` 兜底键不能省**：HNSW 是近似索引，
  距离相同时返回顺序不保证。「同一问题检索两次结果一致」这条验收标准
  靠它才成立
- **兜底键没有牺牲索引效率**（`EXPLAIN` 验证过）：
  Postgres 用 `Incremental Sort` 叠在 `Index Scan using idx_kb_chunk_embedding` 上

**★ 关于「结果稳定」的真实含义（实测推翻了原有假设）**：

向量化接口**不是逐位确定的** —— 同一个问题连续调用 6 次 `/v1/embeddings`，
出现了 2 种不同结果，差异量级约 **3e-4**。
这不是 bug，是 GPU 并行计算里浮点归约顺序不同导致的固有性质。

所以判定「稳定」只看 **ID 序列**是否逐位一致（实测 5 次完全相同），
不看分值是否相等。详见 ADR-018。

**⚠️ 相似度不能当阈值用**：实测 bge-m3 在中文上的相似度区间被压缩，
相关和不相关文档的分布会重叠。必须用**相对 Top-K 排序**，
不能写「相似度 > 0.6 就算相关」。这也正是重排序模型存在的理由。

### 4.9 端到端数据流（阶段 3 版）

```
POST /api/kb/documents（上传）
   │
   ▼
KbDocumentController              参数校验，包装 ApiResponse
   │
   ▼
KbIngestServiceImpl
   ├─ DocumentStore.save()        原件落盘 + 算 SHA-256（一遍读完）
   ├─ 按 file_hash 查重            命中 status=3 的已有文档 → 直接返回，不重复花钱
   ├─ 写 kb_document(status=1)
   └─ submit() → ingestExecutor
   │
   ▼（异步）
DocumentIngestWorker
   ├─ status 1 → 2
   ├─ ① DocumentParser.parse()    Tika → XHTML → jsoup → List<TextBlock>
   ├─ ② HeadingAwareChunker       标题切段 + 定长 + 重叠窗口
```


### ★★ 两条运行方式并存（这是刻意的）

| | 本地开发 | 容器全栈 |
|---|---|---|
| 命令 | `docker compose up -d` + `./mvnw spring-boot:run` | `docker compose --profile full up -d` |
| 应用端口 | 宿主机 **8080** | 容器内 8080，**不映射** |
| Spring profile | `local` | `prod` |
| 密钥来自 | `application-local.yml` | 环境变量 |

★ **为什么必须并存**：阶段 7 的 `eval_run.py`、`probe_*.py`、
以及 `./mvnw clean test`（860 个用例）**全部假设 `localhost:8080`**
和宿主机上的中间件。把本地那条路弄断，等于把「可复现」那条链弄断。

★ 做法：`app`/`nginx` 挂在 compose **profile** 上（默认 `up -d` 行为一字不变），
且 **app 容器不映射端口**（ADR-089）。

> ⚠️ **阶段 6 实际交付的和这一行原来写的【不完全一样】**：原写「Redis 信号量」，
> 实际做的是**带租约的名额表**（ZSet + score = 过期毫秒 + 看门狗续期）。
> 改动理由是架构级的：`RSemaphore` 表达不了「给单个名额设过期时间」，
> 而那正是「进程被强杀不泄漏名额」唯一可行的做法。见 `docs/02` §23⑤ 和 ADR-075。

### ⚠️ 阶段 3 留下的已知问题

| # | 问题 | 影响 | 计划 |
|---|---|---|---|
| 1 | **入库接口没有鉴权** | 任何人都能上传文件并触发向量化，而向量化要花钱 | 🟡 **一半已解决（2026-09-24）**：鉴权由 **Nginx 层的 Basic Auth** 提供 —— 它加在 `server` 级，覆盖**全部** `/api/*`（含 `/api/kb/`）。★ 放在反代层而不是逐端点加，是因为逐端点就是那个「有一个口子忘了加」的形态。⚠️ 但**限流没有覆盖它**：只有聊天路径过 `ChatAdmissionService`，入库不走那里。⇒ 拿到口令的人可以反复触发向量化。**这个缺口是已知的、有界的**（口令只发给演示对象），但没有被修 |
