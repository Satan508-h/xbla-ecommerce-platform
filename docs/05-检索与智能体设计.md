## 一、整条链路

```
用户提问
  │
  ├─① 查询计划      QueryPlanner          ← 4.3 重写 / 4.4 子问题拆分，★ 默认关闭
  │
  ├─② 并行双路召回 ─┬─ VectorRetriever    向量化 HTTP + pgvector HNSW
  │                 └─ KeywordRetriever   中文 bigram + ts_rank + GIN 索引
  │
  ├─③ RRF 融合      RrfFuser             按【名次】合并，完全丢弃分数
  │
  ├─④ 精排          ChunkReranker        bge-reranker-v2-m3，失败回落融合顺序
  │
  └─⑤ 截断          取 finalTopK(=5) 条 → 拼进 system prompt
```

对应代码：`rag/RetrievalPipeline.java`（编排者）、`rag/RetrievalTrace.java`（轨迹收集）。

## 二、★ 为什么是双路召回

因为两路的**强弱项不重叠**，这不是「多一路总比少一路好」：

| | 向量路 | 关键词路 |
|---|---|---|
| **擅长** | 语义泛化 —— 「送长辈」能匹配「适合老年人」 | 字面精确 —— 型号、编码、专有名词 |
| **弱点** | 对「符号」不敏感：`星辰X1` 在向量空间里没有语义 | 对同义改写无能为力 |
| **实测** | 「这个适合送长辈吗」命中「1.1 适合送长辈的商品」0.98 | 「星辰X1 电池」把「充电与电池」排到第一 |

一个具体例子说明向量路为什么需要关键词路配合：问「星辰X1 电池能用多久」，
型号 `X1` 在向量空间里和别的型号挤在一起分不开，但关键词路能把它精确锚定。

反过来也成立：问「退货要几天」时，文档写的是「7 天内」，
关键词路只能靠「退货」一个 bigram 对上 —— 这时向量路负责语义那一半。

## 三、★ 中文关键词检索：为什么是 bigram

这一节记录一个**推翻了原设计**的实测过程。原方案见 `docs/04` §11.1（推荐 `pg_trgm`）。

### 3.1 问题是 PostgreSQL 切不开中文

```sql
SELECT to_tsvector('simple', '电池容量是5000mAh支持快充');
--  '电池容量是5000mah支持快充':1        ← 整句粘成【一个】词元
```

实测漏检率（全库 1652 条切片）：

| 词 | 裸 FTS 命中 | `content LIKE` 命中 | 漏检率 |
|---|---|---|---|
| 退货 | 3 | 43 | **93%** |
| 电池 | 94 | 135 | 30% |
| 星辰 | 5 | 5 | 0% |

### 3.2 三个方案的实测对比

查询「退货要几天」：

| 方案 | 召回 | 排序区分度 | 证据 |
|---|---|---|---|
| `pg_trgm` `word_similarity` | ✅ | ❌ **完全并列** | 4 条正确切片全是 `0.3333` |
| 单字 + `plainto_tsquery` | ❌ 0 行 | — | 被拆成 `退 & 货 & 要 & 几 & 天`，AND 语义必然空 |
| **双字 + OR + `ts_rank`** | ✅ | ✅ | `0.022244 / 0.021636 / 0.020686` |

**`pg_trgm` 为什么没有排序能力**：它只生成 **3 字窗口**，而中文词大多是 2 字。
查询「退货要几天」产生的 6 个三元组里，首尾补空格得到的 `"  退"` 和 `"几天 "`
在长文本中间**永远不可能出现**，所以最多只有 3 个可能命中。

这一条对 RRF 是致命的：融合只取排名不取分数，并列时的顺序等于「按 id 排」，
语义上毫无意义 —— 等于把关键词这一路废掉。

### 3.3 分词规则：只在「连续同类字符段」内部生成词元

```
段类型              处理                          例子
─────────────────────────────────────────────────────────────────
CJK（长度 ≥ 2）     切 2-gram                     退货要几天 → 退货 货要 要几 几天
CJK（长度 = 1）     ★ 丢弃                         日 → （无）
ASCII / 数字        整体保留为一个词元（转小写）      X1 → x1、5000mAh → 5000mah
ASCII（长度 = 1）   ★ 丢弃                         7 → （无）
跨段                不生成任何词元
```

**「不跨段」是核心**。跨段切出的词元（如 `"1 "`）写进 `search_text` 后，
`to_tsvector` 会把它们**退化成裸的单字词元**：

```sql
SELECT to_tsvector('simple','星辰 辰X X1 1 电 电池');
→  '1':4 'x1':3 '星辰':1 '电':5 '电池':6 '辰x':2      ← 裸单字 1 和 电 出现了
```

裸单字在中文里是最高频词元，OR 起来候选集从 3.8% 爆炸到 **36.6%**。

**「单字丢弃」是实测推着改的**（最初的设计是保留，理由「丢字会丢信息」）：

| 裸单字 | 出现条数（/1652） | 来源 |
|---|---|---|
| `元` | 192（12%） | 「5999 元」行尾 |
| `年` | 159（10%） | 「2026 年」行尾 |
| `2` | 166（10%） | 小节号「2.1 有效期」 |

一个字符没有任何区分能力，只有污染候选集的作用。

### 3.4 ★ 保留词频（不做去重）—— 一个被实测纠正的错误

最初对词元做了去重，理由是「倒排索引只关心有没有这个词，词频是噪声」。
**这是错的，而且错得很隐蔽**：

| | 查询「退货要几天」命中 43 条切片，不同分值个数 |
|---|---|
| 去重版 | **1 种** —— 排序退化成「按 id 排」 |
| 不去重版 | 8 种 —— 正解「自签收之日起 7 天内」排第 3 |

根因：`ts_rank` 对 **OR 查询**取的是「单个词元得分的**最大值**」，
而单词语元的得分**只取决于词频**。去重让频率恒为 1，所有命中同一个词的切片
拿到完全相同的分数。（`ts_rank_cd` 也一样，实测同样全部并列 0.1。）

**教训：在替换掉一个排序信号之前，先确认它是不是那个算法唯一的输入。**

### 3.5 数据库侧

```sql
ALTER TABLE kb_chunk ADD COLUMN search_text TEXT;              -- Java 分词器写的词元串
ALTER TABLE kb_chunk ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (to_tsvector('simple', search_text)) STORED;
CREATE INDEX idx_kb_chunk_search ON kb_chunk USING GIN (search_vector);
```

用**生成列**而不是表达式索引：表达式索引要求查询里的表达式与索引定义**字面完全一致**，
差一个引号就**静默退化成全表扫描**；生成列没有这个陷阱，而且 `ts_rank`
能直接读存储列而不是给每个候选重算。

⚠️ 生成列**不能引用另一个生成列**，所以 `search_text` 必须保持普通列 ——
这正好是「分词留在 Java」的额外理由。

## 四、RRF 融合

### 4.1 公式

```
score(d) = Σ   weight_L / (k + rank_L(d))        rank 从 1 开始
          L∈路
```

### 4.2 ★ 为什么不能加权求和

两路的分值**量纲不可比**：

```
向量路：余弦相似度   实测 0.5 ~ 0.7
关键词路：ts_rank    实测 0.01 ~ 0.03
```

差两个数量级。要加权求和就得先归一化，而归一化需要知道分数分布 ——
那个分布**随语料变化**，今天调好的参数明天就不对。
而且向量相似度的绝对值**根本不能当阈值用**（相关和不相关的分布互相重叠，
见 `VectorSearcher` 的注释），归一化的分母本身就不可靠。

RRF **只用名次、完全丢弃分数**，一举绕开所有这些问题。

### 4.3 k=60 在做什么

```
k=60 时：第 1 名得 1/61 = 0.01639    第 10 名得 1/70 = 0.01429    只差 13%
k=0  时：第 1 名得 1/1  = 1.0        第 10 名得 1/10 = 0.1        差 10 倍
```

k 的作用是**削弱名次差异**，让「在某一路排第 1」不至于压倒「在两路都排第 5」。
换句话说：**RRF 奖励的是「被多路共同认可」，不是单路的极端高分**。

## 五、★ 失败语义

| 情况 | 行为 | 理由 |
|---|---|---|
| 单路失败 | **继续**，用另一路的结果 | 两路互补，丢一路只是候选少一份 |
| 两路都失败 | **继续**，返回空上下文 | 退化成裸聊，比整次问答 500 好 |
| 重排失败 | **回落**到 RRF 顺序 | `RerankClient` 无降级链（只有硅基流动提供），一次 429 就能让整次请求失败 |
| 线程池满 | 该路记失败，另一路照常 | `AbortPolicy` 下 `supplyAsync` 在**提交时**同步抛异常 |
| 查询切不出词元 | **短路**关键词路 | 实测 `to_tsquery('simple','')` **不抛异常**，静默返回 0 行 |

**任何情况下 `RetrievalPipeline` 都不向上抛异常。** 调用方拿到的永远是一个可用的
（哪怕是空的）结果列表。

⚠️ **检索的异常绝不能冒到 `ChatServiceImpl` 的 `catch`**。那个 catch 的语义是
「模型链路失败 → `qa_log.status=2`」，检索的问题混进去，阶段 7 会把
「检索挂了」统计成「模型挂了」—— **归因彻底错乱，且从数据上看不出来**。
所以 `retrieveSafely()` 自己吞掉一切。

## 六、★ 三个线程池的取值逻辑

| 池 | core/max | 队列 | 拒绝策略 | 关闭等待 | 一句话理由 |
|---|---|---|---|---|---|
| `sse-` | 8 / 32 | 16 | Abort | 30s | 用户在盯着，宁可快速报错 |
| `ingest-` | 2 / 4 | 200 | CallerRuns | 60s | 后台非幂等，宁可慢不可丢 |
| `retrieve-` | 4 / 16 | 64 | Abort | 5s | 只读幂等，且调用方就是用户线程 |

**★ `retrieve-` 的 max 上限不是线程数，是 Hikari 连接池。**
`maximum-pool-size: 10`、`connection-timeout: 30000` —— 16 个并发检索任务会抢 10 个连接，
抢不到的卡在 **30 秒**超时上，比我们自己毫秒级拒绝糟得多。

**不用虚拟线程**：虚拟线程是无界的，没有队列、没有上限，也就没有背压。
在阶段 6 的 Redis 分布式限流到位之前，有界平台线程池更稳妥。

## 七、调试与运维接口

> ⚠️ 全部标了 `@Profile("local")`，只在本地开发时存在。
> 它们会无条件消耗 API 额度，**绝不能暴露到生产**。

```bash
# ★ 完整链路的中间输出（路线图阶段 4 验收标准 1 的落点）
curl -s -G localhost:8080/api/debug/kb/retrieve --data-urlencode "q=退货要几天"

# ★ 分词索引覆盖率。missing 必须是 0
curl -s localhost:8080/api/debug/kb/search-text-stats

# 重建 search_text（force=true 是全量重建，换分词器后用）
curl -s -X POST "localhost:8080/api/debug/kb/reindex?force=true"

# 加载评测集（会重新解析锚点）
curl -s -X POST localhost:8080/api/debug/eval/reload
```

⚠️ **中文参数请用 `scripts/probe_kb.py`，不要直接用 curl** ——
Windows + Git Bash 下有两层编码陷阱，直接用 curl 会得到「像乱码又像 bug」的结果。

### ★ 为什么 `search-text-stats` 这个探针很重要

关键词检索的条件是 `search_vector @@ query`，而 SQL 里 **`NULL` 参与布尔运算的结果是
NULL 而不是 false**，于是 `search_text` 为空的切片会被 `WHERE` **静默排除**。

也就是说：如果有人改了入库代码却忘了写 `search_text`，症状是
「**新文档检索不到，老文档一切正常**」，而且没有任何报错。
覆盖率探针把那个静默的故障变成一行数字。

## 八、已知问题

### 8.1 阶段 4 收尾时已修（2026-09-19）

这三条是阶段 4 遗留的，在同日的收尾里处理掉了。

**① `doc_type` 错标 → 改为语料清单驱动。**

原本 scan 时统一传 `?docType=2`，于是**整个目录**的文件全被标成「售后政策」——
促销活动规则、售后FAQ、商品说明书、商品导购指南全中招。实测 18 份里错了 4 份。

修法是 `data/corpus/manifest.yml` **逐文件声明** `doc_type`
（见 `CorpusManifest`）。选显式清单而不是文件名启发式，是因为启发式对
不认识的文件名会**静默给默认值** —— 加一份「2026春季新品.md」就又一次安静地标错。

⚠️ 顺带发现一个必须一起解决的问题：`findReusableByHash` 命中去重时**直接返回**，
不会更新 `doc_type`。所以「改了清单里的归类」如果不做额外处理，
表现为**改了 YAML 却毫无效果**。现在命中去重时会**校正**
（`kb_document` 和冗余的 `kb_chunk.doc_type` 一起改，**不重新向量化** ——
`doc_type` 不参与 embedding 和分词）。

**② 售后政策汇编被灌了两份 → 删掉 PDF 那份。**

doc 3（.docx）和 doc 4（.pdf）内容逐字相同，被异步入库灌了两遍
（文件字节不同 → 哈希不同 → 去重拦不住）。重复内容会长期挤占 Top-5 名额。
已删除 doc 4，并从 `scripts/generate_corpus.py` 移除该 PDF 的生成。

> ★ 这件事暴露了一个更深的问题：**`findReusableByHash` 比的是文件字节的哈希，
> 而 docx / xlsx / PDF 都会把创建时间写进文件头** —— 于是「内容一模一样但
> 重新生成了一次」的文件哈希完全不同，重扫会**再灌一遍并真的调用向量化接口**。
> 已通过让生成器产出**字节确定**的文件解决（见 `generate_corpus.py`
> 的 `FIXED_TIMESTAMP` 和 `_normalize_ooxml`）。

**③ 评测集的单答案 gold 标错了 → 补全为多答案。**

详见 `docs/06` §3.0。这一条最后**推翻了阶段 4 报告里的两个主要结论**。

### 8.2 仍然存在的问题（留给后面）
