# 06 · 评测体系设计

> 这份文档回答一个问题：**「检索质量好不好」这句话怎么变成数字。**
>
> 没有它，所有的优化都只能靠「感觉好像准了点」—— 而人的直觉在检索质量上
> 极不可靠：同一个改动，可能把 3 道原本答对的题挪到第 6 位、同时把 2 道答错的题
> 提到第 3 位，净效果是**变差**，而肉眼完全看不出来。

**当前状态**：阶段 4 建立了基线（20 题）。阶段 7 才会做完整评测体系（150 题 + RAGAS + A/B 框架）。

---

## 一、指标定义

### 1.1 检索类指标

| 指标 | 公式 | 回答什么问题 |
|---|---|---|
| `HitRate@K` | 前 K 条里**至少命中一条**正确答案的题占比 | 用户能不能找到答案 |
| `Recall@K` | `\|正确答案 ∩ 前K条\| / \|正确答案\|` 的平均 | 答案分散在多片时漏没漏 |
| `MRR@K` | 第一条正确答案名次的倒数的平均（未命中记 0） | 正解排得靠不靠前 |

★ **`HitRate@K` 必须和 `Recall@K` 一起看**：当一道题的正确答案有多个切片时，
`Recall` 会被摊薄（命中 1/3 只有 0.33），而用户其实已经找到答案了。
`HitRate` 更接近用户感知。

### 1.2 延迟指标

| 指标 | 说明 |
|---|---|
| `retrieval_latency_ms` | **整条检索链路**的耗时（含重排） |
| `rerank_latency_ms` | 其中**重排那一段**的耗时 |

两者是**包含关系**，不是并列关系。这样拆是为了回答「P95 变慢了，慢在召回还是慢在重排」。

### 1.3 ★ 未命中归因（最有价值的一列）

每一道没答对的题，必须能回答「**死在哪一步**」：

| 归因 | 判据 | 该往哪调 |
|---|---|---|
| `not_recalled` | 两路原始输出里都没有正解 | **召回/切分**：切分粒度、分词方案、TopK |
| `fusion_dropped` | 两路有，融合后掉出前 20 | **RRF 参数**：k 值、两路权重 |
| `rerank_dropped` | 融合里有，重排后掉出前 5 | **重排模型**：候选数、阈值 |

**三种死法的优化方向完全不同。** 只报一个总分的报告，只能告诉你「变差了」，
告诉不了你「该改哪里」。

### 1.4 ★ 意图类指标（阶段 5.2 新增）

路线图 7.2 原本只写了「Top-1 意图准确率」。**实测之后加了第二个**：

| 指标 | 定义 | 回答什么 |
|---|---|---|
| **Top-1 意图准确率** | 分类结果的 code 与标注一致的题占比 | 分类体系本身好不好理解 |
| **★ 检索范围准确率** | 分类结果的 `doc_types` 集合与标注一致的题占比 | 它对**系统**有没有伤害 |

**为什么要两个**（2026-09-19 实测）：

```
Top-1 意图准确率（code 完全一致）       19/20 = 95%
检索范围准确率（doc_types 集合一致）   20/20 = 100%
```

> ★ 2026-09-20 复测：Top-1 = **18/20 = 90%**（8 次取众数 × 2 轮独立测量），检索范围那一半未复测。原因、方法与「票型跨会话会变」的发现见 docs/05 §5.2 ④-b。
>
> ★★ **2026-09-25 复测（阶段 9.2 改了分类 prompt 之后）：Top-1 = 18/20 = 90%**，
> 8 次取众数、160 次调用 0 失败、耗时 191.1s、花费 ≈ 0.1279 元。
> `python scripts/eval_intent_probe.py --set baseline --repeat 8 --base http://localhost:8081`
>
> ```
>                        2026-09-20（旧契约）      9.2（新 JSON 契约）
>   Top-1                18/20 = 90%              18/20 = 90%
>   错题                  B-012, B-017             B-012, B-017      ← 一样
>   B-017 票型            NEEDS_CLARIFICATION 6:2  NEEDS_CLARIFICATION 6:2
> ```
>
> **★ 结论：把输出从「一个裸码」换成「一行 JSON 计划」没有动分类行为。**
> 分数一样、错的题一样、那道摇摆题的票型也一样。
>
> ★ 这条复测是 **9.2 的验收前置** —— 改了 prompt 却不重测，
> 「95%」那个数就不再是同一个实验条件下的数，而**没有任何东西会提醒你**。
>
> ⚠️ 但**别把「票型也一致」当独立结论**：`docs/05` §5.2 ④-b 已经量过，
> 同一份 prompt 在不同 run 之间票型会变（B-017 旧契约下两次是 6:2 和 8:0）。
> 「重复 N 次取众数」只测得出**会话内**的稳定性。
>
> ★ 顺带解掉一个担心：B-017 偏向 `NEEDS_CLARIFICATION` 是**旧契约下就有的**，
> 不是新加的 `missing` 字段诱导出来的（两者在时间上分得开）。

唯一的错题是 `B-012「满减活动能和优惠券一起用吗」`：标注 `COUPON`、
分类 `FULL_REDUCTION` —— **而两者的 `doc_types` 都是 `{3,4}`**，
5.4 拿到哪个都会去同一批切片里检索。

**两个数字的差值就是「无害的相邻叶子分歧」的量。** 只报 Top-1 会把它和
「路由到错误的知识库区域」平均成一个数，而后者代价大得多。

> ⚠️ 更要命的是，**Top-1 对「树的粒度」敏感，而粒度是设计选择不是质量**：
> 把两个相邻叶子合并，分类器不再可能搞错，Top-1 会升高 —— 而检索行为一点没变。
> 拆分则相反。只有第二个指标在这种改动面前是稳定的。

**Top-1 仍然要报**：它衡量的是「分类体系对人好不好理解」，
那是树的可用性，不能用第二个指标代替。

#### ★ 测量纪律：单次结果不可归因

`temperature = 0.0` **不等于确定性**。实测同一问题 8 次出现过 7:1 的结果分裂
（见 `docs/05` §9.2 ⑤）。成因是推理模型的浮点并行归约，和
「向量化有 3e-4 漂移」是同一类现象 —— 而分类的输出只有几个 token，
几个 token 的差异就直接是另一个答案。

**所以：**

- 报意图准确率**必须重复多次取众数**，并**同时报出波动范围**
- n=20 时一道题就是 5% —— **不要拿 90% 和 100% 去比较两个 prompt**
- 判断改动有没有效，看的不是准确率的小数点，而是
  **「某几道题从稳定错变成稳定对、或反之」**

#### ★ 以及一条反向纪律：不能拿考题拟合 prompt

`B-012` 那个分歧**刻意不修**。补一句判据让它变对是很容易的，
但 **n=20 时「修判据歧义」和「照考题拟合 prompt」分不出来** ——
补完之后准确率会变成 100%，而那个 100% 不描述任何东西。

这是 `ADR-029`「不能拿系统输出拟合标准答案」的**镜像**。

### 1.5 ★★ 哪些 `qa_log` 行是「可评测」的（阶段 5.3 新增）

**所有检索类与答案质量类指标，一律只统计 `status = 1`。**

| status | 含义 | 能不能拿来算指标 |
|---|---|---|
| **1** | 成功生成答案 | ✅ **只有这一种可以** |
| 2 | 模型链路失败 | ❌ 根本没有答案 |
| **3** | **澄清反问**（5.3 新增） | ❌ **没有答案可评** —— `final_answer` 里存的是一句反问 |

`status=3` 的行是这样产生的：系统判定用户那句话信息不足
（「那个怎么样」），于是**不检索、不调生成模型**，直接反问一句。
它既没成功也没失败 —— 那是系统正确工作的表现。

> ⚠️ **如果把它算进指标**：
> - 答案质量类（RAGAS faithfulness / answer_relevancy）
>   会给一句「你指的是哪款商品呢？」打分 —— 而它不是一个答案
> - 检索类（Recall / HitRate）会把它算成「没召回到」——
>   凭空拉低召回率，而且**从数字上看不出来**

**为什么不用 `intent = 'NEEDS_CLARIFICATION'` 来筛**：
那需要每处统计都写 `WHERE status = 1 AND intent <> 'NEEDS_CLARIFICATION'`，
而「每处都要记得加一个条件」是最容易漏的形态 ——
漏了不报错，只是数字偏低。变成 `status` 的取值之后，
`WHERE status = 1` 天然就是对的。详见 ADR-041。

### 1.6 ★★ 答案质量类指标（RAGAS，阶段 7.5 新增）

前面几节量的都是**检索**（召回没有、排得准不准）和**路由**（分对没有）。
这一节量的是**生成**：拿到这些上下文之后，答案到底好不好。

**它是这套评测里唯一「要调模型来打分」的部分**，也是唯一**不写 `qa_log`** 的部分
（judge 的调用不属于任何一次用户问答）。成本独立、账本看不见 —— 已记为已知局限。

#### 工具：`ragas 0.4.3` + 独立 venv

```bash
python -m venv .venv-eval
.venv-eval/Scripts/python.exe -m pip install "ragas==0.4.3" "langchain-community<0.4"
```

> ⚠️ **第二个参数不是可选的。** ragas 0.4.3 对 `langchain-community` 的依赖**无上限**，
> 而 0.4.x 删掉了 ragas 要 `import` 的 `chat_community.chat_models.vertexai`
> → `import ragas` 直接 `ModuleNotFoundError`。按默认装法**必然装出一个装完就崩的组合**。

| 角色 | 用什么 | 为什么 |
|---|---|---|
| judge | DeepSeek 官方 `deepseek-flash` | 与生成模型同源（代价见下） |
| embedding | 硅基流动 `BAAI/bge-m3` | 与线上检索**同一个**嵌入模型 |
| `max_tokens` | **8192**（ragas 默认 1024） | `deepseek-flash` 是推理模型，1024 会被推理 token 吃光 → 空 content |

#### 取数与评判分开：`GET /api/debug/eval/answers?runId=`

RAGAS 要四样东西：`user_input` / `response` / `retrieved_contexts` / `reference`。
前两样和第四样在 `qa_log` 里，第三样要拼接三次：

```
qa_log.references 只有 chunk_id（没有正文）  → 回查 kb_chunk
   ↓
正文要按 RagPromptBuilder.truncate 截断      → 模型看到的是【截断后】的
   ↓
★★ 还要加上【结构化硬数据段】                → 它不在 references 里
```

**为什么端点返回两个 contexts 而不是一个**：

| 指标 | 用哪份 | 理由 |
|---|---|---|
| `faithfulness` | `contexts`（切片 **+ 硬数据**） | 判的是「答案有没有被**模型看到的全部输入**支持」 |
| `context_recall` | `contextsRetrievedOnly`（**只**切片） | 判的是「**检索**回来的东西准不准」 |
| `answer_relevancy` / `answer_correctness` | 不用 contexts | — |

> ★★ 把硬数据喂给 `context_recall` 会让它**虚高**：那段天数是**注入**的、不是检索来的，
> 拿它证明「检索质量好」是循环论证。而拿掉它又会让 `faithfulness` **虚低**。
> **一个数组满足不了两件事。**

> ★ 重建硬数据段必须走 `RagPromptBuilder.factsSection` **同一个方法**（已改 `public`），
> 切片截断同理。在评测里重写一遍就是**第二个事实来源**，它和 prompt 的漂移是静默的。

#### 五个指标（读装好的源码核实过，不是照文档抄的）

```
faithfulness        (user_input, response, retrieved_contexts)   答案每条陈述有没有依据
answer_relevancy    (user_input, response) + 嵌入                答案切不切题
context_recall      (user_input, retrieved_contexts, reference)  上下文能不能推出参考答案
answer_correctness  (user_input, response, reference) + 嵌入     答案对不对（★ 唯一测「对」的）
```

> ⚠️ **`context_precision` 默认不跑**：它每行要对**每条上下文**各判一次（一行约 5 次调用，
> 单项最大开销），而检索质量已由 §1.1 用 gold chunk id 精确量过。
> ⚠️ 但两者量的**不是同一件事**：§1.1 问「命中标注的切片了吗」，
> 它问「这段上下文里有没有能推出参考答案的信息」。
> 实测就撞上过一次矛盾（`MB-003`：归因桶 `ok` 而 `context_recall = 0`）。
> 要跑就 `--metrics` 显式加回来，**并与 §1.1 的数字并排读**。

> ⚠️ **0.4.3 的 `MetricResult.reason` 恒为 `None`**（四个指标的源码都是
> `return MetricResult(value=float(score))`）。所以**「为什么这题 0.389」不能靠判词解释** ——
> 本项目改用 §1.3 的**未命中归因桶**做替代依据。要拿 statement 级判定得实现
> 记录 `_create_verdicts` 返回值的子类，且**每次调用新建指标实例**
> （共用一个实例会让并发互相踩 `self.last_verdicts`）—— 本阶段不做。

#### 跑法与两条纪律

```bash
# 冒烟
.venv-eval/Scripts/python.exe scripts/eval_ragas.py --run <id> --limit 5 --tag smoke
# 分层抽样（每个 gold 叶子取 3 题，等距、无随机数）
.venv-eval/Scripts/python.exe scripts/eval_ragas.py --run <id> --stratify 3 --tag sample43
# 反-对照：上下文换成【不同意图】的题的，faithfulness / context_recall 必须掉
.venv-eval/Scripts/python.exe scripts/eval_ragas.py --run <id> --limit 4 --contexts scrambled --tag negative-control
# 续跑
.venv-eval/Scripts/python.exe scripts/eval_ragas.py --run <id> --stratify 3 --tag sample43 --resume
```

**① 排除判据是 `retrievalOf(intent) != KB`，不是 `references IS NULL`。**

工具题/兜底题的答案没有「检索上下文」可言，拿 `faithfulness` 去量它们是在量一个不存在的分母。
⚠️ 不能用 `references IS NULL`：它会把**「检索跑了但零召回」**的行也一起丢掉
（代码里确认过两者不等价），而那恰恰是 `faithfulness` 最该看的行。

**② 反-对照的对照物必须离得足够远。**

实测踩过一次：第一版只要求「换一道**别的题**的上下文」，结果 `C-007` 借到了 `C-011` ——
**同是 `COUPON`** 的题，上下文高度重叠，`faithfulness` 纹丝不动停在 `1.000`。
那次「对照通过」是假的：它证明的是「同类题的上下文很像」。
改成**必须借不同 `goldIntent`** 之后，依赖上下文的指标 4/4 归零，
而不依赖上下文的两个（`answer_relevancy` / `answer_correctness`）**纹丝不动** ——
★ 后者才是这个对照真正有说服力的地方：它证明扰动是**定向的**。

> ⚠️ **别引用没跑完的结果。** 实测：只跑 9 行时报 `faithfulness 0.978`，跑完 43 行是 `0.786`。
> 原因是完成顺序 = 题号字母序 = 意图前缀序，前几行系统性地更容易。
> **部分完成的结果不是「小一点的全体」，而是「排在前面的那一部分」** ——
> 而且从数字上看不出任何迹象。

> ⚠️ **性能**：judge 每次 `ascore` ≈ 2 次 HTTP、每次约 16 秒；换 `deepseek-v3-2` **更慢**（26 秒）；
> 并发 4 相对串行只有 **1.26×** 的吞吐增益（两家都硬限流）。
> 一行 4~5 个指标 ≈ 11~13 次调用 ≈ 3~5 分钟。43 题实测**约 2 小时**。

## 二、标注集规范

### 2.1 ★ 不存 chunk_id，存锚点

`kb_chunk.id` 是 **BIGSERIAL**，每台机器、每次重灌语料都不一样。
把硬编码的 id 提交进 git，换台机器后 ground truth 全部失效 ——
**而且不会报错**，只会让 `Recall@K` 变成 0 或随机数。

这是「阶段 7 的 A/B 对比做不了」最隐蔽的一种成因，因为它**没有任何症状**。

所以评测集存的是「该切片里独有的一段原文」，加载时反查：

```yaml
anchors:
  - text: 审核通过后，商品寄回并验收合格，退款在三个工作日内发起
    doc_hint: 售后FAQ
```

反查结果的处理**必须 fail loudly**：

| 命中条数 | 含义 | 行为 |
|---|---|---|
| 1 | 正常 | 采用 |
| 0 | 语料变了 / 切分改了 / 锚点写错 | **抛异常** |
| >1 | 锚点太泛，**或**内容真的重复 | 默认**抛异常**；写 `allow_multiple: true` 才接受 |

「静默取第一条」是最糟的选择 —— **基线漂移是评测系统里最难发现、后果最严重的错误**：
你会拿着两份不可比的报告去论证「优化有效」。

### 2.2 ★ 从语料反向构造的两种偏差（必须写进每份报告）

阶段 4 的 20 题是**先看切片、再写问题**构造出来的。这带来**两个独立的偏差**，
第二个是 2026-09-19 修订时才发现的（详见 §3.0）：

**偏差 A：问题太简单。** 用词天然贴近原文，比真实用户提问容易。
具体表现：向量路的 HitRate@5 直接就是 100%。

**偏差 B：★ 以为答案是唯一的，但语料里不是。** 反向构造时只看到**一个**切片，
就把它当成唯一正解 —— 而同一批业务规则往往被**多个文档**覆盖：

| 话题 | 覆盖它的文档（切片数） |
|---|---|
| 优惠券 | 促销活动规则 6 + 售后FAQ 3 + 退款到账时间说明 1 + 以旧换新服务说明 1 |
| 价保 | 促销活动规则 3 + 售后FAQ 2 + 价格保护政策 2 |
| 发票 | 售后FAQ 2 + 七天无理由退货政策 1 + 发票与保修凭证说明 2 |
| 退款 / 换货 / 保修 | 售后FAQ + 售后政策汇编 + 退款到账时间说明 |

**偏差 B 的后果比 A 严重得多**：A 只会让数字偏乐观，B 会让**结论的符号反过来**
—— 一个正确的答案被排到前面时，会被记成「变差」。

因此：

- 这份基线**只能用于「同一套题、不同配置之间」的相对比较**；
- **不能当作线上召回率**。真实分布的评测要等阶段 7 的人工标注集；
- **单答案 MRR 在多答案语料上是错的度量**。要么把 gold 补全（本项目的做法），
  要么改用只看「至少命中一条」的 `HitRate@K`。

### 2.2.1 ★ 补全 gold 的纪律

补 anchors 时，判断依据**只能是**「只读这一段文字 + 问题，它是否回答了问题」。

**不允许因为「某个配置把它排上来了」就补进去** —— 那是拿系统输出拟合标准答案，
评测从此失去意义。这条纪律必须能指出反例，否则等于没有：
**B-013「发票能开纸质的吗」刻意保持单答案**，因为被排到前面的那条讲的是**电子**发票，
它没有回答这个问题。**留着它，才能证明这条纪律真的在起作用。**

另外两条：
- **相关 ≠ 回答**。B-010 未采用 160（「已过期的优惠券不予返还」）——
  它讲的是**退货时**过期券退不退，不是「过期了该怎么办」。
- **每加一条都要在 YAML 里写明理由**，包括**未采用**的候选和原因。
  否则下一个人不知道某个候选是被考虑过并否决的，还是被漏掉了。

### 2.3 查询形态（`category` 列）

`category` 存的是**查询形态**，不是意图：

| 值 | 含义 | 例子 |
|---|---|---|
| `keyword` | 词典型 | 优惠券怎么用 |
| `model` | 型号型 | 星辰X1 电池能用多久 |
| `colloquial` | 口语句 | 这个适合长辈吗 |

三类查询在两条召回路上的表现本来就不同，报告必须能按它切片。

### 2.4 意图（`intent` 列）

> **★ 2026-09-19 阶段 5.1 起，`intent` 是【必填】的，且存【叶子】码。**
> 阶段 4 写的哨兵值 `UNCLASSIFIED` 已不再产生
> （理由「意图树还没定义」在树定义好之后就不成立了）。

**取值来源**：`data/agent/intent-tree.yml` 里的某个**叶子** `code`。
20 道基线题当前的分布：

```
RETURN_EXCHANGE 5   RULES_AND_PROCESS 4   COUPON 3   SCENARIO_PICK 3
REFUND 2            PRICE_PROTECTION 1    TRADE_IN 1  SPEC_QUERY 1
```

**为什么存叶子码而不是顶层码**（如 `PRODUCT_INQUIRY`）：
顶层码可以由树 roll-up 出来，**反过来推不出来**。
只存顶层，「价格保护这类题答得怎么样」就永远算不出来。
而且顶层错（路由去了错误的知识库区域）和叶子错（区域对了但细分偏了）
是两种严重程度不同的错，只存顶层码就分不出来。

**不复用 `doc_type` 的词表** —— 那会把「用户想问什么」和「文档是什么类型」
两个正交概念混在一起。

#### ★ 标注判据，以及它和「树」的责任分界

**标注的人只回答一个问题：「这句话在问什么」。**
**不回答「答案在哪几个 `doc_type` 里」** —— 那是树的声明，由一条自动校验盯着：

```
该题 gold 切片的 doc_type 集合 ⊆ 该题 intent 声明的 doc_types 集合
```

不满足 = **树画错了**，不是题标错了。见 `IntentTreeConsistencyTest`
（当前 20/20 通过），细节见 `docs/05` §9.1 与 ADR-031。

这个分界让 7.1 扩到 150 题时的标注工作变成：**判「在问什么」很快，
判「答案在哪几个 doc_type」很慢**（后者要通读语料）——
而后者已经被自动化了。标完 `intent` 跑一次测试，错了立刻报出来。

## 三、★ 阶段 4 基线结果（2026-09-19，同日修订过一次）

原始报告在 `eval_results/baseline-20260919*.{json,md}`（该目录已 gitignore，故摘录于此）。

**题集**：20 题（`keyword` 13 / `colloquial` 7），全部从真实语料反向构造。

### 3.0 ★★ 先说修订：第一版结论是错的，而且是评测集的错

第一版基线（当天上午）只给每道题标**一个**正解切片，跑出来两个「发现」：

- RRF 融合**有增益**（MRR@5 0.875 → 0.900）
- 重排**拖后腿**（0.900 → 0.883）

**这两个结论都被推翻了。** 起因是重排"弄坏"的 4 道题逐条打开看之后，
发现其中有 3 道的**正解标错了**：

| 题 | 标注的 gold | 重排提到前面的 | 谁真的答对了 |
|---|---|---|---|
| B-011 价格保护怎么申请 | `109` = 价格保护政策 **> 附加条件**「需提供降价截图；每笔订单仅可申请一次」 | `13` = 促销活动规则 4.3 **申请方式**<br>`28` = 售后FAQ「价保怎么申请」 | **重排** —— gold 标的那个是「附加条件」，不是「怎么申请」 |
| B-010 优惠券过期了怎么办 | `5` = 优惠券**有效期** | `25` = 售后FAQ「优惠券过期了能补吗｜**不能，过期自动失效不予补发**」 | **重排** |
| B-009 优惠券怎么用 | `6` = 优惠券**使用限制** | `7` = 优惠券**适用范围** | 两者都是答案 |

**根因**：语料里同一批业务规则被**多个文档**覆盖 ——
优惠券有 4 份文档 12 个切片在讲、价保有 3 份文档 7 个切片、发票有 3 份文档 5 个切片。
而题是**反向构造**的（看了一个切片就写问题，把那一个当唯一正解）。

**于是单答案 MRR 度量的是「有没有命中标注者随手挑的那一片」，不是「有没有答对」。**
重排选了一个同样正确的答案，却被记成变差。

> ⚠️ 修 gold 时有一条**纪律**：判断依据只能是「只读这段文字 + 问题，
> 它是否回答了问题」。**不允许因为「重排把它提上来了」就补进去** ——
> 那是拿系统输出拟合标准答案。
> 反例被刻意保留下来了：**B-013「发票能开纸质的吗」保持单答案**，
> 因为重排提到前面的 30 是「可以开**电子**发票吗」，
> 它**没有**回答「纸质」这个问题。重排在这道题上是**真的错了**。

### 3.1 各配置对比（修订后）

| 配置 | 说明 | HitRate@1 | HitRate@5 | Recall@5 | MRR@5 |
|---|---|---|---|---|---|
| `vector` | 纯向量 | **95.0%** | 100.0% | 98.3% | **0.9750** |
| `keyword` | 纯关键词（bigram + ts_rank） | 85.0% | 95.0% | 93.3% | 0.8917 |

| `full` | 双路 + RRF + 重排（线上实际链路） | **95.0%** | 100.0% | 98.3% | **0.9750** |

**未命中归因：20/20 都是 `ok`。**

### 3.2 ★ 受控对比：同一批检索结果，两种 gold 定义

为了把「gold 修正」的纯粹影响分离出来，拿**同一批检索结果**
分别用两套 gold 打分（`eval_results/baseline-20260919-*.json` 的 `stages` 字段）：

| gold 定义 | `vector` | `keyword` | `fused` | `full` |
|---|---|---|---|---|
| 旧（单答案） | 0.8750 | 0.8405 | 0.9000 | 0.8833 |
| 新（多答案） | 0.9750 | 0.8988 | 0.9500 | 0.9750 |

**两个"发现"的符号同时翻转：**

| 对比 | 旧 gold | 新 gold |
|---|---|---|
| 重排 vs 融合（`full − fused`） | **−0.0167** | **+0.0250** |
| 融合 vs 纯向量（`fused − vector`） | **+0.0250** | **−0.0250** |

**结论：这两条都不是链路的性质，是 gold 不完整的假象。**

> ⚠️ **但新的结论同样不能当结论**：两个量级都恰好是 0.025 = `0.5/20`，
> 也就是**一道题从第 1 名掉到第 2 名**。`fused − vector` 从 +0.025 翻到 −0.025，
> 只说明「在 n=20 上这个差异没有意义」，不是「RRF 有害」。

### 3.3 ★ 唯一稳的结论：效果按查询形态分裂

按 `category` 切片，两个配置正好互补：

| 形态 | 题数 | `vector` | `keyword` | `fused` | `full` |
|---|---|---|---|---|---|
| `colloquial` | 7 | 0.9286 | 0.7857 | 0.9286 | **1.0000** |
| `keyword` | 13 | **1.0000** | 0.9487 | 0.9615 | 0.9615 |

这个结构**有机制解释，因而不像是一次数巧合**：

- **`keyword` 类题上纯向量是满分（1.0000）** —— 因为题是反向构造的，
  词典型提问的用词天然贴近原文，向量一击即中，
  **后面任何环节都只能持平或变差**。这就是「重排伤害词典型」这个说法的真实来源：
  不是重排有问题，是**向量已经封顶了，没有提升空间**。
- **`colloquial` 类题上只有 `full` 是满分（1.0000）** —— 口语句没有词汇重叠，
  向量掉到 0.9286（B-001、B-017 都掉到第 2 名），
  **重排把这 7 道全部救回第 1**。
- **关键词路整体更弱（0.8917）**，而 RRF 会提拔"被关键词路认可"的切片 ——
  这正是 `fused` 略低于 `vector` 的原因。

**这才是重排真正的价值所在：它补的是向量在口语表达上的短板。**
真实用户提问里口语占绝大多数，所以阶段 7 的 150 题集必须含大量口语句
才能真正测出重排的收益。

### 3.5 ★ 这次修订真正的教训

**评测集的问题不会表现为「跑不起来」，只会表现为「结论是错的」。**

第一版基线是能跑的、有数字的、看起来有洞察的 —— 它提出了两个听起来很合理的

这个错误会一路带到阶段 7，然后用一份错误的基线去论证「优化有效」。

## 四、A/B 对比方法（阶段 7 用）

### 4.1 一次只改一个变量

这是能做归因的前提。所以：

- **`xbla.rag.rewrite.enabled` 默认关闭** —— 如果默认开启，阶段 4 的基线就带着改写的影响，
  阶段 7 无法回答「提升来自改写还是来自别的优化」；
- **`rewritten_question` 关闭时必须写 `null`，不能写原文** ——
  否则分不清「没开重写」和「开了但模型没改动」，而这是两个不同的实验条件；
- 所有可调参数都在 `xbla.rag.*` 配置里（召回条数、RRF 的 k、两路权重、重排候选数），
  **同一份代码改配置就能跑对比**，不用改代码重新编译。

★ **上面这个手法在阶段 7.6 之后有一个前提**：它要求
`xbla.rag.retrieve.by-intent.enabled=true`（默认值）。
关掉之后 `--docTypes` 会**静默地什么都不做** —— 见 §4.3。别再照抄这一段。

★ **意图定向检索（5.4）的开关不走配置，走 `RetrievalOptions` 参数** ——
因为它的取值**每道题不同**（由分类结果决定），不是一组固定的配置。
跑 A/B 时给 `/api/debug/kb/retrieve` 传/不传 `docTypes` 即可：

```bash
python scripts/probe_kb.py retrieve 退货要几天                    # 关闭（= 阶段 4 行为）
python scripts/probe_kb.py retrieve 退货要几天 --docTypes 2,4     # 开启
```

**★ 这个 A/B 有一个必须写进报告的坑**：`docTypes` 的正确取值来自意图树的声明，
而「声明对不对」又由 `IntentTreeConsistencyTest`（`gold ⊆ declared`）保证 ——
**两者是同一个来源，所以这个 A/B 测不出「声明错了会怎样」**。
那是分类错误的风险，需要另一套（更难构造的）实验。
见 `docs/05` §9.4 ① 末尾的警告。

### 4.2 报告必须带配置快照

`eval_results/*.json` 里的 `config` 字段记录当次运行的全部 `xbla.*` 配置。
没有它，阶段 7 拿着两份 JSON 只有两个数字，无法解释差异来自哪个参数；
有了它，diff 脚本能直接输出
「这次和上次只有 `chunking.max-chars` 从 500 变成 800」。

### 4.3 ★★ A/B 框架：`scripts/eval_ab.py`（阶段 7.6 新增）

```bash
# 自比对（同配置两轮）—— ★ 先跑这个，拿到噪声底
python scripts/eval_ab.py --a 20260921-stage7 --b 20260922-stage7-run2

# 真 A/B（配置不同）
python scripts/eval_ab.py --a 20260921-baseline --b 20260922-baseline-bad

# report.json 的算法改过之后（比的是算法版本，不是数据）
python scripts/eval_ab.py --a <x> --b <y> --refresh
```

输入是两份 run 目录（各含 `run.raw.json` + `report.json`），输出
**前置检查 → 配置 diff → 指标表 diff → 延迟 → 逐题翻转矩阵 → 连续量 → 怎么读**。

#### ★ 它不重算任何指标

指标只有一个出处：`GET /api/debug/eval/report?runId=`。
在这里重写一遍「取第一次 status=1」「众数投票」「归因桶」，
得到的是**第二份实现**——两边各自都自洽，只是数不一样，而没有任何东西会报错。
（`eval_report_check.py` 是**独立复算**用的对拍工具，不是日常取数用的。）

#### ★★ 它存在的第一理由不是「比较」，是**先量出噪声底**

同一配置跑两遍，翻转矩阵上的每一格翻转都是纯噪声。
**这个数先报出来，再谈差异**——否则「A 比 B 好 3 个百分点」是一句空话：
那 3 个百分点里有多少是抖动，没人知道。

支撑这条纪律的实测（`docs/05` §5.2 ④-b）：同 20 题、同 prompt、两轮各 8 次，
**准确率一样、错题一样，但逐题票型变了**（一道从 6:2 变成 8:0）。
「重复 N 次取众数」只测得出会话内稳定性，**测不出跨 run 漂移**。

#### ★★ 逐题翻转矩阵：三态必须摘掉，不能当 `false`

数据来自 `report.json` 的 `逐题.行`（阶段 7.6 新增的一节，一道题一行）。
每个判据一行：**共同可比几道、翻了几道、翻的是哪些题**。

```
意图正确 = null   ← gold 不是合法分类目标（三个工具叶子码），这一格【不可判】
命中@5   = null   ← 这道题不进检索分母（声明不检索 / 三次全被挡 / 正解切片已不在库里）
```

★★ **把 `null` 当成 `false` 的后果是具体的**：那 15 道工具题的「意图正确」
在**每一轮**里都是 `false`、一格都不会翻，矩阵看起来完全正常 ——
而「可比口径 93% vs 全体 84%」这 9.4 个百分点就这样被摊平进了噪声里。

所以**共同可比集 = 两侧都非 `null` 的题**，不是题库总题数。

#### ★ 连续量不做翻转计数

`recall@5` / `mrr@5` / `越界切片数` / `总耗时ms` 每一格都能「翻」
（0.667 → 0.666 算吗？），混进翻转率里会淹掉真正的信号。
它们报的是**总和与均值 Δ**。

#### ★ 延迟单独一节

延迟几乎每一格都会动，**这是它的性质，不是发现**。
判据只能是「噪声底之上的差异」。⚠️ 而且两轮的样本不同
（`被status≠1截掉的条数` 可能不同），比的**不是同一个总体**。

#### ★★ `--selftest`：先证明比较器不是瞎的

```bash
python scripts/eval_ab.py --selftest        # 11 项，全绿才有资格读它的结论
```

**一个瞎掉的比较器输出全绿。** 「翻转 0 道」既可能是「真的没翻」，
也可能是「它什么都没比」——**两者在屏幕上逐字相同**。

所以自检人为改坏 7 处，每一处都必须被抓到，且**恰好抓到那一处**：

| 人为改动 | 必须发生 |
|---|---|
| 什么都不改（自己比自己） | 配置/指标/翻转**全为 0** |
| 改 1 格 `命中@5` | 恰好 1 道翻转，**其它判据一道都不翻**（判据之间不串） |
| ★★ 把 1 格改成 `None` | 共同可比 −1，**翻转仍为 0** ← 三态的要害 |
| 改 1 个配置键 | 恰好 1 个差异，且不被算成「只在一边出现」 |
| ★ 删 1 个配置键 | 值差异 0、只在一边 1（自比对不谎报「配置改了」） |
| 改 1 个聚合指标 | 指标表恰好抓到 1 格 |
| — | 指标表里**没有**逐题路径（它们属于翻转矩阵） |

★ 第 3 条是最重要的一条：**若把 `None` 当 `false`，它在这里会变成「1 道翻转」**。
而那意味着每一轮里那些恒为 `None` 的格（15 道工具题的「意图正确」）
都在制造假翻转 —— 矩阵看起来完全正常，只是「可比口径」被摊平进了噪声。

★ 同样的理由写在 `eval_report_check.py --selftest` 里。T4 那次对拍抓到 3 处不一致，
**全是「投影的键对不上」而不是指标算错** —— 而「两边都少同一个键」那种瞎法，
只有自检能发现。

#### ★★ 前置检查不通过就【一个数字都不打印】

| 检查 | 不通过的后果 |
|---|---|
| `complete` / `reconcileOk` | 缺行会让每个比率的分母悄悄变小，**而比率看不出任何异常** |
| 语料 / gold 指纹一致 | 洞 7：重切后锚点部分悬空 → `|gold|` 变小 → Recall **反而悄悄变好** |
| `report.json` 有 `逐题` 段 | 旧算法生成的 report 做不了翻转矩阵 → 提示 `--refresh` |
| 两份 report 的顶层键集合一致 | 不同说明**比的是两个算法版本**，不是两份数据 |

#### ★ 「只在一边出现」的配置键**不算差异**

配置快照是**跑那一轮时**的 yml + 环境变量。跑在「这个键还没被加进 yml」
的那一轮，快照里就没有它 —— 而那一刻生效的是代码里的默认值
（很可能就是另一轮写的那个）。

把它算成差异的后果很具体：**自比对会谎报「配置改了」**，
而自比对的意义就是「配置一字未改，翻的都是噪声」。

#### ★ `final-top-k=1` 验证（2026-09-22 实测）

用一个**已知会变差**的假配置验证矩阵不是瞎的：

```

检索.Recall@5      0.958 → 0.525        Δ −0.433
检索.HitRate@5     1.000 → 0.900        Δ −0.100

```

★★ **同时它也演示了噪声**：`final-top-k` 只决定「几条切片进 prompt」，
**碰不到分类器**。可是同一批 20 题、同一个分类器，

★ 它证明的是一件更基本的事：**「配置不可能影响这一栏」不等于「这一栏不会变」**。

★★★ **三条设计纪律**，每一条都对应一个会静默出错的地方：

```
① 报告里一个硬编码的数字都不许有。

   同一个事实两个实现 = 迟早漂移，而且漂移是静默的。

③ 逐题表「只标差异」：两轮一致印一个值，不一致才印 `A→B`。
   全印会把 159 行变成 318 个值，真正的差异反而淹在重复里。
   ★ 同一条纪律在【行级】也成立：附录的「两轮不一致格数」把 `总耗时ms` 排除掉了 ——

```

#### ★★★ 4.5.1 §11 迭代实验：把「动了什么、然后去了哪」变成可复算的

前面十节回答的是「**我们现在在哪**」。§11 回答的是「**动了什么，然后去了哪**」——
这才是路线图验收里那句「体现迭代过程」的落点。

```bash
python scripts/eval_report.py \
  --t8-noise 20260922-stage7-run2,20260923-t8-noise,20260923-t8-noise2 \
  --t8-axes  20260923-t8-rerank-off,20260923-t8-topk8,20260924-t8-mc20
```

★★★ **它与前面十节在方法上的两点不同：**

```
① 噪声是【链】不是【一对】。
   N 轮同配置给出 N-1 个独立的噪声底样本，而「底稳不稳定」本身就是要报的事 ——
   只有一个样本时，「这个数换个时间跑还会不会是这样」没有答案。
   ★ 实测：13.2%（跨日）/ 14.5%（跨日）/ 16.4%（同会话）→ 【噪声不随日期漂移】。
   ⚠️ 而这一条推翻作者加第三轮时的假设：当时以为「同会话的底更紧」。不是。

② 基线取【链尾】，不取链首。
   三条轴紧跟在链尾后面跑，间隔最小 —— 拿链首当基线会白白多算一段漂移。

③ 轴的名字【不写死】。
   标题由 `config_diff(基线, 该轴)` 现算：「`xbla.rag.rerank.enabled` `true` → `false`」。
   换一期做别的旋钮，脚本不用改一行。
```

**每一条轴里有什么**（全部从数据算，没有一个写死的数）：

| 块 | 判据 |
|---|---|
| 配置差异 + **来源证据** | 每轮 `run.raw.json` 记了每个配置键的**来源**；只信 `origin` 非 `Config resource ...` 的那几条 ⇒ 「这一轮真的跑在它的覆盖下」是证据不是信任 |
| 延迟五段 | ★ `rerank_latency_ms` 在关掉重排时是 **NULL 而不是 0** —— 「没有发生」和「用了 0 毫秒」不是一回事 |
| 按 `category` 的检索侧切片 | 每片**自带该片的噪声底** + 二项单侧 p；★★★ **另有总体判据**，见下 |
| 连续量切片 | 每个 Δ 旁边就是**同一片**的噪声 Δ（命中率有翻转矩阵当尺子，**均值没有**） |
| `归因` 桶分布 | 「没召回到 / 被范围过滤 / 被重排截断」**修法完全相反**，必须分开数 |
| **命中集合的包含关系** | 见下 |
| 成本 + **缓存命中率（反推）** | 见下 |

★★★ **总体判据不能省** —— 实测撞到的形状：

```
命中@5 翻转 4 / 130，噪声 1 / 130，总体 p = 0.018  →  ★★ 超过噪声
而切到 87 / 26 / 17 之后，【三片全都不显著】

⇒ 只印逐片判据的话，读的人会得出「这个旋钮没效果」的【错结论】。
  正确的读法：效果是真的，但小到切完就指不出集中在哪一类。
  ⚠️ 反过来说：任何「效果集中在某一类」的说法在这一轮【都没有证据】。
```

**★★★ 命中集合的包含关系 —— 把结构性论证从原理变成实证**

有些旋钮的效果**在原理上就是单向的**，可以直接判方向而不用等数据：

```
final-top-k 调大        ⇒ contexts 是超集 ⇒ context_recall / faithfulness 【结构性不可能下降】
rerank.max-candidates 调小 ⇒ 重排候选是子集 ⇒ 召回【结构性不可能上升】
rerank.enabled 开关      ⇒ 两条完全不同的排序 ⇒ 两个方向都不该压倒
```

★ 但「原理上成立」和「这一轮真成立」是两件事 —— 重排分数有约 3e-4 的漂移，
边界的切片偶尔会进出。所以报告把它**量出来**：

| | n | B ⊇ A | 命中的正解切片**丢了** |
|---|---|---|---|
| 同配置噪声对 | 131 | 98.5% | **2（1.5%）** ← 纯重排漂移的底 |
| `final-top-k` 5→8 | 131 | **100.0%** | **0（0.0%）** ← 超集关系无一例外 |
| `rerank.enabled` 关 | 130 | 94.6% | **7（5.4%）** ← 噪声的 3.6 倍 |

⚠️ `逐题.命中的正解切片` 在 `report.json` 里是**字符串**（形如 `[5, 25]/[5, 25]`），
不是数组。直接当集合用会得到一个**逐字符**的垃圾集，而且**不报错** ——
所以解析失败时整段静默跳过，`n` 必须印出来。

**★ 缓存命中率为什么要反推**

```
关掉重排之后：token 只涨 1.6%，成本却涨 9.5%  ——  涨了 9 倍，不是 token 能解释的
```

`ModelCostCalculator` 的公式是三档加权的：

```
cost = 未命中输入 × input + 命中输入 × cacheHitInput + 输出 × output    （都除以百万）
```

而 **`prompt_cache_hit_tokens` 参与计费、却不落库** —— 算完就丢，
`qa_log` 里没有这一列。所以「成本为什么变」只能从 **成本 + token 拆分 + 三档定价**
反推出来（后两样都在 `run.raw.json` 的配置快照里）。

⚠️ **反推假定整轮只用一个模型** —— 有降级行（P1/P2）时它不成立。
脚本因此有两道自检：解出的命中数落在 `[0, 输入 token]` 之外、或成本节点里
没有 token 拆分时，**拒绝出数**并写明原因，而不是印一个看起来像模像样的百分比。

**★ 三个自动检查**（都写进 `--selftest` 或 `--coverage`）：

```
--selftest        21 项。含三条【反对照】：
                  · 比值相同但分母不同 → 必须标差异（只比 `值` 的版本会漏）
                  · 不同 bootstrap 种子 → 必须给出不同区间（否则「种子固定」是空话）
                  · false 与 —（三态）在报告里必须可区分
--coverage        report.json 的每个叶子路径，报告要么访问过、要么在 OMITTED_PATHS 里写了理由。
                  ★★ 【没有这个检查，`EvalReportService` 加的新键会静默地不进报告】
                  ★ 判据用「访问记录」而不是「文本匹配」—— 后者会漏，
                    而漏掉的后果是这个检查慢慢变成噪声、然后被无视。
可复算            同一份数据连跑两次，报告与附录【逐字节相同】（bootstrap 种子固定）
```

**★★ 两处它会主动喊出来的事**（都不是「算错了」，是「不该忽略」）：

- **代码版本混淆**：用 `归因.★截断可判定性` 当**代码版本代理指标** ——
  它数的是 `retrieval_detail` 里有没有 `sizes` 段。两轮这个数不同，就说明它们不只差了配置。
  ⚠️ 这一条不查是查不出来的：`run.raw.json` 里**没有代码版本字段**。
- **工作区未提交**：报告头写 `HEAD` 的同时，会报「工作区有 N 项未提交改动」——
  ★ 只写 HEAD 是不诚实的，它指向的是**上一个里程碑**，而数字来自工作区。
