# 01 · 产品需求文档

> **读者**：第一次接触这个仓库的人（面试官 / 同行 / 想跑一遍的人）。
> **本文不回答**「怎么实现的」（→ `docs/03` 架构 / `docs/05` 检索与智能体）、
> 「为什么这么选」（→ `docs/08` ADR）、「现在做到哪了」（→ `docs/10` 路线图）、
> 「跑出来多少分」（→ `docs/11` 评测报告）。
> ★ **本文只回答两件事：要什么，以及怎么算做到了。**

---

## 一、这是什么

### 一句话

用户在电商场景里问一句话（商品咨询 / 规格对比 / 促销政策 / 售后服务），
系统**先判断该去哪找答案**（知识库 / 实时数据库 / 都不用），找到之后
**用检索到的原文作答并给出出处**；资料不够时**反问**，而不是猜一个答案。

### 不是什么

| 它不是 | 因为 |
|---|---|
| 通用聊天机器人 | 范围锁在商品导购与售后。超出范围的输入会明说「我只处理这些问题」，而不是硬答 |
| 「包了一层大模型 API 的问答」 | 回答的依据是**检索到的切片**，并且**出处随回答一起返回**。没有依据时不假装有 |
| 一次性的 demo | 检索质量**可量化、可复现、可优化**：每个结论都要能跟"同配置重跑一遍能差多少"比大小 |
| 已经能对外营业的服务 | 见第七节「明确不做的事」。身份是明文头、没有登录、没有公网入口 |

### 这个项目真正想证明的一件事

★★ **"检索质量可量化、可复现、可优化"不是一句口号，它是一组能被违反的纪律。**
本仓库里最贵的几条产出不是功能，而是：

1. **噪声底** —— 同配置跑两轮，**至少翻一格的题约占 13%~16%**（每期实测值见 `docs/11` §1）。
   ⇒ 任何「提升了 X%」的结论，**先跟这个数比大小**，否则是在读噪声。
2. **判据用「实际发生」，不用「门控说了什么」** —— 见 F3 / F5 的判据列。
3. **一个只被写过、没被跑过的检查，和没写过在验收上没有区别。** 这条有实测代价，见 `docs/10` 坑 51/53。

## 二、需求从哪来

### 语料（答案的来源）

本项目的知识库是**仿真语料**，不是真实企业的文档 —— 这一条必须先说清楚。

| 项 | 实测值（2026-09-26） |
|---|---|
| 文档 | 207 篇（商品详情 / 售后政策 / 促销规则 / FAQ / 说明书，五类） |
| 切片 | 1643 条（1024 维向量，`bge-m3`） |
| 业务数据 | 200 个商品（189 个在售）/ 30 个用户 / 120 笔订单 |
| 生成方式 | `scripts/generate_corpus.py`，★ **字节确定**（产物一变，入库去重静默失效） |

★ **为什么要仿真语料**：真实电商文档拿不到，而"随便编几段文本"测不出真问题。
仿真语料的价值在于它**复刻了真实语料的难点**，实测有据的几条：

- **同一件事被写在三份文档里** —— 「价格保护」的答案横跨促销规则(3) / 售后政策(2) / FAQ(4)。
  任何"按类型硬过滤"的做法都会切掉一部分正确答案。这是**故意保留**的压力测试。
- **商品名会重复** —— 200 个商品里 17 组重名。这是真实电商的常态，不是数据 bug；
  它逼出了"正文永远带 `product_no`"这条约定。
- **售后是问题最密集的域** —— 它只占切片总数的 4.1%，却承接 55% 的评测题。
  这正是"只对窄类型做定向收窄"能拿到收益的根本原因。

### 问题（要回答什么）

从语料里可回答的问题，按**用户想干什么**分成 5 类业务意图 + 2 个非业务分支。
完整的判据在 `data/agent/intent-tree.yml`（那份文件本身就是需求文档）：
**商品咨询 / 购买决策 / 促销活动 / 售后服务 / 订单物流**，
外加 `OUT_OF_SCOPE`（不是我的业务）和 `NEEDS_CLARIFICATION`（是我的业务，但没说清）。

★ **为什么这两者必须分开**：混起来用户会拿到错误的回答 ——
问「那个怎么样」会收到「我只处理商品导购与售后问题」，而那句话明明就是在问商品。

### 用户与场景

| 用户 | 场景 | 他真正要的 |
|---|---|---|
| 买家（售前） | 「星辰X1 电池多大」「这个适合送长辈吗」 | 参数事实 / 选购建议 + 依据 |
| 买家（售中） | 「满减怎么算」「优惠券能叠加吗」「保价怎么申请」 | 规则里的**数值和条件**，不能含糊 |
| 买家（售后） | 「退货要几天」「退款多久到账」「保修吗」 | **时限 + 我要做什么**（去哪点、传什么材料） |
| 买家（查自己） | 「我的订单到哪了」「我还有几张券」 | **实时数据**，知识库里没有 —— 必须查库 |
| 运营 / 评测者 | 想知道"这次改动到底有没有用" | 可复算的指标，不是感觉 |

★★ **最后一类是这个项目的差异点。** 大多数问答系统的"效果"只能靠体感，
而本仓库把「效果」做成了**一个能被别人重跑一遍的数字**（见 F10）。

## 三、功能需求

> **状态列怎么读**（★ 这三档必须分开，混起来这份文档就没用了）：
> ✅ **已实测** = 有命令、有输出、有日期，能找到证据；
> 🔶 **已实现、未实测** = 代码在，但没有跑出过数字；
> ❌ **未做**。
>
> ★ 判据列写的是**「怎么算做到了」**，不是「怎么实现的」。
> 凡判据里出现「应该」「预期」而没有对应实测命令的，等于没有判据。

### 问答主链

| # | 需求 | 判据 | 状态 |
|---|---|---|---|
| **F1** | 用户提问后**逐字流式返回**，并在回答末尾给出**引用出处** | SSE 每帧以空行结束、`event:` 与 `data:` 之间无空行；由时间量 delta 的到达分布证明**真的在流**（而不是被代理攒着一次吐出）；`probe_stage8.py` 33 项 | ✅ |
| **F2** | **先判断这句话在问什么**，再决定去哪找答案 | 20 题基线集 × 8 次取众数，Top-1 意图 = **18/20 = 90%**（2026-09-25 复测，`eval_intent_probe.py`） | ✅ |
| **F3** | **「这次要不要检索」由模型在分类那一次调用里同时给出**，且判断只在**一处**发生 | ① `intent_plan.shape = JSON` 占比 **100%**（契约生效的唯一判据，9.6a 实测）；② `★算对了但没用的行`（门控说了和实际做的不一致）**恒为 0** | ✅ |
| **F4** | 资料不够时**反问**，而不是猜一个类别去检索 | 单轮：`status=3`；多轮：首轮该反问的反问到了 **16/18**、不该反问的**一次都没反问（6/6）**；追问后**恢复 16/16 全部成立**（9.6a，8 题 × 3 次） | ✅ |
| **F5** | 需要**实时数据**的问题去调工具（订单 / 库存 / 券 / 商品搜索比价推荐） | ① `不该有工具_却调了` **恒为 0** —— 白名单拒绝也留调用记录，所以这一格是「白名单在**服务端**强制」那条不变式**在数据上的形状**，可观测；② **纯工具轮：手上真有工具的 33 行里调了 30（91%）**（库存 12/12、我的券 3/3、订单状态 15/18） | ⚠️ **一半，且有一个明确的空洞** |

★★ **F5 的空洞要说清楚（实测，2026-09-26，159 题 × 3 次）**：

```
【手上真的有工具】的行 73 条，模型调了 30 条 = 41%
  ├─ 纯工具轮（订单/库存/券）  33 条 → 调了 30 = 91%   ✅
  └─ 混合轮（按场景选购）      36 条 → 调了  0 =  0%   ❌ 一次都没调
```

**混合轮（先检索知识库、再给三个商品工具）在数据上没有产生任何行为** ——
12 道题 × 3 次，模型全部只用了检索到的切片作答。
⚠️ 而**这一格分不出**「切片够用了所以不用调」和「忘了调」——
要判它得逐条读那 36 个回答原文。**没读之前不许把它写成缺陷。**

★ 另有一个缺口**不在工具层，在分类层**：`我的优惠券` 有 9 行压根没被分到工具意图上
（手上就没有工具）—— 那是 F2 的问题，不是 F5 的。

### 检索

| # | 需求 | 判据 | 状态 |
|---|---|---|---|
| **F6** | **双路召回 + 融合 + 重排**，而不是单路向量搜索 | 检索中间产物（召回 / 融合 / 重排 / 最终）**六段全部落库**，且与调试接口**同一纯函数**产出（永不漂移） | ✅ |
| **F7** | 按意图**收窄候选池**（但只对窄类型收窄） | 过滤与否的判据是**池子绝对大小 ≥ top-k**，不是收窄倍数 —— 实测倍数跨 1.1×~328×，而**倍数越大越危险**（ADR-043） | ✅ |
| **F8** | 检索失败**不影响问答**（退化成裸聊，而不是 500） | ⚠️ **目前只有代码里的设计，没有判据**：`retrieveSafely` 吞掉异常，但**没有任何测试让它抛过**。这条要么补一个「让检索抛异常、断言仍然回答」的用例，要么承认它是没验过的 | 🔶 **已实现、未实测** |
| **F9** | 给用户的**出处**必须与生成时用的是同一批切片 | `retrieval_detail.final_top_k` 与 `references` 同源 | ✅ |

## 四、非功能需求

### N1 延迟

- **目标**：端到端 p50 在秒级可接受范围内，且**延迟要能拆开看**，不是看一个总数。
- **实测数字**见 `docs/11` §2.8（本文不复制 —— 它每一轮都会变）。
- ★★ **两条结构性事实**（比数字本身更重要，也是它们让「拆开看」这件事不平凡）：
  1. **五段不相加等于 total** —— `rerank ⊂ retrieval` 是**包含关系**不是并列项；
     而**意图分类是一次 0.5~2.5 秒的模型往返**，它进了 total 却**不在任何一段里**（就叫「未归类」）。
     ⇒ 它的量级（0.5~2.5 秒）**与「生成」相当**，也就是说**它值得被单独优化**，
     而正常读报告的人会在「五段」里到处找它，找不到。
     ⚠️ 别把「检索慢」和「分类慢」并成一格 —— **两者的修法完全相反**。
  2. **客户端测的「总耗时」噪声底是 ±230 ms** —— 延迟差异只有**服务端那几列**能判。
     拿客户端时钟测出来的「快了 100ms」是在读噪声。

### N2 容量与过载行为

| 项 | 值 | 为什么是这个数 |
|---|---|---|
| 并发上限 | **8** | 从三处下游约束推出来的（应答池 8 / 检索池 16 / **数据库连接池 10 才是真瓶颈**）。调大它不会让吞吐变高，只会让更多请求同时抢 10 个连接 |
| 队列上限 | **500** | 满了**如实拒绝**，而不是无限排下去 |
| 排队超时（流式） | **120 s** | 每 200ms 推「你前面还有 N 位」⇒ 是**有信息的等待** |
| 排队超时（非流式） | **30 s** | 没有推送通道 ⇒ 120 秒就是一个转圈的页面。且必须**比客户端自己的超时先发生** |
| SSE 连接超时 | **180 s** | 比排队超时多 60 秒余量，让"排队超时"先发生 —— 否则用户看到的是**没有任何说明的断流** |

★ **过载时的行为是被设计过的，不是被容忍的**：四种拒绝（队列满 / 池满 / 排队超时 / 名额耗尽）
各自对症一个**不同的旋钮**，但它们在 `qa_log.queue_ms` 上**长得一样**（实测 0 在两种拒绝下都出现过）——
⇒ 判据只能是 `error_msg` 的原因串。

### N3 成本

- ★ 所有模型调用**经过同一层封装**，计费逐条落库（服务端账本），**可归因到每一次问答**。
- 量级：一期评测（多轮 × 159 题 × 3 次重复）的成本在**一元上下**，逐轮的准确数字见 `docs/11` 报告头。
- ⚠️ **账本有三个刻意的例外**（不记在 `qa_log`），报告里必须写明，否则成本看起来比实际低：
  意图分类、摘要压缩、RAGAS 判官。
- ★ 一次问答的成本与延迟的大头在**生成**，不在检索 —— 这决定了优化的方向。
- ★★ **成本还取决于缓存命中**：同样的 prompt 前缀命中率实测在 **70% 上下**，
  而 `prompt_cache_hit_tokens` **参与计费但不落库** —— 只能从 token 数和三档定价**反推**。
  ⇒ 这是**「优化了前缀稳定性」这类改动的唯一可见收益点**，也是**最容易看不见的收益点**。

### N4 可复现（★ 这是纪律，不是特性）

- **评测必须串行**。并发会让 `queue_ms` 混进延迟分位数 —— 实测数字照样印出来、照样好看，**只是它量的不再是那条链路**。
- ★★ **一个 run id 只能跑一次**，而保护必须问**它的语义所在的存储**（数据库），不能只问本地产物。
  实测事故：删掉本地目录再跑同一个 id，两轮的行落进同一个筛子，**而账面对得上**（它防行少了，不防行多了）。
- ★★ **任何 A/B 结论先跟噪声底比大小**。同配置两轮「至少翻一格」的比例就是那把尺子（每期值见 `docs/11` §1）。
- ⚠️ **噪声不随日期漂移** —— 实测同会话的 16.4% **不**比跨日的 13.2% 小。
  ⇒ 「换个时间重跑一遍」消不掉它。

### N5 安全与身份

| 项 | 现状 | ★ 必须如实说明的边界 |
|---|---|---|
| 模型 API Key | 只走环境变量 / 已 gitignore 的本地配置，**从不进代码、从不进 git** | ✅ |
| 工具的身份 | **只能来自服务端上下文**，不能是工具参数 | ★ 工具参数是**模型填的** —— 加一个 `user_id` 参数就是模型可控的越权入口，一段提示注入就够了 |
| `X-Xbla-User-Id` | 明文、**未签名** | ⚠️ **这不是认证**。它做到的是「身份不进模型的可控范围」，另一半需要 OAuth —— **未做，不要含糊过去** |
| 伪造身份头 | 会被**核对**；查不到就按匿名处理 | ★ 实测代价：不核对会让「每次对话 500」，而报错里一个字都不提那个头 |
| 调试端点 | 全部 `@Profile("local")`，**公网上必须 404** | ⚠️ 默认配置是 `local` —— 容器化必须**显式**切到 `prod`，否则这些端点跟着公网一起暴露 |
| 生产只读端点 | 判据是**白名单**，不是黑名单 | ✅ |
| 内网穿透 | **未开** | ★ 开它 = 把服务暴露到公网，是外向动作，需要单独决策 |

### N6 可观测

- **`traceId` 贯穿一次问答的全部环节**：排队 → 分类 → 检索 → 工具 → 生成 → 落库。
  前端「技术面板」和运维排查读的是同一条。
- ★★ **落库的每一列都要能回答一个具体问题**，不许有"为了以后可能有用"的列。
  反例（实测踩过）：一门新的指标要算，而它需要的列**没在显式列清单里** ——
  症状是**一个看起来合法的 0**（null 被 `!= null` 挡掉），**不报错**。
- ★ **「读了但读不到」和「本来就没有」必须能分开** —— 前者是 bug，后者是事实。
  两者在数据库里都是 NULL，只有专门的调试接口 + 日志分得开。

### N7 数据与配置的确定性

- **语料生成字节确定**（时间戳钉死）—— 产物一变，入库去重静默失效、重扫会**重复灌并真的花向量化钱**。
- ★ **凡会进 Prompt 前缀的 JSON，一律用插入有序的容器** ——
  哈希序会随每次 JVM 启动变，代价是前缀缓存**整段未命中（差 50 倍）**。
- ★ **兜底异常处理器会把 404 变成 500** —— 本项目**每一个 404 都曾被渲染成 500**，
  一直到有人真的去验"必须 404"的那一条才发现。⇒ **任何想要特定状态码的异常都必须显式注册。**

## 五、需求之间的依赖与取舍

几条**成对出现、改一个必须看另一个**的关系（违反都不报错）：

| 关系 | 为什么 |
|---|---|
| 「检索」与「工具」**互斥**（除一个混合轮叶子） | 工具意图去检索知识库，会让模型**编一个订单状态出来**（静态文档里没有实时数据，而它会填一个看起来合理的） |
| 「澄清」与「检索」**互斥** | 澄清路径不检索不生成，所以出处/成本/延迟**全是 NULL** —— 那是「没有发生」的诚实表达。⚠️ 别传空对象：空 trace 和「检索跑了但没召回」序列化出来**逐字相同** |
| 「偏好」只能**重排** | 让它参与召回：买过 3 次吸尘器的人问「送长辈」会收到一台吸尘器，而那个列表**读起来像一份很贴心的推荐**，没有任何东西会报错 |
| 「历史」只喂**生成**、不喂**分类** | 分类的准确率基线建立在「分类器只看这一句话」之上。喂了历史，那条基线当场作废 |
| 澄清状态**只进分类那一次调用** | 与上一条的边界：禁的是喂**自由文本历史**；这里是一小段**结构化状态**，且**只出现一轮**（读后即清） |

## 六、明确不做的事（★ 边界也是需求）

| 不做 | 原因 |
|---|---|
| 真实登录 / OAuth | 身份是明文头。**如实说**，不含糊过去 |
| 多租户 / 权限体系 | 本项目是单租户演示 |
| 流式工具轮的**打字机** | 工具轮正文**一次推完** —— 这是拍板过的边界，不是没做完 |
| 第五个 `status`（"无依据的闲聊"） | 引入它要付一次迁移 + 一处短路，而收益只是措辞更精确 |
| 画像表 / 偏好缓存 | 偏好从订单**实时派生**。缓存会引入"改了订单多久生效"这个新问题 |
| 内网穿透（公网演示） | 外向动作，需要单独决策 |
| 「猜测式」的兜底 | 资料不足时**反问**（F4），超范围时**明说**（F2），两者都不猜 |
| 把 `docs/00` / `docs/09` 进仓库 | 那是**给面试用的叙述材料**，不是项目交付物 |

## 七、验收：怎么知道它成了

一条需求被算作「做到了」，要同时满足：

```
① 有判据，且判据是「实际发生」而不是「代码说了什么」
② 有正-反对照（断言 A 成立的同时，断言「不做 A 的版本确实不成立」）
      否则断言可能恒真
③ 有从【入口】进去的测试，不只是纯函数单测
      实测代价：门控的 34 项单测全绿，而每一句「你好」都会 500
④ 有活体证据（命令 + 输出 + 日期），且数字跟噪声底比过大小
```

★ **第 ③ 条是本项目最贵的一课**：

```
纯函数单测证明了「判据是对的」
集成测试证明了「调用点用了它之后还活着」
两条缺一不可。
```

★ 自动化验收入口：`./mvnw clean test`（**1122** 项，`docs/10` 记着每个阶段加了多少）
+ `scripts/` 下的探针（`probe_*.py` / `eval_*.py`，多数**不花钱**）。
