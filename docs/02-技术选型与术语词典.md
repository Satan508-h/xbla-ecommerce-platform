# 第一部分 · 后端地基

## 1. JDK / JVM

**① 是什么**
JDK（Java Development Kit）= 写 Java 程序用的工具箱，包含编译器（把 `.java` 变成 `.class`）、运行时、和自带类库。JVM 是运行时的核心——**Java 代码不是直接在你电脑上跑，而是跑在一个虚拟的"小电脑"里**，这台虚拟小电脑就是 JVM。

**② 解决什么问题**
"一次编写，到处运行"。同一份 `.class` 文件，Windows、Linux、Mac 上都能跑，因为每个平台各有一套 JVM 负责翻译。

**③ 不用它会怎样**
没有 JDK 就没有 `javac` 命令，Java 代码根本编译不了。

**④ 优点**
- 生态最庞大的企业级语言，银行 / 电商 / 大厂后端主力
- 有垃圾回收（GC），不用手动管理内存
- JDK 21 引入虚拟线程，高并发场景下能用更少资源扛更多连接

**⑤ 缺点**
- 内存占用大，JVM 本身就要吃几百 MB
- 启动慢（Spring Boot 应用启动 5–15 秒很正常）
- 版本碎片化严重，不同项目要不同 JDK 版本，得来回切

**⑥ 本项目用在哪**
全程。固定用 **JDK 21 LTS**。LTS = Long Term Support，长期支持版，官方会维护很多年。你电脑里有 JDK 8、11、24 但都没配好；**JDK 24 不是 LTS，且部分做字节码增强的库（MyBatis-Plus、Redisson、Lombok）可能报 `Unsupported class file version`**，所以选 21。

---

## 2. Spring Boot

**① 是什么**
一个 Java 后端"框架的框架"。原本写一个 Web 服务，你要手动配 Tomcat 服务器、配 JSON 转换、配数据库连接池、写一堆 XML；Spring Boot 把这些**全都预设好了**，你只写业务代码。

打个比方：Spring 是"给你一堆零件自己组装电脑"，Spring Boot 是"给你一台装好系统、开箱能用的品牌机"。

它核心是三件事：
- **自动配置**：引入数据库依赖，它自动帮你配好数据源
- **起步依赖（Starter）**：一句 `spring-boot-starter-web` 拉进一整套 Web 开发需要的库
- **内嵌服务器**：不需要单独装 Tomcat，你的程序自己就是服务器

**② 解决什么问题**
解决 Java 后端的"配置地狱"。没有 Spring Boot 之前，搭一个能跑的 Web 项目要写几十行 XML。

**③ 不用它会怎样**
得手动管理几十个库的版本兼容、手动配 Tomcat、手动写配置文件，开发效率下降数倍。

**④ 优点**
- 上手极快，`main` 方法一跑服务就起来了
- 生态无敌：几乎所有 Java 库都提供 Spring Boot 集成包
- 面试刚需：国内 Java 后端岗位 90%+ 要求 Spring Boot

**⑤ 缺点**
- **"魔法太多"**：自动配置帮你做了很多事，出问题时不知道从哪查（这是它最常被吐槽的点）
- 启动慢、内存占用大
- 版本升级有破坏性变更（2.x → 3.x 要求 JDK 至少 17）

**⑥ 本项目用在哪**
整个后端的地基。使用 **Spring Boot 3.x**（3.x 强制要求 JDK 17+，所以必须配 JDK 21）。

---

## 3. Maven

**① 是什么**
Java 的**依赖管理和构建工具**。干两件事：
1. **依赖管理**：你要用 MyBatis-Plus，不用去官网下 jar 包，在 `pom.xml` 里写一行 `<dependency>`，Maven 自动从中央仓库下载，还会自动把它依赖的其他库一并拉下来（叫"传递性依赖"）
2. **构建**：一条命令完成编译、测试、打包成可运行的 jar

**② 解决什么问题**
在没有 Maven 的年代，你要手动下载几十个 jar 包、手动解决 "A 库需要 B 库 1.2 版，C 库需要 B 库 2.0 版" 这种版本冲突地狱。

**③ 不用它会怎样**
要么手动管 jar 包（噩梦），要么换 Gradle（另一个同类工具，用 Groovy/Kotlin 写配置，更灵活但学习曲线陡）。

**④ 优点**
- 用 XML 写配置，结构清晰，约定大于配置
- 中央仓库几乎收录了所有 Java 开源库
- 国内有阿里云镜像，下载速度从"等半小时"变成"等十秒"

**⑤ 缺点**
- XML 配置文件啰嗦，依赖一多 `pom.xml` 就变得很长
- 版本冲突排查困难，遇到 `NoSuchMethodError` 经常要花很久
- **不配国内镜像的话，从中央仓库下载依赖在国内会慢到崩溃**

**⑥ 本项目用在哪**
构建整个后端。**第一件必须做的事就是配阿里云镜像**，否则你会在"下载依赖"这一步卡一整天。

---

## 4. MyBatis-Plus

**① 是什么**
**数据库操作工具**。它让你不用手写 SQL 就能完成大部分数据库的增删改查。

对比感受一下：

```java
// 用原生 JDBC 查一个商品
String sql = "SELECT * FROM product WHERE id = ?";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setLong(1, id);
ResultSet rs = ps.executeQuery();
Product p = new Product();
if (rs.next()) { p.setName(rs.getString("name")); /* 几十个字段挨个 set */ }

// 用 MyBatis-Plus
Product p = productMapper.selectById(id);
```

**② 解决什么问题**
解决"重复写样板代码"和"数据库字段名到 Java 属性名的手动映射"。MyBatis-Plus 还额外提供了代码生成器、分页插件、条件构造器。

**③ 不用它会怎样**
纯 MyBatis：每个查询都要手写 SQL 和 XML 映射文件。纯 JPA/Hibernate：全自动生成 SQL，但复杂查询不好控制、性能不透明。

**④ 优点**
- **简单查询零 SQL**，复杂查询仍可手写 SQL——**保留了对 SQL 的完全控制权**（这点对 RAG 项目很关键，因为向量检索必须手写 SQL）
- 支持分页、逻辑删除、乐观锁等常用插件
- 国内使用极广，面试认可度高

**⑤ 缺点**
- 是个**国产框架**，外企/海外团队基本不用（他们用 JPA 或 jOOQ）
- 过度使用 `QueryWrapper` 会让复杂查询变得难以阅读
- 更新迭代快，版本兼容性偶尔有小坑

**⑥ 本项目用在哪**
所有业务表的增删改查（商品、订单、优惠券、会话记录等）。**但向量检索部分不通过它，而是手写 SQL**——因为 `embedding <=> ?` 这种 pgvector 特有的操作符 MyBatis-Plus 不支持。

# 第二部分 · 数据存储

## 5. PostgreSQL

**① 是什么**
一个**关系型数据库**，和 MySQL 是同类产品。你可以把它理解成一个超级 Excel：数据存在一张张表里，表与表之间可以关联，用 SQL 语句查询。

**② 解决什么问题**
持久化存储结构化数据。程序重启数据不丢，多个人同时读写不会乱。

**③ 不用它会怎样**
用 MySQL（国内更常见）、Oracle（贵）、SQL Server（微软系）。或者用文件存（并发一上来就废）。

**④ 优点**
- **功能比 MySQL 强很多**：支持 JSON 字段、数组类型、全文检索、地理信息、自定义类型
- **有 pgvector 这样的插件生态**——这是本项目选它而不是 MySQL 的决定性原因
- 严格遵循 SQL 标准，行为可预测
- 开源免费，没有 MySQL 那样的商业授权顾虑

**⑤ 缺点**
- 国内熟悉的人比 MySQL 少，很多公司还在用 MySQL
- 默认配置偏保守，需要调优
- 主从复制、分库分表生态不如 MySQL 成熟（但本项目用不到）

**⑥ 本项目用在哪**
存所有业务数据 + 知识库切片 + **向量**。因为 pgvector 只支持 PostgreSQL，所以这是硬性选择，不是偏好。

## 6. PgVector

**① 是什么**
PostgreSQL 的一个**扩展插件**，让数据库多了一种叫 `vector` 的数据类型，并且能对这种类型做"相似度检索"。

安装后你就能这样建表：
```sql
CREATE EXTENSION vector;

CREATE TABLE kb_chunk (
    id        BIGSERIAL PRIMARY KEY,
    content   TEXT,
    embedding vector(1024)   -- 一列存 1024 个浮点数
);
```

然后这样查"最相似的 5 条"：
```sql
SELECT content FROM kb_chunk
ORDER BY embedding <=> '[0.1, 0.2, ...]'::vector
LIMIT 5;
```

`<=>` 是 pgvector 提供的"余弦距离"操作符。

**② 解决什么问题**
RAG 的核心是"**从知识库里找出和用户问题语义最接近的几段文字**"。传统数据库只能做精确匹配（`WHERE name = 'iPhone'`），做不了"意思相近"。pgvector 让数据库能直接做语义检索。

**③ 不用它会怎样**
你得**额外部署一个专门的向量数据库**——Milvus、Qdrant、Weaviate、Chroma 等等。这意味着你的项目要多一个中间件、多一套运维、多一份数据一致性风险（业务数据在 PG，向量在另一个库，两边要同步）。

**④ 优点**
- **业务数据和向量数据在同一个库里**，一个事务就能保证一致，不需要跨库同步
- **可以用 SQL 把向量检索和业务过滤条件结合起来**，比如："在'售后政策'类文档里，找与问题最相似的 5 段，且只找 2026 年之后生效的"——一个 SQL 搞定
- 不用多部署一个中间件

**⑤ 缺点**
- **性能不如专业向量数据库**。数据量到千万级以上时，专用向量库（Milvus 等）的检索速度和并发能力更强
- 索引类型和调优参数比专用库少
- 只在 PostgreSQL 上能用（MySQL 用不了）

> **面试时这样答**："我们数据量在十万级切片，pgvector 完全够用；选它最大的理由是**避免跨库数据一致性问题**，而且能用 SQL 把向量检索和业务过滤条件写在一起。如果未来涨到千万级，才需要考虑遷移到 Milvus。"

## 7. 向量 / Embedding / 余弦相似度

**① 是什么**

这三件事是一条链，一起讲：

**Embedding（嵌入/向量化）**：把一段文字变成一串数字。比如 `"退款怎么申请"` → `[0.023, -0.871, 0.442, ...]`（1024 个数字）。这串数字叫**向量**。

关键在于：**意思相近的文字，变出来的数字串也相近**。
```
"退款怎么申请"   → [0.023, -0.871, 0.442, ...]
"如何办理退货"   → [0.031, -0.855, 0.460, ...]   ← 和上一行很接近
"这个多少钱"     → [-0.612, 0.203, -0.088, ...]  ← 差很远
```

**余弦相似度**：衡量两个向量"有多像"的数学方法。计算两个向量夹角的余弦值，结果在 -1 到 1 之间，越接近 1 越相似。公式是 `cos(a,b) = (a·b) / (|a| × |b|)`，就是点积除以两个向量长度之积。

**② 解决什么问题**
让计算机能判断"两句话意思像不像"。传统的关键词匹配做不到这点——"退款"和"退货"字面上完全不同，但意思接近；而"苹果手机"和"苹果派"字面很像，意思完全不同。向量能捕捉到这种语义关系。

**③ 不用它会怎样**
只能做关键词匹配。用户问"怎么退钱"，文档里写的是"退款流程"，关键词匹配会漏掉。

**④ 优点**
- 能捕捉语义，不受用词影响
- 支持跨语言：bge-m3 这类多语言模型能把中文"退款"和英文"refund"映射到相近的位置
- 一次计算，反复使用（入库时算一次，之后检索只算问题那边）

**⑤ 缺点**
- **无法精确匹配专有名词**。用户问"iPhone 17 Pro Max 256G 版"，向量检索可能返回一堆手机，但就是找不到那个确切的型号——因为向量是"模糊"的
- 需要调用模型，有网络延迟和成本
- **模型换了，所有向量必须重算**——这是个大坑，所以模型选型要一次定好
- 1024 维意味着每段文字要存 4KB 左右的数据

> **解决方案**：这就是为什么我们要做**双路召回**——向量检索负责"语义相近"，关键词检索负责"精确命中"。

**⑥ 本项目用在哪**
- 入库时：把知识库文档切片后逐段向量化，存进 `kb_chunk.embedding` 列
- 查询时：把用户问题向量化，用 `<=>` 操作符在数据库里找最近的 N 条

模型用**硅基流动的 `BAAI/bge-m3`**，输出 1024 维，单条最多 8192 token，免费。

## 8. HNSW 索引

**① 是什么**
一种**向量索引算法**，全称 Hierarchical Navigable Small World（分层可导航小世界图）。

**它解决的问题用一个类比解释**：你要在一个有 100 万人的城市里找到和你最像的人。挨家挨户敲门（全表扫描）要找 100 万次。HNSW 的做法是先把人组织成"熟人网络"：最上层是几个社交达人，中间层是各个圈子的活跃分子，最下层是所有人。找人的时候先从社交达人开始，一层层往下缩小范围，几十步就能找到。

**② 解决什么问题**
**加速向量检索**。没有索引，pgvector 要把你的查询向量和表里**每一行**都比一遍——10 万行就是 10 万次相似度计算，慢到不可接受。有了 HNSW，通常几十次比较就能找到近似最优解。

**③ 不用它会怎样**
全表扫描。数据量小（几千条）还能忍，上到十万级就明显卡顿。

**④ 优点**
- 查询快，10 万级数据毫秒级返回
- 检索精度高（召回率通常 95%+）
- 支持增量插入，不需要像 IVF 那样定期重建

**⑤ 缺点**
- **它是"近似"检索，不是精确检索**——极端情况下会漏掉真正的最近邻
- **建索引慢、占内存**。HNSW 把图结构存在内存里，100 万条 1024 维向量大概要几 GB 内存
- 有两个关键参数要调：`m`（每层连几个邻居）和 `ef_construction`（建索引时的搜索宽度）——调大精度高但慢，调小反之

**⑥ 本项目用在哪**
在 `kb_chunk.embedding` 列上建 HNSW 索引：
```sql
CREATE INDEX idx_kb_chunk_embedding ON kb_chunk
USING hnsw (embedding vector_cosine_ops);
```
注意 `vector_cosine_ops` 表示用余弦距离——**必须和查询时用的操作符 `<=>` 匹配**，否则索引不会被使用（这是常见坑）。

## 9. 全文检索（PostgreSQL tsvector）

**① 是什么**
PostgreSQL **自带的**关键词检索能力。它会把文本拆成词，建立倒排索引（记录"哪个词出现在哪几行"），然后用 `ts_rank` 按相关度排序。

```sql
SELECT content FROM kb_chunk
WHERE to_tsvector('simple', content) @@ plainto_tsquery('simple', '退款 流程')
ORDER BY ts_rank(...) DESC;
```

（`simple` 是不做词干还原的配置，适合中文；中文分词更精细的方案是装 `zhparser` 或 `pg_jieba` 扩展。）

**② 解决什么问题**
补上向量检索的短板——**精确命中**。用户问型号、订单号、专有名词时，关键词检索比向量检索可靠得多。

**③ 不用它会怎样**
只有向量检索这一路，专有名词类问题会答不准。或者引入 Elasticsearch（另一个专门的搜索引擎），但那就多了一个中间件和一套数据同步。

**④ 优点**
- 数据库自带，**零额外部署**
- 精确匹配能力强，专有名词、型号、编号类查询表现远好于向量
- 可以用 GIN 索引加速
- 和向量检索写在**同一个 SQL 里**做混合查询

**⑤ 缺点**
- **中文分词能力弱**。内置配置不支持中文分词，需要额外装扩展或改用 `pg_trgm`（三元组模糊匹配）
- 相关度算法（ts_rank）不如 Elasticsearch 的 BM25 成熟
- 大火拼量下性能不如 ES

**⑥ 本项目用在哪**
双路召回的第二路。`kb_chunk` 表上建 `tsvector` 列 + GIN 索引，与向量检索并行执行，结果交给 RRF 融合。

## 10. Redis

**① 是什么**
一个**内存数据库**。数据放在内存里而不是硬盘上，所以读写速度是普通数据库的几十到几百倍（微秒级）。

它最常用的四种数据结构：
- **String**：普通键值，用于缓存
- **ZSet（有序集合）**：每个元素带一个分数，自动按分数排序——**做排行榜和队列的利器**
- **List**：列表，可以当队列用
- **Hash**：哈希表，存对象

**② 解决什么问题**
- **缓存**：数据库查一次要 10ms，Redis 查一次 0.1ms。热点数据放 Redis，数据库压力降一个数量级
- **分布式协调**：多个服务实例之间需要共享状态（比如"当前有多少个请求在处理中"），Redis 是天然的共享内存
- **限流和排队**：计数器 + 过期时间就能实现

**③ 不用它会怎样**
所有请求直接打到数据库，高并发下数据库被打爆。分布式场景下没有共享状态，多个实例各算各的，无法协调。

**④ 优点**
- 极快（内存操作）
- 数据结构丰富，很多功能不用写代码就有现成方案
- 支持原子操作（`INCR`、`SETNX`）和 Lua 脚本，能保证并发安全
- 支持过期时间，做缓存和限流很方便

**⑤ 缺点**
- **内存贵**：数据全在内存，成本远高于硬盘
- **可能丢数据**：默认配置下宕机会丢一部分（可以开 AOF 持久化，但会牺牲性能）
- 单线程模型（指命令执行），单个大 key 操作会阻塞所有请求
- 缓存和数据库的一致性问题需要额外设计

**⑥ 本项目用在哪**
- **分布式排队限流**：用 String 做计数器 + ZSet 做等待队列
- **会话缓存**：最近几轮对话放 Redis，读得快
- **幂等控制**：防止用户重复提交问题

## 11. Redisson

**① 是什么**
Redis 的 **Java 客户端**——但它不只是"发命令的工具"，而是在 Redis 之上封装了一套**分布式并发工具**，让你能像用 Java 原生锁一样用分布式锁。

```java
// 原生 Java 的锁
synchronized (obj) { /* 临界区 */ }

// Redisson 的分布式锁（多个服务实例之间也有效）
RLock lock = redisson.getLock("order:123");
lock.lock();
try { /* 临界区 */ } finally { lock.unlock(); }
```

除了锁，它还提供：`RSemaphore`（分布式信号量）、`RCountDownLatch`、`RMap`、`RDelayedQueue` 等。

**② 解决什么问题**
**分布式场景下的并发控制**。你的服务部署了 3 个实例，"当前并发处理数不能超过 10"这个约束是全局的，用 Java 原生的 `synchronized` 或 `Semaphore` 完全无效——它们只作用于单个 JVM 内部。

**③ 不用它会怎样**
你得自己用 Redis 的 `SETNX` + `EXPIRE` 手写分布式锁。但手写版本有大量坑：锁过期了业务还没执行完怎么办？释放锁时误删了别人的锁怎么办？这些 Redisson 都用"看门狗（watchdog）自动续期"和"锁值校验"解决了。

**④ 优点**
- **看门狗机制**：业务没执行完，自动给锁续期，避免"锁提前过期"
- 提供现成的分布式信号量、限流器，不用自己写 Lua
- API 设计贴近 Java 原生并发包，学习成本低
- 社区活跃，文档好

**⑤ 缺点**
- **它不能替代对原理的理解**。面试官问"Redisson 的锁是怎么实现的"，你答"调个 API 就行了"会被扣分——底层是 Lua 脚本 + Hash 结构 + 发布订阅，要能讲清楚
- 比直接用 Lettuce/Jedis 重一些
- 看门狗默认续期 30 秒，如果业务卡死超过这个时间仍会出问题

**⑥ 本项目用在哪**
- `RSemaphore` 控制"同时处理的问答请求数"（对应简历里的"分布式排队限流"）
- `RLock` 保护会话语义更新的临界区
- 但**排队队列本身用 ZSet + 手写 Lua 脚本**实现，因为需要自定义出队逻辑

# 第三部分 · RAG 与 AI

## 12. Token 与上下文窗口

**① 是什么**

**Token** 是大模型处理文字的最小单位。它不是"字"也不是"词"——一个汉字大约 0.6–1 个 token，一个英文单词大约 1.3 个 token。`"你好世界"` 大概是 4 个 token，`"Hello world"` 大概是 2 个 token。

**上下文窗口** = 模型一次最多能"看见"多少 token。早期模型是 4K（约 3000 个汉字），现在的模型动辄 128K、1M。

关键点：**上下文窗口是"输入 + 输出"的总和**，不是只有输入。

**② 解决什么问题**
两个问题：**① 计费**——API 按 token 收费，输入和输出分开计价；**② 容量上限**——超过窗口的对话历史会被截断或直接报错。

**③ 不用它会怎样**
你不算 token 就会遇到两种事故：一是账单失控（把 10 万字文档每轮都塞给模型），二是请求报错（`maximum context length exceeded`）。

**④ 优点（为什么理解它有价值）**
- 能精确估算成本和延迟，做出工程权衡
- 能设计"什么时候该压缩历史"的策略

**⑤ 缺点（这是 RAG 的痛点所在）**
- **上下文窗口再大也不等于可以随便塞**。塞得越多，模型越容易"迷失在中间"（Lost in the Middle 现象）——关键信息在长上下文中部时容易被忽略
- 塞得越多，每轮请求越慢、越贵
- **算 token 本身就是麻烦事**，不同模型的分词器不一样，本地估算和实际计费总有偏差

**⑥ 本项目用在哪**
- 会话记忆模块：统计当前对话的 token 数，超过阈值触发 LLM 摘要压缩（对应简历里的"控制 Token 消耗"）
- Prompt 组装：控制召回的文档片段总数，避免超过预算
- `qa_log` 表记录每次请求的输入/输出 token，用于成本统计

> **一个重要认知**：RAG 的价值恰恰在于**用检索把上下文从"全部塞"变成"只塞相关的"**。如果无脑把整个知识库丢给模型，就不需要 RAG 了。

## 13. Apache Tika

**① 是什么**
一个**文档内容提取工具**。你给它一个文件，不管是什么格式，它都吐出纯文本。

```java
// 一行代码，PDF / Word / Excel / PPT 全都能读
String text = tika.parseToString(new File("售后政策.pdf"));
```

支持的格式有上千种：PDF、Word、Excel、PowerPoint、HTML、EPUB、RTF、各种图片的元数据……

**② 解决什么问题**
知识库的原始文档格式五花八门，但 LLM 只认纯文本。PDF 里的文字不是"文字"，是"画在某个坐标上的图形指令"；Word 是一个 zip 压缩包里的 XML。**你需要一个能把它们统一转成文本的工具**。

**③ 不用它会怎样**
你必须为每种格式写一个解析器：PDF 用 PDFBox、Word 用 POI、Excel 也用 POI 但 API 不同……而且每种格式都有各种变体和坑。代码量翻几倍，还容易漏掉格式。

**④ 优点**
- **一个 API 处理所有格式**，自动识别文件类型
- 还能提取元数据（作者、创建时间、页数）
- Apache 顶级项目，稳定，社区大

**⑤ 缺点**
- **依赖包很大**（几十 MB），因为内含各种格式的解析器
- **对复杂 PDF 效果不好**：扫描件（图片型 PDF）完全读不出文字；多栏排版的 PDF 会把左右栏的文字交错拼接；表格会丢失结构变成一堆散乱的文字
- 解析速度不算快
- 不做 OCR（图片里的文字识别不出来）

**⑥ 本项目用在哪**
知识库文档入库的第一步。我会生成 PDF/Word/Markdown/Excel 四种格式的仿真文档，正好覆盖：
- Markdown、Word → Tika 表现好
- Excel → 能提取，但表格结构要额外处理
- PDF → **我会故意生成一份多栏排版的 PDF 当"难例"**，用来演示"为什么真实项目里文档解析是最脏的一环"

## 14. 文本切分（Chunking）

**① 是什么**
把长文档**切成一段一段的小块**（chunk），每块单独向量化。

为什么要切？因为：
- 一整篇 5000 字的售后政策，向量化后只得到一个向量——**这个向量是整篇文章的"平均意思"，什么都代表不了**。你问"退款要几天"，它匹配不上。
- 切成 300 字一块，每块有自己明确的主题，检索精度大幅提升。

**② 解决什么问题**
在"检索精度"和"上下文完整性"之间找平衡：切得太碎，答案被切断；切得太大，向量不精准。

**③ 不用它会怎样**
整篇文档一个向量，检索基本失效——这是初学者最常见的 RAG 失败原因。

**④ 常见策略与优缺点**

| 策略 | 怎么做 | 优点 | 缺点 |
|---|---|---|---|
| **定长切分** | 每 300 字切一刀 | 实现简单，块大小均匀 | 会在句子中间切断，语义破碎 |
| **重叠切分** | 每 300 字切一刀，但**相邻块重叠 50 字** | 避免答案正好卡在切割点被切断 | 存储和计算量增加 |
| **按标题层级切分** | 按 Markdown 的 `#`、`##` 切 | 每块语义完整，符合文档原本结构 | 依赖文档结构良好，PDF 解析后往往没有标题层级 |
| **语义切分** | 用模型判断"意思在哪里转折了" | 效果最好 | 要额外调模型，慢且贵 |
| **父子块** | 检索用小块，喂给模型用大块 | 兼顾精度和完整性 | 实现复杂，要维护两层映射 |

**⑤ 缺点（共性）**
**没有一种策略是万能的**。不同文档类型适合不同策略——这就是为什么需要 `docs/06-评测体系设计.md` 里的对照实验：**用数据决定切分参数，而不是拍脑袋**。

**⑥ 本项目用在哪**
`rag/` 包下的切分器。基础策略：**按标题层级切 + 定长切 + 重叠窗口**。阶段 7 评测时会对比不同 chunk 大小（300/500/800）对召回命中率的影响，选出最优值——**这个实验过程和结论就是面试时可以讲的干货**。

## 15. 双路召回（Hybrid Retrieval）

**① 是什么**
**同时用两种不同的方法检索，然后把结果合并**：
- **第一路：向量检索**（Dense）——擅长"语义相近"
- **第二路：关键词检索**（Sparse）——擅长"精确命中"

**② 解决什么问题**
弥补单一方法的短板（详见第 7 节向量检索的缺点）：

| 用户问题 | 向量检索 | 关键词检索 | 双路效果 |
|---|---|---|---|
| "怎么退钱" | ✅ 能匹配到"退款流程" | ❌ 字面不匹配 | ✅ |
| "iPhone 17 Pro Max 256G" | ❌ 返回一堆相似手机 | ✅ 精确命中 | ✅ |
| "这个能送老人吗" | ✅ 匹配到"适用人群" | ❌ | ✅ |

**③ 不用它会怎样**
只用向量检索 → 专有名词、型号、订单号类问题答不准。只用关键词 → 同义表达、口语化提问全都匹配不上。

**④ 优点**
- 召回率显著高于单路（每一路的短板被另一路补上）
- 抗"查询类型变化"能力强，不管是口语提问还是精确搜索都能应付

**⑤ 缺点**
- **计算成本翻倍**（两次检索 + 一次向量化）
- **两路的分数量纲完全不同**——向量给出的是 0–1 的余弦相似度，关键词给出的是可能到几十的 `ts_rank` 分数，**不能直接相加**。这就是为什么需要 RRF
- 需要额外维护关键词索引（存储成本）

**⑥ 本项目用在哪**
`rag/retriever/` 下的 `VectorRetriever` 和 `KeywordRetriever`，两个都实现同一个接口，通过 `CompletableFuture` 并行执行，结果交给 RRF 融合。

## 16. RRF（倒数排名融合）

**① 是什么**
**Reciprocal Rank Fusion**，一种把多个检索结果列表合并成一个的方法。公式极简：

```
RRF_score(文档) = Σ  1 / (k + rank)
                各路
```

其中 `rank` 是这份文档在**某一路结果里的排名**（第 1 名 rank=1），`k` 是平滑常数，通常取 60。

**举个例子**：文档 A 在向量检索里排第 1、在关键词检索里排第 5；文档 B 在向量里排第 3、关键词里没出现。

```
A 的分数 = 1/(60+1) + 1/(60+5) = 0.01639 + 0.01538 = 0.03177
B 的分数 = 1/(60+3)                      = 0.01587
```
A 胜出——**因为它两路都表现不错，比只在单路表现好的更可信**。

**② 解决什么问题**
**解决"两路分数不能相加"的问题**。这是双路召回的核心难点。

**③ 不用它会怎样**
你得想办法把余弦相似度（0–1）和 ts_rank（0–几十）归一化到同一尺度。常见做法是 Min-Max 归一化，但问题是：**分数的绝对大小在不同查询之间没有可比性**——今天最相关的文档得分 0.95，明天另一个查询最相关的文档得分 0.72，归一化后的相对关系会失真。

**④ 优点**
- **只用排名，不用分数**——完美规避了量纲不一致的问题
- 极其简单，没有需要训练的参数
- 对异常分数鲁棒（某一路给出个离谱的高分，也不影响，因为只看排名）
- 工业界事实标准（Elasticsearch 的混合检索默认就用 RRF）

**⑤ 缺点**
- **丢掉了分数里的信息**。第 1 名得分 0.99 还是 0.51，RRF 一视同仁——而这两者可信度其实差很多
- `k` 值的选取是个经验值，需要实验确定（本项目放在评测阶段调）
- 对于只有一路有结果的情况，RRF 的区分度不如直接按分数排

**⑥ 本项目用在哪**
`rag/fusion/RrfFuser.java`，手写约 40 行。**面试追问点**："k 取 60 是什么道理？"——答案是：k 越大，排名靠后的文档权重差别越小（更"平权"）；k 越小，越强调头部结果。取 60 是原论文的经验值，实际项目要调。**我们会在阶段 7 用评测数据验证这个取值。**

## 17. 重排序（Cross-Encoder Rerank）

**① 是什么**
召回之后，用另一个模型对候选文档**重新打分排序**。

关键在于两种模型的架构差异：

| | **双塔模型（Bi-Encoder）** | **交叉编码器（Cross-Encoder）** |
|---|---|---|
| 工作方式 | 问题和文档**分别**编码成向量，再算相似度 | 问题**和**文档**拼在一起**送进模型，直接输出相关性分数 |
| 能否预计算 | ✅ 文档向量可以提前算好存库 | ❌ 每次查询都要重新算 |
| 速度 | 快（数据库索引查找） | 慢（每个文档都要跑一次模型） |
| 精度 | 一般 | **高得多** |

比喻：双塔像是**分别看两个人的照片判断他们合不合得来**；Cross-Encoder 像是**让两个人当面聊一次再判断**。后者准得多，但成本高得多。

**② 解决什么问题**
向量检索为了速度牺牲了精度（问题在编码时"看不到"文档，只能各自编码）。重排序用慢但准的模型，**对召回的前 20–50 条精排**，把真正相关的顶到最前面。

**③ 不用它会怎样**
向量检索的 Top1 经常不是真正最相关的。你的答案质量会明显下降。

**④ 优点**
- **精度提升显著**，通常能把 Top1 命中率提升十几个百分点
- 只对少量候选重排，成本可控（不会对全库跑）
- 能捕捉细粒度的语义关系（否定、条件、限定词）

**⑤ 缺点**
- **有延迟代价**：每个候选都要跑一次模型推理，20 个候选就是 20 次，通常增加 100–500ms
- 不能省掉召回阶段（它只重排，不能从全库找）
- 对超长文档效果下降（模型有输入长度限制，太长会被截断）

**⑥ 本项目用在哪**
`rag/rerank/` 下调用硅基流动的 `BAAI/bge-reranker-v2-m3`（免费）。
**典型流程**：向量+关键词各召回 20 条 → RRF 融合去重得到约 25 条 → 重排序精选出 Top 5 → 喂给 LLM。
**面试追问点**："为什么不全库重排？"——因为延迟和成本，重排的复杂度是 O(候选数 × 模型推理时间)，全库重排不可接受。

## 18. SSE（Server-Sent Events）

**① 是什么**
一种**让服务器主动往浏览器推送数据**的技术。基于普通 HTTP 连接，服务器可以持续不断地往浏览器发消息，直到主动关闭。

**② 解决什么问题**
大模型生成答案是一个字一个字吐出来的，整个过程可能持续 10–30 秒。如果用普通 HTTP 请求，用户要**盯着转圈圈等 30 秒**，然后答案"啪"地一下全出现。

SSE 让答案像打字机一样一个字一个字地出现——**用户 1 秒内就能看到第一个字**，感知等待时间大幅缩短。

**③ 不用它会怎样**
三种替代方案，各有缺点：
- **普通轮询**：客户端每秒问一次"好了吗"——浪费请求，还是有延迟
- **WebSocket**：全双工通信，能力更强，但**对于"服务器单向推、客户端只听"的场景属于杀鸡用牛刀**，还要处理心跳、重连、协议升级
- **长轮询**：客户端发请求，服务器 hold 住不返回直到有数据——比轮询好但实现复杂

**④ 优点**
- **基于普通 HTTP**，不需要协议升级，浏览器原生支持（`EventSource` API）
- 自动重连（浏览器内置）
- 实现简单，服务端就是往响应流里写文本
- 单向推送场景的最优解

**⑤ 缺点**
- **只能服务器→客户端单向**，客户端要发消息得另开请求
- **有连接数限制**：HTTP/1.1 下同一域名最多 6 个并发连接，SSE 长连接会占用配额（HTTP/2 下没这个问题）
- **容易被中间层缓冲**：Nginx、CDN 默认会缓冲响应，导致"一个字都收不到，最后一次性全来"——**必须显式配置 `proxy_buffering off;`**（这是最常见的坑）
- 断线重连后的"续传"要自己实现

**⑥ 本项目用在哪**
- 答案的流式推送（打字机效果）
- **排队状态的实时推送**——用户排在第 5 位、第 4 位……通过 SSE 实时更新（对应简历里的"通过 SSE 实时推送队列状态"）

## 19. MCP（Model Context Protocol）

**① 是什么**
一个**开放协议**，规定了"大模型如何发现和调用外部工具"。

类比：**MCP 之于 AI 应用，就像 USB-C 之于硬件**。以前每个外设都有自己的接口，现在统一成 USB-C。MCP 之前，每个 AI 框架都自己定义一套工具调用格式；有了 MCP，工具提供方写一次 Server，所有支持 MCP 的 AI 应用都能用。

它的核心概念：
- **Tools（工具）**：可被调用的函数，有名字、描述、参数 schema
- **Resources（资源）**：可读的数据源
- **Prompts（提示模板）**：预置的提示词模板
- **Transport（传输层）**：stdio（本地进程通信）或 SSE/HTTP（远程）

工作流程：
```
1. Client 连接 Server，问："你有哪些工具？"
2. Server 返回工具清单（含 JSON Schema 描述的参数）
3. Client 把工具清单转成模型的 function calling 格式
4. 模型决定调用哪个工具、传什么参数
5. Client 把调用请求转发给 Server
6. Server 执行（比如查数据库），返回结果
7. Client 把结果喂回模型，模型据此生成回答
```

**② 解决什么问题**
让大模型能访问**实时数据**和**执行动作**。知识库是静态的，回答不了"我的订单现在到哪了"——这需要查实时数据库。MCP 提供了一套标准化的方式让模型调用这些能力。

**③ 不用它会怎样**
自己定义一套"意图 → 调哪个接口"的映射，硬编码在代码里。能用，但：
- 每接一个新工具就要改代码
- 工具的参数校验、错误处理都要自己定规范
- 无法复用别人的工具生态

**④ 优点**
- **标准化**：工具写一次，所有 MCP 客户端都能用
- **可组合**：可以同时挂多个 MCP Server
- **自描述**：工具的参数 schema 是机器可读的，模型自己就知道怎么传参
- 生态在快速成长（GitHub、数据库、文件系统等都有官方 Server）

**⑤ 缺点**
- **协议较新**（2024 年底才提出），版本还在快速演进，API 有变动风险
- **多一跳通信开销**：Client 和 Server 之间要序列化/反序列化，比直接函数调用慢
- **调试困难**：工具调用失败时，是模型选错了工具？参数格式不对？还是 Server 报错？排查链路长
- **安全风险**：工具能执行真实操作，提示注入攻击可能诱导模型调用危险工具

**⑥ 本项目用在哪**
- **手写 MCP Server**：暴露 4 个工具——商品库存查询、优惠券查询、订单状态查询、售后政策查询
- **官方 Java SDK 做 Client**：负责连接 Server、获取工具清单、转发调用
- 对应简历里的"MCP 工具调用：基于意图识别路由外部工具，由 LLM 提取结构化参数"

> **为什么 Client 用 SDK 而 Server 手写？** Client 侧要处理协议握手、版本协商、传输层细节，用 SDK 保证兼容性；Server 侧手写能让你完全掌控"工具是怎么定义和暴露的"——面试官问"你的工具 schema 长什么样、模型怎么知道该传什么参数"，你能直接指着代码讲。

## 20. RAGAS

**① 是什么**
一个 **Python 库**，专门用来评测 RAG 系统的质量。它定义了四个核心指标：

| 指标 | 中文 | 衡量什么 | 怎么算 |
|---|---|---|---|
| **faithfulness** | 答案忠诚度 | 答案里的每句话，是否都能在召回的文档里找到依据（**有没有编造**） | 把答案拆成若干断言，逐条判断能否被上下文支持 |
| **answer_relevancy** | 答案相关性 | 答案是否切题（**有没有答非所问**） | 用 LLM 根据答案反推问题，看和原问题有多像 |
| **context_precision** | 上下文精确度 | 召回的文档里有多少是真正相关的（**噪声多不多**） | 相关文档排在越前面分数越高 |
| **context_recall** | 上下文召回率 | 真正需要的文档有没有被召回（**有没有漏**） | 用标准答案反查应该召回的文档 |

**关键特点：它用 LLM 当裁判（LLM-as-a-Judge）**。比如判断"答案里的这句话能否被上下文支持"，是让另一个大模型来判的。

**② 解决什么问题**
RAG 系统的质量很难用传统方式测。传统软件测试是"输入 A 必须输出 B"，但 RAG 的答案每次措辞都不一样。你需要一套**能量化"好不好"的方法**，否则优化全靠感觉——"我感觉这次改完效果好了"，面试官一句"你怎么证明"就崩了。

**③ 不用它会怎样**
只能人工看几十个案例，主观判断。无法做 A/B 对比，无法证明优化有效，简历里的"提升 28.5%"就没有依据。

**④ 优点**
- **开箱即用**，几个指标几行代码就能算
- 指标定义有论文支撑，是业界共识，面试官认可
- 支持自定义指标
- 不需要人工标注标准答案（部分指标只需要问题和上下文）

**⑤ 缺点**
- **用 LLM 当裁判，本身就有噪声**：同一个答案跑两次可能得到不同分数；裁判模型的能力上限决定了评测的上限
- **有成本**：评测过程本身要调用大量 LLM（每题要调好几次）
- **慢**：150 道题跑一遍可能要几十分钟到几小时
- **它是 Python 生态**，和 Java 主服务是两套技术栈（这就是我们把它做成独立脚本的原因）
- 对中文场景的适配不如英文（虽然 bge/Qwen 这类模型做裁判效果尚可）

**⑥ 本项目用在哪**
`scripts/eval_ragas.py`——独立 Python 脚本，读取 PostgreSQL 里 `qa_log` 表记录的问答日志，跑 RAGAS 算四个指标，输出 Markdown 报告。
**为什么不做成常驻服务**：评测是离线行为（一天跑一次或改完代码跑一次），做成常驻服务纯属增加部署复杂度和资源占用。

## 21. Resilience4j 与熔断器

**① 是什么**

**熔断器（Circuit Breaker）** 借用的是电路里的保险丝概念。当某个外部服务连续失败，就"跳闸"——**不再往它发请求**，直接走降级逻辑，避免把资源和时间浪费在一个已经挂掉的服务上。过一段时间后进入"半开"状态，放几个请求去试探，如果恢复了就重新合闸。

三个状态：

```
CLOSED（正常）──失败率超阈值──→ OPEN（跳闸，直接降级）
     ↑                              │
     └──试探成功── HALF_OPEN（半开） ←──等待 60 秒──┘
                        │
                        └──试探失败──→ 回到 OPEN
```

**Resilience4j** 是 Spring Boot 生态里的标准实现（Spring Cloud Circuit Breaker 的默认选择）。

**② 解决什么问题**
**防止"雪崩"**。假设 DeepSeek 官方 API 挂了，每个请求都要等 30 秒超时才失败——100 个并发请求会瞬间占满所有线程，导致你的服务整体不可用（即使其他功能是好的）。熔断让你在检测到失败后**立刻失败并降级**，保护自身。

**③ 不用它会怎样**
每个请求都要死等到超时。用户体验极差，线程池被拖垮。

**④ 优点**
- **滑动窗口统计**：基于最近 N 次调用算失败率，而不是全局历史（老数据不会拖累判断）
- **半开状态自动探测**：服务恢复了能自动恢复，不需要人工干预
- 除了熔断还有**限流（RateLimiter）、舱壁隔离（Bulkhead）、重试（Retry）、超时（TimeLimiter）**，可以组合使用
- 和 Spring Boot 集成好，用注解就能生效
- **面试认可度高**，是标准答案

**⑤ 缺点**
- **参数调优靠经验**：失败率阈值设 50% 还是 80%？滑动窗口用次数还是时间？需要结合实际情况调
- **半开状态的并发控制有坑**：默认半开时只允许有限个请求通过，配置不当会让探测很慢
- 多个熔断器组合时行为复杂，调试困难
- 它只解决"失败后怎么办"，不解决"为什么失败"

**⑥ 本项目用在哪**

配置一条 **P0 → P1 → P2 的跨供应商降级链**：

| 优先级 | 供应商 | 模型 | 触发降级的原因 |
|---|---|---|---|
| P0 | DeepSeek 官方 | `deepseek-flash` | — |
| P1 | 硅基流动 | `deepseek-ai/DeepSeek-V3.2` | 官方返回 429 限流 / 超时 / 5xx / 402 余额不足 / 熔断打开 |
| P2 | 硅基流动 | `Qwen/Qwen3.5-9B` | P1 也不可用 |

> ✅ 以上 ID 于 2026-09-18 经 `GET /v1/models` + 真实调用实测确认。
> 原文档写的「DeepSeek-V4.1-Flash」**不存在** —— 硅基流动上的实际 ID 是
> `DeepSeek-V4-Flash`（无 `.1`）。这是「模型 ID 会变，不能凭记忆写」的又一个实例。

**面试可以讲的配置细节**：滑动窗口基于最近 10 次调用；失败率超过 50% 跳闸；跳闸后 30 秒进入半开状态放 3 个请求探测；探测成功则恢复，失败则继续跳闸。每次降级事件写入 `qa_log`，可通过 `/actuator/circuitbreakers` 查询实时状态。

> **注意一个关于降级质量的设计细节**：
> 理想情况下 P0 → P1 应该是「**同一个模型的另一个部署**」，答案质量不变；
> P1 → P2 才是真正的「**能力降级**」。这样能最大限度做到用户无感知。
>
> 本项目当前的选择略有偏离：P1 用的是 DeepSeek-V3.2 而非
> deepseek-flash 的同源版本 —— 实测发现 **V3.2 不是推理模型**
> （reasoning 长度为 0），比同源的 V4-Flash 更快更省，
> 代价是 P0→P1 也变成了一次模型切换。
> 这个取舍记在 `docs/08-技术决策记录(ADR).md`。
>
> 另外，**熔断器是「每个模型一个」而不是「每个供应商一个」**：
> 硅基流动上 P1 被限流时 P2 可能还是健康的，按供应商做会把健康的 P2 一起拖下水。

## 22. Lua 脚本

**① 是什么**
Lua 是一门轻量脚本语言，Redis **内置**了它的解释器。你可以把一段逻辑写成 Lua 脚本发给 Redis 执行。

**关键在于：Redis 执行 Lua 脚本时是原子的**——脚本执行期间不会被其他命令打断。要么全部执行完，要么完全不执行。

```lua
-- 示例：原子地"检查并发数，没超就加一"
local current = tonumber(redis.call('GET', KEYS[1]) or '0')
if current < tonumber(ARGV[1]) then
    redis.call('INCR', KEYS[1])
    return 1    -- 成功
else
    return 0    -- 并发已满
end
```

**② 解决什么问题**
**把"读-判断-写"三步变成一步原子操作**。

看不用 Lua 会怎样：
```java
int current = redis.get("concurrency");   // 第 1 步：读，此时是 9
// ← 就在这一瞬间，另一个请求也读到了 9
if (current < 10) {                       // 第 2 步：判断，两个请求都通过
    redis.incr("concurrency");            // 第 3 步：写，结果变成 11
}
```
并发下就会超卖——限制 10 个并发，实际跑进去 11 个甚至更多。

**③ 不用它会怎样**
- 用 Java 端的 `synchronized` 锁：只能锁住单个 JVM，多实例部署失效
- 用 Redis 的 `WATCH/MULTI/EXEC` 事务：要写重试逻辑，代码复杂且性能差
- 用 Redisson 的现成组件：很多场景够用，但自定义逻辑（比如我们需要的排队出队规则）覆盖不到

**④ 优点**
- **保证原子性**，从根本上解决并发安全问题
- **减少网络往返**：原本要 3 次 RTT 的操作，现在 1 次
- Redis 内执行，性能极高

**⑤ 缺点**
- **脚本执行期间会阻塞 Redis**（Redis 执行命令是单线程的）。脚本写太长、循环太多，会卡住整个 Redis
- **调试极其困难**：没有断点，出错只能靠 `redis.log` 和返回值猜
- 不支持事务回滚——**脚本执行到一半出错，前面已执行的写操作不会撤销**（要先写只读逻辑再做写操作）
- 逻辑散落在脚本和 Java 两处，维护时要两边看
- Redis 集群下所有 key 必须在同一个 slot（要用 hash tag）

**⑥ 本项目用在哪**
`ratelimit/` 包下的排队限流核心逻辑：
1. **原子获取令牌**：检查当前并发数，未满则加一放行，满了则进入排队
2. **原子出队**：用户完成时，从 ZSet 队列取下一个等待者并直接占用名额（**"释放 + 分配"必须原子，否则名额会凭空消失或重复分配**）

> **面试追问点**："为什么不用 `INCR` + `DECR` 就够了？"——因为我们需要 "释放名额的同时立刻把名额分给排队中的下一个人"，这两步之间如果有间隙，名额就会短暂空转，或者被新请求插队。

## 23. 分布式信号量

**① 是什么**
**信号量（Semaphore）** 是一个计数器，用来限制"同时有多少个操作可以执行"。Java 自带的 `java.util.concurrent.Semaphore` 只作用于单个 JVM。

**分布式信号量**把计数器放在 Redis 里，所以**多个服务实例共享同一个计数**。

```
限制 10 个并发：
第 1 个请求进来 → 计数 0→1 → 放行
...
第 10 个请求进来 → 计数 9→10 → 放行
第 11 个请求进来 → 计数已是 10 → 进入排队
第 3 个请求完成 → 计数 10→9 → 从队列唤醒一个等待者
```

**② 解决什么问题**
**保护昂贵的下游资源**。我们的下游是 LLM API：
- LLM 调用慢（5–30 秒），占用线程久
- 有并发限制（超了返回 429）
- 按 token 计费，突发流量会让成本失控

限制并发数能保证：① 不触发对方限流；② 自己的线程池不被占满；③ 成本可预测。

**③ 不用它会怎样**
流量一来全部请求涌向 LLM API，触发 429 限流，用户看到一堆错误；或者线程池被打满，整个服务无响应。

**④ 优点**
- **保护下游**，避免雪崩
- 排队让用户有序等待，而不是随机失败
- 计数在 Redis，多实例部署天然共享

**⑤ 缺点**
- **多了一次 Redis 往返**，给每个请求增加 1–2ms 延迟
- **名额泄漏风险**：如果服务实例崩溃，它持有的名额没被释放，计数会永远偏高——**必须给名额加过期时间兜底**
- 排队意味着用户要等，要有良好的前端提示（这就是为什么需要 SSE 推送队列位置）

**⑥ 本项目用在哪**
`ratelimit/QueueLimiter.java`。流程：
1. 请求进来，用 Lua 脚本原子地尝试获取名额
2. 拿到名额 → 直接处理，通过 SSE 推送"处理中"
3. 没拿到 → 加入 ZSet 队列（score 用时间戳，保证先到先服务），通过 SSE 推送"你排在第 N 位"
4. 有人处理完 → Lua 脚本原子地"释放名额 + 分配给队首等待者"，通过 Pub/Sub 通知对方

## 24. ZSet（有序集合）

**① 是什么**
Redis 的一种数据结构。每个元素带一个**分数（score）**，Redis 自动按分数排序，可以高效地按分数范围查询。

```
ZADD queue 1726560000 "user_A"     # 加入，分数是时间戳
ZADD queue 1726560001 "user_B"
ZRANGE queue 0 0 WITHSCORES        # 取分数最小的那个（最早排队的）
ZRANK queue "user_B"               # 查 B 排在第几位 → 1
```

**② 解决什么问题**
**实现"先到先服务"的公平排队**。用普通 List 也能做队列，但：
- List 无法高效地"查某个元素排在第几位"（用户想看自己排第几，List 要遍历）
- List 无法"把超时未处理的请求移除"（ZSet 用 `ZREMRANGEBYSCORE` 一行搞定）

**③ 不用它会怎样**
用 List 做队列，然后自己维护一个 Map 记录位置——多一份状态要同步，还容易不一致。

**④ 优点**
- **插入、删除、范围查询都是 O(log N)**，性能极好
- 天然有序，取队首就是 `ZRANGE key 0 0`
- 支持按分数范围批量删除（清理超时请求）
- 查排名 `ZRANK` 是 O(log N)

**⑤ 缺点**
- **分数相同时按字典序排**，如果多个请求的 score 完全相同（时间戳精度不够），顺序就不完全是先到先服务——**要么用毫秒时间戳，要么在 score 里拼接序列号**
- 没有"阻塞等待"能力（不像 List 的 `BLPOP`），出队要靠轮询或 Pub/Sub 通知
- 元素不会被自动清理，**必须有超时清理机制**，否则队列无限增长

**⑥ 本项目用在哪**
`ratelimit/` 下的等待队列。`score = 当前毫秒时间戳`，`member = 请求 ID`。用户通过 SSE 查询自己排第几（`ZRANK`），出队时取 `ZRANGE 0 0`。定时任务用 `ZREMRANGEBYSCORE` 清理超过 5 分钟未处理的僵尸请求。

## 25. Pub/Sub（发布订阅）

**① 是什么**
Redis 的消息广播机制。发布者往一个"频道（channel）"发消息，**所有订阅了这个频道的客户端都会收到**。

```
发布者: PUBLISH queue:notify "user_A 已获得名额"
订阅者: SUBSCRIBE queue:notify      # 收到上面那条消息
```

**② 解决什么问题**
**跨实例的实时通知**。用户 A 的请求在你的 1 号实例上处理完了，但用户 B 的排队请求连接在 2 号实例上——1 号实例怎么告诉 2 号实例"名额空出来了"？通过 Redis 的 Pub/Sub 广播。

**③ 不用它会怎样**
只能用轮询。每个实例每秒去 Redis 查一次"有名额了吗"——延迟高（最多等 1 秒）、Redis 压力大（N 个实例 × 每秒 1 次）。

**④ 优点**
- **实时**：消息发出后毫秒级送达
- **解耦**：发布者不需要知道有多少订阅者、它们在哪
- 实现简单，几行代码

**⑤ 缺点**
- **消息不持久化，也不保证送达**。如果订阅者那一刻正好断线（比如正在重启），消息就永远丢了——**这是它和 Kafka 这类消息队列最大的区别**
- 没有确认机制（ACK），发布者不知道有没有人收到
- 没有消费组概念，所有订阅者收到相同的消息
- 订阅者在断线重连期间的消息全部丢失

**⑥ 本项目用在哪**
**只用于"提醒"，不用于"数据传递"**。Pub/Sub 发出的通知内容是"队列有新变化，请重新查询你的位置"——**真正的状态存在 Redis 的 ZSet 里**。这样即使通知丢了，下次轮询也能拿到正确状态。

> **这是一个重要的设计原则**：Pub/Sub 用来降延迟，不用来保正确性。面试官问"消息丢了怎么办"，你答"通知丢了只会让这次更新晚一点（下一次轮询/心跳会补上），不会导致状态错误"，这就是可靠的答案。

## 26. 两家模型供应商的差异（必须记住）

| 项 | DeepSeek 官方 | 硅基流动 |
|---|---|---|
| Base URL | `https://api.deepseek.com` | `https://api.siliconflow.cn/v1` |
| 对话模型 | `deepseek-flash` | 需用 `GET /v1/models` 核实硅基流动上的确切 ID |
| 向量模型 | ❌ **不提供** | `BAAI/bge-m3`（免费，1024 维） |
| 重排模型 | ❌ **不提供** | `BAAI/bge-reranker-v2-m3`（免费） |
| 并发限制 | Flash 约 2500 | rerank RPM 约 2000 |
| 价格 | 更低（官方直连） | 略高，但向量和重排免费 |
| 协议 | OpenAI 兼容 | OpenAI 兼容 |

> ⚠️ **两个大坑**：
> 1. **并发限制不一样**。做压测时如果把硅基流动的 RPM 限制触发当成"我代码有 bug"，会浪费大量时间排查。压测时先看清是哪个供应商报的 429。
> 2. **模型 ID 会变**。DeepSeek 在 2026 年就废弃过 `deepseek-chat` / `deepseek-reasoner` 这两个旧名字。**写代码前永远先 `GET /v1/models` 核实**，不要凭记忆硬编码。

# 第五部分 · 工程化与部署

## 27. Docker 与 Docker Compose

**① 是什么**

**Docker** 是一个"软件集装箱"系统。它把你的程序**连同它需要的整个运行环境**（操作系统库、依赖、配置）打包成一个**镜像（image）**，这个镜像在任何装了 Docker 的机器上都能原样跑起来，这个运行中的实例叫**容器（container）**。

类比：以前你搬家要把家具一件件拆开、搬到新家、再按新家的格局重新组装（经常装不上）。Docker 是**把整个房间原封不动装箱搬走**。

**Docker Compose** 是编排多个容器的工具。你的项目需要 PostgreSQL、Redis 两个容器协同工作，用 `docker-compose.yml` 一个文件描述它们，一条 `docker compose up -d` 全部启动。

```yaml
services:
  postgres:
    image: pgvector/pgvector:pg17    # 官方打包好的 PostgreSQL + pgvector
    ports: ["5432:5432"]
  redis:
    image: redis:7-alpine
    ports: ["6379:6379"]
```

**② 解决什么问题**
**"在我电脑上明明是好的"** 这个经典问题。开发环境、测试环境、生产环境的操作系统、库版本、配置全都不同，导致代码在本地能跑、上线就崩。Docker 让三个环境跑的是**同一个镜像**。

具体到本项目：**pgvector 在 Windows 上几乎装不了**（要用 Visual Studio 手动编译 C 扩展）。用 Docker 的话，官方的 `pgvector/pgvector` 镜像已经编译好了，拉下来就能用——**这是本项目选 Docker 的决定性原因**。

**③ 不用它会怎样**
- 本项目：要在 Windows 上手动编译 pgvector，新手成功率极低
- 一般场景：手动在每台机器上装数据库、配环境变量、对齐版本，换台机器就要重来一遍

**④ 优点**
- **环境一致性**：一次构建，到处运行
- **隔离**：容器之间互不影响，删掉容器不留垃圾（镜像和数据卷可以选择保留）
- **秒级启动**：比装一个数据库快得多
- **版本可锁定**：`pgvector/pgvector:pg17` 明确指定版本，不会某天自动升级导致不兼容
- 是行业标准，**面试官听到"用 Docker Compose 编排"会认可你有工程化意识**

**⑤ 缺点**
- **Windows 上需要 WSL2 后端**，占资源（Docker Desktop 本身要吃 1–2GB 内存）
- **数据卷管理要小心**：`docker compose down -v` 会**删掉数据卷**，你的数据库数据就没了（这个坑几乎所有新手都踩过）
- 镜像我下载慢，国内需要配镜像加速器
- 容器里的文件系统和宿主机隔离，挂载路径出问题时排查麻烦（中文路径尤其容易出问题——这就是我们改英文目录的原因）
- 图形界面（Docker Desktop）在 Windows 上偶尔会抽风，需要重启

**⑥ 本项目用在哪**
`docker-compose.yml` 编排三个服务：
- `postgres`：用 `pgvector/pgvector:pgXX` 镜像
- `redis`：用 `redis:7-alpine`
- `pgadmin`：数据库图形界面（可选，方便你查看数据）

**所有数据用命名卷（named volume）持久化**，`down` 不加 `-v` 就不会丢。

## 28. Nginx

**① 是什么**
一个高性能的 Web 服务器和**反向代理**。

**反向代理**是什么：用户访问 `http://你的域名/`，请求先到 Nginx，Nginx 再决定转给谁——访问 `/api/xxx` 转给后端 Java 服务（8080 端口），访问 `/` 转给前端静态文件。

```
用户 ──→ Nginx (80/443) ──┬──→ /api/*  → Spring Boot (8080)
                          └──→ /*      → 前端静态文件
```

（和它相对的是**正向代理**，比如你用的翻墙软件——正向代理代表客户端，反向代理代表服务器。）

**② 解决什么问题**
- **统一入口**：前后端分离后，前端在 5173 端口、后端在 8080 端口，浏览器直接访问会有跨域问题。用 Nginx 统一在 80 端口下，`/api` 走后端、`/` 走前端，**跨域问题从根源消失**
- **静态文件服务**：Nginx 服务静态文件（HTML/JS/CSS）的性能远高于 Java
- **HTTPS 终止**：证书配在 Nginx 上，后端不用管
- **负载均衡**：多个后端实例时，Nginx 分发请求

**③ 不用它会怎样**
- 前端直接调后端 8080 端口，浏览器因为跨域（CORS）拦截请求，你得在 Spring Boot 里配 CORS 白名单
- 要把前端打包后的静态文件塞进 Spring Boot 的 `resources/static`，前后端耦合在一起
- 上 HTTPS 要直接在 Java 里配证书，麻烦且重启成本高

**④ 优点**
- **性能极高**，处理静态文件和并发连接能力远超 Java
- 配置简单，几十行就能搞定常见场景
- 生态成熟，几乎所有部署方案都用它

**⑤ 缺点**
- **配置语法自成一派**，不常写就容易忘
- **SSE 场景有坑**：默认开启 `proxy_buffering`，会把流式响应缓冲起来，导致**前端一个字都收不到，等 30 秒后答案一次性出现**。必须显式配置：
  ```nginx
  location /api/chat/stream {
      proxy_buffering off;
      proxy_cache off;
      proxy_read_timeout 300s;
      proxy_set_header Connection '';
      proxy_http_version 1.1;
  }
  ```
- 配置文件写错会导致 Nginx 起不来，而它的错误提示不够友好

**⑥ 本项目用在哪**
阶段 8 部署时。统一入口 + 静态文件 + **专门为 SSE 接口关掉缓冲**（这是本项目最容易踩的部署坑）。

## 29. 内网穿透

**① 是什么**
让你的**本地电脑**能被公网访问的技术。

问题在于：你家/学校的路由器给电脑分配的是**内网 IP**（如 `192.168.1.100`），公网上的用户根本访问不到，而且这个 IP 还会变。

内网穿透的做法是：你在本地电脑上跑一个客户端，它**主动**连接一台有公网 IP 的服务器，建立一条隧道。之后外部用户访问那台服务器的地址，流量就通过隧道转发到你的电脑。

```
外部用户 ──→ 公网服务器 (有固定 IP) ──隧道──→ 你的电脑 (内网)
```

**② 解决什么问题**
- 学生没有公网 IP，也不一定能买服务器
- 想让别人（比如面试官）访问你本地跑的项目
- 临时演示、调试 Webhook 回调

**③ 不用它会怎样**
只能本机 `localhost` 访问，或者在同一局域网内用内网 IP 访问。别人看不到。

**④ 优点**
- **零成本**（免费版够用）
- 配置简单，下载客户端跑一条命令就给一个公网地址
- 不需要改路由器、不需要公网 IP

**⑤ 缺点**
- **免费版地址不固定**：每次重启客户端地址就变了，你得重新发给别人
- **带宽和速度受限**：免费版通常限速，SSE 流式传输可能有延迟
- **依赖第三方服务**：对方服务挂了、或者免费额度用完了，你的项目就访问不了
- **安全问题**：等于把你本地服务暴露到公网，别人可以扫描到。**必须加访问控制**，别把数据库端口也暴露出去
- 电脑关机 / 休眠 → 服务立刻不可用

**⑥ 本项目用在哪**
阶段 8 部署。工具选型的时候我会给你几个方案对比（cpolar / frp / ngrok / 花生壳），由你决定用哪个。

> ⚠️ **重要提醒**：内网穿透**只暴露应用端口（8080 或 Nginx 的 80）**，绝对不要把 PostgreSQL 的 5432 和 Redis 的 6379 暴露出去——数据库裸奔在公网上会在几小时内被扫描并被勒索。

## 30. Vue 3 / Vite / Element Plus

这三个是一套前端组合，一起讲：

**Vue 3** —— **前端框架**。原本写网页要手动操作 DOM（`document.getElementById(...).innerHTML = ...`），页面一复杂就失控。Vue 让你**声明式**地写："数据变了，界面自动更新"。

```vue
<!-- 数据 messages 一变，界面自动重新渲染，不用手动操作 DOM -->
<div v-for="msg in messages" :key="msg.id">{{ msg.content }}</div>
```

**Vite** —— **前端构建工具**。负责把 `.vue` 文件编译成浏览器能懂的 JS、打包、以及提供一个开发服务器。特点是**启动极快**（利用浏览器原生 ES 模块，不需要先打包整个项目）。同类产品是 Webpack（更老、更慢、配置更复杂）。

**Element Plus** —— **UI 组件库**。按钮、输入框、表格、对话气泡等现成组件，不用自己写 CSS。Vue 3 生态里最主流的组件库。

**② 解决什么问题**
- Vue：解决"手动操作 DOM 导致代码难以维护"
- Vite：解决"改一行代码要等 10 秒才看到效果"
- Element Plus：解决"每个项目都重写一遍按钮和表格"

**③ 不用它会怎样**
用原生 JS 手写：代码量大、状态管理混乱、界面样式要自己写。或者用 React（另一个主流框架，生态更大但学习曲线更陡）。

**④ 优点**
- **Vue 中文文档质量极高**，是国内前端事实标准
- **国内 Java 后端岗位的标配前端**，简历上写"Vue3 + Element Plus"是加分项
- Vite 开发体验好，热更新毫秒级
- Element Plus 组件丰富，做后台管理类界面几乎不用写 CSS

**⑤ 缺点**
- Vue 生态在国际上不如 React，外企岗位认可度略低
- Element Plus 默认样式比较"后台管理系统风"，要做出好看的聊天界面需要额外调样式
- **SSE 需要手写接收逻辑**（`EventSource` API），Element Plus 没有现成组件
- 学 Vue 要理解响应式、组件生命周期、组合式 API 等概念，有学习成本

**⑥ 本项目用在哪**
阶段 8 的聊天界面：
- 消息列表（用户气泡 / AI 气泡）
- **SSE 流式接收 + 打字机效果**
- 排队状态提示（"你前面还有 3 人"）
- 引用来源展示（回答下面列出参考了哪几段知识库文档）
