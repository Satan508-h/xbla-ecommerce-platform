#### 2.1.1 ★★ 为什么意图准确率有两个数（差的就是那几道工具题）

`IntentTree.classificationTargets()` 的规则是「行为相同的不区分」：

```
retrieval = KB   →  展开到【叶子】
retrieval ≠ KB   →  只算【一个】目标，用【顶层 code】
```

所以 `ORDER_LOGISTICS` 是合法输出，而 **`INVENTORY` / `MY_COUPON` / `ORDER_STATUS` 这几个工具叶子码模型永远不可能输出** —— 而题库里那 **15 道**工具题的 gold 恰恰是它们。

```
逐题取众数      134/159 = 0.8428    ← 含 15 道恒错的题
★★ 可比口径     134/144 = 0.9306    ← 剔除 gold 不是合法分类目标的题
差              8.78 个百分点，与分类质量无关
```

★ 这不是 bug，是「两套粒度」必然的接缝。**但一个数字旁边挂着错的口径就不可解释** —— 所以两个数都报，并写清哪个是哪个。

★★ **它有可测量的质量后果，不只是记账问题** —— 见 §4.3：那 15 道题的 `context_recall` 是 **0**。

★★ **`context_recall` 是唯一不含 `response` 的** —— 而 `response` 是模型每次重新生成的。⇒ 它的波动**只来自检索侧**；其余三个的波动**主要来自生成侧**。这两个源的量级和测法是两回事。

**contexts 的两种口径**（本项目自己定的，不是 ragas 的）

- `faithfulness` 用 **contexts（切片 + 结构化硬数据）—— 模型看到的全部输入**
- `context_recall` 用 **contextsRetrievedOnly（只切片）—— 它量的是检索质量，注入的硬数据算进去是循环论证**

★★ 一个 contexts 满足不了两件事：`faithfulness` 判的是「**模型看到的全部输入**」（结构化硬数据确实进了 prompt），`context_recall` 判的是「**检索**回来的东西准不准」—— 拿注入的硬数据证明「检索好」是**循环论证**。

## 6 多轮集（单独分母）

★★ **多轮题单独一套、单独分母、单独报告。** 理由是范畴性的，不是谨慎：

```
分类器的输入【按决策不含历史】—— 所以「追问轮的意图」不是一个可测量的量。
```

把多轮题混进单轮的分母，会让「意图准确率」这个数字**同时描述两件不同的事**。

#### 澄清恢复（阶段 9.4 的机制在不在）

★★ **轮次边界靠 `session_id` 还原，不靠位置推算。** 一轮多轮题把 N 轮提交在**同一个题号**下，而 `qa_log` 没有轮次列。「第 r 次重复的第 t 轮 = 第 r×T+t 行」依赖的是**客户端的两层循环顺序**，客户端一改循环就静默错位；而每次重复**新建一个会话**，所以「同题号 + 同 session」是**服务端看得见的事实**。

## 10 未被解释的现象

以下现象**曾经**没解释清。★ 10.1 已于 2026-09-24 **结案**，其余仍未解释 —— 留着比删掉好，它们标记的是「这条链路里还有我们不知道的东西」。

### 10.1 ★ 已结案：`Set.copyOf` 的渲染顺序

**现象**：同一份数据、同一份 `intent-tree.yml`（`doc_types: [1, 5]`），旧一轮 `report.json` 印 `[1, 5]`、新一轮印 `[5, 1]`。当时用**同一个 JDK** 单独跑 `Set.copyOf(List.copyOf(new ArrayList<>(List.of(1,5))))` 得到的是 `[1, 5]` —— **复现不出来，也就没解释清**。

**★★★ 2026-09-24 解释清楚了**：

```
Set.copyOf 走的是 ImmutableCollections.SetN（不是保留插入顺序的 Set12），
它的迭代顺序是 floorMod(hash ^ SALT, tableSize) ——
而 SALT 【每次 JVM 启动都随机】（JDK 9+）。

实测 20 个独立 JVM，Set.copyOf(List.of(4, 2)).toString()：
    [4, 2] 14 次        [2, 4] 6 次
换成 3 个元素，20 个 JVM 跑出了【5 种不同顺序】。
```

★ 所以「同一个 JDK 复现不出来」**正是这个机制的表现**：
**在【单个 JVM 内】它是确定的**（同一个 SALT），换个 JVM 就变 —— 而当时的复现尝试全都在一个 JVM 里。

★★ 同一个 SALT 还让一个**测试**变成 flaky（约 50% 概率红）：`EvalReportServiceTest` 里断言 `Set.copyOf([4,2]).toString() == "[4, 2]"`，而 `n≥3` 时盲区**不随元素个数下降**（稳定在约 1/4）。处置见 `docs/10` 坑 19 —— 对照物换成顺序可控的 `LinkedHashSet`。

★ 处置不变，而且现在**有理由**了：不再依赖它 —— `Set` 的迭代顺序**根本不是它承诺的东西**。渲染前排序之后，那两个字符串由我们决定（`EvalReportService.sorted()`）。

★ **数字不受影响** —— `Set.equals` 与顺序无关，实测两轮检索范围准确率的**分子分母逐字相同**（§2.3 那一行的 `✅` 就是这个证据）。

### 10.2 RAGAS 的 `MetricResult.reason` 恒为 `None`

`ragas 0.4.3` 四个 collections 指标的源码就是 `return MetricResult(value=float(score))`，**压根不填 reason**。

★ 所以「为什么这道题 0.389」**不能从 RAGAS 自己的输出问**，只能用 T4 的归因桶做替代依据。要拿 statement 级判定得实现一个记录 `_create_verdicts` 返回值的子类，且**每次调用新建指标实例**（共用一个实例会让并发互相踩 `self.last_verdicts`）—— 本期不做。

### 10.3 出站调用的超时没有触发

阶段 6 的跑批里发现两个线程在 `httpClient.send()` 上挂了 **60+ 分钟**，而 `.timeout(180s)` 已经设在 `HttpRequest` 上。

★ 处置：换成 `sendAsync(...).get(timeout)` —— **我们自己的闸门**，不依赖 JDK 内部的定时器。★ **没做**：查清 JDK 的 `.timeout()` 为什么没触发。绕开它需要一次定向复现，收益是「知道 JDK 的行为」而不是「修好我们的东西」。

### 10.4 部分完成的结果不是「小一点的全体」

RAGAS 跑到 9 行时报的是 `faithfulness 0.978`，跑完 43 行是 **0.786**。

```
完成顺序 = asyncio.gather 的顺序 = 题号字母序 = 意图前缀序
  C-/F-/FR-/IN-/MB-... 先完成（faith 高）
  TI-/UG-/W- 最后完成（faith 低）
```
