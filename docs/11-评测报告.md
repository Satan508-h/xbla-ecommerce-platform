#### 2.1.1 ★★ 为什么意图准确率有两个数（差的就是那几道工具题）

`IntentTree.classificationTargets()` 的规则是「行为相同的不区分」：

```
retrieval = KB   →  展开到【叶子】
retrieval ≠ KB   →  只算【一个】目标，用【顶层 code】
```

所以 `ORDER_LOGISTICS` 是合法输出，而 **`INVENTORY` / `MY_COUPON` / `ORDER_STATUS` 这几个工具叶子码模型永远不可能输出** —— 而题库里那 **15 道**工具题的 gold 恰恰是它们。

```
逐题取众数      134/159 = 0.8428    ← 含 15 道恒错的题
★★ 可比口径     134/144 = 0.9306    ← 剔除 gold 不是合法分类目标的题
差              8.78 个百分点，与分类质量无关
```

★ 这不是 bug，是「两套粒度」必然的接缝。**但一个数字旁边挂着错的口径就不可解释** —— 所以两个数都报，并写清哪个是哪个。

★★ **它有可测量的质量后果，不只是记账问题** —— 见 §4.3：那 15 道题的 `context_recall` 是 **0**。

| `gold_missing` | 正解切片已经不在库里 | **标注集失效** |
| `beyond_record_cutoff` | 无法判定（记录被截断） | **证据不足** |

★ 三个桶和 `检索` 那一节的关系：`ok + filtered_out + gold_missing = 检索分母`；剩下的是「进了分母但没命中」，`beyond_record_cutoff` 是其中的**不可判定**部分。

**★★ `beyond_record_cutoff` 必须和这张表一起读：**

|  | 噪声底轮 | 主体轮 |
|---|---|---|
| 有 `sizes` 段（可判定） | 0 | 130 |
| 无 `sizes` 段（**不可判定**） | 130 | 0 |

⚠️ **噪声底轮有 130 行没有 `sizes` 段**（`sizes` 是 2026-09-21 才加进 `retrieval_detail` 的）。那一轮里「融合有没有丢正解」是**证不了的** —— `fusion_dropped = 0` **不构成「RRF 没丢东西」的证据**，它只是「没有证据说它丢了」。

★★ 这是**两轮的数据形状不同**，不是数据变了。缺的那个段当时就没写进库 —— **只能重跑才能对齐，重算报告没用。**

★ **部分被过滤的题：1 道** —— 正解里有**一部分**切片的类型不在生效的 `doc_types` 里。它们归到 `ok`（正解确实进了 prompt），但**上下文是残缺的**。★ 这一栏存在的意义：`filtered_out` 是全有全无的判据，而真实情况经常是「来了 3 条里的 1 条」。

### 4.0 ★★ 先说清四个数各自吃的是什么

**判据不是「文档这么说」，是「源码里 `ascore` 的签名」** —— 下面这张表是读出来的：

★★ **`answer_relevancy` / `answer_correctness` 根本看不到检索结果** —— 它们测不到检索质量，只在测「答案贴不贴题 / 对不对」。把它们当成检索指标读是本项目最反对的那种误读。

★★ **`context_recall` 是唯一不含 `response` 的** —— 而 `response` 是模型每次重新生成的。⇒ 它的波动**只来自检索侧**；其余三个的波动**主要来自生成侧**。这两个源的量级和测法是两回事。

- `context_recall` 用 **contextsRetrievedOnly（只切片）—— 它量的是检索质量，注入的硬数据算进去是循环论证**

★★ 一个 contexts 满足不了两件事：`faithfulness` 判的是「**模型看到的全部输入**」（结构化硬数据确实进了 prompt），`context_recall` 判的是「**检索**回来的东西准不准」—— 拿注入的硬数据证明「检索好」是**循环论证**。

把两轮之间**实际存在**的差异按成因分类。判据只有一条：**这个差异能不能被一个已证伪的成因解释掉。**

| 类 | 判据 | 这一期的数 |
|---|---|---|
| 🔴 **序列 churn**（顺序变了，命中没变） | `跨次序列变了` | 17 道 |
| 🟡 **命中变化**（真的换了切片） | `命中@5` | 1 道 |
| 🟡 **归因变化** | `归因` | 1 道 |
| 🟢 **分类变化**（含漂移，不代表变好变坏） | `意图正确` | 4 道 |
| 🟢 **闸门变化** | `闸门` | 0 道 |

**读法**

- 🔴 序列 churn **不构成**「变好 / 变坏」的证据 —— 它只改顺序，不改命中集合
- 🟡 **命中 / 归因的变化才有资格被叫作信号**，但**仍然不是「变好」** —— 换一个同样合法的 gold 命中也是 `ok → ok`（洞 1）

**标注与构造**

- **标注者 = Claude，审核 = 你抽查。** 不写「人工标注集」这种含糊说法

## 10 未被解释的现象

以下都是**观察到了、但没解释清**的现象。留着比删掉好 —— 它们标记的是「这条链路里还有我们不知道的东西」。

### 10.1 `Set.copyOf` 的渲染顺序

同一份数据、同一份 `intent-tree.yml`（`doc_types: [1, 5]`），旧一轮 `report.json` 印 `[1, 5]`、新一轮印 `[5, 1]`。
用**同一个 JDK** 单独跑 `Set.copyOf(List.copyOf(new ArrayList<>(List.of(1,5))))` 得到的是 `[1, 5]` —— **没解释清楚**。

★ 处置不是继续查 JDK，是**不再依赖它**：`Set` 的迭代顺序**根本不是它承诺的东西**。渲染前排序之后，那两个字符串由我们决定（`EvalReportService.sorted()`）。

★ **数字不受影响** —— `Set.equals` 与顺序无关，实测两轮检索范围准确率的**分子分母逐字相同**（§2.3 那一行的 `✅` 就是这个证据）。

### 10.2 RAGAS 的 `MetricResult.reason` 恒为 `None`

`ragas 0.4.3` 四个 collections 指标的源码就是 `return MetricResult(value=float(score))`，**压根不填 reason**。

★ 所以「为什么这道题 0.389」**不能从 RAGAS 自己的输出问**，只能用 T4 的归因桶做替代依据。要拿 statement 级判定得实现一个记录 `_create_verdicts` 返回值的子类，且**每次调用新建指标实例**（共用一个实例会让并发互相踩 `self.last_verdicts`）—— 本期不做。

### 10.3 出站调用的超时没有触发

阶段 6 的跑批里发现两个线程在 `httpClient.send()` 上挂了 **60+ 分钟**，而 `.timeout(180s)` 已经设在 `HttpRequest` 上。

★ 处置：换成 `sendAsync(...).get(timeout)` —— **我们自己的闸门**，不依赖 JDK 内部的定时器。★ **没做**：查清 JDK 的 `.timeout()` 为什么没触发。绕开它需要一次定向复现，收益是「知道 JDK 的行为」而不是「修好我们的东西」。

### 10.4 部分完成的结果不是「小一点的全体」

RAGAS 跑到 9 行时报的是 `faithfulness 0.978`，跑完 43 行是 **0.786**。

```
完成顺序 = asyncio.gather 的顺序 = 题号字母序 = 意图前缀序
  C-/F-/FR-/IN-/MB-... 先完成（faith 高）
  TI-/UG-/W- 最后完成（faith 低）
```

★★ **在报告里引用未跑完的数字，等于系统性挑了一个乐观的子集** —— 而且没有任何迹象。

丢了的题号：PP-008

★★ 用法：**先看原理允许哪个方向，再看这一轮是不是那个方向。**

- `final-top-k` 调**大** ⇒ contexts 是超集 ⇒ 期望 `B ⊇ A` 占压倒多数
  （`context_recall` / `faithfulness` 因此**结构性不可能下降**）
- `rerank.max-candidates` 调**小** ⇒ 重排候选是子集 ⇒ 期望 `B ⊆ A`
  （召回因此**结构性不可能上升**）
- `rerank.enabled` 开关 ⇒ 两条完全不同的排序 ⇒ **两个方向都不该压倒**
