# 04 · 数据库设计

> 本文档是阶段 1 建表的**唯一依据**。写建表 SQL 时对着这里抄，不要临时发挥。
>
> **为什么先写文档再建表**：表结构一旦建好、灌了种子数据，再改的代价极高
> （要改 DDL + 实体类 + Mapper + 已有 SQL + 重新生成数据）。
> 先在纸上把关系理清楚，比在数据库里反复 `ALTER TABLE` 便宜得多。

---

## 一、设计原则

### 1.1 全局约定

每个设计决策都有理由，不是随手定的：

| 约定 | 取值 | 理由 |
|---|---|---|
| 表名/字段名 | `snake_case` 全小写 | CLAUDE.md 第 7 条。PostgreSQL 对未加引号的标识符会转小写，用驼峰会逼着你到处加引号 |
| Java 侧 | `camelCase` | MyBatis-Plus 开启 `map-underscore-to-camel-case` 自动映射，无需手写 `@Results` |
| 主键 | `BIGSERIAL` 自增 | 单机开发环境不需要分布式 ID。自增 ID 在调试时可读、索引局部性好、`COUNT` 快 |
| 外键 | **加 `FOREIGN KEY` 约束** | 本项目单库单机，加外键能挡住脏数据。灌 200 条商品种子数据时，写错 ID 会立刻报错而不是默默写进去 |
| 时间类型 | `TIMESTAMPTZ` | 带时区。`TIMESTAMP` 不带时区，跨时区或夏令时会出错。项目要记录问答延迟、优惠券有效期，时间必须准 |
| 金额类型 | `NUMERIC(12,2)` | **绝不用 `FLOAT`/`DOUBLE`** —— 浮点数存不下 0.1，算钱会出 0.30000000000000004 这种结果 |
| 软删除 | `deleted SMALLINT DEFAULT 0` | 0=正常，1=已删除。MyBatis-Plus 的 `@TableLogic` 会自动给查询拼上 `WHERE deleted = 0` |
| 布尔语义 | 用 `SMALLINT` 而非 `BOOLEAN` | 和软删除保持一致，也方便将来扩展成多状态。纯真假语义的字段（如 `is_baseline`）用 `BOOLEAN` |

### 1.2 哪些表有软删除

**不是所有表都要软删除**——日志类表加了反而累赘：

| 类型 | 表 | 软删除 | 理由 |
|---|---|---|---|
| 业务表 | `product` / `product_sku` / `orders` / `coupon` … | ✅ 有 | 商品下架、订单作废都是业务状态，数据要留着 |
| 知识库表 | `kb_document` / `kb_chunk` | ✅ 有 | 文档换版本时旧切片要保留，评测要能追溯 |
| 会话表 | `chat_session` | ✅ 有 | 用户"删除"会话通常只是隐藏 |
| **日志表** | `qa_log` / `chat_message` | ❌ **无** | **只增不删**。CLAUDE.md 第 4 条：评测数据来源于 `qa_log`，删了就断了证据链 |
| 标注表 | `eval_question` | ❌ 无 | 人工标注成本极高，不允许删除 |

### 1.3 通用字段

除日志表外，所有表都带这几个字段：

```sql
created_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),   -- 创建时间
updated_at  TIMESTAMPTZ  NOT NULL DEFAULT now(),   -- 更新时间（由应用层或触发器维护）
deleted     SMALLINT     NOT NULL DEFAULT 0        -- 软删除标记（日志表没有这个）
```

## 二、用户域

### app_user

> **为什么不叫 `user`**：`USER` 是 SQL 标准保留字（等价于 `CURRENT_USER`）。
> 用它做表名，之后每条 SQL 都得写成 `SELECT * FROM "user"`，漏了引号就报错。
> 加个 `app_` 前缀是最省事的规避方式。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| user_no | VARCHAR(64) | UNIQUE NOT NULL | 用户编号，对外展示用，不暴露自增 ID |
| nickname | VARCHAR(64) | NOT NULL | 昵称 |
| phone | VARCHAR(32) | | 手机号，**脱敏存储**（如 `138****8888`） |
| member_level | SMALLINT | NOT NULL DEFAULT 1 | 会员等级。1普通 2银卡 3金卡 4钻石 |
| created_at / updated_at / deleted | | | 通用字段 |

**设计点**：`phone` 脱敏存。虽然本项目是仿真数据，但**这个习惯要在真实项目里养成**——
手机号属于个人敏感信息，明文入库一旦泄露后果严重。

## 三、商品域

### product

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| product_no | VARCHAR(64) | UNIQUE NOT NULL | 商品编号 |
| name | VARCHAR(255) | NOT NULL | 商品名称 |
| category | VARCHAR(64) | NOT NULL | 类目名，如"手机"、"笔记本电脑"、"家用电器" |
| sub_category | VARCHAR(64) | | 子类目 |
| brand | VARCHAR(64) | | 品牌 |
| price | NUMERIC(12,2) | NOT NULL | 售价 |
| original_price | NUMERIC(12,2) | | 划线价（原价），用于展示折扣 |
| description | TEXT | | 商品描述 |
| **selling_points** | TEXT | | **卖点**，如"续航 18 小时 / 重量 1.2kg" |
| **suitable_for** | VARCHAR(512) | | **适用人群/场景**，如"适合送长辈、商务人士" |
| status | SMALLINT | NOT NULL DEFAULT 1 | 1上架 0下架 |
| created_at / updated_at / deleted | | | 通用字段 |

**设计点**：`selling_points` 和 `suitable_for` 是**为 RAG 场景专门加的**。

朴素 RAG 的典型失败是：用户问"这个适合送长辈吗"，向量检索匹配到的是
规格参数表（"屏幕 6.7 英寸 / 电池 5000mAh"），答非所问。
把"适用场景"显式建模成一个字段，再连同它一起向量化，
检索时就有一条明确的语义线索可以命中。这是**用数据建模解决检索问题**，
比单纯调 prompt 更根本。

### product_sku

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| product_id | BIGINT | FK → product(id) NOT NULL | 所属商品 |
| sku_no | VARCHAR(64) | UNIQUE NOT NULL | SKU 编号 |
| spec_name | VARCHAR(255) | NOT NULL | 规格描述，如"256G 星空黑" |
| **spec_json** | JSONB | | **结构化规格**，如 `{"颜色":"星空黑","存储":"256G"}` |
| price | NUMERIC(12,2) | NOT NULL | 该 SKU 售价（可能不同于商品价） |
| barcode | VARCHAR(64) | | 条形码 |
| status | SMALLINT | NOT NULL DEFAULT 1 | 1可售 0停售 |
| created_at / updated_at / deleted | | | 通用字段 |

**索引**：`CREATE INDEX idx_product_sku_product_id ON product_sku(product_id);`

**设计点**：规格用 `JSONB` 而不是拆成多列。因为**不同类目的规格维度完全不同**——
手机是"颜色/存储"，衣服是"尺码/颜色"，家电是"容量/能效"。
如果拆成固定列，就得建一堆大部分为空的行。`JSONB` 既能灵活存，
又支持 `spec_json @> '{"颜色":"星空黑"}'` 这样的索引查询。
阶段 4 做**规格对比**时直接读这个字段。

### product_attribute

> 这是**参数表**（"屏幕尺寸 6.7 英寸"），和上面的 `product_sku`（**可购买的具体型号**）是两回事。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| product_id | BIGINT | FK → product(id) NOT NULL | 所属商品 |
| attr_group | VARCHAR(64) | NOT NULL | 参数分组，如"基本参数"、"屏幕"、"摄像头" |
| attr_name | VARCHAR(64) | NOT NULL | 参数名，如"屏幕尺寸" |
| attr_value | VARCHAR(255) | NOT NULL | 参数值，如"6.7 英寸" |
| sort_order | INT | NOT NULL DEFAULT 0 | 组内排序 |
| created_at / updated_at | | | 通用字段（参数变更直接改，不做软删除） |

**索引**：`CREATE INDEX idx_product_attribute_product_id ON product_attribute(product_id);`

**唯一约束**：`UNIQUE (product_id, attr_group, attr_name)`

## 四、库存域

### inventory

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| sku_id | BIGINT | FK → product_sku(id) UNIQUE NOT NULL | 一个 SKU 一条库存记录 |
| total_stock | INT | NOT NULL DEFAULT 0 | 总库存 |
| available_stock | INT | NOT NULL DEFAULT 0 | **可售库存**（MCP 工具查的就是它） |
| locked_stock | INT | NOT NULL DEFAULT 0 | 锁定库存（已下单未付款） |
| warehouse | VARCHAR(64) | | 仓库位置 |
| version | INT | NOT NULL DEFAULT 0 | **乐观锁版本号** |
| created_at / updated_at | | | 通用字段 |

**约束**：`CHECK (available_stock >= 0)`

**设计点**：
- 拆成"可售/锁定"两个字段，而不是只留一个 `stock`。
  下单时先 `available_stock -= n; locked_stock += n`，付款后 `locked_stock -= n`，
  取消订单则反向操作。**这样"已下单未付款"不会导致超卖**。
- `version` 字段是乐观锁。阶段 6 做并发控制时，
  `UPDATE inventory SET available_stock = available_stock - 1, version = version + 1 WHERE id = ? AND version = ?`
  靠这个避免并发覆盖。
- `CHECK (available_stock >= 0)` 是**最后一道防线**——
  即使应用层逻辑写错了，数据库也会拒绝把库存扣成负数。

## 五、交易域

### orders

> 表名用复数 `orders`。`order` 是 SQL 关键字（`ORDER BY`），
> 单数做表名容易踩坑，业界惯例就是加 s。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| order_no | VARCHAR(64) | UNIQUE NOT NULL | 订单号，对外展示 |
| user_id | BIGINT | FK → app_user(id) NOT NULL | 下单用户 |
| total_amount | NUMERIC(12,2) | NOT NULL | 商品总额 |
| discount_amount | NUMERIC(12,2) | NOT NULL DEFAULT 0 | 优惠金额 |
| pay_amount | NUMERIC(12,2) | NOT NULL | 实付 = total - discount |
| status | SMALLINT | NOT NULL | 见下方状态机 |
| receiver_name | VARCHAR(64) | | 收货人 |
| receiver_phone | VARCHAR(32) | | 收货电话（脱敏） |
| receiver_address | VARCHAR(512) | | 收货地址 |
| logistics_no | VARCHAR(64) | | 物流单号 |
| logistics_company | VARCHAR(64) | | 物流公司 |
| paid_at / shipped_at / completed_at / cancelled_at | TIMESTAMPTZ | | 各状态时间点 |
| created_at / updated_at / deleted | | | 通用字段 |

**订单状态机**（MCP 工具「订单状态查询」直接读这个字段）：

```
10 待付款 ──付款──> 20 待发货 ──发货──> 30 已发货 ──签收──> 40 已完成
   │                    │
   └──取消──> 50 已取消 <──┘
```

**为什么用数字而不是字符串**：状态值存 `'待发货'` 这种中文，
将来改文案就要 `UPDATE` 全表；存数字，展示文案由应用层映射，改文案不动数据。

**索引**：
```sql
CREATE INDEX idx_orders_user_id ON orders(user_id);
CREATE INDEX idx_orders_status ON orders(status);
CREATE INDEX idx_orders_created_at ON orders(created_at DESC);
```

### order_item

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| order_id | BIGINT | FK → orders(id) NOT NULL | 所属订单 |
| product_id | BIGINT | FK → product(id) NOT NULL | 商品 |
| sku_id | BIGINT | FK → product_sku(id) NOT NULL | SKU |
| **product_name** | VARCHAR(255) | NOT NULL | **下单时的商品名（快照）** |
| **spec_name** | VARCHAR(255) | NOT NULL | **下单时的规格（快照）** |
| price | NUMERIC(12,2) | NOT NULL | **下单时的单价（快照）** |
| quantity | INT | NOT NULL | 数量 |
| subtotal | NUMERIC(12,2) | NOT NULL | 小计 = price × quantity |
| created_at | | | 通用字段 |

**设计点（面试常问）**：为什么把商品名、规格、单价**冗余**存一份？

因为**商品是会变的**。商品改名、调价、下架之后，
如果订单明细只存 `product_id`，回看历史订单时查到的是**现在的**商品信息——
用户会看到"我明明 99 买的，怎么显示 199"。

这叫**快照冗余**，是交易系统的标准做法：
`product_id` 用于关联查询，快照字段用于展示，两者用途不同，都要保留。

**索引**：`CREATE INDEX idx_order_item_order_id ON order_item(order_id);`

### after_sale_policy

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| policy_no | VARCHAR(64) | UNIQUE NOT NULL | 政策编号 |
| category | VARCHAR(64) | | 适用类目，NULL 表示通用 |
| title | VARCHAR(255) | NOT NULL | 政策标题，如"七天无理由退货规则" |
| content | TEXT | NOT NULL | **政策正文**——会被切分并向量化进知识库 |
| return_days | INT | | 可退货天数 |
| exchange_days | INT | | 可换货天数 |
| conditions | TEXT | | 附加条件，如"拆封后不支持" |
| effective_from / effective_to | TIMESTAMPTZ | | 生效区间 |
| version | INT | NOT NULL DEFAULT 1 | 版本号 |
| status | SMALLINT | NOT NULL DEFAULT 1 | 1生效 0失效 |
| created_at / updated_at / deleted | | | 通用字段 |

**设计点**：`content` 是自由文本，是**知识库的语料来源之一**。
阶段 3 会把这张表的内容同步到 `kb_document` / `kb_chunk` 并向量化，
这样"退货要几天"这类问题才能被语义检索命中。

**为什么同时有 `content`（文本）和 `return_days`（结构化字段）**：
两者服务不同场景——`content` 供 RAG 语义检索（能回答"我拆封了还能退吗"这种
文本里才有答案的问题）；`return_days` 供 MCP 工具做精确查询
（"退货政策是几天"可以直接 `SELECT return_days`，比向量检索更准更快）。

## 八、知识库域 ★

这是整个项目**最核心的两张表**。

### kb_document

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| doc_no | VARCHAR(64) | UNIQUE NOT NULL | 文档编号 |
| title | VARCHAR(255) | NOT NULL | 文档标题 |
| doc_type | SMALLINT | NOT NULL | 1商品详情 2售后政策 3促销规则 4FAQ 5说明书 |
| source_type | SMALLINT | NOT NULL | 1文件上传 2数据库同步 |
| file_name | VARCHAR(255) | | 原始文件名 |
| file_path | VARCHAR(512) | | 存储路径 |
| file_size | BIGINT | | 文件字节数 |
| **file_hash** | VARCHAR(64) | | **文件内容的 SHA-256** |
| mime_type | VARCHAR(128) | | 如 `application/pdf` |
| related_product_id | BIGINT | FK → product(id) | 关联商品（可为空） |
| effective_from / effective_to | TIMESTAMPTZ | | 生效区间 |
| version | INT | NOT NULL DEFAULT 1 | 版本号 |
| status | SMALLINT | NOT NULL DEFAULT 1 | 1待处理 2处理中 3已入库 4处理失败 |
| chunk_count | INT | NOT NULL DEFAULT 0 | 切分出的切片数 |
| error_msg | TEXT | | 处理失败时的错误信息 |
| created_at / updated_at / deleted | | | 通用字段 |

**索引**：`CREATE INDEX idx_kb_document_file_hash ON kb_document(file_hash);`

**设计点**：
- `file_hash` 用于**重复上传去重**。同一个文件重复上传时，
  先算 SHA-256 查一下，命中就直接跳过，省掉一次完整的解析 + 向量化
  （向量化要调用模型 API，是花钱和花时间的操作）。

  ⚠️ **它比的是「文件字节」而不是「内容」，这个区别有后果**：
  docx / xlsx / PDF 都会把**创建时间**写进文件头，
  所以「内容一模一样但重新导出过一次」的文件哈希**完全不同**，
  去重**不会命中**，会被当成新文档再灌一遍（并真的调用向量化接口）。

  两个已知的应对（都在 `docs/08` ADR-028）：
  1. 语料生成器 `generate_corpus.py` 产出**字节确定**的文件，
     于是「重新生成 + 重新扫描」是幂等的；
  2. 命中去重时**会校正 `doc_type`**（`docs/08` ADR-027）——
     因为「文件内容没变」不等于「元数据没变」，
     改了语料清单的归类之后，去重照样命中，不校正就表现为**改了 YAML 却毫无效果**。

  ⚠️ 但**用户上传**的路径没有这层保护：同一份文档导出两次上传，会进两份库。
  目前靠人工留意，阶段 7 之后再考虑内容级去重（要先把文档解析出来才能比，
  而那正是去重想省掉的那一步）。
- `status` 是**异步处理的状态机**。文档入库要经过
  解析 → 切分 → 批量向量化 → 写库 四步，耗时可能几十秒到几分钟，
  不可能在 HTTP 请求里同步完成，必须有状态字段跟踪。
- `version` + `effective_from/to` 支持**文档换版**。
  政策改了不是删掉旧的，而是新增一个版本，旧版本标记失效时间——
  这样阶段 7 评测才能追溯"当时那个问题命中的是哪一版文档"。

### kb_chunk ★ 含向量列

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|

```sql
-- ① HNSW 向量索引：向量召回的加速器

    USING hnsw (embedding vector_cosine_ops)
    WITH (m = 16, ef_construction = 64);

-- ② 外键查询索引
CREATE INDEX idx_kb_chunk_document_id ON kb_chunk(document_id);

-- ③ 意图定向检索：先按类型+商品过滤，再做向量检索
CREATE INDEX idx_kb_chunk_doc_type ON kb_chunk(doc_type);
CREATE INDEX idx_kb_chunk_product ON kb_chunk(related_product_id);

-- ④ 内容去重
CREATE INDEX idx_kb_chunk_content_hash ON kb_chunk(content_hash);

-- ⑤ JSONB 元数据查询
CREATE INDEX idx_kb_chunk_metadata ON kb_chunk USING gin(metadata);
```

**设计点（这几个是面试重点）**：

**1. 为什么用 `vector_cosine_ops`（余弦距离）而不是欧氏距离？**

本项目的向量来自 `bge-m3`，**文本向量关心的是方向而不是长度**。
"手机很好用" 和 "这款手机真的很好用" 语义相同但长度不同，
欧氏距离会认为它们有差距，余弦距离只看夹角，判定为高度相似。
这是文本检索的通用选择。

**2. 为什么用 HNSW 而不是 IVFFlat？**

| | HNSW | IVFFlat |
|---|---|---|
| 查询速度 | 快 | 中等 |
| 召回率 | 高 | 依赖聚类数调参 |
| 建索引速度 | **慢** | 快 |
| 内存占用 | 高 | 低 |
| 增量插入 | **友好**（直接插） | 需要重建或退化 |

本项目数据量小（几千到几万切片）、**查询频繁**、**增量入库**（阶段 3 会不断灌文档），
HNSW 的"增量友好 + 高召回"更契合。IVFFlat 更适合"一次性灌完海量数据再查"的场景。

参数 `m = 16`（每个节点的邻居数）和 `ef_construction = 64`（建索引时的候选集大小）
是 pgvector 官方推荐的默认值，先按默认跑，阶段 7 评测时再调优——
**这就是"参数调优要基于指标而不是拍脑袋"的实践**。

> ✅ **语法已实测**：2026-09-18 在项目数据库上执行
> `CREATE INDEX ... USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64)`
> 创建成功，参数被 pgvector 0.8.6 接受。

**3. 为什么要冗余 `doc_type` / `related_product_id` / `effective_from`？**

因为**向量检索是"先过滤再算距离"还是"先算距离再过滤"，性能差几十倍**。

阶段 5 要做**意图定向检索**："用户问售后政策 → 只在 `doc_type = 2` 的切片里搜"。
如果这几个字段只在 `kb_document` 上，每次检索都要 join 一次文档表才能过滤，
而且 HNSW 索引在 join 场景下往往用不上，会退化成全表扫描 + 逐条算距离。

冗余到 `kb_chunk` 上之后，过滤条件可以和向量索引走同一个索引扫描。
**用少量存储空间换检索性能**，是检索系统的标准优化手段。

**4. `content_hash` 的作用**

阶段 3 切分时，相邻切片会有重叠窗口（保证语义不被切断）。
如果一份文档的中间某段被修改后重新入库，未变的部分不应该重新向量化。
按 `content_hash` 比对就能只处理变化的部分——
**省的是模型 API 的钱**，这是很实际的工程考量。

### chat_summary

> 会话记忆的**摘要层**。滑动窗口保留最近 N 轮原文，更早的压缩成摘要。

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| session_id | BIGINT | FK → chat_session(id) NOT NULL | 所属会话 |
| summary_level | SMALLINT | NOT NULL DEFAULT 1 | 1段落级摘要 2会话级摘要 —— ⚠️ **实际恒为 1，见下** |
| start_message_id | BIGINT | FK → chat_message(id) NOT NULL | 摘要覆盖的起始消息 ID |
| end_message_id | BIGINT | FK → chat_message(id) NOT NULL | **摘要游标** —— 覆盖到哪一条为止 |
| summary | TEXT | NOT NULL | 摘要正文 |
| token_count | INT | | ⚠️ **实际恒为 NULL，见下** |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

**索引**：`CREATE INDEX idx_chat_summary_session ON chat_summary(session_id, summary_level);`
⚠️ **非唯一**。所以「一个会话一行摘要」是**应用层保证的**（CAS 更新），不是数据库保证的。

**设计点：双层记忆策略**（本表于 2026-09-19 的 5.6 才第一次真正写入，
在此之前它从 V5 建好起一直是 0 行）

```
最近 10 轮  → 保留原文（细节不能丢）
更早的对话  → 压缩成摘要（保留语义，省 token）
```

为什么两层都要？**摘要会丢细节**（用户第 3 轮说的"我要买红色的"可能被压缩掉），
但**只保留原文又会 token 爆炸**（聊 20 轮后每轮都塞全部历史）。
两层策略是精度和成本的折中。

★ **`end_message_id` 是游标，不是「写了多少」**。它唯一的工作是回答
「摘要覆盖到哪一条为止」，于是「还有没有没压的」变成一次纯比较：

```
窗口起点 W  >  end_message_id + 1   →  中间那段没人管，该压了
窗口起点 W  == end_message_id + 1   →  严丝合缝
```

★★ **接缝必须严丝合缝**：`(end_message_id, W)` 之间的消息**谁都不覆盖**，
而且**永远不会被补上**。这就是「压缩终点锚在窗口起点 - 1」而不是
「溢出几条压几条」的全部理由。详见 ADR-048。

**为什么 `start_message_id` 不动**：摘要是**累积**的
（新摘要 = 合并(旧摘要, 新增对话)），所以它始终覆盖 `[start, 游标]` 这一整段。

#### ⚠️ 两处「有列但不用」—— 都是刻意的

| 列 | 实际值 | 为什么 |
|---|---|---|
| `summary_level` | 恒为 **1** | 单行滚动，每个会话永远只有一行。**level 2 是教科书式的分层摘要**，但它解的是「极长会话里 level-1 累积太多行」，而本项目真实会话最长 10 轮 —— 为一个没发生过的规模做两层是过度设计。**刻意不删**：删列要动 V5 迁移，而 V1–V5 一个字都不能改（`validate-on-migrate: true`）。见 ADR-051 |
| `token_count` | 恒为 **NULL** | 它那一列的含义是「这段摘要占多少 prompt 预算」，而 `usage.completionTokens` **包含推理 token**（实测占输出 87%）—— 存进去会让它系统性偏大，变成一个「有值但用途错」的列。`WHERE token_count IS NULL` 因此**不是**故障信号。同 ADR-010 原则 |

**摘要这一次调用的真实花费**在 `SessionSummarizer` 的 DEBUG 日志里
（实测每次约 **0.003–0.005 元**），**不进 `qa_log`** ——
`qa_log` 的语义是「一次问答」，而摘要是**记忆的维护**。见 `docs/05` §9.6 ⑤。

> 塞进去等于在最需要它的那条路上把它丢掉。

> ★★★ **`shape` 是这一列里最重要的一格**：

> ```
>   JSON      模型按新契约答的（拿得到 retrieve / missing）
>   CODE      模型只回了一个裸码 —— 老契约。此时 retrieve 取保守值 true
>   UNPARSED  两种都不是 → 分类整体失败

> 工具意图上两者会不同（模型说 `true`，而工具意图根本不检索）——

> 一个看起来像好消息的数，不会报错。（那个方法已经坏过两次，见坑 18）

**设计点**：

**1. 为什么要 `retrieval_detail` 这个 JSONB 字段？**

阶段 4 验收标准第 1 条要求：**"给定 20 个测试问题，能看到完整召回链路的中间输出
（每一路的原始结果、融合后、重排后）"**。这个字段就是用来装这些中间结果的：

```json
{
  "vector_hits":     [{"chunk_id": 12, "score": 0.87}, ...],   // 向量召回原始结果
  "keyword_hits":    [{"chunk_id": 45, "score": 3.2},  ...],   // 关键字召回原始结果
  "fused":           [{"chunk_id": 12, "rrf_score": 0.032}, ...], // RRF 融合后
  "reranked":        [{"chunk_id": 45, "rerank_score": 0.95}, ...], // 重排后
  "final_top_k":     [45, 12, 8],                               // 最终送进 prompt 的
  "filter":          {"doc_types": [2, 4], "applied": true,     // 阶段 5.4 加的第 6 段
                      "pool_size": 67, "reason": "ok"}
}
```

**没有这个字段，整个评测体系就无从谈起**——你无法回答
"召回失败是因为向量检索没找到，还是重排排错了，还是切分粒度不对"。
把中间结果落库，是让检索质量**可归因**的前提。

> ★ **`filter` 是阶段 5.4 加的第 6 段，也是唯一一次扩这个结构。**
> 前 5 个 key 的含义一个都没变，所以阶段 4 的基线脚本不受影响 ——
> 这是「加法式扩展」而不是「改结构」。
> 它回答的是另一个问题：**这次检索被收窄过吗、按什么收窄的、池子有多大**。
> `pool_size` 小 = 意图声明得太窄；池子大却召回不到 = 检索或切分的问题 ——
> **两种原因的修法完全相反**。详见 `docs/05` §9.4。
>
> ⚠️ `filter` 属于「**恒定存在的 key**」（永远出现，哪怕值全是空的），
> 而不是「非空才出现」的附加字段（`events` / `sub_questions`）。
> 区别在于「这次到底过滤了没有」是一次检索的固有属性，
> 即使答案是「没有」也必须能被机器读到。

**2. 为什么 latency 要拆成四段？**

`retrieval + rerank + llm + total` 四段分开记，才能定位性能瓶颈。
如果只记一个 `total_latency_ms`，P95 变慢了你也只能猜。
阶段 7 要报"延迟 P50/P95"，拆开之后还能说明**慢在哪一段**。

**3. `degradation_events` 长什么样**

```json
[
  {"from": "deepseek-p0", "to": "siliconflow-p1",
   "reason": "circuit_open", "at": "2026-09-18T00:12:33Z"}
]
```

阶段 2 验收标准第 2 条："故意把 P0 的 API Key 改错，确认自动降级到 P1，
**且 `qa_log` 记录了降级事件**"——就是查这个字段。

### eval_question

> 人工标注的评测集。CLAUDE.md 明确要求：
> **"评测的标准答案由人工标注，不用另一个模型生成——否则评测就变成了模型给自己打分。"**

| 字段 | 类型 | 约束 | 说明 |
|---|---|---|---|
| id | BIGSERIAL | PK | |
| question_no | VARCHAR(64) | UNIQUE NOT NULL | 题目编号 |
| question | TEXT | NOT NULL | 测试问题 |
| intent | VARCHAR(32) | NOT NULL | **人工标注的**正确意图。★ 存的是**叶子码**（如 `PRICE_PROTECTION`），不是顶层码；取值见 `data/agent/intent-tree.yml` |
| expected_answer | TEXT | | 人工撰写的标准答案 |
| expected_chunk_ids | BIGINT[] | | 应当被召回的切片 ID 列表 |
| expected_doc_ids | BIGINT[] | | 应当被召回的文档 ID 列表 |
| category | VARCHAR(64) | | 题目分类 |
| difficulty | SMALLINT | | 1易 2中 3难 |
| is_baseline | BOOLEAN | NOT NULL DEFAULT false | 是否纳入基线评测集 |
| source | VARCHAR(64) | | 题目来源（真实提问 / 人工构造） |
| annotated_by | VARCHAR(64) | | 标注人 |
| annotated_at | TIMESTAMPTZ | | 标注时间 |
| created_at | TIMESTAMPTZ | NOT NULL DEFAULT now() | |

**索引**：
```sql
CREATE INDEX idx_eval_question_intent ON eval_question(intent);
CREATE INDEX idx_eval_question_baseline ON eval_question(is_baseline) WHERE is_baseline = true;
```

**设计点**：
- `expected_chunk_ids` 用 **PostgreSQL 数组类型** `BIGINT[]`，
  而不是建一张关联表。因为这里只是"一组 ID"，不需要额外属性，
  数组查询 `WHERE 12 = ANY(expected_chunk_ids)` 也很直观。
- `is_baseline` 配合**部分索引**（`WHERE is_baseline = true`）——
  评测集可能攒到几百题，但做 A/B 对比时只用基线集，
  部分索引只索引这部分数据，体积更小、查询更快。

## 十一、已知问题与待决策

### 11.1 中文全文检索（阶段 4 阻塞项）

CLAUDE.md 说阶段 4 的 `KeywordRetriever` 用 **PostgreSQL 全文检索**。
但这里有一个**必须先解决的问题**：

PostgreSQL 内置的全文检索分词器是为英文设计的，**不支持中文分词**。
以下结果是在本项目数据库上**实测**的，不是推测：

```sql
-- 中文：整句被当成一个词，什么都检索不到
SELECT to_tsvector('simple', '这款手机支持七天无理由退货');
--  '这款手机支持七天无理由退货':1        ← 一个 token

-- 英文：正常分词
SELECT to_tsvector('english', 'this phone supports seven day return');
--  'day':5 'phone':2 'return':6 'seven':4 'support':3
```

四个可选方案，**阶段 4 动工前需要决策**：

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A. `pg_jieba` | Jieba 中文分词扩展 | 分词准确，可选词库 | **当前镜像不含**，要自建 Docker 镜像编译 |
| B. `zhparser` | SCWS 中文分词扩展 | 成熟，可配词典 | **当前镜像不含**，同上且配置较复杂 |
| C. `pg_trgm` | 字符三元组模糊匹配 | **当前镜像已自带**（1.6），零额外成本 | 不是真正分词，长文本召回精度略低 |
| D. 应用层分词 | Java 侧 HanLP / IK 分词后存 `tsvector` | 分词器完全可控 | 索引维护复杂，词表变更要重建索引 |

**已实测的镜像扩展可用性**（`pg_available_extensions`）：

```
pg_trgm : 1.6    可用（未安装，随时可装）
vector  : 0.8.6  已安装
pg_jieba:  不在可用列表中  ← 需要自建镜像
zhparser:  不在可用列表中  ← 需要自建镜像
```

> ## ★ 本节结论已于 2026-09-19 被实测推翻并改写（阶段 4）
>
> 上面「当前倾向 C（`pg_trgm`）」的判断**是错的**。在真实语料上实测后：
>
> | 方案 | 召回 | 排序区分度 | 实测证据（查询「退货要几天」） |
> |---|---|---|---|
> | A/B `pg_jieba` / `zhparser` | — | — | 仍是候选，但换分词器的入口已留好，不急 |
> | **C `pg_trgm`** | ✅ | ❌ **完全并列** | 4 条正确切片全是 `0.3333` |
> | 单字 + `plainto_tsquery` | ❌ 0 行 | — | 被拆成 `退 & 货 & 要 & 几 & 天`，AND 语义必然空 |
> | **★ 最终选择：双字(bigram) + OR + `ts_rank`** | ✅ | ✅ | `0.022244 / 0.021636 / 0.020686` |
>
> **`pg_trgm` 为什么不行**：它只生成 **3 字窗口**，而中文词大多是 2 字。
> 查询产生的 6 个三元组里，首尾补空格得到的 `"  退"` 和 `"几天 "`
> 在长文本中间**永远不可能出现**，所以最多 3 个可能命中。
> 它只能当二元过滤器，**在相关集合内部没有任何排序能力**。
>
> **这一条对 RRF 是致命的**：融合只取**排名**不取**分数**，
> 并列时的顺序等于「按 id 排」，语义上毫无意义 —— 等于把关键词这一路废掉。
>
> 另外实测裸 `to_tsvector('simple', 中文)` 几乎不可用：整句粘成**一个**词元，
> 导致「退货」在全库 43 条相关切片里只能命中 **3** 条（漏检 93%）。
>
> **阶段 4 的实际落地**：
>
> ```sql
> ALTER TABLE kb_chunk ADD COLUMN search_text TEXT;              -- Java 分词器写的词元串
> ALTER TABLE kb_chunk ADD COLUMN search_vector tsvector
>     GENERATED ALWAYS AS (to_tsvector('simple', search_text)) STORED;
> CREATE INDEX idx_kb_chunk_search ON kb_chunk USING GIN (search_vector);
> ```
>
> 完整设计、分词规则（「只在连续同类字符段内部生成词元」）、
> 以及「为什么保留词频而**不**去重」见 `docs/05-检索与智能体设计.md` 第三节，
> 决策记录见 `docs/08` 的 ADR-020 ~ ADR-022。
>
> 阶段 7 仍可做 A/B：换分词器后走
> `POST /api/debug/kb/reindex?force=true` 全量重建索引即可。

### 11.2 `updated_at` 由谁维护

两种做法：
- **应用层维护**：MyBatis-Plus 的 `@TableField(fill = FieldFill.INSERT_UPDATE)` 自动填充
- **数据库触发器**：`CREATE TRIGGER` 在 `UPDATE` 时自动改

**当前倾向**：应用层维护。理由是本项目所有写操作都走应用，
不存在绕过应用直接改库的场景，而触发器会让"数据为什么变了"更难排查。

### 11.3 分区表

`qa_log` 和 `chat_message` 是增长最快的两张表。
PostgreSQL 支持按时间范围分区（如按月分区）。

**当前决策：暂不分区。** 本项目数据量在万级，分区带来的收益为零，
反而增加维护复杂度。**但如果面试官问"数据量涨到千万级怎么办"，
这就是你的答案**——说明你知道有这条路，也知道现在不该用。

## 十二、设计权衡速查（面试用）

面试官问"你怎么设计表"，快速过一遍这些点：

| 设计点 | 一句话回答 |
|---|---|
| 主键 | BIGSERIAL 自增。单机项目不需要分布式 ID，自增 ID 调试时可读、索引局部性好 |
| 金额 | NUMERIC(12,2)，绝不用浮点数。浮点数算钱会出精度误差 |
| 时间 | TIMESTAMPTZ 带时区。TIMESTAMP 跨时区会错 |
| 订单明细冗余商品名 | 快照冗余。商品改名调价后，历史订单必须显示下单当时的信息 |
| 规格用 JSONB | 不同类目规格维度不同（手机看存储、衣服看尺码），拆成固定列会大量为空 |
| 库存拆可售/锁定 | 避免超卖。下单锁库存，付款才真扣 |
| 向量用余弦距离 | 文本向量关心方向不关心长度，语义相同但长短不同的句子应判定相似 |
| 向量索引用 HNSW | 增量插入友好 + 召回率高，适合"持续入库 + 频繁查询" |
| kb_chunk 冗余 doc_type | 避免向量检索时 join 回表导致索引失效，用空间换检索性能 |
| 评测表用数组类型 | expected_chunk_ids 只是一组 ID，不需要额外属性，数组比关联表直观 |
| qa_log 记中间结果 | 没有 retrieval_detail 就无法归因"召回失败是哪个环节的问题" |
| 延迟拆四段 | 只记 total 的话，P95 变慢了只能猜，拆开才知道慢在哪 |
| qa_log 只增不删 | 它是评测的数据来源，删了证据链就断了 |
| 日志表不做软删除 | 软删除是为业务表的"删除但保留"设计的，日志表本来就不删 |
