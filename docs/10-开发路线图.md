## 阶段 3 · RAG 核心 — 文档入库（第 3 周）

- [x] 3.1 `scripts/generate_corpus.py` 生成仿真文档（PDF / Word / MD / Excel）
      → 6 份语料：售后政策汇编（docx + pdf）、商品说明书（pdf）、
        商品导购指南（md）、促销活动规则（md）、售后FAQ（xlsx）
      → ★ 四种格式**刻意都生成**，因为 Tika 对它们的标题提取路径完全不同
        （见 3.2）。只生成一种的话另外三条路径永远得不到验证
      → 输出到 `data/corpus/`（**进 git**，60KB，让仓库克隆下来就能直接跑）
- [x] 3.2 Apache Tika 多格式解析
      → Tika **3.3.2**（不是最新的 4.0.0，理由见 ADR-012）
      → ★ **实测发现四种格式的标题形态完全不同**：
        · `.docx` 正文里直接有 `<h1>` `<h2>` `<h3>`
        · `.pdf` **正文里一个 h 标签都没有**，标题被抽成 `<body>` 末尾
          一个嵌套 `<ul>`（文档大纲），和正文完全分离
        · `.md` **Tika 根本没有 Markdown 解析器**（翻遍所有 tika jar 确认），
          实际由 `TextAndCSVParser` 兜底 —— 整个文件塞进一个 `<p>`，# 号原样保留
        · `.xlsx` sheet 名变成 `<h1>`，数据在 `<table>` 里
      → 对应三条提取策略。PDF 那条用「大纲建映射表 + 回正文按行精确匹配」
      → ★★ **踩到的坑**：Tika 生成的 PDF 大纲 HTML 不是良构的，
        同样的层级会输出成**两种嵌套形态**（嵌套 `<ul>` 在 `<li>` 里 vs 是兄弟）。
        第一版只处理了一种，导致**一份 PDF 正常、另一份标题层级整个丢失**，
        而且不报错。现在两种都处理，并有专门的回归测试钉死
      → ★ **第二个坑**：`tika-parsers-standard-package` 里 `tika-core` 是
        `<scope>provided</scope>`，而 provided **不具有传递性** ——
        编译直接报「程序包 org.apache.tika.parser 不存在」。必须显式再引一次
- [x] 3.3 文本切分（标题层级 + 定长 + 重叠窗口）
      → `HeadingAwareChunker`：按标题切段 → 段内滑动窗口 → 优先断在标点后
      → **标题路径会拼进切片正文**（「退货」二字可能只在标题里有）
      → ★ **实测发现的问题**：20 行 FAQ 表被合并成 2 个切片，每片混了
        十几条互不相关的问答 —— 向量变成十几个主题的「平均值」，检索精度被稀释。
        修法是给 `TextBlock` 加 `standalone` 标记，表格行各自成片。
        实测 FAQ 从 **2 片变成 21 片**（见 ADR-015）
      → 参数校验里挡掉一个会**死循环**的组合（`overlapChars >= maxChars` 时
        滑动窗口步进为 0）—— 在构造期拦住比在死循环里 debug 便宜一万倍
- [x] 3.4 批量向量化 + 写入 `kb_chunk`
      → 复用阶段 2 的 `EmbeddingClient`（客户端内部已按 32 分批）
      → **入库异步化**：上传接口立刻返回，`ingestExecutor` 后台跑，
        前端轮询 `kb_document.status`
      → ★ **不在事务里做整条流水线**：向量化要几分钟，
        事务开着会独占数据库连接（池子只有 10 条），改用**补偿删除**（见 ADR-014）
      → ★ **向量列从 `String` 改成 `float[]` + 自定义 `VectorTypeHandler`**：
        用 String 时编译器拦不住维度错误。`autoResultMap = true` 不能漏 ——
        漏了的话写入正常、查询也正常，就是查出来永远是 null（见 ADR-016）

**验收标准（2026-09-18 全部实测通过 ✅）**

1. ✅ **上传一份 PDF，数据库里能查到切片和向量**
   —— 实测走完整流程：上传返回 `status=待处理, finished=false`，
      轮询到 `已入库, chunks=3`
   —— 全库 1649 个切片，**有向量的 1649 个，缺向量的 0 个**
   —— 去重实测：同一份 PDF 再传一次，直接复用已有文档，
      **不重复花向量化的钱**

2. ✅ **向量维度确实是 1024**
   —— `SELECT COUNT(DISTINCT vector_dims(embedding))` = **1 种维度**，值是 1024
   —— 更强的证据：**数据库在强制执行这个约束** ——
      写一个 512 维的向量会被拒绝，报错 `expected 1024 dimensions`

3. ✅ **同一个问题检索两次，结果稳定一致**
   —— 同一问题检索 5 次，**命中的 chunk_id 序列逐位相同**：
      `[15, 158, 105, 55, 72]` × 5
   —— ⚠️ **但分值不是逐位相同的**：实测最大漂移 **3.767e-04**。
      直接原因是**向量化接口本身不是确定的** —— 同一个问题连续调 6 次，
      出现了 2 种不同结果。这是 GPU 并行计算里浮点归约顺序不同导致的固有性质，
      **不是 bug**
   —— 所以判定「稳定」只看 ID 序列（用户能感知的东西）。
      **这条判据最初写错了**（用 `equals` 比 double），于是永远报「不稳定」——
      判据写错比没有判据更糟，它会让人去查一个根本不存在的问题（见 ADR-018）
   —— 附带验证：`ORDER BY ..., id` 的兜底键**没有牺牲索引效率**，
      `EXPLAIN` 显示走 `Incremental Sort` → `Index Scan using idx_kb_chunk_embedding`

  `TikaDocumentParserTest` 34、`HeadingAwareChunkerTest` 29、
  `PdfOutlineTest` 7、`CorpusPipelineTest` 4，以及 `EntityMappingTest` 新增 2 条）
- ★ **修复的真 bug 清单**（每一个都是「不报错、只是结果变差」的类型）：
  1. **小于 8KB 的文件全部解析失败** —— 空文件探测时套的 `BufferedInputStream`

  2. **PDF 大纲两种嵌套形状只处理了一种** —— 导致一份 PDF 的标题层级整个丢失

     声称零分配实际有分配、声称 `finished` 会序列化实际不会）——

### ★ 动工前推翻了 docs/04 §11.1 的结论

那节原本倾向 `pg_trgm`（理由是零成本）。在真实语料上实测后**站不住**：

```
查询「退货要几天」，全库 1652 条切片：
  pg_trgm word_similarity ：4 条正确切片全部并列 0.3333   ← 没有排序能力
  单字 + plainto_tsquery  ：0 行                          ← AND 语义，中文必然空
  双字 + OR + ts_rank     ：0.022244 / 0.021636 / 0.020686 ← 有区分度 ✓
```

`pg_trgm` 只生成 3 字窗口，而中文词大多是 2 字 —— 查询产生的 6 个三元组里，
首尾补空格得到的 `"  退"` / `"几天 "` 在长文本中间**永远不可能出现**。
它只能当二元过滤器，**在相关集合内没有排序能力**，而 RRF 只看排名不取分数，
并列时等于「按 id 排」→ 关键词这一路等于废掉。

### ★ 三个靠实测抓出来的设计错误

| # | 错误 | 症状 | 修正 |
|---|---|---|---|
| 1 | 「丢弃含空格的 bigram」 | 拦不住 `5000mAh`（切成 `50 00 0m ma ah`，都不含空格） | 改成「只在连续同类字符段内部生成词元」 |
| 2 | 保留单字词元 | 「元」出现在 **12%** 的切片里（行尾的「5999 元」），零区分度纯噪音 | 单字一律丢弃，裸单字从 946 条降到 **0** |
| 3 | ★ **词元去重** | 43 条命中切片拿到**同一个分数** —— `ts_rank` 对 OR 查询取「单词元得分最大值」，而得分只取决于词频 | 去掉去重，恢复成 8 种分值 |

> 第 3 条如果没被实测抓到，系统会「能跑、不报错、结果看起来也合理」，
> 但关键词这一路在 RRF 里完全失效。**这正是基线指标存在的意义。**

### ★ 一个被证伪的负面发现（当天修订）

第一次跑基线（20 题）时得到两个「发现」：

| 配置 | HitRate@1 | HitRate@5 | MRR@5 |
|---|---|---|---|
| 纯向量 | 75.0% | 100.0% | 0.8750 |
| 纯关键词 | 75.0% | 95.0% | 0.8292 |
| 双路 + RRF | **80.0%** | 100.0% | **0.9000** |
| + 重排 | **80.0%** | 100.0% | 0.8833 |

读作「RRF 有增益」「重排拖后腿（0.900 → 0.883）」。

**两个结论都是错的。** 起因是逐题打开看那 4 道「被重排弄坏」的题时，
发现其中 3 道的**正解标错了** —— 语料里同一批业务规则被多个文档覆盖
（优惠券有 4 份文档在讲、价保有 3 份），而题是反向构造的，只标了其中一个。
重排选了另一个同样正确的答案，被记成变差。

修法是**补全 gold 为多答案**。受控对比（同一批检索结果、两套 gold 定义）
显示**两个符号同时翻转**：

| 对比 | 旧 gold | 新 gold |
|---|---|---|
| 重排 vs 融合 | −0.0167 | **+0.0250** |
| 融合 vs 纯向量 | +0.0250 | **−0.0250** |

修订后的基线：

| 配置 | HitRate@1 | HitRate@5 | Recall@5 | MRR@5 |
|---|---|---|---|---|
| 纯向量 | 95.0% | 100.0% | 98.3% | **0.9750** |
| 纯关键词 | 85.0% | 95.0% | 93.3% | 0.8917 |
| 双路 + RRF | 90.0% | 100.0% | 98.3% | 0.9500 |
| + 重排 | 95.0% | 100.0% | 98.3% | **0.9750** |

> ⚠️ 新数字同样**不能当结论**：差异量级 0.025 = `0.5/20`，
> 就是一道题从第 1 名掉到第 2 名。**n=20 上任何「X 比 Y 好」都不可信。**
>
> 唯一稳的是**按查询形态切片的互补结构**：词典型题上纯向量已经封顶（1.0000），
> 口语句上只有带重排的完整链路是满分（1.0000）。
> 详见 `docs/06` §3。

还配了机制解释 —— 但两个发现都是假象。

### ★ 动工前实测出来的两件事

**① 「4.1% 的切片回答 55% 的问题」** —— 语料的切片分布和问题分布严重倒挂：

```
切片   doc_type=1 商品详情  1555 / 1643 = 94.6%
       doc_type=2/4 售后      67 / 1643 =  4.1%
问题   售后 11/20 = 55%   促销 5/20 = 25%   商品·购买 4/20 = 20%
```

这条直接决定了 5.4 的策略：**只对窄类型过滤**。
映射到 `{2,4}` 能把候选池从 1643 砍到 67（24 倍），映射到 `{1}` 只砍 5.4%。
过滤的收益与风险都由「候选池收窄倍数」决定 —— 池子大时过滤本来也没用，
所以「收益大的地方才过滤」和「风险大的地方别过滤」是同一个判断。

**② 一半的题，答案横跨多个 `doc_type`**（10/20）：
`B-011` 跨 `{2,3,4}`，`B-010` / `B-012` 跨 `{3,4}`，8 道售后题跨 `{2,4}`。
成因是语料本身 —— 同一条规则被写在三份文档里，而 `doc_type=4`（售后FAQ）

#### ★★ 一个推翻了自己注释的实测

```
「退货要几天」跑 8 次（全部走 deepseek-flash，modelKey 全程一致）：
  RETURN_EXCHANGE ×7
  REFUND          ×1      ← 翻转了

`application.yml` 和 `AgentProperties` 里原先写的「分类是确定性任务，
温度调高会测不准」**是错的**，两处都已按实测改正。

> 「同一问题采样 N 次的一致度」才可以当置信度用 —— 那是 5.3 的候选信号。

#### ★★ 动工前推翻了这一项的前提

路线图写的是「**置信度计算** + 澄清反问」。三种候选信号全测了一遍，
**全都不成立**，而且采样一致度是**反相关**的：

```
logprobs     所有问题首 token 都是 -0.000  → 零区分度
             ★ 连那个 8 次里翻过 1 次的问题都报 -0.000、领先次候选 10.1

采样一致度   「那个怎么样」  8/8 = 1.00   ← 最该澄清的
           「退货要几天」  7/8 = 0.88   ← 完全正常的问题
             → 阈值设 0.9 的话，两个方向都反了
```

**根因是两个问题正交**：信号度量的是「分类有多确定」，
而这里要的是「这句话是否包含足够的信息来回答」。

**所以路线图这一项被重新定义为「信息充分性判断 + 澄清反问」**
（见上面那条勾选）。详见 `docs/05` §9.3 与 ADR-039。

#### ★ 顺带发现的一件事：`role` 从布尔量升级成枚举

没有「信息不足」这个选项时，分类器对「那个怎么样」给出的是一个
**自信的 `OUT_OF_SCOPE`** → 用户收到「我只处理商品导购与售后问题」，
而那句话明明就是在问商品。

加了 `role: CLARIFY` 之后，`out_of_scope: true` 这个布尔量也顺势
升级成 `role` 枚举（三者互斥）。16 个分类目标。

#### ★ 又一个「两种东西共用一个值」的坑

`qa_log.status` 原来是 `1成功 2失败`。**澄清两种都不是** ——
它没生成答案，但也没失败（那恰恰是系统正确工作的表现）。
硬塞进任何一个都会污染阶段 7 的统计。V7 加了 `status=3`。

> 这已经是**第三次**了：阶段 4 的检索异常差点被记成「模型挂了」→
> 5.2 的分类失败要分三种原因 → 这次是澄清。

### 一处只有真启动应用才会暴露的坑

`IntentTree` 有**两个构造函数**（Spring 用的 `AgentProperties` 版 + 测试用的 `Path` 版）。
Spring 的构造器注入规则是：只有一个构造函数时可以省略注解，
**有两个及以上时必须显式标出用哪一个**，否则它会退回去找无参构造函数，
然后报 `No default constructor found`。

26 个单测全绿也照样会踩 —— 因为单测直接 `new IntentTree(path)`，压根不走 Spring 的装配路径。
**单元测试通过不等于应用能起来**，涉及 Spring 装配的改动必须真启动一次。
教训已写进 `IntentTree` 的构造函数注释。

#### ★★ 动工前的实测又和路线图的假设不一样

**（a）加了 `doc_type` 条件后，PostgreSQL 反而弃用 HNSW，改成精确扫描。**
连 `enable_seqscan=off` 都逼不动它用近似索引。
pgvector 那个「过滤时近邻数不够」的著名坑**当前规模轮不到** ——
但表一大规划器会翻回去，那时需要 `hnsw.iterative_scan`。
`DocTypeFilterIntegrationTest.filteredVectorSearchIsExact` 就是钉这件事的。

**（b）收窄倍数从 1.1× 到 328× 都有，而且「倍数越大越危险」。**
`[5]`（说明书）的 328× 意味着池子只有 5 条、比 `topK=20` 还小 ——
取出来的恒等于全池，**「按相关度截断」这个动作消失了**。

所以判据用**池子绝对大小**（`poolSize >= vector-top-k`），不用倍数。
**判据的方向和风险的方向正好相反**，这是「收窄倍数」这个指标本身的缺陷。

#### ★ 5.1 那条验收标准在这里兑现了

`gold doc_types ⊆ declared`（20/20）在 5.1 写出来时，
看起来只是一句「树画得对不对」的自检。到 5.4 它变成了
**硬过滤的安全证明**：正解必然通过过滤，而干扰项变少 ——
**过滤只可能让召回更好或持平**。

> 一个设计决策能在几天后白拿一条证明，那是好决策。
> 反过来：如果当初把 `doc_types` 定义成「5.4 要过滤成哪个类型」，
> 就**没有任何可自动验证的东西**。

#### 又一个「Java 侧完全看不出来」的坑

```sql
AND (#{docTypes} IS NULL OR doc_type = ANY(CAST(#{docTypes} AS int[])))
-- ERROR: could not determine data type of parameter $2
```

`$2 IS NULL` 里没有任何东西能告诉 PostgreSQL 这个参数是什么类型，
而 JDBC URL 上的 `stringtype=unspecified` 让驱动把字符串按「未知类型」发出去 ——
于是「推断不出来」成了**报错**。修法是给那一半也套一层 `CAST`，
**语义完全等价，那层 CAST 唯一的用途是给 PG 一个类型线索**。

#### ★ 两个只有写代码才会撞到的坑

**（a）读历史必须在「落用户消息」之前。** 反过来的话历史里会有一份本轮的提问，
而它马上又作为 `userQuestion` 再发一次 —— **模型收到两条一样的用户消息**。
而日志和落库数据**两边各自都是对的**，错的是相对顺序。
护栏只能建在「形状」上（断言 history 不含本轮提问、且以助手回复结尾）。

**（b）孤儿用户消息必须丢弃。** 上一轮在落用户消息之后、落助手回复之前挂了，
库里就留一条落单的用户消息 → `messages` 数组里**连续两条 user 消息是畸形输入**
→ 400，而 400 在降级链里属于「**不降级**」那一类，**整次问答直接失败**。
⚠️ 还有个容易漏的半轮：取数要**多取一条**，否则丢完孤儿窗口变成 9.5 轮，
少的那半轮是**最早**的那条。

### 5.6 会话记忆：LLM 摘要压缩 + 持久化（2026-09-19 完成）

> 滑动窗口只保留最近 10 轮，**更早的会被静默丢掉** ——
> 而第 1 轮那句「预算两千左右」恰恰是信息密度最高的一条。
> 5.6 把掉出窗口的原文压成摘要接着用，`chat_summary` 终于不再是 0 行。

#### ★★ 验收标准 3 这次是**真的**满足了，而且因果链可以直接看出来

上一次（5.5）只满足了一半：窗口正好是 10 轮，所以「10 轮之后还记得」靠的是**窗口本身**，
不是记忆层。5.6 之后窗口外的内容才第一次有了去处。**20 轮、默认 `max-turns=10`**：

```
sessionNo = 2698ae71…
  chat_summary  覆盖 msg 3365 → 3381，885 字   ← 「两千左右」在这里
  窗口原文      覆盖 msg 3385 → 3404           ← 只有第 11-20 轮
  接缝          windowStartId=3385, coveredEnd=3381
```

「两千左右」**在摘要里、不在窗口里**。窗口从第 11 轮开始，
模型不可能从原文里拿到它 —— **只能是摘要带过去的**，而实际回答里出现了。

先跑的是 `max-turns=4` 的**机制验证**（便宜，10 轮就能溢出）：
3 次压缩把游标从 3326 推到 3332，接缝收敛到 `tight: true`。

**验收入口**

```bash
# ① 机制验证（便宜）：临时把窗口调小，10 轮就能触发压缩
SPRING_APPLICATION_JSON='{"xbla":{"chat":{"history":{"max-turns":4}}}}' ./mvnw spring-boot:run
python scripts/probe_memory.py --rounds 10

# ② 真实验收：20 轮（第 1 轮埋的预算必须能从摘要里被捞回来）
./mvnw spring-boot:run
python scripts/probe_memory.py --rounds 20

# ③ ★ 看接缝：摘要覆盖到哪、窗口从哪开始、中间有没有人都不管的消息
curl -s "localhost:8080/api/debug/agent/memory?sessionNo=<上一步打出来的>" | python -m json.tool
```

#### ★★ 实测挖出来的三个真问题

**（a）摘要会一路涨，比字数上限快得多。** `209 → 435 → 740 → 1129 字`（目标 800）。
成因是提示词里两条要求**互相打架**（保事实 vs 不超字数），
而模型的默认行为是**追加**，上限被它当成了建议。
修法是给出**可执行的丢弃顺序**，支点是那条洞察：
**助手的回答「下次检索还能再查到」，用户的预算/用途/型号「再检索一次也查不到」**。
→ 同样规模 1129 → **885 字**，第一句就是「用户要给爸妈买手机，预算两千左右」。

⚠️ **没有完全解决**：稳定态是 **900–1100 字的振荡**（硬上限 1600）。
又加了一层「超预算时切强制压缩模式」，实测只做到 1066 → 936。
已知遗留，见 `docs/05` §9.6 ⑤。

**（b）压缩的延迟可以非常长：实测最慢 41.5 秒。** 日志显示那一次**降级到了 P1**
（`deepseek-flash` 失败）。★ **这一条直接验证了「异步」的决定** ——
同步的话一次普通问答会从 2 秒变成 43 秒。也正是它说明
`memoryExecutor` 单线程 + 大队列的必要性。

**（c）★ 顺手修掉一个会让会话【永久死掉】的 5.5 bug。**
`chat_message` 失败路径**故意不写助手消息**（写「服务异常」会污染评测语料），
所以每轮失败都留一条孤儿。而 5.5 只丢**最新那一条**：

```
第 N 轮、第 N+1 轮连续失败 → 丢掉 O_{N+1}，但 O_N 还在且现在是末尾
  → history 以 user 结尾 + 本轮问题 = 连续两条 user
  → 400 → 不降级 → 这一轮也失败 → 又留一条孤儿 → 每一轮都重演
```

**两次连续失败之后这个会话就再也答不出话了**，而单次失败完全看不出来。
修法：丢掉末尾**所有**连续的 user 消息。

#### ★ 新增的探针

`GET /api/debug/agent/memory?sessionNo=…` —— ★ **不调模型，不花钱**。
它把「接缝」直接摊开：摘要游标、窗口起点、`pending`、`overlap`、以及**一句话的 verdict**。

为什么要它：`SELECT * FROM chat_summary` 看到的三个值**单看是看不出对错的**，
判据是接缝 —— 得**同时**拿到摘要的游标和窗口的起点。同 `/intent-tree` 之于 5.1。

### 5.7 MCP Server 手写（2026-09-19 完成）

> 把「我的订单到哪了」这类**实时数据**问题从知识库里接出来 ——
> 知识库答不了「你那笔订单现在在哪」，那是动态数据。

**边界**：协议骨架 + 工具注册机制 + **一个真工具端到端**。~~剩下三个在 5.9~~
⚠️ **修正（5.9 完成时回填）**：5.9 实际只加了**两个** MCP 工具
（库存、优惠券）—— 第四个（售后政策）**没做成工具**，因为
`AFTER_SALE` 是 `retrieval: KB`，模型在那个意图下拿不到任何工具。
它改走结构化注入，见 ADR-067。**这句话当时写错了，留着不改。**
为什么先只做一个：**只有真工具才能暴露** schema、参数提取、空结果、越权这些真问题。

#### ★★ 验收标准 1 有了第一个可跑的落点

```bash
python scripts/probe_mcp.py     # ★ 不调模型，不花钱。12/12 通过
```

```
身份 17 查自己的 SO202607200008 → 已取消 / 京东物流 SF000000103502 / 惠普 战 66 Pro ×3
身份 18 拿同一个订单号来查       → 「没有找到订单号 … 也可能是这笔订单不属于当前账号」
身份 18 拿一个不存在的单号来查   → 「没有找到订单号 … 也可能是这笔订单不属于当前账号」  ← 逐字相同
```

**后两句必须逐字相同** —— 否则就是个**枚举预言机**：
换个订单号看回复是哪一个，就能逐个确认哪些订单号真实存在，哪怕拿不到内容。

#### ★★ 三个最重要的决策

**① 身份不进工具参数（防 IDOR）。** 「我的订单」里的「我」如果是个工具参数，
那就是**模型可控的越权入口** —— 一段提示注入就够了，而代码看起来全对。
身份从 `X-Xbla-User-Id` 头来，进 `McpToolContext`，参数里没有它。

⚠️ **这不是认证** —— 那个头是明文未签名的。做到的是「身份不进模型的可控范围」
这一半，而那一半恰恰是 MCP 场景**新增**的风险。另一半（验证身份是真的）
需要 OAuth，是另一项工作。**边界写在 `docs/05` §9.7 ②，不含糊过去。**

**② 协议版本跟【SDK】对齐，不跟规范仓库对齐。** 规范仓库里已经有 `2026-07-28`，
但官方 Java SDK 2.0.1 反编译出来的 `ProtocolVersions` **只到 `2025-11-25`**。
声明一个 SDK 不认识的版本，唯一效果是每次握手都协商降级。

**③ `ToolField` 让 schema 和实现不可能漂移。**
名字只写一次（一个常量），生成 schema 和取值都走它。两处各写一份的漂移是静默的 ——
5.6 的接缝锚点刚踩过一次。

#### ★ 一个意外发现（探针第一版没测到它想测的东西）

`probe_mcp.py` 最初复用会话但换了身份头，拿到 **403** 而不是预期的「没找到订单」——
被**会话 ↔ 身份绑定**这一层挡在了更前面。

**那是个正确的防护**，但它测的是「会话不能被顶替」，不是「工具会不会
把别人的订单交出去」。要验后者，陌生人必须**自己握一次手**。
两层职责不同，都要有 —— 见 `McpControllerGuardTest.Session`。

#### ★ 另一个真踩到的坑：`Map.copyOf` 拒绝 null

`McpToolResult` 的防御性拷贝第一版写的 `Map.copyOf(data)`，
而「key 在、值是 null」恰恰是 JSON Schema 里**可选字段**的合法形态
（未发货的订单没有物流单号）。NPE 还抛在**构造函数**里 ——
现象是「工具查到数据了但包装失败」，栈顶指向不相关的地方。

#### ★★ 5.8 挖出的三类坑（都值得单独记）

**① 486 个测试全绿，真实调用当场 400 —— 而且犯了两次**

而领域对象是平的。两个方向各错一次，各被不同的盲区漏掉：

- **收**：测试都 `new ToolCall(...)` 直接构造，**从没反序列化过**
  → `name` 静默变 null → SDK 抛 `name must not be empty` → 整次问答 status=2
- **发**：断言都下在领域对象上，**从没序列化过**
  → `HTTP 422 messages[1]: missing field type`

> **教训：DTO 的形状，只有真的序列化/反序列化过一次才算验证过。**
> 桩造出来的对象，验证不了「桩自己是不是照协议造的」。
>
> ⚠️ 手写 JSON 也不行 —— 写 JSON 的人和写 record 的人是同一个，
> 盲区是同一个。所以 `WireToolCallTest` 里的报文是**从真实响应逐字抄的**。

**② `Map.copyOf` 第二次踩，这次是「打乱顺序」**

5.7 的 `McpToolRegistry` 注释写着「保证顺序稳定」，实际用的是 `Map.copyOf`
—— 而 JDK 9+ 的 `ImmutableCollections` 有一个**每次 JVM 启动随机**的 SALT。
实测三个 JVM 三种顺序。**5.7 只有一个工具所以怎么测都测不出来。**

代价是 `tools` 数组（Prompt 前缀）每次重启都变 → 缓存命中价差 50 倍。

**③ 「空正文」在工具场景下是成功**

阶段 2 的探测器（抓推理模型吃光 max-tokens）会**每一次工具调用都误判**。
实测连续 5 次让 `deepseek-flash`「直接调工具不要说话」，5 次 `content` 全是空串。

### ★★★ 顺带抓到的一个真机 bug（6.9）

**三段新指标（都是一张 2×2，不是一个「准确率」）**

| 段 | 判据 | 数据源 |
|---|---|---|
| `检索决策` | 声明不检索×实际没检索/检索了；声明要检索×检索了/没检索 | `expect_no_retrieval` × **`retrieval_detail` 非空** |

**★★★ 四条「判据本身会错」的防线**（每一条都对应一个曾经会错的地方）

1. **判据用「实际发生」，不用「门控说了什么」** —— 取 `retrieval_detail` 而不是
   `intent_plan.retrieve`。后者是门控自己的输出，拿它当判据会漏掉
   「**算对了但调用点忘了用**」那类只改一半的实现。
   配套判据 `★算对了但没用的行`（两者不一致）**应恒 0**。
2. **被限流拒掉的行不算一次决策**（`status=4`）—— 那条路上检索压根没跑。
   算进去会让过度检索率**归零**，一个看起来像好消息的 0，而它百分之百是容量造成的。
3. **「调了」不等于「用上了」** —— 白名单拒绝**也会留调用记录**（`isError=true`）。
   所以「越权的调用」非 0 不是数据泄露，而 `★★越权且成功的调用` **应恒 0**
   ——★ 那是 ADR-093 那条不变式**在数据上的形状**，可观测，不是一句承诺。
4. **多轮题的判据不能派生** —— 多轮题的 `intent` 指**末轮**，拿它给首轮下结论
   必然得出「每一道都不该反问」。⇒ 新增 `expect_clarify`（V17，**三态**），
   没标的判**不可判**并排除出分子分母，**不猜**。

**★★ 测量结果：瓶颈在「该不该反问」，不在「恢复」**

### 坑 1 · Docker Desktop 引擎起不来，所有命令返回 500

**现象**

```
docker info
request returned 500 Internal Server Error for API route and version
http://%2F%2F.%2Fpipe%2FdockerDesktopLinuxEngine/v1.56/info
```

Docker Desktop 进程在跑，但引擎不可用，`docker desktop status` 永远停在 `starting`。

**排查过程**

1. 看 `com.docker.backend.exe.log`，发现
   `"supportsVirtualization": false` + `virtualization-not-detected-screen`
2. 查 Windows 可选功能，`Microsoft-Windows-Subsystem-Linux` 和
   `VirtualMachinePlatform` 都是 **Disabled** → 启用它们（管理员 + 重启）
3. 重启后 `wsl --status` 提示「未找到 WSL 2 内核文件」→ 装内核
   （⚠️ `aka.ms/wsl2kernel` 现在跳转到文档页，真实地址是 Azure Blob：
   `https://wslstorestorage.blob.core.windows.net/wslblob/wsl_update_x64.msi`）
4. 内核装好后 Docker **仍然起不来**。日志里真正的报错是：

   ```
   [com.docker.backend.exe.wslexec][E] c:\windows\system32\wsl.exe --version
     failed: exit status 0xffffffff
   ```

**根因**：Docker Desktop 4.91 需要**商店版 WSL 应用**（WSL 2.x）来探测版本，
而系统内置的是老版 `wsl.exe`，**不支持 `--version` 参数**（执行它只会回显帮助文本）。
Docker 据此判定 WSL 不可用，拒绝启动虚拟机。

**决定性的一步**：装商店版 WSL 时，**下载能完成、安装却永远卡在「正在安装」**。
原因是商店安装除了下载，还要向 `licensing.mp.microsoft.com` 申请许可证，
而这个域名被墙了 → 永远卡住。

**解决**：打开代理（Clash Verge），系统代理置为 `127.0.0.1:7897` 之后，
商店安装立刻从「卡死」变成正常下载安装。

> **教训**：这个项目后续会大量依赖境外服务——Docker Hub 拉镜像、

### 坑 3 · `mvnw` 的换行符

**现象**：Windows 上 `git add` 时警告 `LF will be replaced by CRLF`。

**隐患**：`mvnw` 是 shell 脚本，一旦被写成 CRLF 换行，在 Linux / Docker 里执行会报

### 坑 4 · pgAdmin 容器无限重启

**现象**：`docker compose ps` 里 pgadmin 显示 `Restarting (1)`，反复崩。

**日志**：

```
'admin@xbla.local' does not appear to be a valid email address.
Please reset the PGADMIN_DEFAULT_EMAIL environment variable and try again.
Validation output: The part after the @-sign is a special-use or reserved name
```

**根因**：`.local` 是 RFC 6762 保留给 mDNS 的专用域名，pgAdmin 9.x 的邮箱校验
直接判定它非法。注意不是「密码错了」或「配置读取失败」——**是邮箱格式校验**。

**解决**：改用 `admin@xbla.com` 之类的正常域名。

> **教训**：容器不断重启时，第一件事永远是 `docker compose logs <服务名>`。
> 这个报错信息其实写得很清楚，不看日志会误以为是挂载或权限问题。

### 坑 5 · pom.xml 里的 XML 注释不能出现 `--`

**现象**：

```
Non-parseable POM: in comment after two dashes (--) next character must be > not -
```

**根因**：XML 规范规定注释内容里不能有连续两个短横线（因为 `-->` 是结束标记，
`--` 会造成歧义）。用它画分隔线 `<!-- ---- 标题 ---- -->` 就会直接报错。

同理，`.gitattributes`、HTML、XML 配置里都要注意这点。
（顺带一提：Markdown 和 YAML 没这个限制，所以 docs 里可以随便画。）

### 坑 7 · jsonb / vector 列写入报类型不匹配

**现象**：

```
column "references" is of type jsonb but expression is of type character varying
```

**根因**：pgjdbc 默认把 Java `String` 当 `varchar` 发送。
而 PostgreSQL **不会把 varchar 隐式转换成 jsonb**（也不认识 pgvector 的 vector 类型），
于是直接报错。

**解决**：JDBC URL 加 `stringtype=unspecified`：

```
jdbc:postgresql://localhost:5432/xbla_rag?stringtype=unspecified
```

加上之后驱动把字符串以「未指定类型」发送，由 PostgreSQL 按目标列类型自行推断。

> **这条对阶段 3 很关键**：`kb_chunk.embedding` 是 `vector(1024)` 类型，
> 也是靠这个参数才能用字符串形式写入。现在配好了，到时候不用再踩一次。

### 坑 8 · `Long[]` 数组类型没有默认 TypeHandler

**现象**：

```
Type handler was null on parameter mapping for property 'expectedChunkIds'.
It was either not specified and/or could not be found for the
javaType ([Ljava.lang.Long;) : jdbcType (null) combination.
```

**根因**：MyBatis 内置了 `Object[]` 的处理器（`ObjectArrayTypeHandler`），
但**没有 `Long[]` 的**。类型注册表按精确类型查找，`Long[]` 匹配不到 `Object[]`。

**解决**：写一个 `LongArrayTypeHandler`（见
`com.xbla.rag.common.handler.LongArrayTypeHandler`），在字段上标注：

```java
@TableName(value = "eval_question", autoResultMap = true)   // ★ 不能漏
public class EvalQuestion {
    @TableField(typeHandler = LongArrayTypeHandler.class)
    private Long[] expectedChunkIds;
}
```

⚠️ **`autoResultMap = true` 最容易漏**。漏了的话写入正常、读取静默失败
（查出来是 null），属于「一半能跑」的 bug，最难排查。

### 坑 9 · 逻辑删除的「查不到」不等于「删掉了」

**现象**：调 `deleteById()` 之后 `selectById()` 返回 null，看起来删干净了。

**真相**：数据还在表里，只是 `deleted` 变成了 1。
查询时 MyBatis-Plus 自动追加了 `WHERE deleted = 0`，所以查不到。

**验证方法**：用 psql 直接查（绕过 MyBatis-Plus）：

```sql
SELECT id, deleted FROM product WHERE id = ?;   -- 能看到 deleted = 1
```

> **这条的重要性**：阶段 7 做评测时，如果怀疑「数据怎么少了」，
> 先想想是不是被逻辑删除了。**逻辑删除的数据不会真的消失**，
> 这正是不用物理删除的原因——评测要能追溯到历史。

### 坑 10 · Spring Boot 的 profile 是「覆盖」不是「追加」

**现象**：加了 `seed` profile 后启动失败：

```
The server requested SCRAM-based authentication, but no password was provided.
```

**根因**：`spring.profiles.active` 是**覆盖**语义。

```
application.yml 里配的:   active: local
命令行传的:               -Dspring-boot.run.profiles=seed
实际生效的:               seed        ← local 被顶掉了！
```

`local` 不生效 → `application-local.yml` 不加载 → 数据库密码读不到 →
连接被 PostgreSQL 以 SCRAM 认证失败拒绝（报错信息里「no password」就是指这个）。

**解决**：写成两个，用逗号分隔：

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=local,seed
```

> **教训**：报错说「没提供密码」时，第一反应容易去查 application-local.yml
> 是不是写错了。但真正的问题往往是**那个文件根本没被加载**。
> 排查这类问题先看启动日志里的这一行：
> `The following N profile(s) are active: ...`

### 坑 11 · `@Transactional` 回滚数据，但不回滚序列

**现象**：集成测试跑过之后，`product` 表的 id 从 **5** 开始而不是 1，
中间有空洞。

**根因**：`@Transactional` 回滚的是**数据行的变更**，
**不会回滚自增序列的值**。每次插入尝试都会消耗一个序列号，
即使最后事务回滚了，这个号也不会还回去。

所以：
- 测试插入了 4 条商品 → 回滚，数据没了
- 但序列已经走到 5 → 之后正式灌数据从 5 开始

**这是 PostgreSQL 序列的正常行为，不是 bug。**

> **教训**（这条很实用）：**永远不要假设自增 id 从 1 开始、也不要在 SQL 里写死 id**。
> 本阶段验证时我就犯了这个错——写了 `WHERE p.id IN (1, 2)` 查规格对比，
> 结果返回 0 行，一度以为种子数据的外键回填逻辑坏了。
> 正确做法是用 `ORDER BY id LIMIT 2` 动态取。

### 坑 12 · `./mvnw test-compile` 不 `clean` 时会【静默跳过】编译

**现象**：改了 `Retriever` 接口的签名，测试里有 **21 处**调用还是旧签名 ——
而 `./mvnw test-compile` 返回 **`BUILD SUCCESS`**：

```
[INFO] --- compiler:3.14.1:testCompile (default-testCompile) @ xbla-rag ---
[INFO] Nothing to compile - all classes are up to date.
```

**根因**：`maven-compiler-plugin` 的增量判断看的是
**「源文件时间戳 vs 已编译的 .class 时间戳」**。
这次改的是**主代码**（`Retriever.java`），测试源文件一个字节都没动 ——
于是插件认为测试不需要重编译，尽管它依赖的那个接口已经变了。

**危险的地方不是慢，是它报成功**：`target/test-classes/` 里躺着的是
**针对旧接口编译的旧 class**，接着跑 `mvn test` 会拿它们去跑 ——
**测试"通过"了，但跑的是一份早就不存在的代码。**

> **教训**：**改了任何接口/签名之后，跑测试前先 `clean`。**
> ```
> ./mvnw clean test
> ```
> 这不只是本项目的问题，是 Maven 增量编译的固有行为；
> 但本项目里它格外容易咬人 —— 因为「静默地漏跑/跑了旧代码」
> 正是这个项目反复在防的那一类失败
> （同 R13「改 surefire 加 `@Tag` 会静默漏跑」、坑 9「逻辑删除的查不到不等于删掉了」）。

### 坑 13 · ★★★「对账通过」不等于「这一轮能用」

**现象**（2026-09-23，T8 轴 2b）：477 条提交里 **408 条是 HTTP 503**
「智能助手暂时不可用」，只有 **69 条**真的答了 —— 而 `run.raw.json` 里

```
complete    = True
reconcileOk = True      ← ★ 对账说【通过】
```

**根因**：`reconcile()` 的三条判据问的全是「**行有没有丢**」：

```
提交 → 库：拿到的 traceId 在库里找不到吗？      （洞 4 的哨兵）
库 → 提交：有我们不知道来源的幽灵行吗？
半标记   ：有题号但没 runId 的行吗？
```

**没有一条问「行有没有成」。** 那 408 条失败的行**老老实实写了 qa_log、
老老实实标了 runId、编号也一一对上** —— 在对账的眼里它们和成功的行没有区别。

**真正的故障**：`java.nio.channels.UnresolvedAddressException` —— **DNS 解析失败**，
出站调用全连不上 → 连续失败触发三个模型熔断器全跳闸 → 之后每个请求都是 503。

**危险的地方**：`complete=True` + `reconcileOk=True`，报告生成器的前置检查
**会放它进去**，然后拿 69 道题的样本去算「159 题的指标」——
而且分母缩小的同时，**活下来的那些行在时间上和题号顺序上都偏向某一端**
（熔断器是成簇跳闸的，不是随机丢的）。它不是一个无偏的子样本。

> **处置**：`eval_run.py` 加了**第四个哨兵** ——
> `status=2`（模型链路失败）+ `status=4`（被限流拒）的占比超过 **5%** 就整轮作废，
> 并盖章 `tooManyFailed` 进 `run.raw.json`。
> 消费端（`eval_ab.py` / `eval_report.py`）读那个章，旧文件则从
> `reconcile.rowsByStatus` 现算。
>
> ⚠️ `status=3`（澄清反问）**不算失败** —— 它是设计好的行为（CLAUDE.md 那条）。
>
> **教训**：**「完整性」和「可用性」是两个不同的判据，缺一个都会静默。**
> 同坑 9「逻辑删除的查不到不等于删掉了」、坑 12「BUILD SUCCESS 不等于编译了」。

### 坑 14 · `./mvnw clean test` 会清掉**正在运行的应用**读的 `target/classes`

**现象**：跑 T8 的三条轴要重启应用、每轮 20~26 分钟。
中途想改一行 Java，跑 `./mvnw clean test` —— 而 `clean` 会删掉 `target/`。

**为什么危险**：`./mvnw spring-boot:run` 用的是 **`target/classes` 里已编译的类**，
不是源文件。`clean` 把它们删掉的那一刻，正在跑的那一轮**已经加载的类不受影响**
（JVM 已经把字节码读进内存了），但：

- 如果应用此时需要**懒加载**一个新类（第一次走到某条分支），**它找不到**
- 更常见的是：你**以为**新代码生效了，实际跑的还是旧进程里那一份 ——
  判据是「返回里有没有新加的键」，**别信 HTTP 200**（同 T4 那个 TaskStop 的坑）

> **处置**：**跑 A/B 期间不编译。** 顺序固定为
> 「跑完所有轮 → 改 Java → `clean test` → `--refresh` 重生成报告」。
> ★ `--refresh` 那一步不能省：报告是从端点重新拉的，
> 而端点跑的是**改完之后**的代码 —— 不 refresh 的话，五份 report.json
> 是前后两个版本生成的，混在一张对比表里。

### 坑 15 · ★★ 子串匹配当判据，第三次咬人：`spring.application.json` 含 `application`

**现象**（T8）：想验证「环境变量覆盖生效了没有」，写了

```python
over = {k: v for k, v in origin.items() if 'application' not in v}   # ★ 错的
```

结果 `{'xbla.rag.rerank.enabled': 'false'}` 这个**明明已经生效**的覆盖
被判成「**覆盖没生效，别往下跑**」。

**根因**：Spring 给环境变量覆盖标的来源是 **`spring.application.json`** ——
它**包含子串 `application`**，被自己的过滤器滤掉了。

**这是同一个形状的第三次**：

| 第几次 | 误伤 | 被误伤的那个 |
|---|---|---|
| 1 | 脱敏规则用子串匹配 | `keyword-weight` / `keyword-top-k` 含 `key` → 被抹成 `***`，而它们正是要 A/B 的旋钮 |
| 2 | `Map.of` / `Map.copyOf` 拒 null | JSON Schema 的合法可选字段就是 null |
| 3 | 「非 yml 来源」用子串过滤 | `spring.application.json` 含 `application` |

> **处置**：判据改**正面**写 ——
> yml 来源一律长成 `Config resource ...`，**以它开头**的才是文件来源。
> 反过来写（「不含某某」）会把你要找的东西自己排除掉。

### 坑 16 · 只读的诊断命令**不许有副作用**：`--coverage` 曾经覆盖交付物

### 坑 17 · 标志组合会**静默短路**：`--refresh --selftest` 只跑了自检

**现象**：恢复 T8 时按清单跑 `python scripts/eval_report.py --refresh --selftest`。
它只印了 `selftest: 28 项通过`，**`--refresh` 一个字节都没做** ——
五个旧的 `report.json`（两个代码版本生成的）原样躺在磁盘上。

**机制**：`main()` 的第一句是

```python
if args.selftest:
    return selftest()          # ★ 直接 return，后面全不执行
```

**教训**：**多个标志拼在一起时，「每个标志都生效」是一个需要核实的假设，不是默认行为。**
判据不能用「命令跑完了、退出码 0」—— 要看**它宣称做的那件事有没有留下痕迹**
（mtime、新键、行数）。同坑 12「BUILD SUCCESS 不等于编译了」、坑 13「对账通过不等于能用」。
> **处置**：**分开跑**，并把它写进 `_T8_RESUME.md` 的命令顺序。本轮另外把
> `--refresh` 和 `--coverage` 一起改成**只读**（见坑 18），于是三个标志
> 现在是「互不叠加、都不写交付物」。

### 坑 18 · 显式列清单漂移（**第二次，同一个方法**）—— 症状是一个**合法的 0**

**现象**：T8 给 `EvalReportService.costSection` 加了
`prompt_tokens` / `completion_tokens` 的累加（为了让**缓存命中率可反推**）。
累加代码是对的，**`QaLogMapper.selectByEvalRun` 的列清单没跟着加**
→ 每一行的这两个字段都是 `null` → 被 `!= null` 挡掉 → 两个合计**恒为 0**。

★★★ **它比第一次更难发现**（T5 那次是 RAGAS 报 `user_input cannot be empty`）：

```
① 不报错        —— 查询成功、返回 460 行
② 返回的不是 null 而是【0】—— 「少读一列」被渲染成「这一轮真的没有 token」，
                 而后者是一个【合法值】
③ 键在、格式对、旁边那个数还对 —— token合计 是 386591（正常），
                 紧挨着的两行是 0，并排印出来看着像「拆分粒度不同」
```

★★ **判据（免费且精确，全库 17 轮实测 0 例外）**：
`prompt_tokens + completion_tokens == total_tokens`。
只要有 `total_tokens`，这两列就都在且相加恰好相等 ——
所以 `0 + 0 ≠ 386591` **本身就证明是读路径坏了**，不可能是数据如此。

> **处置**：补上两列 + 在 `QaLogMapper` 的 javadoc 里写明「改这条查询时把两边的
> getter 清单拉出来逐个对照」+ ★★ 新增 `QaLogMapperProjectionTest`（5 个用例）：
> **遍历实体的全部字段，要求每个要么在投影里、要么在 `NOT_SELECTED` 里显式声明过**
> —— 例外是一份**受审的清单**（同 `OMITTED_PATHS`），不是一句「其余都忽略」。
> ★ 为什么原来的测试抓不到：`EvalReportServiceTest` 是**纯单测**，
> 喂的是**手工 new 出来的 `QaLog` 对象** —— 投影漏没漏列它看不见。
> 同 ADR-061：**桩造的对象验证不了它自己**。

### 坑 19 · ★★ 把 JVM 的**内部桶序**当成自己的承诺 → 一个约 50% 概率红的测试

**现象**：`./mvnw clean test` 在 19:27 是 819 全绿，19:50 同一个提交反而红了 ——
**中间没有改过 `EvalReportService`**。红的是
`EvalReportServiceTest.sortingIsWhatChangedIt`：

```java
Set<Integer> unsorted = Set.copyOf(List.of(4, 2));
assertEquals("[4, 2]", unsorted.toString(), "……");
```

**机制**：`Set.copyOf` 走的是 `ImmutableCollections.SetN`（**不是** 保留插入顺序的 `Set12`），
它的迭代顺序是 `floorMod(hash ^ SALT, tableSize)` —— 而 `SALT`
**每次 JVM 启动都随机**（JDK 9+，就是 CLAUDE.md 里 `Map.of` 那条的同源机制）。

**实测（30 个独立 JVM）**：

```
n=2   约一半印 [4, 2]，约一半印 [2, 4]     ← 这条断言自己约 50% 概率红
n≥3   盲区【不随元素个数下降】，稳定在约 1/4
```

★★★ 所以「多塞几个元素」**修不好**这个对照 —— 它是结构性巧合，不是抽样误差。
★★ 更深的一层：在那些 JVM 上，**「直接拼 Set」的实现真的会印出正确结果** ——
那条对照在那些 JVM 上**结构性地不具区分力**。这不是测试写坏了。

> **处置**：换成**顺序可控**的对照物 —— `LinkedHashSet`（保留插入顺序），
> 所以「不排序的样子」是**确定**的 `[4, 2]`；再加一条确定性的
> 「Set 打印顺序与**声明顺序**无关」。**30 个独立 JVM 实测 30/30 稳定。**
> ★ 残余盲区如实写进注释，不假装它不存在。
> ★★ 这是本项目第四次「子串匹配 / 不受控的量当判据」——
> 前三次是 `key` 撞 `keyword-weight`、`application` 撞 `spring.application.json`、
> 裸字符串当集合用。**判据必须是「我们承诺过的东西」，不是「观察到的东西」。**

### 坑 22 · ★★ JSONB 往返会把**键序和空白都改掉** —— 字节比较是非法判据

**现象**：写进去的 `references` 字符串，读出来和原文**不相等**，
导致一个「库里存的确实是字符串」的断言红。

**实测（2026-09-24，psql 直接验的）**：

```
写进去：[{"no":1,"chunk_id":15,"document_id":2,"score":0.9276,"heading_path":"售后FAQ"}]
读回来：[{"no": 1, "score": 0.9276, "chunk_id": 15, "document_id": 2, "heading_path": "售后FAQ"}]
              ↑ 冒号后多了空格        ↑↑ 键序变了
```

PostgreSQL 的 JSONB 存的是**解析后的结构**，不是原始文本。输出时按
**键名长度升序**重排（`no`=2 → `score`=5 → `chunk_id`=8 → `document_id`=11 → `heading_path`=12）。

★★ **这和阶段 7 那个 `Set.copyOf` 的 SALT 坑是同一类**：
「我们以为自己控制着顺序，其实没有」—— 只不过这次重排的是数据库，不是 JVM。

⇒ **推论：凡是进 JSONB 列再读出来的东西，「用 `LinkedHashMap` 保证顺序」
这条纪律在往返之后就失效了。**
⚠️ 本项目当前**没有**「JSONB 往返 → 拼进 prompt 前缀」的路径，
所以还没有缓存命中率的问题 —— 但这是一条该被写下来的边界。

★ **处置**：断言写成 `readTree(读回来) == readTree(写进去)`（比语义），
**不写** `isNotEqualTo(写进去)` —— 那会把 Postgres 当前的实现当成我们的契约，
哪天它改成保留原始字节，那条断言就会红，而那个红不代表任何东西坏了。
（同坑 19：只能断言我们承诺过的东西。）

### 坑 23 · ★ PostgreSQL 的 `now()` 是**事务开始时间** —— 排序需要次级键

**现象**：`ORDER BY last_active_at DESC` 在测试里返回的顺序**不稳定**。

**机制**：`now()` 等价于 `transaction_timestamp()`，返回的是**事务开始**的时刻，
不是语句执行的时刻。而 `chat_session.last_active_at` 的默认值正是 `now()`。

```
同一个事务里插入两行
    → 两行的 last_active_at 【完全相同】
    → 只按它排序时，这两行的先后【未定义】
```

**为什么生产上碰不到、测试里一定碰到**：串行问答路径下每个请求各自一个事务，
所以线上两行不会同事务。而评测（一个事务里连建多个会话）和
`@Transactional` 的集成测试**会**。

★ 真碰到时的症状是**「翻页时同一行出现在两页，或者干脆不出现」**，
而不报错、不稳定复现。

⇒ **处置**：`ORDER BY s.last_active_at DESC, s.id DESC` —— 加一个单调键让排序成为**全序**。
代价是一次几乎免费的比较。

★ **测试里也要防**：集成测试造数据时**显式指定** `lastActiveAt`，
不要依赖默认值（同事务里它们会全一样）。

### 坑 30 · ★★★ 兜底异常处理器把**每一个 404 都渲染成了 500**

**现象**（阶段 8 第一次验「公网访问 `/api/debug/**` 必须 404」）：

```
$ curl -u u:p http://host/api/debug/ratelimit/state
500                      ← 期望 404

ERROR GlobalExceptionHandler : 未预期的异常
org.springframework.web.servlet.resource.NoResourceFoundException:
    No static resource api/debug/ratelimit/state.
```

**机制**：Spring Boot 3.2 起，未匹配的路径**不是机械地回 404**，
而是抛 `NoResourceFoundException`（静态资源处理器是链上最后一个，
它用异常报告「找不到」）。而 `GlobalExceptionHandler` 末尾那个
`@ExceptionHandler(Exception.class)` 把它接走了 → 500。

**★★ 这是阶段 8 之前就存在的 bug** —— 只是「某条路径必须 404」这个判据
到阶段 8 才第一次被检查。**判据不到，bug 就不存在。**

**后果三条，都不是「功能坏了」而是「信号坏了」**：

```
① 任何拼错的 URL 都回 500 —— 客户端分不清「没有这个接口」和「服务炸了」
② ★ 每一次扫描器探测都写一行 ERROR（"未预期的异常" + 完整堆栈）
   → 监控按 ERROR 计数时，错误率被探测流量污染
   → 「用户关页面」和「数据库连不上」会变成同一个信号
③ 验收判据失效：404 与 500 无法区分时，
   「控制器没注册」和「注册了但炸了」就分不开了
```

**★★★ 最讽刺的一点**：`GlobalExceptionHandler` 里**已经有一段长注释**
在讲「一个完全预期之内的条件被归到『未预期的异常』里，后果是信号被淹没」，
并说本项目已经因此踩过两次（阶段 6.7 的 `ExecutionException`、客户端断开）。
**而那一大段注释正贴在制造第三个反例的代码上面。**

**处置**：加 `@ExceptionHandler(NoResourceFoundException.class)` → 404，
记 **DEBUG**（请求不存在的路径是完全正常的事：favicon、爬虫、拼错地址）。
★ 真想看「有没有人在扫我的站」应该看 **Nginx 访问日志**（有 IP / UA / 模式），
不是靠 Spring 的异常处理器。

**验证**：`UnmappedPathMappingTest` —— 含正-反对照：
不存在的路径 → 404，**而存在的路径抛未预期异常仍然 → 500**
（少了第二条，一个「把 `Exception` 也映射成 404」的实现会让第一条通过，
而那个实现比原来的 bug 更糟）。

「`SeedRunner` 会灌业务表（商品/订单/券），但知识库要单独触发」——
后半句对，**前半句是假的**。而它是在**实测逐表 count 之后**才被发现的。

★ 教训：**「它会自动做 X」这种话，必须在空环境里真的看过才写。**
在有数据的机器上跑一次，看到数据都在，会得出完全相反的结论。

### 坑 32 · ★★ 管道后的 `$?` 是**最后一个命令**的退出码

**现象**：一条命令看起来「成功退出」：

```bash
timeout 300 docker compose run --rm app --spring.main.web-application-type=none 2>&1 \
  | grep -iE "seed|完成" | head -20
echo "EXIT=$?"      # → EXIT=0
```

而实际上**那个容器一直活着**（`docker ps` 里 `Up 14 minutes`）。
`0` 是 **`grep` 的退出码**。

**为什么这一条单列**：它和本项目那句「**别信 HTTP 200，要看返回里有没有新加的键**」
是**同一类判据错位** —— 取了一个「看起来在测那件事、实际上在测别的事」的指标。
而它比 HTTP 200 那条更隐蔽：管道是那么自然，`$?` 是那么像。

**处置**：要看真退出码就别走管道，或者 `set -o pipefail`，
或者把结果写文件再读。

**顺带记一个连带发现**：这个应用**灌完种子不会自己退出** ——
`--spring.main.web-application-type=none` 只关掉了 Tomcat，
关不掉三个 `ThreadPoolTaskExecutor` + 排队心跳 + Pub/Sub 订阅监听这些
**常驻非守护线程**。所以 `scripts/seed.sh` 用的是
「起 → **轮询日志找完成标记** → 拆容器」，而不是「起 → 等它自己退」。

### 坑 33 · ★★ 明文未签名的身份头 + 目标列上有 FK = 一发免费的拒绝服务

**现象**（阶段 9.1 实测，**不是推断**）：给 `chat_session.user_id` 接上真实身份之后，
去掉「核对这个人存在」那一步，测试里出现的是：

```
ERROR: insert or update on table "chat_session" violates
       foreign key constraint "fk_chat_session_user"
```

**成因**：两件各自都合理的事撞在一起 ——

```
① chat_session.user_id 上有 FK → app_user(id)   （V5 迁移写的）
② X-Xbla-User-Id 是【明文未签名】的请求头        （ADR-054 反复声明它「不是认证」）
```

⇒ 任何客户端发一个 `X-Xbla-User-Id: 999999`，就能让**每一次对话**在建会话
那一步 500。**它不需要任何权限，也不需要猜任何东西。**

**为什么它属于「会静默咬人」那一类**：报错信息长得像一个普通的数据库错误，
**没有一个字提到那个请求头**。第一个来查的人会去翻迁移、翻实体映射、
翻连接池配置 —— 而真正缺的是一个 `getById`。

**处置**：写入前核对存在性，**查不到就如实记 NULL**。
★ NULL 在这里是**正确答案**而不是失败：那个头和「没带头」在语义上没有区别，
都是「我们不知道你是谁」。

**★ 这条的普适形态**：本项目对 `X-Xbla-User-Id` 的**边界声明**是
「它不是认证，只是让身份不进模型的可控范围」。
一旦有代码开始**信任**它（写库、建索引、发通知），那条边界就被悄悄越过了 ——
而**越过它的那一刻不会有任何提示**，只有下游的约束违例。
⇒ **凡是「只做过格式校验的输入」要去碰一个有约束的列，先问一句：
这个人/这个键真的存在吗？**

### 坑 34 · ★★★ 形状表是**量**出来的，不是**推**出来的 —— 一次活体验证推翻三处文档

**现象**：阶段 9.1 给 `qa_log.user_id` 写形状表时，我照着推理写下：

```
阶段 9 之前的行           恒为 NULL
之后 · 头缺席             NULL（匿名）
之后 · 头指向不存在的人    NULL（app_user 里没有这个 id）    ← 这一格是错的
之后 · 正常              请求头里那个 id
```

然后把这张表**抄进了三个地方**：`docs/08` ADR-091、`docs/04` 的列说明、
以及 `ChatServiceImpl.baseLog` 的代码注释。

**验证**（活体打一发伪造的头，`X-Xbla-User-Id: 999999`）：

```
chat_session.user_id  →  NULL      （它写前核对 app_user，且该列有 FK）
qa_log.user_id        →  999999    ← 与上面那张表逐字相反
```

**为什么会推错**：我从「`chat_session` 那一列要核对存在性」推出了
「另一列也应该这样」，而**这两列的正确行为本来就不同**（见 ADR-091）——
工具那条路执行的是 `WHERE user_id = <请求头里的值>`，
所以 `999999` 才是「这一次真正被使用的身份」。

**★★ 更要紧的是：这个错误如果没被活体验证抓住，会以什么形态存在？**

```
文档说 NULL，实现写 999999
→ 读文档的人据此写 JOIN app_user / distinct(user_id)，得到静默少算的结果
→ 而「少了几行」和「那几行本来就不该有」在数字上长得一模一样
```

**它和第 20 条坑是同一个病**（「错误路径里写听起来合理的成因」）：
**读者无法分辨「我核实过」和「我想了想」。**

⇒ **处置**：形状表只能由**实际数据**产生（探针/查询/日志），不能由设计意图产生。
写形状表时，每一格都要能指出**它是从哪一条命令的输出里抄来的**。

### 坑 35 · ★★★ 「判据算对了」≠「调用点接上了」—— 一个纯函数测试抓不到的 NPE

**现象**（阶段 9.2，集成测试抓到）：

```
java.lang.NullPointerException: Cannot invoke "RetrievalTrace.summary()"
                                because "retrievalTrace" is null
	at ChatServiceImpl.ask(ChatServiceImpl.java:535)
```

成因很直接：那两行日志无条件调 `retrievalTrace.summary()`，而 9.2 让
「不检索」成了一条**正常路径** —— 于是**每一句「你好」都会 500**。

**★★ 为什么它值得单列：写这一段的那个小时，单测是全绿的。**

```
RetrievalGateTest                13 项绿    门控表对、两条边界规则对、反对照对
IntentReplyParserTest            21 项绿    两种契约的切换可判
→ 而线上每一句闲聊都会 500
```

**因为那一层测试证明的是「判据是对的」，证不了「调用点用了它之后还活着」。**
两者之间那一段（`retrievalTrace` 从「一定有」变成「可能是 null」）
**在纯函数的视野之外**。

**★ 它和第 32 条坑是同一个形状**：取了一个「看起来在测那件事、
实际上在测别的事」的指标 —— 那里是 `$?` 被 `grep` 改掉，
这里是「门控判对了」被当成「链路跑通了」。

**处置**：凡是「某条分支从『不可能发生』变成『正常发生』」的改动，
必须有一条**从入口进去的**测试。判据不是「单测绿了」，
是 **`verify(下游, never())` 这种**对真实调用链的断言：

```java
verify(retrievalPipeline, never()).retrieve(any(), any(), any());
```

★ 顺带一条反过来的经验：这个 bug **不是**「多想一步就能避免」的那种 ——
它是 9.1/9.2 那种「把一条边界挪开」的改动必然产生的副作用。
所以真正的防线是**改动时问一句「这条路径以前不可能为 null，现在可能了吗」**，
而不是写得更小心。

### 坑 36 · ★★★ 探针打到了**旧进程**上 —— 而它吐出了一整页看起来很合理的结论

**现象**（阶段 9.2 实测）：新起的实例报 `Port 8081 was already in use` 起不来，
而**旧实例还活着**。探测脚本照样连上了 8081，于是它测的是**上一版的代码**：

```
问：你好呀
  意图      : OUT_OF_SCOPE  [CLASSIFIED]
  shape     : None                      ← 键根本不存在
  门控      : path=None reason=None      ← 同上
★ JSON 占比：0/5  ⚠️ 有契约回退
```

**当时真实情况是 5/5 全部 `shape=JSON`**（换到新实例后实测）。
★ 也就是说：**那一页输出把「契约完全生效」报成了「契约一次都没生效」。**

**★ 它为什么危险**：输出**格式完全正常** —— 有意图、有耗时、有 cost、
有分布统计、有 `⚠️` 标记，看上去就是一次成功的探测。
唯一不对劲的是几个 `None`，而 `None` 在「键不存在」和「键的值是 null」
两种情况下**长得一模一样**。

⇒ **这正是坑 24（`jsonPath(...).exists()` 分不清两种 null）换了个地方重现。**
那一次在 Java 测试里，这一次在探测脚本里。

**根因**：`mvnw spring-boot:run` 是一个**包装进程**，
后台任务被停掉（或 Maven 退出）之后，它 **fork 出来的 JVM 还活着**。
于是「我以为我重启了应用」和「8081 上跑的是哪一版」是**两件事**。

**处置**：

```
① 重启前先确认端口归属：netstat -ano | grep ":8081.*LISTENING"
   要杀的是那个 java 进程，不是 maven 包装器
② 探测脚本【必须】先断言键存在，再读值
   写 d.get("shape") 的话，键不存在和值为 null 分不开
③ ★ 换版本后先打一发「金丝雀」：/api/debug/agent/intent-prompt
   看它的头两行是不是新文案 —— 那是零成本、一眼可辨的版本指纹
```

**★ 最值钱的一条**：那次探测**差点被当成结论**。
它印出的数字很好看、格式很正规、还有一个 ⚠️ 显得很严谨 ——
**而它是反的**。判据只有一个：`shape` 那一格**不该是 None**。

### 坑 37 · ★★★ 白名单只写在**请求**里 ≠ 服务端强制 —— 一个幻觉出来的工具名会被**真的执行**

**现象**（阶段 9.3，写测试时顺着「模型要是乱叫一个工具会怎样」问下去发现的）

```
请求侧的 tools 数组确实裁剪了（模型只看到 3 个工具）
但 ToolLoop.invoke() 把模型给出的名字【直接】转发给网关
而 MCP 服务端只拒绝「注册表里没有的名字」
⇒ 模型吐出一个【注册过、但不在本轮白名单里】的名字 → 那条调用被真的执行
   → 返回【这个用户的真实数据】
⇒ qa_log.tool_calls 里长得和正常调用一模一样，没有任何指标会红
```

**为什么它危险**：`query_my_coupons` / `query_order_status` 这类名字**很好猜**
（工具清单同时出现在意图树、docs、`/api/debug/mcp/tools` 里），
一次提示注入、甚至只是模型的一次自我发挥就够了。按意图裁剪**只剩一半效力**。

**判据**（也是修完之后必须留下的测试形状）：

```java
// 负路径：不在白名单里的名字 → 网关【一次都没被调用】
verify(gateway, never()).callTool(anyLong(), anyString(), any());
// 正对照：白名单里的那次 → 真的到了网关（否则「全部拒绝」的实现也是绿的）
verify(gateway, times(1)).callTool(USER_ID, "query_order_status", Map.of());
```

**规律**：**「不提供」和「不允许」是两件事**。前者只影响对方**看得见**什么，
后者才约束它**做得成**什么 —— 而只要对方能自己拼出那个名字，前者就等于没做。
同族的还有「身份不进工具参数」（ADR-054）：那一半已经做了，这一半才补上。

### 坑 38 · ★★ 硬编码的上限进了正文，就变成一句**关于平台的假话**

**两个实例，同一类错**（阶段 9.3）：

```
① compare_prices 的正文写「同类目在售 N 个商品」——
   而统计样本有 STAT_SAMPLE=200 的上限。商品更多的类目上，
   这句话把「我数了 200 个」说成了「平台一共有这么多」。
   ⇒ 改成「取样 N 个在售商品」：数量词必须说清【它是什么的】数量。

② search_products 的「还有更多」判据写反了：
   returned.size() == take  ← 应为 matched.size() > take
   ⇒ 12 个命中时报「共 10 个」（少报）
     刚好 5 个时报「可能还有更多」（凭空多报）
   ⇒ 而且 matched_count 恒等于 returned_count，和它自己的字段描述不符
```

**为什么难发现**：两个方向**都读得通**。用户看到「共 10 个」不会怀疑，
模型看到「可能还有更多」也不会 —— 直到有人真的去数。

**规律**：**正文里的每个数字，要么确切，要么标明它是下界/样本**。
★ 而且判据要**同时断言两个方向**（多报和少报），
只断言一边的话，把判据写反仍然可能绿。

### 坑 39 · ★★ 最坏情况的夹具必须**从 schema 派生** —— 抄字面量会静默失效

**现象**：`ToolResultBudgetTest` 的夹具一开始是硬编码的「255 个字的商品名」。

```
某天有人把 product.name 从 VARCHAR(255) 放宽到 VARCHAR(512)
→ 夹具【不再是最坏情况】
→ 测试照样绿（它测的是「我以为的最坏情况」）
→ 而真实流量在那个边缘形状上被 ToolLoop 静默截断
```

**修法**：夹具的长度**从库里读**，于是放宽一列会自动扩大夹具：

```sql
select character_maximum_length from information_schema.columns
 where table_schema = current_schema() and table_name = 'product'
```

★ 同一查询顺带回答了一个更根本的问题：**TEXT 列的
`character_maximum_length` 是 NULL**（无上限）——
`selling_points` 就是这种列，所以它**只能靠工具侧截断**兜住，schema 给不了保证。
★ 断言写成**区间**（`isBetween(3400, 3800)`）而不是等号：
实测 **3575**，而文档里一度写着估算值 3594 —— 估算当场被实测推翻，
留着它会让下一个改代码的人以为差值是 bug（同坑 20）。

### 坑 40 · ★★ 一个响应有**两个构建器**时，改一个就等于没改

**现象**（阶段 9.3 活体验证抓到的）

```
混合轮的 references 是 null —— 回答里明明挂着 [1][2][5]
根因：buildToolResponse 和 buildStreamToolResponse 是两个【独立】的方法，
     两处都硬编码了 references = null，注释还写着「工具轮没检索」
     —— 而那个理由在混合轮（检索 ∧ 工具）上已经不成立
```

**为什么危险**：**非流式修好了、流式还是坏的**（或反之），
而两条路各自「看起来」都是对的 —— 前端只用流式，
所以真实用户看到的仍然是空的引用栏，而测试全绿。

**规律**：这个仓库里「平行的两条路」至少有三组，**每一组都要问「另一条呢」**：

```
ask()  / askStream()                      代码路径（9.1 栽过：工具分支只接了一条）
buildToolResponse / buildStreamToolResponse   响应形状（本坑）
qa_log 的 4 个以上 CallContext 构造点         评测标记（ADR-081/坑 18）
```

★ 判据不是「主路径绿了」，是**两条路各有一个测试 + 一个正-反对照**
（混合轮引用非空 / 纯工具轮引用仍为 null）。

### 坑 41 · ★★★ `updateById` **清不掉**一列 —— 它会把 null 静默跳过

**现象**（阶段 9.4，写「读后即清」时差点埋进去）

```
chatSessionService.updateById(只 set 了 pendingClarify = null 的实体)
→ 生成的 SQL 里【根本没有那一列】（MyBatis-Plus 默认 NOT_NULL 更新策略）
→ 一次空更新：不报错、返回 1（受影响行数按主键命中算）
→ 状态永不清空 → 每一轮都把那个旧反问注入一次
```

**为什么危险**：`touchSession` 的注释里**早就写着**这条策略（「未 set 的字段不会进
SET 子句」），而它在那边是**优点**（不会误清 userId/title）—— 在这里却是**致命**的：
我们要做的动作恰恰是「清空」。**同一个特性，在两个方向上是两件事。**

**判据/修法**：清空一律走显式语句

```java
chatSessionService.lambdaUpdate()
        .eq(ChatSession::getId, id)
        .set(ChatSession::getPendingClarify, json)   // ★ null 也会写进 SET
        .update();
```

★ 规律：**「想做的动作」和「实际写下去的语句」必须对得上**。
`updateById(entity)` 的语义是「按非空字段局部更新」，不是「把这几个字段设成我给的这些值」。
同族的还有 `claimSession` 用条件 UPDATE 而不是先读后写。

**测试怎么守**：断言「清空之后从库里读回来是 null」——
而不是断言「方法被调用了」。前者才看得见这一点。

### 坑 42 · ★★ 断言的锚点选太宽 —— 那条断言从第一天起就是错的

**现象**（阶段 9.4，第一次跑 `IntentPromptBuilderTest` 就红了）

```java
// 我想断言的是「没有待澄清时，注入那一段不出现」
assertThat(prompt).doesNotContain("上一轮");     // ← 红的，而代码是对的
```

根因：**基础 prompt 里本来就有「上一轮」三个字** ——
9.2 的 retrieve 契约写着「只有当它完全不需要任何平台资料就能回答时
（纯问候、纯感谢、**对你上一轮反问的确认**）才写 false」。

**教训**：`doesNotContain` 的锚点必须是**被断言那件事的特征串**
（`"## 上一轮的澄清"`），不是「我记得它没出现过」。
★ 反过来也成立：断言「有」的时候同样要挑特征串 ——
挑一个基础 prompt 里就有的词，那条断言**恒真**，它守不住任何东西
（同「纯单测必须写正-反对照」那条纪律的另一面：**恒真的断言也是假绿**）。

### 坑 43 · ★★ jsonb 列**存不进坏 JSON** —— 「坏数据」的真实形态是「形状不对」

**现象**（阶段 9.4，写「坏状态不炸」那个用例时）

```java
// 想模拟「库里有一份坏数据」
.set(ChatSession::getPendingClarify, "{半截")
→ org.postgresql.util.PSQLException: DataIntegrityViolation（invalid input syntax for type json）

**数据库自己先拦住了** —— jsonb 的输入解析是强校验的。
⇒ 这一列上「坏数据」的真实形态**只有一种**：

```
合法 JSON、但形状不对：缺 question / 不是对象 / slots 不是数组 / 值是旧版本的键
```

★ 而**语法坏掉的 JSON 只可能来自代码里的读法改了**（那是单测的事，不是集成测试的事）。
⇒ 集成测试该构造的是「形状不对」，单测才构造「语法坏」——
把两者搞混的代价是那条用例**永远红**，而它会被人当成 flaky 跳过。

### 坑 44 · ★★★ **「放在这一步之后」是一条要在测试里钉住的位置约束**

**现象**（阶段 9.5，`AffinityRouteIntegrationTest` 第一次跑就红了）

我把 `ctx.withAffinity(...)` 插在 `consumePendingClarify` 之后、**澄清判断之前** ——
而它的注释里写着「必须在澄清分支之后」。测试直接把它抓了出来：

```
[澄清轮的诚实值是 NULL]  expected: null
 but was: "【这位用户的购买记录】…近 180 天内 3 笔已付款订单…"
```

**为什么危险**：澄清反问**不调生成模型**，所以那一轮**没有 prompt**。

在澄清轮上写它有值，等于**存了一段模型从来没见过的文字**，
评测拿着它去算 faithfulness，只会得到一个偏低的分数，
而看报告的人会去调一个没坏的东西。

★ 更一般地：**「这一步必须在那个分支之后」是代码里最常见的隐性约束**，

⇒ 判据只能是**从入口进去**的测试：同一条断言换一个分支就红。

⚠️ 我自己就写错了 —— 注释写对了，**代码放错了**。
「注释里写了」不是约束，**测试才是**。

### 坑 45 · ★★★ 截断的清单不标记 = **那句话读起来就是完整的**

**现象**（阶段 9.5，**活体验收**时发现的，单测全绿）

`/api/debug/profile/affinity?userId=8` 打出来的偏好块里：

```
涉及 4 个类目：家用电器×3、笔记本电脑×2、平板电脑×1（其余略）   ← 类目标了
买过的品牌：联想×2、华为×1、戴森×1、海尔×1、索尼×1              ← 品牌【没标】
```

而 user 8 **有 6 个品牌**（第 6 个是「西门子」）—— 它被静默丢掉了。

**为什么危险**：`买过的品牌：A、B、C、D、E` 与
`买过的品牌：A、B、C、D、E（其余略）` 是两句**不同**的话，
而前者会让模型认定「他一共买过这五个品牌」并转述出去。
⇒ 这正是 `ADR-094` 那条「每个数字要么确切、要么标明它是样本」的又一次应用。

**为什么单测没抓到**：那条渲染用例的夹具恰好只有 **2** 个品牌，**没到上限**。
⇒ 夹具必须**超过上限**，否则测的是「没截断」那个形状（本项目的标志性失败形态：
「测试绿着，但它测的不是它声称要测的东西」）。

★ 规律：**「省略」这个动作本身必须留下痕迹。**
凡是 `top-N` / `limit` / `subList` 出现的地方，都问一句
「读的人怎么知道我砍掉了一部分」。截断本身不是错，**无声的截断**才是。

### 坑 46 · ★★ **用户级常数**加进商品得分 = 一个不生效的旋钮 + 一句假话

**现象**（阶段 9.5，规划阶段的纸面推演，还没有写代码就拦下了）

原计划是「会员等级 +1」进推荐打分。但 `app_user.member_level` 是**用户级**的 ——
给**每一个**候选商品都加同一个数，**任何两个商品的先后都不变**。

**为什么危险**：这不只是「没用」。它会在**正文里**留下一句
「排序依据包括你的会员等级」，而模型会照着它转述成
「按你的会员等级为你推荐了这几款」—— 那是一个**我们没做过的判断**。
⇒ 一个不生效的旋钮，比没有这个旋钮更坏：它生产一句**听起来有依据的假话**。

**判据（写下来，因为它是个通用检查）**：
加分项的**取值必须依赖商品**（或依赖「商品 × 用户」这一对）。
只依赖用户的分量 = 常数项 = 只影响所有商品的**同一次平移** ⇒ 排序上恒等于 0。

★ 它的正确归宿是**偏好块**（那里它是一个**事实**：「会员等级：银卡」），
而不是打分函数。同一个数据，在两个位置上的性质完全不同。

### 坑 47 · ★★ 桩一个方法就够了吗 —— **流式走的是另一个方法**

**现象**（阶段 9.5，写流式那条路由测试时）

```java
when(router.chat(any(), any())).thenReturn(...);        // 只桩了非流式
chatService.askStream(request, sink, user, ctx);
→ sink.onError("抱歉，智能助手暂时不可用，请稍后重试。")
```

根因：`askStream` 走的是 **`router.chatStream`**，没桩的方法 Mockito 返回 `null`，
于是 `streamResult.usage()` NPE —— **而报出来的错误和你正在测的东西毫无关系**。

★ 连带发现的一件事（**既有行为，不是 9.5 引入的**）：
这次 NPE 留下了**两行 qa_log** —— 先一行 `status=1`，再一行 `status=2`。
因为异常发生在 `saveQaLogStreamSuccess` **之后**的 `buildStreamResponse` 里。
⇒ 「一个 traceId 恰好一行」这个前提**在流式的异常路径上不成立**，
按它写断言（或按它做对账）会踩到。

⚠️ 它是怎么暴露的：我那两条断言是「恰好一行」，于是**红了**。
如果当初写的是 `rows.get(0)`，它会**静默地**拿到那一行 `status=1`（成功的那个），
然后断言「失败路径也会落库」—— 一条**看起来在守东西、其实守反了**的用例。

### 坑 48 · ★★★ 判据里的「池子」必须和**实现真正搜的那个池子**对得上

**现象**（阶段 9.5，写 `probe_recommend.py` 的池子自检时）

`recommend-gold.yml` 里「运动健身」那个 need 的档位清单是按 **19 件**标的
（人工挑出来的、`suitable_for` 提到运动的那批）。而工具实测
`matched_count = 189` —— **全部在售商品**。差的 170 件不是「个性化推荐出来的」，
是它们本来就落在工具的池子里。

根因：`recommend_products` 的命中判据是「need 和三个文本字段有 **≥2 字**的
连续公共子串」，而那个 need 写的是「**适合**运动健身、防水防汗」——
**「适合」是每一个 `suitable_for` 的连续两字子串**（那批文案全是「适合…」开头）。
⇒ 池子变成整个目录，而档位清单只盖住其中 19 件。

**为什么危险**：`hit@3`/`reject@3` 是「命中了清单里的哪一档」。
清单盖不住池子时，一个**真的合适**的商品会被算成「乙档」——
**指标偏小**，而偏小的方向恰好是「个性化看起来没效果」，
于是人会去调一个没坏的东西。★ 而且它**不报错**：清单本身就是一份合法数据。

★ 同类问题还有两个更隐蔽的变体：
- **`candidate_count` ≠ `matched_count`**：前者是「池子里有多少商品」（189），
  后者是「字面重合分 > 0 的有多少」。我第一次就是拿错的这个数去比，
  于是**每一行都报「对不上」** —— 而人一旦习惯忽略那个警告，它就再也拦不住东西了。
- 池子会**随商品上下架变**：清单是「当时的池子」的快照，所以要有那条自检。

⇒ 做法：把 need 换成「运动健身」（池子 30），并按**同一条规则**在**完整池子**上
重新枚举（甲 4 → 15）。★ 这条修正**改变了结论**（见 `docs/05` §9.12 ⑧）。

★ 更一般地：**任何「离线判据 vs 在线实现」的对比，第一件事是确认两边
说的「候选集」是同一个集合。** 判据可以更窄（只看最关心的那几个），
但那时指标的含义就变成「最关心的那几个里有没有」，**不能再叫 hit@3**。

### 坑 49 · ★★ 排序规则一改，正文里那句「同分按编号排」就成了一句假话

**现象**（阶段 9.5 做「组内细排」时）

加了细排之后，`render()` 里那句

```
★ 最后 N 个的得分相同，它们之间的先后只按商品编号排，不代表谁更好。
```

**当场变成假的** —— 同分的商品现在是按「买过几次 / 价格多近」排的。
而这句话是**给模型看的**，它会原样转述成「这几款是随便排的」或者反过来
（更糟）「这几款是平台按你的习惯推的」。

**为什么危险**：这句话的存在意义就是**防止模型过度解读排序**。
一句写死的「说破」在排序规则变了之后，从「防止误解」变成「制造误解」，
而**没有任何东西会报错** —— 正文照常渲染，模型照常回答。

★ 修法不是「改一句文案」，而是**让它现算**：
「这一组的先后到底是不是历史决定的」是一个**只有比较器才知道**的事实。
判据不是「有没有偏好」——**有偏好、但组内三项键全相等时，仍然是编号说了算**，
那时候说「按你的历史再排的」是**另一个方向的假话**。

⇒ 现在 `differentiatedByHistory()` 和排序**共用同一个比较器**（`historyOrder`），
正文的措辞由它当场判定。测试里两条断言是**成对**的：
同一个夹具只换 userId，一条必须出现「只按商品编号排」，另一条必须**不出现**它。

★ 更一般地：**凡是写进正文的「关于这段输出的事实」，都要能指向一个单一出处。**
写死在字符串里的事实，会在它描述的机制变化时静默作废。

### 坑 50 · ★★★ 「判据与实现正交」有一个没被写下来的前提：**两者看的资料要自洽**

**现象**（阶段 9.5 的 A/B 负例，2026-09-26 查明）

user 8 问「运动健身」，工具推了 3 件丙档家电（丙 0 → 3）；而同一份 A/B 的
另外 3 个组合又是变好的。查下去发现**这一格不是排序错**，是**判据和工具看的是
两套互相矛盾的资料** —— 于是这个问题在数据里**没有答案**。

三条证据（前两条可自己复算）：

```
源码（判决性） SeedDataFactory.java:276-278，相邻两行：
              卖点   SELLING_POINTS.get(t.category())  【按类目取】
              适用人群 pick(SUITABLE_FOR)               【不看类目】（平铺 10 句等概率抽）
分布           19/189 = 10.05% ≈ 1/10；(类目 × 句子) 60 个格子只有 1 个空
自洽           同一篇 KB 文档里 chunk1 卖点说家电、chunk2 适用人群说运动器材，
              chunk3 的「商品描述」把两者拼进同一个句子
```

**为什么危险**：本项目从阶段 7 起有一条纪律 —— 判据必须与实现**正交**
（不用实现的特征、不用实现的打分，否则是自证）。这条纪律**只解决了
「判据会不会自证」**，没解决「两边看的资料一不一致」。而当资料自己跟自己矛盾时，
**正交的两套证据必然给出不同的答案，而这与实现的优劣无关** ——
症状就是「A/B 里有一格怎么改都改不好」，而每一次改动都在别的格子上付代价。

★★ 这次的具体形态：工具排序的第一依据是 `suitable_for`（+3，权重最高），
而 gold 的纪律 ① 把那个字段**排除**了（理由正是防自证）⇒ **两者证据的交集是空集**。
那一格的分歧于是是**结构性**的：换成任何一件「类目与 `suitable_for` 打架」的商品，
同一格都会出现。

**怎么辨别是哪一边**（可复用的方法）：

1. **别拿常识当证据** —— 「冰箱当然不适合运动」是常识，不是证据；
2. 问「这个字段是不是在**描述这件商品**」，判据是它和**它旁边那些字段**打不打得通；
3. **判决性证据在生成器源码**（字段是按类目造的吗）；**佐证在分布**（与类目独立吗）
   与**自洽**（同一篇文档里前后矛盾吗）—— 后两条别人**不需要相信你**，跑一句 SQL 就能验。

⚠️ 三个修法方向的代价**都在别处**，所以这一次的处置是**停手（不改代码、不改语料）**：
改 gold = 用上实现的分数字段 ⇒ **自证**，A/B 只剩「输出变了」；
改语料 = 重 seed + **重灌知识库（花钱、1652 条切片作废）** + gold 的池子与档位全部重做；
改工具 = 动排序键的哲学（与 9.5 的拍板冲突）。**先算代价再选，别默认「修」是对的。**

★ 更一般地：**拿 A/B 数字之前先问一句「两边看的是同一套资料吗」。**
「判据与实现正交」是**必要**条件，不是充分条件。

### 坑 51 · ★★★ **往题库目录放一个非题库文件 = 整条评测链断，而测试全绿**

**发现**：2026-09-26（做 9.6a 时，reload 第一次调用就红了）。

```
★ 题库加载失败，共 1 处问题（锚点必须唯一命中）：
  [recommend-gold.yml] 顶层缺少 question_set。
```

**成因**：阶段 9.5 把 `recommend-gold.yml`（推荐排序的**人工判据**，不是题库）
放进了 `data/eval/`。而 `EvalQuestionLoader` 的目录契约是**明写**的 ——
「这里的每一个 `*.yml` 都是题库的一部分」，而且那段注释专门论证过
「**扫目录**而不是列文件名清单」是为了「加错了**当场报错**」。

★★ **报错是对的，报错的内容指错了修法** —— 最自然的反应是给一个
**根本不是题库**的文件补一个 `question_set`，那会把它静默地变成一套 0 道题的题集。

**为什么测试全绿**：`reload` 是一个 **HTTP 端点**，
`./mvnw clean test` 里没有任何用例走它。而 `scripts/eval_run.py` 的**第 ① 步就是它**
⇒ **整条评测链断了整整一天**（9.5 提交 → 9.6a 开工），没有任何东西会红。

```
能守住的：单元测试（改坏了当场红）
守不住的：一条【只在集成路径上存在】的契约 ——
          它的判据是「端点能不能跑」，而那个判据不在 `mvn test` 的范围内
```

**修法**（ADR-100）：目录里每个 `*.yml` 顶层**必须自报家门** `kind: bank` / `kind: gold`，
缺 `kind` 当场报错并**告诉你要写哪个值**，`kind: gold` 的跳过并打日志。

★ **为什么不是「缺 `question_set` 就跳过」**：那会让**真的写漏了**的题库被静默跳过 ——
正是上面那段论证要防的东西（题数从 150 变成 120，没人知道少了什么）。
**判据必须是「显式声明」，不是「缺什么就猜什么」。**

**更一般地三条**：

1. ★★ **「某件事的信号源」和「这件事的判据」不是一回事**。
   这里的信号源是 `.yml` 文件，而判据是「端点跑不跑得起来」——
   两步之间没有任何东西强制同步。**新加一个文件时，问一句「谁会扫这个目录」。**
2. ★★ **报错的内容和报错本身一样重要**。
   「缺少 question_set」把下一个人的注意力引向了错误的修法，
   而正确的修法是「这个文件不该在这里」。
3. ★ 这条和坑 30（兜底 handler 把 404 变 500）是**同一族**：
   **一个正确的机制，配上一条指向错误方向的信息，比不报错更难查** ——
   不报错至少你知道要看代码，报错说错方向你会去改一个不该改的东西。

### 坑 52 · ★★★ 复用一个 run id = **两轮的行走进同一个筛子，而对账照样通过**

**发现**：2026-09-26（做 9.6a 的多轮验收时，**是我自己犯的**）。

**怎么犯的**：多轮题库改过一次措辞，我想重跑。为了「干净」，
先把 `eval_results/20260926-stage9-clarify-multi/` 删掉再跑同一个 run id。

```
★ 这个 run id 已经用过了：eval_results/20260926-stage9-clarify-multi
  对账靠 run_id 唯一 —— 复用会让两轮的行走进同一个筛子。换一个。
```

**这条保护是有的，而它判的是【本地目录存在】**。`rm -rf` 之后它就不响了。
于是两轮的 **96 行**（各 48）落在同一个 `eval_run_id` 下，
报告把**两个版本的题库**混在一起算 —— 表现是
「分母 48 次尝试」（应 24 次）和 `CL-006` 的 `③末轮落点 = NEEDS_CLARIFICATION`
（一个**不可能**的值：末轮落在澄清分支上，而它上一轮已经澄清过了）。

★★★ **对账全程是绿的**，而且它**必然**是绿的 —— 对账的判据是
「每个提交的 `traceId` 都能查到、且 `eval_run_id` 相符」，
而两轮的行**真的**都相符。**对账防的是「行丢了」，不防「行多了」。**

```
能守住的：行少了（eval_run_id 在某个 CallContext 构造点上被丢掉）
守不住的：行多了（同一个 id 底下躺着两批互不相干的数据）
          —— 它们各自都是合法数据，只有【跨批次的语义】不成立
```

**修法**：换 run id 重跑（本次），并把那 48 行旧数据**删掉** ——
★ 光换 id 不够，库里那批旧行会继续被任何按 `eval_run_id` 聚合的查询捞到。

**三条更一般的**：

1. ★★★ **一个键的「唯一性」被两个存储各自守着一半时，只有一边会响。**
   这里 `run_id` 的唯一性**落在** `qa_log`（数据库）上，
   而**检查**它的是 `eval_results/<id>/`（本地目录）。**两个判据，两个存储。**
   ⇒ 判断一个 id 能不能用，要去**它的语义所在的那个存储**里问。
   （待做：把 `eval_run.py` 的判据从「本地目录存在」改成
   「本地目录存在 **或** 库里已有这个 `run_id` 的行」—— 这次没改。）
2. ★★ **「删掉本地产物重跑」是一个看起来很干净、实际很脏的动作。**
   它清掉的是**记录**，不是**数据**。凡是有「本地文件 + 远端库」两层的地方，
   这一条都成立 —— **先问一句「删这个会不会让某个检查失效」**。
3. ★★ **数据的形状不对时，先看「多」而不是「少」。**
   报告里的症状是一个**不可能的值**（末轮落在澄清分支）和一个**偏大的分母**。
   ★ 而「分母不对」这件事本身不报错 —— 48 和 24 都是合法的数，
   **只有把「题库有 8 道题 × 2 轮 × 3 次 = 48 行」算一遍才知道 96 是错的**。
   ⇒ 拿到一个聚合数时，**用题库反算一遍它的量级**。

### 坑 53 · ★★★ **jsonb 列经 `json_agg` 出来【是对象，不是字符串】** —— 而 `except` 把 TypeError 吞成了「没有」

**发现**：2026-09-26（提交 9.6a 前，第一次真跑 `eval_report_check.py`）。

```
★★ 对拍失败：25 处不一致
   .槽位声明.分母_声明缺槽位    Java=66    Python=0
   .工具调用.静默降级行数        Java=42    Python=0
   .检索决策.shape分布.无计划    Java=None  Python=477
```

★ 每一处都是「**Python 侧全是 0**」。而 0 是一个**看起来完全合法的数** ——
二十五处不一致全在**同一边**，这个形状本身就是线索。

**成因**（同一个错犯了**三次**，在同一段代码里）：

```python
def _plan(r):
    return json.loads(r["intent_plan"])      # ← r["intent_plan"] 已经是 dict
```

`fetch_rows` 把整行包在 `SELECT json_agg(x) FROM (...) x` 里，
而 `intent_plan` / `tool_calls` / `turns` 都是 **jsonb** ——
经 `json_agg` 出来**直接被解析成 Python 对象**（dict / list），**不是字符串**。

```
json.loads(dict)  →  TypeError
                      ↑ 被 `except (ValueError, TypeError): return None` 吞掉
                      ⇒ 「我读不到」被表示成「这一行没有计划」
```

★★★ **`except` 里那个 `return None` 才是真正的凶手**，不是类型错。
`_plan` 的返回值同时承担两个意思（「没有计划」/「解析失败」），
而下游把它们当成同一件事 —— 于是「读不到」伪装成「没有」。

**修法**：按**列的类型**收，形状不对就**抛**（不回退）——
`retrieval_detail` 那一路上，全项目一直就是这么写的
（`filt = d.get("filter") or {}`），只有新写的三处照「JSON 列是字符串」的直觉写。

**三条更一般的**：

1. ★★★ **错在【同一边】的成批不一致，先怀疑「这边根本没读到」，不是「两边算得不同」。**
   如果真是算法分歧，差异应该是**双向**的。全部指向一侧 ⇒ 数据没进来。
2. ★★ **`except: return None` 会把「读不到」和「没有」合并**，而这两个在报告里
   长得一样。**凡是「失败」和「空」都要区分的地方，错误分支得能出声**
   （同坑 20：错误分支只能报告它核实过的东西）。
3. ★★★ **这段代码是 9.6a 写的，而它【从来没有被执行过】。**
   `--selftest` 不读数据、`--coverage` 不渲染 ——
   一份**只被写过、没被跑过**的代码，和一份**没写过**的代码在验收上的区别是零。
   ⇒ **新写的检查/对拍，第一次真跑它本身就是一个验收步骤。**
   ★ 这条和坑 51（`kind` 那次）**同族**：判据存在 ≠ 判据被执行过。

⚠️ 另有一处**不是**这个成因、但同样从没跑过：对拍脚本的「跨次决策翻转的题」
没有排除多轮题（Java 侧排了），实测报 1 处假差异 —— 已对齐。
