## 阶段 3 · RAG 核心 — 文档入库（第 3 周）

- [x] 3.1 `scripts/generate_corpus.py` 生成仿真文档（PDF / Word / MD / Excel）
      → 6 份语料：售后政策汇编（docx + pdf）、商品说明书（pdf）、
        商品导购指南（md）、促销活动规则（md）、售后FAQ（xlsx）
      → ★ 四种格式**刻意都生成**，因为 Tika 对它们的标题提取路径完全不同
        （见 3.2）。只生成一种的话另外三条路径永远得不到验证
      → 输出到 `data/corpus/`（**进 git**，60KB，让仓库克隆下来就能直接跑）
- [x] 3.2 Apache Tika 多格式解析
      → Tika **3.3.2**（不是最新的 4.0.0，理由见 ADR-012）
      → ★ **实测发现四种格式的标题形态完全不同**：
        · `.docx` 正文里直接有 `<h1>` `<h2>` `<h3>`
        · `.pdf` **正文里一个 h 标签都没有**，标题被抽成 `<body>` 末尾
          一个嵌套 `<ul>`（文档大纲），和正文完全分离
        · `.md` **Tika 根本没有 Markdown 解析器**（翻遍所有 tika jar 确认），
          实际由 `TextAndCSVParser` 兜底 —— 整个文件塞进一个 `<p>`，# 号原样保留
        · `.xlsx` sheet 名变成 `<h1>`，数据在 `<table>` 里
      → 对应三条提取策略。PDF 那条用「大纲建映射表 + 回正文按行精确匹配」
      → ★★ **踩到的坑**：Tika 生成的 PDF 大纲 HTML 不是良构的，
        同样的层级会输出成**两种嵌套形态**（嵌套 `<ul>` 在 `<li>` 里 vs 是兄弟）。
        第一版只处理了一种，导致**一份 PDF 正常、另一份标题层级整个丢失**，
        而且不报错。现在两种都处理，并有专门的回归测试钉死
      → ★ **第二个坑**：`tika-parsers-standard-package` 里 `tika-core` 是
        `<scope>provided</scope>`，而 provided **不具有传递性** ——
        编译直接报「程序包 org.apache.tika.parser 不存在」。必须显式再引一次
- [x] 3.3 文本切分（标题层级 + 定长 + 重叠窗口）
      → `HeadingAwareChunker`：按标题切段 → 段内滑动窗口 → 优先断在标点后
      → **标题路径会拼进切片正文**（「退货」二字可能只在标题里有）
      → ★ **实测发现的问题**：20 行 FAQ 表被合并成 2 个切片，每片混了
        十几条互不相关的问答 —— 向量变成十几个主题的「平均值」，检索精度被稀释。
        修法是给 `TextBlock` 加 `standalone` 标记，表格行各自成片。
        实测 FAQ 从 **2 片变成 21 片**（见 ADR-015）
      → 参数校验里挡掉一个会**死循环**的组合（`overlapChars >= maxChars` 时
        滑动窗口步进为 0）—— 在构造期拦住比在死循环里 debug 便宜一万倍
- [x] 3.4 批量向量化 + 写入 `kb_chunk`
      → 复用阶段 2 的 `EmbeddingClient`（客户端内部已按 32 分批）
      → **入库异步化**：上传接口立刻返回，`ingestExecutor` 后台跑，
        前端轮询 `kb_document.status`
      → ★ **不在事务里做整条流水线**：向量化要几分钟，
        事务开着会独占数据库连接（池子只有 10 条），改用**补偿删除**（见 ADR-014）
      → ★ **向量列从 `String` 改成 `float[]` + 自定义 `VectorTypeHandler`**：
        用 String 时编译器拦不住维度错误。`autoResultMap = true` 不能漏 ——
        漏了的话写入正常、查询也正常，就是查出来永远是 null（见 ADR-016）

**验收标准（2026-09-18 全部实测通过 ✅）**

1. ✅ **上传一份 PDF，数据库里能查到切片和向量**
   —— 实测走完整流程：上传返回 `status=待处理, finished=false`，
      轮询到 `已入库, chunks=3`
   —— 全库 1649 个切片，**有向量的 1649 个，缺向量的 0 个**
   —— 去重实测：同一份 PDF 再传一次，直接复用已有文档，
      **不重复花向量化的钱**

2. ✅ **向量维度确实是 1024**
   —— `SELECT COUNT(DISTINCT vector_dims(embedding))` = **1 种维度**，值是 1024
   —— 更强的证据：**数据库在强制执行这个约束** ——
      写一个 512 维的向量会被拒绝，报错 `expected 1024 dimensions`

3. ✅ **同一个问题检索两次，结果稳定一致**
   —— 同一问题检索 5 次，**命中的 chunk_id 序列逐位相同**：
      `[15, 158, 105, 55, 72]` × 5
   —— ⚠️ **但分值不是逐位相同的**：实测最大漂移 **3.767e-04**。
      直接原因是**向量化接口本身不是确定的** —— 同一个问题连续调 6 次，
      出现了 2 种不同结果。这是 GPU 并行计算里浮点归约顺序不同导致的固有性质，
      **不是 bug**
   —— 所以判定「稳定」只看 ID 序列（用户能感知的东西）。
      **这条判据最初写错了**（用 `equals` 比 double），于是永远报「不稳定」——
      判据写错比没有判据更糟，它会让人去查一个根本不存在的问题（见 ADR-018）
   —— 附带验证：`ORDER BY ..., id` 的兜底键**没有牺牲索引效率**，
      `EXPLAIN` 显示走 `Incremental Sort` → `Index Scan using idx_kb_chunk_embedding`

  2. **PDF 大纲两种嵌套形状只处理了一种** —— 导致一份 PDF 的标题层级整个丢失

  4. **Markdown 标题的 `#` 号残留** —— 会一路写进 `kb_chunk.heading_path`
  5. **定义 `ObjectMapper` Bean 导致 Boot 的 Jackson 自动配置静默退让** ——
     所有带时间字段的接口全部 500（见 ADR-019）
  6. **`KbDocumentResponse.finished()` 不被 Jackson 序列化** ——
     Jackson 处理 record 时只输出 record 组件，普通方法不算属性
  7. **注释与代码不一致 3 处**（声称用物理删除实际是逻辑删除、
     声称零分配实际有分配、声称 `finished` 会序列化实际不会）——
     都已改正。**这类问题不会导致功能出错，但会误导下一个读代码的人**
- `scripts/probe_kb.py` —— 检索探针的命令行客户端。
  ★ 存在的理由：Windows + Git Bash 下有**两层**中文编码陷阱
  （shell 破坏命令行参数、Python 按 GBK 读 UTF-8 响应），
  直接用 curl 会得到「像乱码又像 bug」的结果，白白浪费排查时间

## 环境排障记录

> 记录搭环境时真实踩过的坑。**再装一遍环境时直接照这个查，不用重新试错。**
> 面试问「你环境是怎么搭的、遇到过什么问题」，这些就是素材。

### 坑 1 · Docker Desktop 引擎起不来，所有命令返回 500

**现象**

```
docker info
request returned 500 Internal Server Error for API route and version
http://%2F%2F.%2Fpipe%2FdockerDesktopLinuxEngine/v1.56/info
```

Docker Desktop 进程在跑，但引擎不可用，`docker desktop status` 永远停在 `starting`。

**排查过程**

1. 看 `com.docker.backend.exe.log`，发现
   `"supportsVirtualization": false` + `virtualization-not-detected-screen`
2. 查 Windows 可选功能，`Microsoft-Windows-Subsystem-Linux` 和
   `VirtualMachinePlatform` 都是 **Disabled** → 启用它们（管理员 + 重启）
3. 重启后 `wsl --status` 提示「未找到 WSL 2 内核文件」→ 装内核
   （⚠️ `aka.ms/wsl2kernel` 现在跳转到文档页，真实地址是 Azure Blob：
   `https://wslstorestorage.blob.core.windows.net/wslblob/wsl_update_x64.msi`）
4. 内核装好后 Docker **仍然起不来**。日志里真正的报错是：

   ```
   [com.docker.backend.exe.wslexec][E] c:\windows\system32\wsl.exe --version
     failed: exit status 0xffffffff
   ```

**根因**：Docker Desktop 4.91 需要**商店版 WSL 应用**（WSL 2.x）来探测版本，
而系统内置的是老版 `wsl.exe`，**不支持 `--version` 参数**（执行它只会回显帮助文本）。
Docker 据此判定 WSL 不可用，拒绝启动虚拟机。

**决定性的一步**：装商店版 WSL 时，**下载能完成、安装却永远卡在「正在安装」**。
原因是商店安装除了下载，还要向 `licensing.mp.microsoft.com` 申请许可证，
而这个域名被墙了 → 永远卡住。

**解决**：打开代理（Clash Verge），系统代理置为 `127.0.0.1:7897` 之后，
商店安装立刻从「卡死」变成正常下载安装。

> **教训**：这个项目后续会大量依赖境外服务——Docker Hub 拉镜像、
> 两家模型供应商的 API、GitHub。**开工前先把代理打开**，
> 能省掉 90% 的「莫名其妙的卡住」。

### 坑 2 · 用户主目录被误建成了 git 仓库

**现象**：在项目目录里敲 `git status`，列出来的是整个 `C:\Users\33879`，
里面能看到 `.ssh/`、`.gnupg/`、`NTUSER.DAT` 这些。

**根因**：8 月 27 日在主目录下误执行过 `git init`（本意是在另一个项目里执行）。
该仓库没有任何提交（objects 数为 0），但它的存在会让项目里的 git 命令
全部落到错误的仓库上——一旦 `git add .`，私钥目录会被一起加进去。

**解决**：删掉 `C:\Users\33879\.git`，然后在项目目录里 `git init`。
remote 配置已备份到 `桌面\bookkeeping_APP-git-remote-备份.txt`。

> **教训**：`git init` 前先 `pwd` 确认目录。判断当前在哪个仓库用
> `git rev-parse --show-toplevel`。

### 坑 3 · `mvnw` 的换行符

**现象**：Windows 上 `git add` 时警告 `LF will be replaced by CRLF`。

**隐患**：`mvnw` 是 shell 脚本，一旦被写成 CRLF 换行，在 Linux / Docker 里执行会报
`/bin/sh^M: bad interpreter: No such file or directory`。
阶段 8 要在容器里跑 `mvnw`，这个坑现在不堵以后很难查。

**解决**：加 `.gitattributes`，`* text=auto eol=lf`，只给 `*.cmd` / `*.bat` 保留 CRLF。

### 坑 4 · pgAdmin 容器无限重启

**现象**：`docker compose ps` 里 pgadmin 显示 `Restarting (1)`，反复崩。

**日志**：

```
'admin@xbla.local' does not appear to be a valid email address.
Please reset the PGADMIN_DEFAULT_EMAIL environment variable and try again.
Validation output: The part after the @-sign is a special-use or reserved name
```

**根因**：`.local` 是 RFC 6762 保留给 mDNS 的专用域名，pgAdmin 9.x 的邮箱校验
直接判定它非法。注意不是「密码错了」或「配置读取失败」——**是邮箱格式校验**。

**解决**：改用 `admin@xbla.com` 之类的正常域名。

> **教训**：容器不断重启时，第一件事永远是 `docker compose logs <服务名>`。
> 这个报错信息其实写得很清楚，不看日志会误以为是挂载或权限问题。

### 坑 5 · pom.xml 里的 XML 注释不能出现 `--`

**现象**：

```
Non-parseable POM: in comment after two dashes (--) next character must be > not -
```

**根因**：XML 规范规定注释内容里不能有连续两个短横线（因为 `-->` 是结束标记，
`--` 会造成歧义）。用它画分隔线 `<!-- ---- 标题 ---- -->` 就会直接报错。

同理，`.gitattributes`、HTML、XML 配置里都要注意这点。
（顺带一提：Markdown 和 YAML 没这个限制，所以 docs 里可以随便画。）

### 坑 6 · MyBatis-Plus 3.5.9+ 改了包路径

**现象**：编译报 `程序包 com.baomidou.mybatisplus.extension.service 不存在`。

**根因**：`IService` / `ServiceImpl` 从 `mybatis-plus-extension` 模块
搬到了 `mybatis-plus-spring` 模块，包路径也随之改变。

```
旧（多数教程和我的记忆里）: com.baomidou.mybatisplus.extension.service.IService
新（3.5.17 实际）:        com.baomidou.mybatisplus.spring.service.IService
```

**怎么快速确认**：直接翻 jar 看类到底在哪，比搜教程快：

```bash
unzip -l ~/.m2/repository/com/baomidou/mybatis-plus-spring/3.5.17/\
mybatis-plus-spring-3.5.17.jar | grep IService
```

> **教训**：CLAUDE.md 里那条「不要凭记忆硬编码」不只适用于模型 ID，
> 同样适用于库的包名、API 签名。**版本一变，记忆就过期**。
> 遇到「包不存在」先翻 jar，别先怀疑自己的 pom。

### 坑 7 · jsonb / vector 列写入报类型不匹配

**现象**：

```
column "references" is of type jsonb but expression is of type character varying
```

**根因**：pgjdbc 默认把 Java `String` 当 `varchar` 发送。
而 PostgreSQL **不会把 varchar 隐式转换成 jsonb**（也不认识 pgvector 的 vector 类型），
于是直接报错。

**解决**：JDBC URL 加 `stringtype=unspecified`：

```
jdbc:postgresql://localhost:5432/xbla_rag?stringtype=unspecified
```

加上之后驱动把字符串以「未指定类型」发送，由 PostgreSQL 按目标列类型自行推断。

> **这条对阶段 3 很关键**：`kb_chunk.embedding` 是 `vector(1024)` 类型，
> 也是靠这个参数才能用字符串形式写入。现在配好了，到时候不用再踩一次。

### 坑 8 · `Long[]` 数组类型没有默认 TypeHandler

**现象**：

```
Type handler was null on parameter mapping for property 'expectedChunkIds'.
It was either not specified and/or could not be found for the
javaType ([Ljava.lang.Long;) : jdbcType (null) combination.
```

**根因**：MyBatis 内置了 `Object[]` 的处理器（`ObjectArrayTypeHandler`），
但**没有 `Long[]` 的**。类型注册表按精确类型查找，`Long[]` 匹配不到 `Object[]`。

**解决**：写一个 `LongArrayTypeHandler`（见
`com.xbla.rag.common.handler.LongArrayTypeHandler`），在字段上标注：

```java
@TableName(value = "eval_question", autoResultMap = true)   // ★ 不能漏
public class EvalQuestion {
    @TableField(typeHandler = LongArrayTypeHandler.class)
    private Long[] expectedChunkIds;
}
```

⚠️ **`autoResultMap = true` 最容易漏**。漏了的话写入正常、读取静默失败
（查出来是 null），属于「一半能跑」的 bug，最难排查。

### 坑 9 · 逻辑删除的「查不到」不等于「删掉了」

**现象**：调 `deleteById()` 之后 `selectById()` 返回 null，看起来删干净了。

**真相**：数据还在表里，只是 `deleted` 变成了 1。
查询时 MyBatis-Plus 自动追加了 `WHERE deleted = 0`，所以查不到。

**验证方法**：用 psql 直接查（绕过 MyBatis-Plus）：

```sql
SELECT id, deleted FROM product WHERE id = ?;   -- 能看到 deleted = 1
```

> **这条的重要性**：阶段 7 做评测时，如果怀疑「数据怎么少了」，
> 先想想是不是被逻辑删除了。**逻辑删除的数据不会真的消失**，
> 这正是不用物理删除的原因——评测要能追溯到历史。

### 坑 10 · Spring Boot 的 profile 是「覆盖」不是「追加」

**现象**：加了 `seed` profile 后启动失败：

```
The server requested SCRAM-based authentication, but no password was provided.
```

**根因**：`spring.profiles.active` 是**覆盖**语义。

```
application.yml 里配的:   active: local
命令行传的:               -Dspring-boot.run.profiles=seed
实际生效的:               seed        ← local 被顶掉了！
```

`local` 不生效 → `application-local.yml` 不加载 → 数据库密码读不到 →
连接被 PostgreSQL 以 SCRAM 认证失败拒绝（报错信息里「no password」就是指这个）。

**解决**：写成两个，用逗号分隔：

```bash
./mvnw spring-boot:run -Dspring-boot.run.profiles=local,seed
```

> **教训**：报错说「没提供密码」时，第一反应容易去查 application-local.yml
> 是不是写错了。但真正的问题往往是**那个文件根本没被加载**。
> 排查这类问题先看启动日志里的这一行：
> `The following N profile(s) are active: ...`

### 坑 11 · `@Transactional` 回滚数据，但不回滚序列

**现象**：集成测试跑过之后，`product` 表的 id 从 **5** 开始而不是 1，
中间有空洞。

**根因**：`@Transactional` 回滚的是**数据行的变更**，
**不会回滚自增序列的值**。每次插入尝试都会消耗一个序列号，
即使最后事务回滚了，这个号也不会还回去。

所以：
- 测试插入了 4 条商品 → 回滚，数据没了
- 但序列已经走到 5 → 之后正式灌数据从 5 开始

**这是 PostgreSQL 序列的正常行为，不是 bug。**

> **教训**（这条很实用）：**永远不要假设自增 id 从 1 开始、也不要在 SQL 里写死 id**。
> 本阶段验证时我就犯了这个错——写了 `WHERE p.id IN (1, 2)` 查规格对比，
> 结果返回 0 行，一度以为种子数据的外键回填逻辑坏了。
> 正确做法是用 `ORDER BY id LIMIT 2` 动态取。

## 卡住了怎么办

1. **报错先复制完整错误信息给我**，不要只描述现象
2. **涉及模型调用的报错**，先确认是不是 429（限流）而不是代码 bug —— 两家的限流阈值不同（见 `docs/02` 第 26 节）
3. **Docker 相关报错**，先试 `docker compose down` 再 `up -d`；还不行看 `docker compose logs <服务名>`
4. **实在卡住超过 1 小时**，跳过它标记为 TODO，继续往下走 —— 一口气跑通全链路比死磕一个细节更重要
